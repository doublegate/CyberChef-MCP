# v3.0.0 — MCP 2026-07-28 conformance, and the breaking cleanups it forces

**Status:** implemented; see `docs/internal/v3.0.0-findings-log.md` for what measuring changed.
**Scope derived:** 2026-09-03, by reading the specification changelog against the running server.
**Supersedes:** `docs/planning/future-releases/release-v3.0.0.md` (December 2025).

---

## Why the previous plan could not be executed

The December 2025 plan listed six breaking changes. All six were done, withdrawn, or superseded
before this release opened — the tool-name removal was permanently withdrawn in v2.0.0, named
recipe arguments and structured errors shipped, unified configuration shipped in v2.10.0, the
plugin API was superseded by [ADR 0002](../../adr/0002-tool-registry-is-not-a-plugin-loader.md),
and the "SDK v3.x" it depended on does not exist. F-01 has the table.

That is the sixth consecutive release whose plan was empty on contact, which is the whole argument
for [`RE-MEASURE.md`](RE-MEASURE.md) and for charters instead of plans.

## What v3.0.0 is instead

**Conformance with the 2026-07-28 specification, plus the cleanups conformance forces.** Not new
tools, not the evaluation harness — those are charters. Eight items; four change observable
behaviour, which is what makes this a major.

The specification text is summarised with citations in
[`docs/reference/mcp-2026-07-28-conformance.md`](../../reference/mcp-2026-07-28-conformance.md).

## The items

Ordered as executed. The evidence column is the measurement, not the intention.

| # | Item | Breaking | Evidence it was needed |
|---|---|---|---|
| 7 | Release pipeline: npm publish guard | n/a | three steps guarded `startsWith(ref, 'v2.')`; a `v3.0.0` tag would skip npm as a **green** step |
| 4 | Error codes at the resource boundary | **yes** | every `resources/read` failure answered `-32603` with no `data`; spec says `-32602` |
| 2 | Deterministic `tools/list` ordering | no | nothing pinned the order; spec SHOULD, for client and prompt caching |
| 3 | Recipe-aware scope filtering | **yes** | `visibleTools()` shipped in v2.5.0 and was never called; `bake` cost `network` for offline recipes |
| 1 | Cache hints on list results | **yes** (semantics) | SDK already emitted `{ttlMs: 0, cacheScope: "private"}` — conformant and useless |
| 5 | OTel trace context from `_meta` | no | server spans were roots; `traceparent` appeared nowhere |
| 6 | Tasks and `extensions` | no | assessed and **declined**, with the reasons at `SERVER_CAPABILITIES` |
| 8 | Deprecation alignment | no | Roots, Sampling, Logging, HTTP+SSE, DCR — checked one at a time, none present |

### Sequencing, and why only two orderings mattered

1. **Item 7 first.** It is unobservable until a `v3.0.0` tag exists, so it is the one defect that
   could otherwise only be found by shipping. Proven before commit by simulating the guard across
   `v1.9.2 / v2.10.0 / v3.0.0 / v4.0.0`.
2. **Item 3 before item 1.** Wiring scope filtering makes `tools/list` vary by caller, which
   decides `cacheScope`. Choosing the hint first would have meant choosing it twice — and choosing
   it wrong presents as staleness, not as an error.

Everything else was independent.

## What changed, by file

- `.github/workflows/mcp-release.yml` — three guards rewritten from an allowlist of the
  then-current major to the exclusion they always meant (`!startsWith(ref, 'v1.')`).
- `src/node/lib/resources.mjs` — translate the manager's string `INVALID_INPUT` into the SDK's
  `ResourceNotFoundError` at the resource boundary; unsupported-scheme and malformed-URI keep
  `-32602` with distinguishing `data`.
- `src/node/mcp-server.mjs` — three-tier stable sort on the list path (meta, registry, operations,
  each by code-unit order); `recipeScopesFor()` and `visibleTools()` wired into `handleListTools`;
  `CACHE_HINTS` passed at both construction sites; `parent: parentContextFrom(_meta)` on the call
  path; the tasks/extensions reasoning recorded at `SERVER_CAPABILITIES`.
- `src/node/lib/rbac.mjs` — `RECIPE_SCOPED_TOOLS`, `requiredScopesForRecipe()`, and an `authorise()`
  that takes the recipe-derived requirement rather than the tool's `openWorldHint`.
- `src/node/lib/cache-hints.mjs` (new) — `serverCacheHints(authEnabled)`, the one place the six
  method TTLs and scopes are decided.
- `src/node/lib/otel.mjs` — `parentContextFrom()` and a `parent` argument threaded to `startSpan`.

## Risks, and how each is handled

- **Item 3 is the only change that can surprise a working deployment.** Filtering activates only
  when auth is enabled, which is off by default, so the blast radius is deployments that turned
  auth on and relied — knowingly or not — on being *shown* tools they could not call. Release notes
  must state this as behaviour that changed, not as a tightening.
- **Item 4 changes an error code clients may match on.** That is what a major is for, but the
  before/after table belongs in the migration notes, not only in the findings log.
- **Item 1's failure mode is silence.** A too-long TTL serves a stale list and nothing reports it.
  The two zeros (`resources/list`, `resources/read`) are load-bearing: saved recipes change on any
  caller's write, and this server declares no `listChanged` capability, so the TTL is the only
  invalidation signal a client has.

## Verification

Conformance is verified **through a real MCP client**, never hand-rolled JSON-RPC — the rule three
releases paid for by shipping 524 tools with empty `inputSchema` under a green suite.

```
npm run lint            zero errors
npm run check:versions  every version reference agrees
npm test                Node-API + operation suites
npm run test:mcp        the MCP suite
npm run test:coverage   95/89/96/96 global, 99/94/100/99 for src/node/lib/**
```

Behavioural assertions added, each in the file that owns the surface:

- `stdio-client-contract.test.mjs` — the same server returns tools in the same order across calls.
- `prompts-resources.test.mjs` — an unknown recipe URI yields `-32602` carrying `data.uri`; an
  unsupported scheme yields `-32602` carrying `data.supported`.
- `auth.test.mjs` — a read-scoped token is not shown write or network tools, and `bake` carrying a
  purely local recipe is both **listed and callable** at `read`.
- `protocol-eras.test.mjs` — cache hints reach a 2026-era client and do **not** leak onto the 2025
  wire.
- `otel.test.mjs` — a valid inbound `traceparent` becomes the parent of the server span; an
  all-zero trace or span id is rejected rather than joined.
- `lib-internals.test.mjs` — the negative tripwire for tasks/extensions, so an SDK minor that began
  auto-declaring either cannot ship silently.

And end-to-end against the published artefact, as every release since v2.8.0 has done: pull the
image, mount a config, confirm the behaviour rather than the branch.

## Deliberately not in this release

- The evaluation harness — [charter](charters/v3.1.0-evaluation-harness.md). Every tool-quality
  claim here is currently asserted rather than measured, and v3.2.0 is unprovable without it.
- Result-efficiency work — [charter](charters/v3.2.0-result-efficiency.md), gated on v3.1.0.
- Tasks and `extensions` — declined with reasons, not deferred. See F-08.
- Meta-tool dispatch is still a 23-branch `if` chain beside a parallel `META_TOOLS` literal, so
  adding a tool means editing two places. Carried forward, unchanged by this release.
