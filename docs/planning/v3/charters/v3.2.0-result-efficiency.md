# Charter: v3.2.0 — Tool result efficiency

> **Not a plan.** Run `../RE-MEASURE.md` first and write F-01 before any code.
> **Gated on v3.1.0**: every item here is a claim about token cost, and this project does not ship
> unmeasured performance claims.

## Intent

Reduce what a tool result costs the context window, without losing what the caller needs.

## Candidate scope

- **`response_format: concise | detailed`** on the high-volume tools. Measured elsewhere at 65%
  reduction (206 → 72 tokens on one case) while preserving the identifiers a chained call needs.
  `cyberchef_magic` already does a bespoke version of this, and generalising it is the point.
- **Truncation with guidance.** Where output is cut, say how to narrow the request rather than
  leaving the model to guess. The project truncates in several places today and mostly says nothing.
- **Specific error suggestions.** `errors.mjs` keys `ErrorSuggestions` by error CODE, so every
  `INVALID_INPUT` gets the same advice regardless of which of 504 operations produced it. This was
  explicitly deferred by the v2.9.0 findings log.

## Kill criteria

- v3.1.0 measures the delta as small on this catalogue. The published numbers come from servers with
  a handful of verbose tools; a server whose results are mostly short binary transforms may not
  behave the same way, and that would be worth writing up rather than working around.
