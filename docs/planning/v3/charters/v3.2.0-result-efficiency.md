## Track A — Result efficiency

### Intent

Reduce what a tool result costs the context window, without losing what the caller needs.

### Candidate scope

- **`response_format: concise | detailed`** on the high-volume tools. Measured elsewhere at 65%
  reduction (206 → 72 tokens on one case) while preserving the identifiers a chained call needs.
  `cyberchef_magic` already does a bespoke version of this, and generalising it is the point.
- **Truncation with guidance.** Where output is cut, say how to narrow the request rather than
  leaving the model to guess. The project truncates in several places today and mostly says nothing.
- **Specific error suggestions.** `errors.mjs` keys `ErrorSuggestions` by error CODE, so every
  `INVALID_INPUT` gets the same advice regardless of which of 504 operations produced it. Deferred
  explicitly by the v2.9.0 findings log.

### How it gets measured

`npm run measure:surfaces` measures `tools/list`. Nothing measures a tool RESULT, and every claim
in this track is about result size — so the first task is extending the harness, not editing a
handler. Bytes, for the reason v3.1.0 recorded: no tokenizer is in this repository and adding a
GPT one would substitute a second unvalidated proxy for the first.

### Kill criteria

- The measured delta is small on this catalogue. The published numbers come from servers with a
  handful of verbose tools; a server whose results are mostly short binary transforms may not
  behave the same way, and **that** would be the finding worth writing up.
- A `response_format` enum is added and models ignore it. Measure whether it is used before
  measuring what it saves.

## Track B — The debt, with its evidence

Every item here was found by measurement and left undone with a reason. Each reason has expired.

### B1 — Restore the Trivy severity gate

Two `TODO(PR 7)` comments, in `mcp-docker-build.yml` and `security-scan.yml`, both narrowing the
gate to `CRITICAL` and both stating the same condition — and they are the only two `TODO`s in
**fork-owned** code. (`src/core/**` carries eleven more; that tree is mirrored from upstream on
every sync and must never be hand-edited, so they are upstream's to close, not this project's.)

> restore `CRITICAL,HIGH` once the dependency backlog is cleared to zero

Measured 2026-09-03: **0 open Dependabot alerts, 0 open code-scanning alerts.** The condition has
been met since v2.1.1, and the narrowed gate is now outliving its cause by eight releases.
Re-measure before acting: a count is exactly the kind of claim that expires.

Restoring it may surface findings. That is the point of restoring it, and the disposition process
for exactly this already exists — `docs/security/2026-08-31-open-alert-sweep.md`.

### B2 — Make the performance benchmarks able to fail

`performance-benchmarks.yml` says so in its own PR comment:

> this check cannot fail on a regression. Automated regression detection is tracked …

`continue-on-error: true` on both benchmark steps. So the cold-start work of v2.6.0 (~1300 ms →
~185 ms) and the image-size work of v2.8.0 are unprotected: a regression posts a number to a PR and
nothing stops it merging.

The honest options are a gate with a committed baseline and a tolerance, or keeping it as reporting
and deleting the sentence that implies otherwise. Not both.

### B3 — Lint and render the Helm chart in CI

Found in v3.1.0 (findings log F-10) while adding `image.digest`: **nothing in CI lints, renders or
installs this chart.** A template error reaches a user before it reaches a build, and the chart is
a published artefact with its own version.

Three levels, and the scope should say which it buys:

| Level | Catches | Cost |
|---|---|---|
| `helm lint` | schema and manifest-shape errors | seconds |
| `helm template` for default values **and** `--set image.digest=…` | template errors on paths nobody renders, which is how the v3.1.0 branch could have shipped broken | seconds |
| `helm install --dry-run=server`, or a kind cluster | admission and API-version errors a local render cannot see — a `PodDisruptionBudget` or `ServiceMonitor` the cluster rejects | minutes, and needs a cluster |

The first two are the release's commitment. **Install-time validation is the one the finding
actually names** — "nothing in CI lints, renders or *installs* this chart" — so either a kind-based
smoke install lands here too, or that word comes out of the debt statement. Deciding which is part
of the work, not a detail to leave implicit.

The digest branch added in v3.1.0 was verified by rendering it through a container by hand, which
is precisely the manual step a gate exists to replace.

### B4 — Tool metadata integrity in the sync path

Tool descriptions reach the model from `src/core/config/OperationConfig.json`, mirrored from
upstream on every sync: a path from an upstream commit to text a model reads as instruction.
Measured across all 504 operations:

```text
Unicode TAG-block characters   0
control characters             0
bidi override characters       0
non-ASCII (benign, accents)   27
```

No defect, and no guard. A cheap assertion in the sync path makes an upstream change that
introduces concealed metadata fail loudly rather than ship. Absorbed here from the standing
supply-chain charter, whose own trigger — *"a gate used as evidence must actually gate"* — fired
when v3.1.0's release notes cited the CI gates as verification.

### B5 — Prose counts nothing checks

`check:versions` covers versions and package majors, not counts. Three live documents say **505
operations** where `Object.keys(OperationConfig).length` is **504**: `README.md`,
`docs/wiki/Release-History.md`, and — the one that matters — the alert description in
`deploy/helm/cyberchef-mcp/templates/prometheusrule.yaml`, which an operator reads while
diagnosing a restart loop.

The fix is not editing three files. It is deciding whether a derived count belongs in prose at all,
and gating the ones that stay.

## Track C — Task-level scoring, if and only if it can be honest

v3.1.0 deferred this with a reason (findings log F-06) and the reason has not changed: scoring
"did the model use the tools well" needs a model in the loop, which means an API key in CI, a
per-run cost, and a number that moves when the model changes underneath it — in a repository whose
gating philosophy is that a flaky number must not be a gate.

It is listed here because the v3.1.0 charter's own scope named it and the work is real, not because
the objection has been answered. **Answer the objection first.** The shape that could work:

- **Off the critical path.** Not a required check. A scheduled run, or an opt-in label, the way
  `upstream-sync.yml` is triggered.
- **A pinned model and a pinned task set**, so a change in the number has one of two causes and the
  run says which.
- **A held-out set**, so improvements cannot be tuned into the measurement.
- **Report deltas, not absolutes.** The absolute score of a 504-tool catalogue against an arbitrary
  task set means nothing; the same score before and after a `response_format` change means
  everything, which is also why this belongs beside Track A rather than before it.
- **A cost ceiling stated up front**, since the run pays per token.

Grounded in real workflows rather than sandbox exercises — Anthropic's guidance is explicit that
"search the logs for `purchase_complete`" is a weak task and multi-step forensic triage is a strong
one, and `examples/04-forensic-triage.mjs` is the shape to start from.

### Kill criteria

- No design survives the "must not be a flaky gate" constraint. Then say so plainly and keep the
  tool-quality axis at what v3.1.0 built: deterministic wire-cost measurement, gating, plus
  conformance against an external oracle.
- The MCP ecosystem ships an eval harness for this in the meantime. **Check first** — that
  criterion fired in v3.1.0 and cost a release its planned scope, which is why the ritual now has a
  step for it.

## Sequencing

1. **Track B first**, and B3 before anything that touches the chart. It is the smallest work in the
   release and it makes the other tracks' evidence trustworthy: a benchmark that cannot fail is not
   evidence, and a chart nothing renders is not verified.
2. **Track A's measurement before Track A's changes.** Extend the harness to results, take a
   baseline, then edit handlers. The reverse order is how a 65% claim from someone else's server
   becomes this project's number without anyone measuring it.
3. **Track C last, or not at all**, and only after its design answers the objection in writing.
