## Intent

Make tool-quality claims measurable instead of asserted.

Every statement this project makes about how well a model uses it — that the index surface is
navigable, that Magic's report is actionable, that a description is clear — is currently a
judgement. Meanwhile the same project refuses to assert anything about *code* without a number.
That asymmetry is the gap.

## Candidate scope

- A task set grounded in real workflows, not sandbox exercises. Anthropic's guidance is explicit
  that "search the logs for `purchase_complete`" is a weak task and a multi-step forensic triage is
  a strong one. `examples/04-forensic-triage.mjs` is the shape to start from.
- Per-task metrics: accuracy against ground truth, **tokens consumed**, tool calls made, error rate,
  redundant-call patterns.
- A held-out set, so improvements are not tuned into the measurement.
- Run it against the three tool surfaces (`index`, `curated`, `all`), because the whole surface
  design rests on the claim that `index` loses no capability.

## Why it comes first in the v3 line

v3.2.0's techniques are all quantified elsewhere — a `response_format` enum measured at 65% token
reduction, tool search at 85%. None of those numbers were measured *here*, on a 504-operation
catalogue. Shipping them on someone else's numbers would be exactly the "asserted, not measured"
failure this project keeps writing up.

## Kill criteria

- The MCP ecosystem ships a conformance/eval harness that covers this — check MCP-Bench, MCP-Atlas
  and the SDK's conformance work before building.
- Measurement proves too noisy to gate on. Then keep it as a reporting tool and say so, rather than
  pretending a flaky number is a gate. `performance-benchmarks.yml` already occupies exactly that
  honest-but-non-gating position.
