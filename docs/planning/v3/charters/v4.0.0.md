# Charter: v4.0.0 — Determined by the specification, not by us

> **Not a plan, and deliberately the thinnest document here.**
> Run `../RE-MEASURE.md` first. Expect most of this to be wrong by the time it is read.

## Intent

A major version should exist because the protocol or the ecosystem forced one, not because the
number was next. v3.0.0 is the worked example: its six planned breaking changes had all evaporated,
and the release that shipped was derived from a specification revision instead.

## What to watch

The MCP roadmap names five priorities. Two bear directly on this server:

- **Progressive tool discovery.** The maintainers describe the problem in this server's exact terms
  — connecting to a server with a hundred tools means paying for the whole surface before the user
  asks anything. This project's `index` surface plus three navigation tools is a *private* solution
  to that problem. When a standard lands, the private one should become an implementation of it, and
  that is a plausible v4.0.0.
- **Agent identity.** DPoP and workload identity federation, for agents with their own identity
  rather than a browser-delegated one. This server is already an OAuth 2.1 resource server, so it is
  on the receiving end of whatever that becomes.

The other three — agentic messaging primitives, HTTP-native transport unification, SDK developer
experience — are worth tracking but land mostly in the SDK.

## What v4.0.0 is explicitly NOT

The v2.x-era ROADMAP's "long-term vision" names distributed execution, ML-optimised operation
selection, full WASM, and quantum-safe cryptography. None of those is derived from evidence about
this server, and two are outside what a CyberChef wrapper should be. They are recorded here as
rejected rather than left in a roadmap where a future reader might execute them.

## Kill criteria

If the specification does not force a breaking change, **do not cut a major version**. Ship minors.
v2.x ran to eleven releases and was the better for it.
