# Charter: v3.3.0+ — The external-project tool programme

> **Not a plan.** Run `../RE-MEASURE.md` first and write F-01 before any code.
> Spans several releases. One phase per release, not one programme in one release.

## Intent

Land the tool backlog that has existed since before v2.0.0: analyses an upstream CyberChef
operation cannot express.

## State, measured

`docs/planning/ext-proj-int/` scopes 80–120 tools across 4 phases and 24 weeks, from 8 reference
projects. Its README still says "not started". That is **stale**: v2.4.0 shipped the `ToolRegistry`
(Sprint 1.1's deliverable) and four tools — `xor_key_length`, `cyclic_pattern`, `hash_identify`,
`rsa_attack`. So roughly 4 of 80–120, with Phase 1 partly done.

The GPL-3.0-or-later relicense in v2.0.0 is what unblocked the rest: katana is GPL-3.0+ and John the
Ripper GPL-2.0+, both incompatible with the previous Apache-2.0.

## Candidate sequence

Phase 2 (JavaScript-native: cryptii encodings, pwntools binary helpers, the recipe corpus) → Phase 3
(algorithm ports: xortool, Ciphey/Ares auto-decode, RsaCtfTool attacks) → Phase 4 (hash
identification, CTF composites).

## Constraints that already exist and must hold

- Registration goes through `src/node/tools/index.mjs` — an explicit import list. **No loader, no
  directory scan, no path from configuration** (ADR 0002: `node:vm` is not a security boundary, and
  that was measured).
- The `cyberchef_` prefix is permanent.
- Preset tools use `preset_*`; `recipe_*` belongs to the v1.6.0 management tools.
- Every new tool needs annotations, or it defaults to the most restrictive scope and silently
  disappears from a scoped `tools/list`.

## Kill criteria

- A phase's tools duplicate operations upstream has since added — re-check `OperationConfig` first;
  the catalogue grew 440 → 504 during v2.x.
- Tool-surface measurement (v3.1.0) shows adding tools degrades selection more than the tools help.
