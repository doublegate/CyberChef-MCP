## Intent

The five candidates with the **strongest evidence and the least dependency risk**. Every one is
gap (b) — *a statistic computed across inputs* — or a near-free extension of a tool that already
ships. None needs a new production dependency.

**This charter does not start until [v4.1.0](./v4.1.0.md) lands.** Nineteen registry tools already
occupy 68% of the index; at 59 the index costs more than `curated`. Adding tools before the surface
can carry them makes the measured problem worse.

## Candidate scope

Ordered by confidence. Each states the gap it fills and why an operation cannot.

**1. `beacon_analyze` — gap (b).** N timestamps (optionally with byte sizes) → periodicity score,
period, jitter. The statistic is defined *only over the set*, so no single-input form exists. Both
reference scorers are fully published, so this is implementation rather than research: RITA's Bowley
skewness of deltas plus MADM, and Elastic's bucketed coefficient-of-variation with autocorrelation —
which is different in kind, never computing inter-arrival deltas. The hand-scripting evidence is the
strongest found: Active Countermeasures' own teaching lab instructs analysts to dump fields to CSV
and *"open the file in a spreadsheet program and calculate some basic statistics."* Composes with
`timestamp_identify`. Dependency: none required — Bowley is `(Q3+Q1−2·Q2)/(Q3−Q1)` over a quantile.

**2. `password_corpus` — gap (b), the cleanest found.** Mask topology, length distribution,
base-word frequency, cumulative mask coverage, reuse counts. A single password's mask is a trivial
char-class map and could be an operation; *"these 12 masks cover 43% of the corpus"* has no
single-input form. npm covers "how strong is this one password" exhaustively and "what is the shape
of this corpus" **not at all**. The reference tools have gone quiet (PACK last pushed 2019, pipal
2023) while practitioners reimplement them from scratch.
**Licence care:** pipal is CC-BY-SA and HashMaster1000 is CC BY-NC — neither is a safe reference for
a GPL-3.0 tree. Use PACK (BSD-3) or cpack (MIT), or derive from the published method.

**3. `pqc_readiness` — gap (b).** Given N keys/certs, classify each as quantum-vulnerable, PQ or
hybrid; roll up counts, expiry-versus-deadline distance, and **chain-level risk — a chain is only as
PQ-ready as its weakest link**, which is a relationship across inputs that per-blob `pqc_identify`
cannot express. The standards it rests on are settled, not moving: **RFC 9881** (ML-DSA in X.509,
Oct 2025), **RFC 9909** (SLH-DSA, Dec 2025), **RFC 9935** (ML-KEM, Mar 2026), **RFC 10024** (PQ/T
hybrid TLS, Aug 2026). Emit CycloneDX CBOM, which v1.7 expanded for exactly this.
**Scope honestly:** lead with risk *ranking*, not exhaustive cataloguing — an exhaustive CBOM takes
long enough to produce that it can be stale on arrival.

**4. `prng_recover` — gap (a) + (b).** Verified absent from CyberChef — precisely: the tree ships
`PseudoRandomNumberGenerator` and `PseudoRandomIntegerGenerator`, which **generate** (via
`crypto.getRandomValues`). Recovering a generator's state from its output is the opposite direction
and nothing does it. MT19937: 624 consecutive
outputs reconstruct the full state by untempering; **623 yields two candidates — a decision inside
the loop.** Pure bit arithmetic, no dependency, for MT19937, Java LCG, bash `$RANDOM`, glibc and PHP
`mt_rand`. The ecosystem is eight separate single-purpose tools. Natural sibling of `ecdsa_recover`
and `jwt_weakness`: *the randomness was not random.*
**Scope out** the Z3-dependent cases — **not because there is no JS SMT solver; there is.**
`z3-solver` is on npm at **5.2.0, MIT, 35.8 MB unpacked** (verified 2026-09-11), an official WASM
build. It is declined on this charter's own kill criterion — *a dependency larger than the tool* — in
a tree that prunes to production-only dependencies and fights a 453 MB image, where 35.8 MB buys a
handful of PRNG cases. Recorded as a measured decline rather than an absence, because an absence
claim rots silently while a cost is re-checkable. Note also that V8 caches 64 values
and returns them **in reverse order**.

**5. PQC *verification*, extending `cert_chain` and `pqc_identify` — gap (c), and nearly free.**
Verified by execution, not documentation: OpenSSL 3.6.4 generated a self-signed ML-DSA-65
certificate, and Node's `X509Certificate` parsed it, reported `asymmetricKeyType: 'ml-dsa-65'`, and
returned **`verify(publicKey) === true`**. `cert_chain` can validate PQC chains today with no new
code path and no dependency. This is not a new tool and should not be counted as one.

## Trigger

**Fired**, on evidence: three candidate families verified dead in ten minutes, five verified live,
and the standards underpinning (3) are published RFCs rather than drafts.

Gated on v4.1.0 landing — which is a dependency, not a trigger.

## Kill criteria

- **Any candidate turns out to be expressible as one pure function over one input.** Then it is an
  upstream operation, not a registry tool, and the three-gap bar decides it — not enthusiasm.
- **A candidate needs network access.** That sidesteps `CYBERCHEF_OFFLINE`, which is a posture the
  server states and tests at four engine entries.
- **A dependency is larger than the tool.** This tree prunes to production-only dependencies and
  fights a 453 MB image; `@jimp` at 89 MB is already the price of real operations.
- **`password_corpus` cannot be built without deriving from a CC-BY-SA or NC source.** Then it does
  not ship. A licence problem discovered after the fact is far more expensive than one avoided.
- **v4.1.0 does not land.** Then this charter does not start, and saying so is the point of writing
  the dependency down.

## Verification

- Each tool tested through a **real client**, with fixtures generated rather than frozen where the
  input is generatable — the `pqc_identify` standard.
- Any borrowed algorithm recorded in `THIRD-PARTY-NOTICES.md` in the same change, with an
  `SPDX-License-Identifier` and a provenance comment — source project, file, commit — at the port
  site. Gated by `registry-tool-docs.test.mjs`, which already treats that file as an exemption
  keyed by borrowed work rather than by tool.
- Each tool's *refusals* tested as carefully as its answers. Every ranking and scoring tool this
  project has shipped has had a defect in what it claimed under ambiguity, not in its happy path.
- Surfaces re-measured after each addition. Post-v4.1.0 the index should **not** move; if it does,
  v4.1.0 did not do what it claimed and that is the finding.
