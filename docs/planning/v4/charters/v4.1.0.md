# Charter: v4.1.0 — Registry tools get a navigation path

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.
>
> **Rewritten 2026-09-11.** The previous v4.1.0 charter (the entry-point guard) shipped as v3.10.0.
> Its content is not lost — it is in `docs/releases/v3.10.0.md` and the v3.10.0 findings log. This
> number was reused because v4.0.0 shipped, so the charter numbers are now real releases rather
> than a reading order.

## Intent

**Nineteen registry tools occupy 68% of the index surface, and the tool programme cannot land on top
of them.** This charter removes that ceiling. It is a prerequisite for v4.3.0–v4.5.0, not an
optimisation, and it is first for that reason.

## The measurement

```text
index today     44,968 bytes / 41 tools
                  14,305  navigation + meta-tools
                  30,663  registry tools -- 19 of them, averaging 1,614 bytes each
```

Against `../../ext-proj-int/`'s scope of 80–120 more tools:

```text
+39 registry tools (58 total)  ->  index costs MORE than `curated`
+80                            ->  174,075 bytes, 1.6x curated
+120                           ->  238,629 bytes, 2.2x curated
```

The progressive-disclosure argument in `tool-catalog.mjs`'s header inverts somewhere around the
fortieth new tool, quietly, with no gate that would notice.

## Why they are all listed, precisely

Six documents say a registry tool *"has no navigation path, so one that is not listed cannot be
called at all."* Measured against the running server, the second clause holds and the first does
not:

| Path | Registry tool |
|---|---|
| `cyberchef_search` | **finds it** — separate `analysis_tools` array, with a summary |
| `cyberchef_describe_operation` | **refuses** — *"no OperationConfig entry … its full schema is already in `tools/list`"* |
| `cyberchef_bake` | **cannot run it** — `Unknown operation: pqc_identify` |
| `cyberchef_categories` | does not mention it |

Discoverable by name; no schema path; no invocation path. The `describe_operation` refusal is the
load-bearing one — **its redirect assumes the tool is listed**, which is the assumption that forces
it to be listed.

## Waiting for the specification to solve this is not an option

The old corpus filed progressive discovery as *"v4.7.0 — if it standardises"*, and DECISION-GATES
escalated the index-size problem to it. Researched 2026-09-11, that route is **dormant**:

| | |
|---|---|
| **SEP-1862 "Tool Resolution"** | **closed unmerged 2026-09-02** — nine days ago — apparently to sponsor inactivity |
| SEP-1928 | closed 2026-03-08, labelled `dormant` |
| SEP-1300 | `rejected` |
| SEP-1881 | closed |
| Live exploration | a **Primitive Grouping Interest Group**, which has no authority to approve spec changes |
| Roadmap | names progressive discovery a priority and assigns it to a **Core Primitives WG that does not exist yet** |

The nearest open work is **SEP-2564, server-side filtering for list methods** (`draft`, 2026-08-31),
which is a different thing.

So: **four attempts closed, no open SEP, and the owning group unformed.** This server's hand-rolled
index was a private solution to a problem the specification has not standardised in eighteen months
of trying. Building the missing half privately is not jumping the gun — it is the only route that
exists, and the measurement says the current design runs out at 58 registry tools.

## Candidate scope

The pieces are already in scope: `mcp-server.mjs:56` imports `buildRegistry` and `ToolRegistry`, and
every registry tool carries a Zod `inputSchema` that `toInputSchema` converts.

1. **`cyberchef_describe_operation` serves registry-tool schemas** instead of redirecting.
2. **`cyberchef_categories` lists the analysis tools** as a category, so the walk down reaches them.
3. **A dispatcher** — `cyberchef_analyse(tool, args)` — so a tool that is not listed is still
   callable. This is the half that makes the rest safe.
4. **Registry tools leave the `index` surface**, once and only once 1–3 are true and tested through
   a real client.

Deliberately **not** in scope: changing what any registry tool does, or the three-gap bar for
admitting one.

## What it buys

```text
index    44,968  ->  ~15,905 bytes    -65%
and the curve flattens: +20, +80, +120 registry tools all leave the index unchanged
ext-proj-int ceiling: 58 tools  ->  effectively unbounded
```

## Trigger

**Fired.** This one needs no external event — the measurement above is the trigger, and it was taken
on 2026-09-11 against the running server.

## Kill criteria

- **The dispatcher does not survive a real client.** If `cyberchef_analyse` cannot carry a tool's
  arguments through schema validation as faithfully as a direct call, stop: this project's rule is
  that *listing must never be stricter than dispatch*, and an unlisted-but-uncallable tool inverts
  it. Better a large index than a lying one.
- **Measured model behaviour degrades.** If a tool behind one extra hop is materially less likely to
  be used when it should be, the index cost was buying something real. Say so, keep the tools
  listed, and re-scope the programme instead — the ceiling is then a fact about the design, not a
  bug in it.
- The byte win fails to materialise once the dispatcher's own schema is counted. `~15,905` assumes
  one dispatcher sized like an average registry tool; measure it, do not assume it.

## Verification

- `npm run measure:surfaces` before and after, with the canonical table and every live document
  updated in the same change — `tool-surface-figures.test.mjs` gates this against the live server.
- A real-client test that discovers a registry tool **and calls it** without it appearing in
  `tools/list`, proving the whole chain rather than each link.
- The negative case: a tool that exists is never reported as absent by `describe_operation`.
