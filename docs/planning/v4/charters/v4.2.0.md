# Charter: v4.2.0 — One place to add a tool

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.
>
> **Rewritten 2026-09-11.** The previous v4.2.0 charter (`ext-proj-int` phase 1) had its first slice
> ship as v3.11.0 — `pqc_identify`, the nineteenth registry tool. The programme itself moves to
> [v4.3.0](./v4.3.0.md), behind [v4.1.0](./v4.1.0.md), for the reason the surface measurement gives.

## Intent

Adding a meta-tool means editing **two** places that must agree, and nothing checks that they do.
This is the oldest item on the carried-forward list — recorded in the v3.0.0 plan, still true today,
and it gets worse the moment v4.1.0 adds a dispatcher.

## The measurement

```text
23   `if (name === "cyberchef_…")` branches in handleCallTool
 1   parallel META_TOOLS literal at mcp-server.mjs:371, feeding metaToolNames() and handleListTools
```

A tool declared in `META_TOOLS` but missing a dispatch branch is **advertised and uncallable**. A
branch with no declaration is **callable and invisible**. Both are silent: the registry's shadow
check compares against `META_TOOLS`, so it cannot see the branches at all.

This is the same defect shape the project keeps finding — *two sources of one truth, and a check
that reads only one of them.* `check:versions` was built for it, `registry-tool-docs` for it,
`tool-surface-figures` for it. The dispatch table has never had its version.

## Why now rather than ever

[v4.1.0](./v4.1.0.md) adds `cyberchef_analyse`, a twenty-fourth branch and a twenty-fourth literal
entry. [v4.3.0](./v4.3.0.md) then adds tools in slices. Consolidating after that is strictly more
work than consolidating before it, and the risk of the two lists drifting rises with every addition.

## Candidate scope

- One table: name, schema, handler. `META_TOOLS` and the dispatch chain derive from it rather than
  mirroring each other.
- A test that fails when a declared tool has no handler **and** when a handler has no declaration —
  discovered from the table, not listed by hand, because a hand-written list is what this is fixing.
- No behaviour change. Every meta-tool answers exactly as it does today, proven through a real
  client rather than by inspection.

Deliberately **not** in scope: a registry or loader for meta-tools. [ADR 0002](../../../adr/0002-tool-registry-is-not-a-plugin-loader.md)
settled that, and a table of explicit imports is not a loader.

## Trigger

**Fired**, and it is local: the 23-branch count above, taken 2026-09-11. It has been on the
carried-forward list since the v3.0.0 plan without a release claiming it.

## Kill criteria

- **The refactor cannot be proven behaviour-preserving.** 23 branches is small enough that a
  mistake is cheap to make and expensive to find; if the full meta-tool surface cannot be asserted
  through a real client before and after, do not do it. A tidier dispatch that answers differently
  is a regression with good intentions.
- v4.1.0 does not land. Then the twenty-fourth entry does not exist and the pressure is unchanged —
  the item goes back on the carried-forward list honestly, rather than being done for neatness.

## Verification

- The full meta-tool surface, called through a real client, before and after — same answers **and
  the same `tools/list` contract**. Names are the cheapest half of that contract and the only half a
  naive parity test checks. `handleListTools` also decides each tool's **description**, its
  **`inputSchema`**, its **annotations and title**, the **three-tier ordering** the 2026-07-28
  SHOULD rests on, and — when auth is on — which tools `visibleTools()` filters out. A table-driven
  rewrite can preserve every name and still change any of those. Snapshot the whole list response,
  under each surface preset and both with and without auth, and diff it.
- The new gate verified by reintroducing the real defect **in both directions**: delete a handler,
  delete a declaration.
- Coverage of `mcp-server.mjs` measured before and after. It is **82.2% of 394 statements** today,
  the file `vitest.config.mjs` already names as carrying the deficit; a consolidation that does not
  move it has probably moved complexity rather than removed it.
