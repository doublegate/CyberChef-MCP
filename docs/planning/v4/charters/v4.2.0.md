# Charter: v4.2.0 — `ext-proj-int`, phase 1

> **The number is an ordering, not a schedule.** This directory is numbered `v4.1.0`-`v4.9.0` for
> reading order, and that quietly assumes a `v4.0.0` the plan beside it explicitly says **not to
> cut**. A v4 charter executed before v4.0.0 ships as a **v3 minor**; the release is decided at
> execution time, by SemVer and by what the work actually is. v4.1.0's content shipped as v3.10.0.

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.

## Intent

The genuine feature backlog. `docs/planning/ext-proj-int/` scopes **80-120 tools drawn from 8
reference projects**; roughly four shipped in v2.4.0 and fourteen more arrived through v3.8.0 as
registry tools. This charter takes the next coherent slice.

## What qualifies, and what does not

The bar is already written and has held for nineteen tools. A registry tool must fill one of three
gaps an operation cannot:

1. a **loop with a decision inside it** (the cipher solvers);
2. a statistic computed **across inputs** (`corpus_diff`, `rsa_multi_key`, `hash_statistics`,
   `ecdsa_recover`, `cert_chain`);
3. a cipher upstream simply lacks (`classical_cipher`).

Anything expressible as `run(input, args)` over one input is an **operation**, and belongs upstream
or nowhere — `src/core/**` is mirrored, so a fork-local operation becomes a `patches/fork` patch
that must keep applying forever.

## Candidate scope

Selection is deliberately deferred to the RE-MEASURE pass, because the last four releases each found
a candidate already covered by an existing operation. Start by re-checking the ext-proj-int list
against the live 504 rather than against its own notes.

**One candidate is already measured and named: post-quantum cryptography.** Zero of the 504
operations match ML-KEM, ML-DSA, SLH-DSA, Kyber, Dilithium or SPHINCS+ — verified against
`OperationConfig.json` on 2026-09-10. These are NIST standards (FIPS 203/204/205), not research, and
a toolkit that covers RSA and ECDSA and not these has a gap a user will notice.

It reaches this charter only because the v4.0.0 plan's rejected list was **wrong as written**: it
inherited "quantum-safe cryptography" from the v2.x roadmap and rejected the label, when what was
correctly out of scope was making the server's *own transport* quantum-safe — a different thing
entirely. See that document's revised table.

Shape it as an identifier/analyser first (which algorithm is this key, this signature, this
encapsulation?) rather than as an implementation of the primitives. That fits the three-gap bar and
avoids this project shipping its own PQC maths, which it should not do.

### A sibling item: the quality of the selection this server already makes

Not a tool, and worth carrying beside the tools work because it is the same subject. `cyberchef_magic`
ranks candidates by chi-squared byte frequencies, and two weaknesses are documented rather than
fixed:

- the language estimate is weak enough to call "Attack at dawn" German at p=1.35e-8, and accuracy
  does not rise monotonically with length, so no cutoff fixes it;
- the ranking needed a fix in v3.9.0 (#130) because a detected **container** outranked its own
  decoded contents, and the promotion rule that fixes it is deliberately narrow.

Improving that scoring is not "ML-optimised operation selection" — the thing the v4.0.0 plan
rejects — and the distinction is now written there.

## Licence gate, which is not optional

The GPL-3.0-or-later relicense in v2.0.0 unblocked katana (GPLv3-or-later) and John the Ripper.
**Any borrowed algorithm must have its licence recorded in `THIRD-PARTY-NOTICES.md` in the same
change**, and that file is checked by `registry-tool-docs.test.mjs` — it is exempt from the
inventory rule *because* it is keyed by borrowed work rather than by tool.

## Trigger

None needed; the backlog exists. Sequenced after v4.1.0 only because the entry-point work makes
tool tests cheaper to write.

## Kill criteria

- A candidate an existing operation already covers. Check `cyberchef_search` and the 504 first.
- A candidate that needs network access — `CYBERCHEF_OFFLINE` guards the recipe, and a registry tool
  that reaches the network sidesteps that guard entirely.
- A candidate requiring a dependency larger than the tool. `@jimp` at 89 MB and `tesseract.js-core`
  at 44 MB are already why `<50 MB` is unreachable for the image.
