# Charter: v4.9.0 — Consolidation, and the v5.0.0 question

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.

## Intent

The release that asks whether the next number should be a major, and answers it with evidence
rather than arithmetic. v2.x ran to **eleven** minors; v3.x ran to ten. Neither was harmed by it.

## Candidate scope

- **Re-measure everything the documentation asserts.** Not spot checks: the surface tuple, the
  operation count, the test count, the coverage tuple, the image size and its package count, the
  Node version in the shipped image. v3.9.0 found the v3.8.0 surface figures were wrong *in the
  shipped artefact*, and the gate that should have caught it could only prove documents agreed with
  each other.
- **Re-measure the carried-forward list.** Two consecutive releases found items whose stated
  obstacle had evaporated — arm64 "needs hardware" while the repo already used that hardware, and
  task-level scoring blocked on a document nobody had written.
- **Retire dead planning.** `docs/planning/future-releases/` and `phases/` are already historical
  with dated banners. Anything in `v4/charters/` that measurement has killed gets the same
  treatment: archived with a banner naming what replaced it, never deleted.
- **Decide on v5.0.0** against the same criterion v4.0.0 uses: a major exists because the protocol
  or the ecosystem forced one.

## Trigger

Six or more v4.x minors shipped, or twelve months since v4.0.0 — whichever comes first.

## Kill criteria

- If nothing needs consolidating, **do not cut a release to consolidate nothing.** Fold the
  re-measurement into whatever minor is open. An empty release executed anyway is worse than a
  re-scoped one; v2.9.0 and v2.10.0 both made that call.
