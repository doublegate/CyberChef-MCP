# Charter: v4.4.0 — The tool programme, slice 2: the ones with a cost

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.
>
> **Written 2026-09-11**, on research retrieved the same day.

## Intent

The candidates that are worth building **and carry a real cost** — a production dependency, a
feasibility ceiling, or a scope that has to be declared rather than implied. Separated from
[v4.3.0](./v4.3.0.md) precisely so the cost is a decision rather than a surprise.

Follows v4.3.0, which follows [v4.1.0](./v4.1.0.md).

## Candidate scope

**1. `yara_scan` — gap (b), and the framing matters.** Not "add YARA": `YARARules.mjs` already
ships. Three facts change the picture, all verified:

- the in-tree operation returns **`outputType: "string"`** — a human-readable report, so an agent
  consumer gets no structured match data at all;
- its backend `libyara-wasm` was **last published 2022-09-18**;
- **`@virustotal/yara-x` v1.20.0** shipped 2026-08-24, BSD-3, first-party, and YARA-X went stable in
  2025 with original YARA moved to maintenance.

Verified on npm directly: **v1.20.0, BSD-3-Clause, zero dependencies, 5.9 MB unpacked** (the
research pass said 5.7 MB from an install; `dist.unpackedSize` is 5,911,883 and the larger figure
is the one to budget). Pure WASM, so arm64 and amd64 are identical and no build step enters the
image. It returns structured
matches with offsets and compiler warnings with source spans.

The tool that earns its place is **corpus-level: N inputs × M rules → a hit matrix with offsets**,
which the single-input string-returning operation cannot express.
**Known constraint, from its own README:** objects live in the WASM heap and must be `.free()`d or
they leak — a real design question for a long-lived server, and the first thing to test.

**2. `archive_bomb` — gap (a).** Every unpacking primitive in the tree is single-shot; *"is this a
bomb"* needs a walk that **decides at each layer whether to descend** against depth, cumulative-byte
and ratio caps, accumulating without materialising. Fifield's zip bomb is **non-recursive** — 10 MB
→ 281.4 TB in one round via overlapping local file headers — so recursion-depth defences never see
it. Live evidence: **CVE-2026-59873 in node-tar**, whose fix introduces `maxDecompressionRatio`
defaulting to **1000**, a citable constant. Two maintainers declare it out of scope explicitly, and
one told a user to *manually* cross-check `offset` and `compressedSize` across all entries — that
manual cross-entry walk **is** the loop with a decision.
**Honest framing:** `@ronomon/pure` already covers overlaps, quines and ratios — but it is a C
library with a Node binding, a real cost for a pruned image, and it is a pass/fail *validator*. The
novelty here is **reporting depth, ratio and tree shape**, not detecting bombs.

**3. `fuzzy_cluster` — gap (b).** `CompareSSDEEPHashes` and `CompareCTPHHashes` ship but are
**strictly pairwise**, so clustering N samples means **N(N-1)/2** invocations — every unordered
pair. The hashes are already computed in-tree; the tool is the loop, the threshold and connected
components. **TLSH is absent
from CyberChef entirely** (gap c) and clusters better than ssdeep.

**4. `steg_detect` — gap (c) + (b), separably.** `Extract LSB` / `Extract RGBA` / `View Bit Plane`
ship — extraction only, **zero statistical detectors**. Chi-square, RS and Sample Pairs are
per-image and could be operations; *"over these 500 images, which are anomalous"* cannot be. The
reference corpus tool, StegExpose, has been **archived since 2021**; everything else is single-file.
Proven twice in JS, and `jimp` is already a production dependency with `image.bitmap.data` as
exactly the access pattern these want.
**Weakest evidence in this charter, and it is absence-shaped:** no first-person "I scripted a
500-image sweep" writeup was found. The 2026 toolkits are wrappers that shell out per file in a
loop, which is the hand-scripted loop packaged — suggestive, not proof.

**5. Node 26 adoption, where it is measurably better.** The floor moved to `>=26 <27` in v4.0.0, so
these are usable unconditionally for the first time:

- **`Uint8Array.fromBase64` / `toBase64` / `fromHex` / `toHex`** — present in 26, **absent in 24**.
  For a server whose whole job is byte transformation this is the most directly relevant platform
  change in years. **Measure against the existing hot paths before adopting**; the benchmark gate
  exists for exactly this.
- **`crypto.argon2` in core** — `hash_crack` currently refuses Argon2 by name; core can now do it
  with no dependency.
- **`crypto.hash()` one-shot** — avoids the create/update/digest allocation triple in corpus loops,
  which is what every gap-(b) tool above is.

**A trap to test for, not assume:** ML-KEM/ML-DSA **pkcs8 export defaults to seed-only in Node 26**,
so the same key exports differently on 24 and 26. `pqc_identify`'s table was extracted from
Node-generated DER; re-extract it rather than trusting it.

## Explicitly capped or declined

- **Lattice work — `hnp_recover`, Coppersmith — is NOT in this charter.** It is the other half of
  `ecdsa_recover` and genuinely wanted, but **there is no LLL on npm** and no WASM build of
  fplll/flatter/NTL. The one TypeScript existence proof caps at 32 signatures with float
  Gram-Schmidt *"because the reduction runs in your browser"* — which covers the ≥4-bit-leak regimes
  and does **not** reach Minerva-class 1-bit leakage, where the published receipt is 824 minutes and
  1,939 GiB on GPU. If it is ever built it ships with a **declared feasibility envelope in its own
  output**, the way `magic` reports language as an estimate. Recorded here so it is not re-proposed
  as though it were cheap.
- **Shellcode emulation.** The static-heuristic half has published recall figures and is fine; adding
  a CPU emulator to run untrusted shellcode inside the server is a **security-posture change, not a
  feature**, and is not decided by a feature charter.
- **Detect It Easy's 2,077 signature files.** They are literally JavaScript `function detect(){}`
  files. Loading them is what [ADR 0002](../../../adr/0002-tool-registry-is-not-a-plugin-loader.md)
  forbids, and `node:vm` is not a boundary. Only viable compiled to inert data at build time.
- **Composite PQC certificates.** `pq-composite-sigs` is at rev 19 and `pq-composite-kem` at rev 21,
  both still Internet-Drafts. A composite identifier built today chases a moving OID table.

## Trigger

**Fired** for 1–4 on verified evidence. Item 5 is unblocked by v4.0.0's floor change and needs a
measurement, not an event.

## Kill criteria

- **`@virustotal/yara-x` leaks under a long-lived server** and `.free()` cannot be made reliable at
  the tool boundary. Then the corpus tool is not worth a 5.9 MB dependency and a memory risk.
- **A Node 26 native is not measurably faster** on this project's hot paths. Then it is a rewrite for
  fashion; the benchmark gate says so and the change does not land.
- **`steg_detect`'s corpus ranking cannot be calibrated** without a labelled corpus whose labels
  encode its author's assumptions — the same trap [v4.5.0](./v4.5.0.md) names for magic scoring.
- Any candidate needs network access, or a dependency larger than the tool.

## Verification

- `yara_scan` memory-tested first and functionally second — a leak in a long-lived server is not a
  performance note.
- Every Node 26 adoption carries a before/after number, and the benchmark gate's 25% same-host
  threshold is the arbiter. **A quarter more work does not fail that gate**; it is printed. Do not
  read silence as improvement.
- Image size re-measured after any dependency lands. It is 453 MB today, down from 643 MB.
