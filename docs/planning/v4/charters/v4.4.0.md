# Charter: v4.4.0 — arm64, from reporting to gating

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.

## Intent

v3.8.0 added a `benchmark-arm64` job on `ubuntu-24.04-arm`. It **reports and does not gate**, and
that was the correct call at the time: there was no arm64 noise floor, and this project has set
three thresholds from a first plausible measurement and moved two of them within days.

This charter is the follow-through: accumulate runs, characterise the noise, and only then decide
whether a threshold is possible.

## What has to be true before a threshold exists

The amd64 gate took three releases and one public disproof to get right, and the history is the
argument for patience:

- 25% from a local four-run study;
- 50% when a developer-machine baseline against a CI runner produced two false failures in three;
- 20% in v3.4.0 once the baseline moved onto the runner — then **back to 50% the same day**, when
  four real CI runs swung `To Hex (100KB)` by -41.8% and `Regular expression (1KB)` by +28.2% on
  the same run, on tasks the release did not touch.

`docs/internal/measurements/v3.4.0-runner-baseline.md` keeps the study **and its disproof**.

## Candidate scope

- Accumulate arm64 runs across releases; record each machine, as `v3.8.0-arm64-first-run.md` does.
- Compute a noise floor and a detection curve the way v3.6.0 did for the same-host gate — a
  deliberate tunable slowdown, not a guess.
- Only then: a threshold, stated with what it does **and does not** catch.

## Trigger

At least **twenty** arm64 runs recorded across at least three releases. One run is a number; twenty
is a distribution.

## Kill criteria

- The spread across runs is wide enough that any threshold catching a real regression also fires on
  noise. Then say so and keep reporting — a gate that cannot fail honestly is worse than none.
- GitHub withdraws free arm64 runners for public repositories.
