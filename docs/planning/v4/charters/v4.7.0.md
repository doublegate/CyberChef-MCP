# Charter: v4.7.0 — Progressive discovery, if it standardises

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.

## Intent

The roadmap describes the problem in this server's exact words: "a server can offer a small entry
point and reveal more of its catalog as the conversation narrows". That **is** the `index` surface —
42 tools / 44,493 bytes rather than 545 / 424,897 — plus `cyberchef_categories` →
`cyberchef_list_operations` → `cyberchef_describe_operation`.

This project's solution is **private**. When a standard lands, the private one should become an
implementation of it rather than a competitor to it.

## Status, measured 2026-09-10

"Proposed; design phase." **No SEP number. No timeline.** That is why this is charter seven and not
part of v4.0.0 — and why the honest scope today is *watching*, not building.

## Candidate scope, when it exists

- Map the three navigation tools onto whatever the standard defines.
- Decide whether they survive **as tools** or become protocol methods. This is the whole question:
  if they become methods, the index shrinks by three tools and every document describing the
  navigation path changes; if they stay tools, adoption may be nearly free.
- Keep the surface measurement honest throughout — `tool-surface-figures.test.mjs` now measures
  through a real client rather than comparing documents to a recorded table, because v3.8.0 shipped
  an artefact serving 44,493 bytes while every document said 44,406.

## Trigger

A SEP number exists for progressive discovery **and** it appears in the draft changelog.

## Kill criteria

- The standard mandates a mechanism that cannot express a 504-operation catalogue. Then keep the
  private surface, document the divergence, and say so upstream.
- It standardises something this server already does, in which case adoption is a rename and belongs
  in whatever minor is open — not its own release.
