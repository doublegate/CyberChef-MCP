# Charter: v4.7.0 — Tool result contracts, if they standardise

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.
>
> **Rewritten 2026-09-11**, from v4.5.0, on research retrieved the same day — which **corrected an
> error this charter had carried since it was written**. See immediately below.

## The correction, first

The previous version of this charter — and the DECISION-GATES row beside it — said tool result
contracts were **SEP-2419**. They are not.

**SEP-2419 is `cache_hint`, a well-known key in `CallToolResult._meta`** telling a caching client not
to cache a particular result. It is open, still at `proposal` (not even `draft`), last touched
2026-09-10. It is adjacent to SEP-2549, which this server already implements at the SDK's encode
seam, and it has nothing to do with result *shape*.

**No SEP proposes a general tool result contract**, and none of the live ones is close to final.
The roadmap assigns "tool result shape" to a **Core Primitives Working Group that does not yet
exist**. Three open SEPs each touch one corner of the problem — which is not the same as a contract,
and is why the trigger below watches for a *result-envelope* SEP rather than any of these reaching
`final`:

| | |
|---|---|
| **SEP-2145** — standardise `tools/call` failure reporting | open, `in-review`, 2026-09-07. Would move tool-resolution and `outputSchema` validation failures from JSON-RPC protocol errors to `CallToolResult{isError:true}` |
| **SEP-2998** — partial tool results | open |
| **SEP-3279** — negotiated tool result variants | open |

None of the three satisfies this charter. SEP-2145 relocates *failures* — it changes where a
tool-resolution or `outputSchema` error is reported, not the shape of a successful result.
SEP-2998 and SEP-3279 change *delivery*: how a result arrives in pieces, and how a client and server
agree which of several forms to send. The thing this charter would adopt — a standard shape for
what a successful tool call returns — is what none of them defines, and what has no SEP number.

That is the actual state, and it is a materially weaker trigger than "a numbered SEP is close to
final". Recording it is the point: the old charter would have had someone watching a SEP that was
never about this.

## Intent

If the specification standardises a richer contract for what a tool returns — result shape, failure
reporting, partial or streamed results — adopt it. Until then, do not invent one.

finding, and it is why the charter stays thin: anything written here now describes a shape nobody
has published.

## What this server already does, so adoption is not confused with invention

- `structuredContent` is returned where meaningful — `cyberchef_magic` returns a plain-text report
  **and** structured results, because the operation's own table put the most actionable field in a
  form `bake` rejected.
- Content blocks cover text, image and media; 44 operations declare a `presentType` differing from
  `outputType`, resolved **before the cache**.
- Cache hints (`ttlMs` / `cacheScope`, SEP-2549) are filled at the SDK's 2026-era encode seam from a
  constructor option, not built by hand — which is also why **SEP-2419 would be cheap if it lands**.
- Failures already return `isError` with a typed code and the offending field, which is most of what
  SEP-2145 asks for. **Read SEP-2145 against the current behaviour before assuming work exists.**

## Trigger

Any one of:

- **SEP-2145 reaches `final`** — the most likely of the three, and the one to watch;
- SEP-2998 or SEP-3279 reaches `final`;
- a Core Primitives WG is chartered **and** files a result-shape SEP;
- the draft changelog gains an entry describing result-shape changes;
- `@modelcontextprotocol/server` ships it — checked by **reading the SDK source, not the changelog**,
  the rule this project wrote after finding the cache-hint seam already existed.

## Kill criteria

- **The SDK already implements it.** Close as a one-line note, not a release.
- **This server already satisfies it**, which is a live possibility for SEP-2145 specifically.
  Confirm against behaviour and record the confirmation — an unrecorded "we already do this" gets
  re-investigated every release.
- **Advisory, and changes a shape callers depend on for no measured benefit.** Decline in writing,
  with a negative test as a tripwire, as tasks and `extensions` are declined at
  `SERVER_CAPABILITIES`.
- Requires state outliving the request — declined on the same ground as tasks.

## A nearer watch than any of the above

**The conformance suite is moving while the specification is not**, and it is the most active
repository in the org — commits on 2026-09-11 including
`feat(tools-list): check deterministic tools/list ordering on the 2026-07-28 wire`.

This server serves **544 tools** on `all` and its ordering has never been asserted against that
check. A pinned-exact conformance bump will surface new scenarios the moment it happens, which is
the mechanism working as designed — but it means **the next conformance bump is a release-sized
event, not a dependency bump.** Budget it as one.

## Verification, when it fires

The official suite is the oracle, not the in-tree tests — `npm run conformance`, both eras,
`--suite all`. The scenarios validating v3.0.0 sat in the **pending** suite that `active` excludes,
which is why `--suite all` is not optional.
