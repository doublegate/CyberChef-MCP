# Charter: v4.6.0 — Auth metadata and mixed-auth surfaces

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.

## Intent

**SEP-1488** proposes `securitySchemes` in tool metadata for mixed-auth servers. This server already
solves a private version of that problem, and badly enough to be worth standardising.

## What exists today

Scope filtering on `tools/list` activates **only when auth is on**. The pricing is by the **recipe
submitted**, not by `openWorldHint`: 502 of 504 operations need only `cyberchef:read`, so pricing
`cyberchef_bake` at `network` made the meta-tool cost more than the operations it runs.

`cyberchef_recipe_execute` is deliberately excluded from scope filtering — it carries only an id,
and resolving that id would move the authorization check **after** a storage read.

And the governing rule, which any standard adoption must not break: **listing must never be stricter
than dispatch.** Hiding a tool a caller could successfully invoke is misinformation, not caution.

## Candidate scope

- Declare per-tool `securitySchemes` from the existing scope map, if SEP-1488 lands.
- Reconcile the `recipe_execute` exclusion with whatever the standard says about tools whose
  authorization is not knowable from their arguments — that is a genuinely interesting edge and
  worth contributing upstream rather than only solving locally.

## Trigger

SEP-1488 reaches `final`, or lands in the draft changelog.

## Kill criteria

- The standard requires resolving authorization from arguments, which would force the
  `recipe_execute` check after a storage read. **Decline and say why** — that ordering is a
  security property, not an implementation detail.
- Adoption would make listing stricter than dispatch.
