## Intent

Two live SEPs touch the same surface: **SEP-2817** (AI invocation audit context in request `_meta`)
and **SEP-3004** (tamper-evident audit record contract). Both were updated on 2026-09-10.

## The constraint that governs any adoption here

**Tool arguments are never recorded.** Not in metrics, not in spans, not in the audit log. The MCP
conventions mark them Opt-In; here they *are* the sensitive material — this is a server whose inputs
are ciphertexts, keys, certificates and forensic artefacts.

Related and equally load-bearing: tool names are resolved against the real dispatch catalogue before
becoming a metric label **or** a span attribute, with a 1024-name cap behind it as defence in depth.
The cap alone is exhaustible — fill it first and legitimate tools collapse into `__other__`.

Any audit standard that requires recording arguments is **declined**, with that reasoning, and the
decline is a contribution upstream rather than a local quirk.

## Candidate scope

- Consume invocation context from request `_meta` where it does not require recording arguments.
- Evaluate the tamper-evident record contract against the existing audit log, which already writes
  who/what/when/scope before a dangerous action.
- Keep `/metrics` behind `hostAllowed()` — unlike the health probes, which may skip it because they
  disclose nothing.

## Trigger

Either SEP reaches `final`, or an audit SEP appears in the draft changelog.

## Kill criteria

- The contract requires recording tool arguments or inputs. **Decline, publicly, with the reason.**
- It requires an external datastore. v2.6.0 withdrew a Redis session store; the same reasoning
  applies to an append-only audit store, and this server has never had a datastore dependency.
