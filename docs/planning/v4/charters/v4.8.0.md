# Charter: v4.8.0 — Auth metadata and audit context, if they standardise

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.
>
> **Merged and renumbered 2026-09-11**, from v4.6.0 (auth metadata, SEP-1488) and v4.8.0 (audit
> context, SEP-2817 / SEP-3004). They are merged because they share a trigger source, a kill
> criterion and a verification path — and because two thin charters watching the same unmoved
> specification are one charter with extra filing.

## Intent

Adopt standardised ways to **declare** what authorization a surface needs, and to **carry**
invocation context for audit — if the specification defines them in a form this server can honour
without breaking its own rules.

## The measurement, taken 2026-09-11

**Zero SEPs have reached Final since 2026-05-18**, and the draft changelog has been the empty stub
for 45 days. The three this charter watches, with their real states rather than their remembered
ones:

| SEP | State | Detail |
|---|---|---|
| **1488** securitySchemes | open **issue**, `draft`, 2026-09-10, 38 comments, ~12 months old | Optional `securitySchemes` on tool descriptors (`noauth` / `oauth2` + scopes) so a mixed-auth server marks which tools need sign-in. **Purely additive and backward compatible** — the cheapest of the three if it lands |
| **2817** AI invocation audit context | open, `proposal`, **still seeking a sponsor**, 2026-09-11, 34 comments | A reserved `_meta` key carrying client-asserted `invocationReason` / `model` / `userIntent` / `turnId`; server MAY echo `turnId`. Explicitly **not authorization evidence**, so read-and-log only |
| **3004** tamper-evident audit record | open, `proposal`, no sponsor, no WG, 2026-09-11, 50 comments | Canonical byte form plus an append-only hash chain third parties can verify. **Far heavier** than 2817 — emitting and chaining signed records |

Two identity SEPs sit behind the same unformed group and are worth knowing about rather than
watching: **SEP-1932 (DPoP)** and **SEP-1933 (workload identity federation)**, both `draft`, both
open ~9 months. The roadmap assigns them to an **Agent Identity WG that does not exist yet**.

`npm run check:v4-triggers` tracks the machine-checkable half; **T-3 to T-7 track individual SEPs
and stay manual**, because a SEP's status needs judgement rather than a regex — and because, as the
table shows, a SEP's *number* is not a reliable handle on what it contains.

## What already exists, so adoption is not confused with invention

| | |
|---|---|
| **Scope filtering** | `rbac.visibleTools()` filters `tools/list` — but **only when auth is on**, and `cyberchef_recipe_execute` is deliberately excluded because it carries only an id, and resolving it would move the authorization check after a storage read |
| **Pricing by recipe** | `cyberchef_bake` and `cyberchef_batch` are priced by the **recipe submitted**, not by `openWorldHint`: 502 of 504 operations need only `cyberchef:read`, so pricing `bake` at `network` made the meta-tool cost more than the operations it runs |
| **Audit entries** | written for unauthenticated and forbidden calls today, with subject, tenant and reason |
| **OpenTelemetry** | spans on the API, with tool names resolved against the real dispatch catalogue before becoming an attribute — the name is caller-controlled |

**Tool arguments are never recorded.** The MCP conventions mark them Opt-In, and here they *are* the
sensitive material — a recipe and its input is the user's data.

## Trigger

Any of SEP-1488, SEP-2817 or SEP-3004 reaching `final`, **and** the standard being expressible
without violating the two rules below.

## Kill criteria — and these are the point of the charter

- **It requires resolving authorization from arguments.** That moves the `recipe_execute` check
  after a storage read, which this server rejected deliberately and wrote down.
- **It makes listing stricter than dispatch.** Hiding a tool the caller could successfully invoke is
  misinformation, not caution. This rule has survived three releases that each had a reason to bend
  it.
- **Audit requires recording tool arguments**, or an external datastore. v2.6.0 withdrew a Redis
  session store rather than take on coordination; the same answer applies.
- The SDK already implements it — confirm by **reading the source**, then close the charter as a
  note.

When one of these fires, **decline publicly with the reason**, the way tasks and `extensions` are
declined at `SERVER_CAPABILITIES` with a negative test as a tripwire. A silent non-adoption reads,
two years later, as an oversight.

## Verification, when it fires

`npm run conformance` against both eras with `--suite all`, plus a real-client test for each new
declaration. The scenarios that validated v3.0.0 sat in the **pending** suite that `active`
excludes, which is why `--suite all` is not optional.
