# Charter: v4.1.0 — The entry point, and the landmine under the test suite

> **The number is an ordering, not a schedule.** This directory is numbered `v4.1.0`-`v4.9.0` for
> reading order, and that quietly assumes a `v4.0.0` the plan beside it explicitly says **not to
> cut**. The release a charter lands in is decided at execution time, by SemVer and by what the work
> actually is. This charter's content shipped as **v3.10.0** — see `docs/internal/v3.10.0-findings-log.md`, F-01.

> Run [`../../v3/RE-MEASURE.md`](../../v3/RE-MEASURE.md) first.

## Intent

`src/node/mcp-server.mjs` calls `runServer()` **at module scope, with no main-module guard**, and
`runServer().catch` ends in `process.exit(1)`. Importing the module therefore starts a real stdio
server and arms a process exit — in every test file that imports it.

## Evidence, not suspicion

Verified during v3.9.0 by importing the module in a bare script: the full startup banner appears.
The consequence was not theoretical. v3.9.0's first CI run failed `mcp-test` on **both** Node
versions while passing locally twice, because four test files repoint `CYBERCHEF_RECIPE_STORAGE` at
a temp directory, import the server, and then delete that directory — and a save landing afterwards
killed the vitest worker. Recorded as **F-13** in `docs/internal/v3.9.0-findings-log.md`.

v3.9.0 fixed the race by leaking four temp directories. That is a workaround and says so in the
code. An independent reviewer reached the same diagnosis unprompted and proposed the same fix.

## Candidate scope

- A main-module guard, or an exported `close()`, or both — the reviewer suggested the second and it
  is the better shape for tests.
- Restore the four deleted teardowns once the server can be shut down.
- A test that **imports the module and asserts no server started**, which is the regression gate;
  without it this reverts silently, which is exactly how it arrived.

## Why its own release

It changes the entry-point semantics of the most important file in the repository. `npm run mcp`,
the Docker `CMD`, the `bin` entry and roughly forty documented quick-starts all run that file
directly. Deliberately **not** done inside v3.9.0's bot-review ceremony on a release whose CI had
already failed once.

## Trigger

None needed — the defect is measured and present. This is the one charter here that is ready now.

## Kill criteria

- If a guard cannot be written that keeps `node src/node/mcp-server.mjs`, the Docker `CMD` and the
  `bin` entry all working, **stop** and document why; the workaround is survivable.
- If removing the module-scope call breaks the era decision in `serveStdio` (2026-07-28 vs 2025),
  that is a protocol regression and outranks test ergonomics.

## Second item: the release pipeline races itself

**Observed at the v3.9.0 tag, 2026-09-10.** `publish-mcp.yml` failed:

```text
attempt 75/75: cyberchef-mcp@3.9.0 not visible yet
##[error] cyberchef-mcp@3.9.0 never appeared on npm within 25 minutes.
```

The guard itself is right and should not be weakened: the MCP registry hosts **metadata**, so a
listing published before its artefact resolves points at nothing. Failing beats shipping a dangling
entry, and the error names its own recovery (`workflow_dispatch` after npm has the version).

**The defect is the structure around it.** `publish-mcp.yml` and `mcp-release.yml` trigger on the
same tag and run **in parallel**, and the former waits 25 minutes for something the latter produces.
That is a bet on a multi-arch image build — amd64 plus arm64 under QEMU — finishing inside 25
minutes. It won at v3.8.0 and lost at v3.9.0 with nothing relevant changed between them. A race
whose outcome is a coin flip is not a pipeline.

### Candidate scope

- Make the dependency explicit rather than temporal: `needs:` on the npm publish job, or split npm
  publishing out of the image workflow so the registry job can depend on it directly.
- If they must stay parallel, the wait has to be bounded by evidence rather than by a round number —
  measure how long the image build actually takes across recent tags and derive the budget.
- Keep the guard. Keep the actionable error message.

### Kill criteria

- If the two workflows cannot be ordered without serialising the image build behind npm (which would
  slow every release to fix an occasional retry), **prefer the retry** and document the manual step
  in the release ceremony rather than pretending it is automatic.
