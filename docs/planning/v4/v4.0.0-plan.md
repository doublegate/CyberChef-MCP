# v4.0.0 — the plan, and why it is not scheduled

> **SUPERSEDED IN PART, 2026-09-11. v4.0.0 SHIPPED.** Everything below about triggers A-D and the
> kill criterion still holds and is not repealed: none of them had fired when v4.0.0 was cut, and
> "a major exists because the protocol forced one" remains true *of those triggers*.
>
> **What this document got wrong is what it left out.** All four triggers are EXTERNAL
> specification events, so the project had no internal path to a major at all — v4.0.0 waited on
> something that might never arrive, deprecated surface accumulated with no mechanism able to
> remove it, and the version number stopped carrying information. By v3.11.0 the only deprecation
> warning a normal `cyberchef_bake` call produced was `DEP007`, a **withdrawn** code reading "No
> action required", and the two migration tools it belonged to cost 995 bytes of every
> `tools/list`.
>
> v4.0.0 was cut on a fifth trigger this plan never had — **T-13, accumulated removals** — now in
> `scripts/check-v4-triggers.mjs` and verified by planting the real defect. See
> `docs/internal/v4.0.0-findings-log.md` (F-01) and `docs/releases/v4.0.0.md`.
>
> *A plan that can only be satisfied by someone else is not a plan.*


**Measured 2026-09-10.** This is the deep document the charter directory points at. It follows the
RE-MEASURE ritual, which means it opens by testing its own premise before proposing anything.

## The finding, first

**There is no forcing function for a major version today, and the measurement is unusually clean:**

```text
https://modelcontextprotocol.io/specification/draft/changelog
  → "Changes since the most recent release will accumulate here."   (empty)
```

The draft revision has accumulated **nothing** since 2026-07-28. Not a small change, not a
non-breaking one — nothing. The current revision remains **2026-07-28**, confirmed against
`/specification/versioning`, which still lists it as **Current** with no successor.

The existing charter's kill criterion is explicit:

> If the specification does not force a breaking change, **do not cut a major version.** Ship
> minors. v2.x ran to eleven releases and was the better for it.

**That criterion fires today.** v4.0.0 is therefore *specified* below but **not scheduled**, and the
nine charters beside it are all minors for exactly this reason.

This is not a passive conclusion. It is the same discipline that produced v3.0.0: that release
existed because a specification revision forced it, and its six *planned* breaking changes had all
evaporated by the time anyone measured them.

## The ecosystem is busy, which is not the same thing

An empty draft changelog could mean the ecosystem has stalled. It has not — six SEPs were updated
on the day of measurement:

| SEP | Title | Why it matters here |
|---|---|---|
| **2419** | `cache_hint` well-known key in `CallToolResult._meta` | This server already implements SEP-2549 cache hints on **list** results, via the SDK's `cacheHints` constructor option. Extending the same idea to tool results lands directly on `bakeOnCore`'s response path. |
| **1488** | `securitySchemes` in tool metadata for mixed-auth servers | This server is an OAuth 2.1 resource server with scope filtering on `tools/list`. Declaring per-tool auth requirements is the standard version of what `rbac.visibleTools()` does privately. |
| **2778** | Type constraints in MCP | Tool schemas here are generated from `OperationConfig` through Zod. Richer constraints would improve 504 schemas at once. |
| **2817** | AI invocation audit context in request `_meta` | The server has an audit log and OTel spans that deliberately record **no tool arguments**. A standard context field changes what is safe to record. |
| **2127** | MCP Server Cards — HTTP discovery | `server.json` and the registry listing already cover part of this. |
| **3004** | Tamper-evident audit record contract | Same surface as 2817. |

And two are settled rather than pending: **SEP-2322** (Multi Round-Trip Requests) is marked
`final`, and the **SEP-2663** Tasks implementation tracking issue closed on 2026-08-23.

**SEP-2663 is the one to watch**, because this server has an explicit, tested position on it. Tasks
are *declined*, with the reason recorded at `SERVER_CAPABILITIES` and a negative test as a tripwire:
tasks need state that outlives the request, and this server deliberately has none. The roadmap
describes the Tasks extension as "maturing toward core specification inclusion". **If tasks enter
the core specification, the declined position becomes a conformance gap, and that is a genuine
v4.0.0.** It is the single most likely trigger.

## What v4.0.0 would contain, when something forces it

Not a wish list — each item is derived from a specific trigger, and would only be in scope if that
trigger fired.

### Trigger A — Tasks enter core (SEP-2663)

The largest. This server is stateless by design and was made so deliberately in v3.0.0, when
MCP 2026-07-28 *deleted* sessions. Supporting tasks means:

- state that outlives a request, which is an architectural change, not a feature flag;
- a decision about where that state lives — in-process (loses the stateless property), or external
  (adds the first datastore dependency this project has ever had, and v2.6.0 already withdrew a
  Redis session store for related reasons);
- the negative test at `SERVER_CAPABILITIES` inverts, and the ADR-level reasoning behind the
  decline has to be rewritten rather than quietly dropped.

Breaking, because `server/discover` and the capability set change shape for every client.

### Trigger B — Tool result contracts standardise (SEP-2419 and successors)

If the standard prescribes a result envelope, this server's response shape moves. It currently
returns `content` plus `structuredContent`, with `presentType`/`outputType` resolution that took
three releases to get right (`JSON Beautify`'s quotes being markup structure is why that is a
correctness rule, not a formatting one). A standard envelope is breaking for anyone parsing the
current shape.

### Trigger C — Progressive discovery standardises

The roadmap describes the problem in this server's exact terms: "a server can offer a small entry
point and reveal more of its catalog as the conversation narrows". That **is** the `index` surface
plus `cyberchef_categories` → `cyberchef_list_operations` → `cyberchef_describe_operation`.

When a standard lands, the private solution should become an implementation of it. Whether that is
breaking depends entirely on whether the three navigation tools survive as tools or become protocol
methods. **Status today: "Proposed; design phase", no SEP number, no timeline.** This is charter
`v4.7.0`, not v4.0.0, precisely because it may never need a major.

### Trigger D — Streamable HTTP over stdio

The roadmap proposes unifying local transports under Streamable HTTP. This server's era decision
lives in the `serveStdio` entry rather than in the transport, so the change is smaller here than it
sounds — but it changes what `docker run -i` speaks, which is the documented quick-start in about
forty places.

## What v4.0.0 is explicitly NOT

Carried forward from the charter, because a rejected idea left unrecorded gets re-proposed:

**Revised 2026-09-10.** The first version of this section inherited four labels from the v2.x-era
ROADMAP and rejected them as written. Three of the four turned out to be **conflations** — each
bundles something correctly out of scope with something squarely in scope — and rejecting the label
wholesale would have foreclosed real work. Separated:

| v2.x label | Correctly rejected | But this part is IN scope |
|---|---|---|
| **Quantum-safe cryptography** | Making the server's *own* transport PQC. It terminates no TLS; its auth is OAuth over whatever the operator provides. | **PQC operations.** Measured: **0 of 504** operations match ML-KEM, ML-DSA, SLH-DSA, Kyber, Dilithium or SPHINCS+. These are NIST standards (FIPS 203/204/205), not research. That is "a cipher upstream simply lacks" — the exact bar `classical_cipher` met. Belongs in [v4.2.0](./charters/v4.2.0.md)/[v4.3.0](./charters/v4.3.0.md) candidate scope. |
| **Full WebAssembly runtime** | Running **untrusted, user-supplied** wasm. That is the plugin loader under another name, and [ADR 0002](../../adr/0002-tool-registry-is-not-a-plugin-loader.md) settled it on a measurement. | **wasm-backed operations, which already ship** — `libyara-wasm`, `libbzip2-wasm`, `jq-web` and `tesseract.js` are production dependencies today. Nothing about wasm is rejected; *arbitrary* wasm is. |
| **ML-optimised operation selection** | A learned model in the selection path, with the training data, drift and non-determinism that implies — the same objections as [`../v3/task-level-scoring.md`](../v3/task-level-scoring.md). | **Improving the selection this server already does.** `cyberchef_magic` ranks by chi-squared byte frequencies; v3.9.0 fixed a ranking defect (#130) where a detected container outranked its own decoded contents, and the language estimator is documented as weak enough to call "Attack at dawn" German at p=1.35e-8. Better scoring is not ML and is real work. |
| **Distributed execution** | All of it. The server is stateless by design, the worker pool covers CPU parallelism, and distribution means coordination plus a datastore — which v2.6.0 already withdrew a Redis store rather than take on. | — |

The lesson generalises: **a rejected label is not a rejected capability.** Recording "quantum-safe
cryptography: no" reads, two years later, as "do not add post-quantum operations", which is not what
was decided and not what the evidence supports.
- **A plugin loader**, in any form. [ADR 0002](../../adr/0002-tool-registry-is-not-a-plugin-loader.md)
  settled it on a measurement: a capability passed into a `node:vm` context reaches the real
  `process` through its own `constructor`. Two of the v2.x "vision" items depended on this.
- **A task-level evaluation harness as a gate.** Declined in writing in
  [`../v3/task-level-scoring.md`](../v3/task-level-scoring.md), on the grounds that model sampling
  noise is independent per invocation and therefore does not cancel in the same-host construction
  that rescued the benchmark gate. Its reopening conditions are written there; none has fired.
