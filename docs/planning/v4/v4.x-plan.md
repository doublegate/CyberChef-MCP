# The v4 line — the measured plan for v4.1.0 through v4.9.0

**Measured 2026-09-11, immediately after v4.0.0 shipped.** This replaces `v4.0.0-plan.md` as the
current deep document; that file stays, with its banner, because its reasoning about *why a major
exists* is still load-bearing and because three release notes cite it.

Everything below opens with a measurement, as `../v3/RE-MEASURE.md` requires. Where a measurement
contradicts something this project has written down repeatedly, that is said plainly rather than
smoothed over — two of the findings here do exactly that.

---

## 1. The finding that reorders everything

**Nineteen registry tools occupy 68% of the index surface, and the tool-growth programme cannot
land on top of them.**

```text
index today     44,968 bytes / 41 tools
                  14,305  navigation + meta-tools
                  30,663  registry tools (19 of them, averaging 1,614 bytes each)
```

`docs/planning/ext-proj-int/` scopes **80–120 more registry tools** drawn from eight reference
projects. Against the measured cost per tool, that programme collides with the surface it would
ship on:

```text
+20 registry tools   index  77,245 bytes     0.7x curated
+40                        109,522           1.01x curated  <- ALREADY past curated, not level
+80                        174,075           1.6x curated
+120                       238,629           2.2x curated
```

At **59 total registry tools the index costs more than `curated`** — the preset progressive
disclosure exists to beat. The whole argument in `tool-catalog.mjs`'s header inverts, quietly,
somewhere around the fortieth new tool.

This is not an argument against the tool programme. It is an argument that **the programme has a
prerequisite nobody had costed.**

### Why they are all listed — and the documented reason is half wrong

Six documents say a registry tool *"has no navigation path, so one that is not listed cannot be
called at all."* Measured against the running server, the second clause is true and the first is
not:

| | |
|---|---|
| `cyberchef_search` | **finds them** — returns a separate `analysis_tools` array with a summary |
| `cyberchef_describe_operation` | **refuses**: *"no OperationConfig entry … its full schema is already in `tools/list`"* |
| `cyberchef_bake` | **cannot run one**: `Unknown operation: pqc_identify` |
| `cyberchef_categories` | does not mention them |

So a registry tool is **discoverable by name and summary**, and has **no schema path and no
invocation path**. The `describe_operation` refusal is the sharp part: its redirect *assumes the
tool is listed*, which is precisely the assumption that forces it to be listed.

**The live documents still carry the imprecise wording, and that is deliberate — deferred, not
missed.** `docs/guides/user_guide.md:164` and its siblings say a registry tool "has no navigation
path". Reviewer-found, and the reason for deferring rather than fixing it here is that the
*consequence* those pages state — one that is not listed cannot be called — is **true today**; only
the stated mechanism is wrong. So the pages mislead about *why*, not about *what a caller can do*.

Fixing the wording now would also mean writing it twice: [v4.1.0](./charters/v4.1.0.md) changes the
underlying behaviour, at which point the sentence needs rewriting again. Its Sprint 1.1 carries the
wording fix explicitly. **If v4.1.0 is killed, the wording fix does not die with it** — it becomes a
standalone correction, and this paragraph is the record of that.

### The unlock, and it needs no specification change

`src/node/mcp-server.mjs:56` already imports `buildRegistry` and `ToolRegistry`. Every registry tool
already carries a Zod `inputSchema` that `toInputSchema` converts. The refusal above is a **choice**,
not a missing capability.

Give registry tools the same three-step navigation operations have, plus a dispatcher for
invocation, and the arithmetic changes shape rather than degree:

```text
index becomes    ~15,905 bytes  (navigation + meta + one `analyse` dispatcher)   -65%
and it STOPS GROWING:
  +20 registry tools   ~15,905      (vs 77,245 today)
  +80                  ~15,905      (vs 174,075)
  +120                 ~15,905      (vs 238,629)
```

**The ext-proj-int ceiling moves from 59 tools to effectively unbounded**, and today's index gets
65% cheaper on the way. That makes this the highest-leverage item in the v4 line and a prerequisite
for the tool programme — which is why it is v4.1.0 and the tool work is v4.3.0+.

**The honest risk**, stated because this project's rule is that listing must never be stricter than
dispatch: removing a tool from `tools/list` removes the model's ability to call it directly. The
dispatcher is what keeps listing and dispatch consistent, and without it this change would be a
regression dressed as an optimisation. That is the charter's kill criterion, not a footnote.

## 2. The cadence the old corpus was not written for

```text
v3.1.0  2026-09-03      v3.7.0  2026-09-04      v3.11.0  2026-09-11
v3.2.0  2026-09-03      v3.8.0  2026-09-04      v4.0.0   2026-09-11
...                     v3.9.0  2026-09-10
                        v3.10.0 2026-09-11
```

**Twelve releases in nine days.** `ext-proj-int` sizes its programme at *"24 weeks as scoped"*, which
is off by roughly two orders of magnitude against observed throughput. Any charter here that reads
like a quarter of work has mis-sized itself, and the correct response is to make charters smaller,
not to claim the cadence will slow down.

## 3. What v4.0.0 changed about how this directory works

v4.0.0 shipped on **T-13, an internal trigger the plan did not have** — the full reasoning is in
`../../internal/v4.0.0-findings-log.md` F-01. Two consequences for everything below:

1. **The numbers are now real.** Under the old regime a "v4.2.0 charter" shipped as a v3 minor,
   because `4.2.0` could not precede a `4.0.0` the plan said not to cut. v4.0.0 exists, so
   `v4.1.0` is simply the next release. Every ordering banner in `charters/` is retired.
2. **A major no longer requires the specification's permission.** Triggers A–D still mean *the
   protocol forced one*; T-13 means *this project has surface to retire*. Both are legitimate, and
   the v5.0.0 question at the end of this line is now answerable without waiting on anyone.

## 4a. The ecosystem, measured rather than assumed

Researched 2026-09-11. **The headline is that almost nothing has moved since 2026-07-28**, and for a
plan whose back half is spec-dependent that is the load-bearing fact:

```text
current revision        2026-07-28, unchanged
draft changelog         EMPTY, untouched for 45 days
SEPs reaching Final     ZERO since 2026-05-18
SDK                     server/node/client all 2.0.0, nothing published since 2026-07-27
server.json schema      2025-12-11 still newest; every 2026 date 404s
registry policy         unchanged since 2026-06-04
```

Three corrections this research forced, each recorded because a plan built on a wrong premise is
worse than no plan:

1. **"Tool result contracts = SEP-2419" was wrong**, and this corpus had carried it. SEP-2419 is
   `cache_hint` in `CallToolResult._meta`. **No result-shape SEP exists**; the roadmap assigns it to
   a Core Primitives WG that is **not chartered**. See [v4.7.0](./charters/v4.7.0.md).
2. **Progressive discovery is not merely unstandardised — four attempts are closed.** SEP-1862 was
   closed **unmerged on 2026-09-02**; SEP-1928 is `dormant`, SEP-1300 `rejected`, SEP-1881 closed.
   That is the strongest available argument for [v4.1.0](./charters/v4.1.0.md) building it privately.
3. **Tasks (SEP-2663) did reach Final** — on 2026-05-15, as the `ext-tasks` **extension**, not in
   core. Trigger T-3 asked for core, so it has not fired, but "no SEP has landed" would have been
   false.

**A new roadmap was published 2026-08-22**, replacing the March one, with five priorities including
tool result shape, progressive discovery, ETag-style result versioning, and agent identity. The
structural caveat matters more than the list: **the two priorities this project cares about most are
owned by working groups that do not yet exist.**

**The one thing genuinely in motion is the conformance suite** — the most active repository in the
org, with commits on the day of measurement including a *deterministic `tools/list` ordering* check
against the 2026-07-28 wire. This server serves 544 tools on `all` and has never asserted its
ordering against that scenario. **The next conformance bump is a release-sized event, not a
dependency bump**, and it is budgeted as one in [v4.7.0](./charters/v4.7.0.md).

## 5. What this line is explicitly NOT

Carried from `v4.0.0-plan.md`, because a rejected idea left unrecorded gets re-proposed — with one
row now **closed by shipping**:

- **A plugin loader**, in any form. [ADR 0002](../../adr/0002-tool-registry-is-not-a-plugin-loader.md)
  settled it on a measurement: a capability passed into a `node:vm` context reaches the real
  `process` through its own `constructor`.
- **A task-level evaluation harness as a gate.** Declined in writing in
  [`../v3/task-level-scoring.md`](../v3/task-level-scoring.md); model sampling noise is independent
  per invocation and does not cancel in the same-host construction that rescued the benchmark gate.
  Its reopening conditions are written there.
- **Distributed execution.** The server is stateless by design; v2.6.0 withdrew a Redis store rather
  than take on coordination.
- **PQC operations — no longer a non-goal, because they shipped.** v3.11.0's `pqc_identify` closed
  the row that said *"0 of 504 operations match ML-KEM, ML-DSA, SLH-DSA"*. Recorded here so the
  table is not read as still-open work.

And the lesson that table exists to carry: **a rejected label is not a rejected capability.**
"Quantum-safe cryptography: no" read, two years on, as "do not add post-quantum operations" — which
was never what was decided, and the evidence said otherwise.

turning it into one would overstate it. **No tool in this plan improves adoption as cheaply.**

## 5b. Binary Ninja and VirusTotal — asked, answered, recorded

Both came up during research, and the answers differ. Recorded here because "should we integrate X"
recurs, and an unrecorded no gets re-proposed.

### VirusTotal: one piece yes, the service no

**Yes — `@virustotal/yara-x`, as a library.** Verified on npm: **v1.20.0, BSD-3-Clause, 5.9 MB
unpacked, zero dependencies**, pure WASM so arm64 and amd64 are identical and no build step enters
the image. It is first-party, shipped 2026-08-24, and YARA-X went stable in 2025 with original YARA
moved to maintenance — while the in-tree `YARARules.mjs` backend `libyara-wasm` was last published
**2022-09-18**. It is scoped in [v4.4.0](./charters/v4.4.0.md) for a corpus hit-matrix, with a
memory-first kill criterion because its objects live in the WASM heap and must be freed.

**No — the VirusTotal *service*.** Their hosted MCP server is remote streamable-HTTP at an external
endpoint. Calling it needs **network access and a token**, and this server refuses the only 2
networked operations of 504 under `CYBERCHEF_OFFLINE`, guarded at four engine entries. A tool that
phones an external API is a **posture change**, not a feature, and it is not one a feature charter
decides.

### Binary Ninja: no, and there is nothing to depend on

**There is no npm package** — `binaryninja` and `@vector35/binaryninja` both 404. It is a commercial
desktop product whose 6.0 release ships **its own MCP server** (GUI variant on
`127.0.0.1:24642`). It disassembles binaries; this server transforms bytes. There is no overlap to
integrate.

### The general rule this establishes

**MCP servers compose at the client, not by wrapping.** An agent can hold this server *and*
VirusTotal's *and* Binary Ninja's at once; that is the point of the protocol. Wrapping a peer server
would add a network dependency, an auth surface and a failure mode, to re-expose tools the client
can already reach.

**What is worth taking from them is design, not features.** Two things, and one is already this
line's first charter:

- **`bethington/ghidra-mcp` serves 200+ tools with lazy tool loading** — which is precisely
  [v4.1.0](./charters/v4.1.0.md), arrived at independently from the index measurement. Useful as
  corroboration that the approach is sound at scale.
- **`radare2-mcp` and Binary Ninja are the only two of ~150 security MCP servers surveyed with a
  real safety story** — readonly mode, sandbox lock, per-tool restriction; bearer token. This server
  has RBAC and an offline posture already, which puts it in a small minority, and that is worth
  knowing rather than assuming it is table stakes.

## 6. How the nine charters are laid out

Three groups, ordered by what blocks what rather than by number:

| | Charters | Depends on |
|---|---|---|
| **Unblock** | v4.1.0 surface navigation · v4.2.0 dispatch consolidation | nothing — measured, local, ready |
| **Build** | v4.3.0–v4.5.0 the tool programme, in slices | v4.1.0 landing first |
| **Watch** | v4.6.0–v4.9.0 spec-dependent and consolidation | triggers that have **not** fired |

The Watch group is deliberately the back half. Every one of its triggers was re-measured today and
none has moved; charters there stay thin on purpose, and the ones that never fire get archived with
a dated banner rather than executed to fill a number.

> **Order is not commitment.** v3 executed its charters out of order twice and was right to. What is
> committed is the dependency: the tool programme does not start before the surface can carry it.
