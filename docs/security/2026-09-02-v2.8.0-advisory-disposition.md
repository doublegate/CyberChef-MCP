## 1. Snyk PR #107 — `@xmldom/xmldom` 0.8.15 → 0.9.12 — **CLOSED, no action**

Two independent reasons, either sufficient.

**We are already patched.** Every `@xmldom/xmldom` advisory carries two patched versions, one per
release line. From the GitHub advisory database:

| Advisory | Severity | 0.8-line patch | 0.9-line patch |
|---|---|---|---|
| GHSA-6gmq-8vp8-gcm6 | Moderate | **0.8.15** | 0.9.12 |
| GHSA-2v35-w6hq-6mfw | High | 0.8.13 | 0.9.10 |
| GHSA-f6ww-3ggp-fr8h | High | 0.8.13 | 0.9.10 |
| GHSA-x6wf-f3px-wcqx | High | 0.8.13 | 0.9.10 |
| GHSA-j759-j44w-7fr8 | High | 0.8.13 | 0.9.10 |

The installed version is `0.8.15`, at or above every 0.8-line patch. `npm audit` reports nothing
against it, because there is nothing. 0.9.12 is the *equivalent* fix on the other branch.

**And the upgrade would break a shipped operation.** `src/core/operations/XPathExpression.mjs:53`
constructs the parser with the `errorHandler` option, which 0.9 removed. Reproduced against both
versions on that exact code path:

```text
@xmldom/xmldom@0.8.15:  parsed OK -> root
@xmldom/xmldom@0.9.12:  THREW -> errorHandler object is no longer supported, switch to onError!
```

The construction sits inside a `try` whose `catch` raises `OperationError("Invalid input XML.")`, so
it would not crash visibly — it would report **"Invalid input XML." for every input**, including
valid XML. A silent wrong answer rather than a failure.

`XPathExpression.mjs` is byte-identical to upstream, so adapting it would need a `patches/fork/`
entry rather than an edit; upstream still declares `^0.8.14`. Migrating to 0.9 is real work to be
done deliberately, ideally upstream first — not an automated bump.

## 2. Code scanning: KSV-0125, "untrusted registry" (MEDIUM) — **CONFIGURED**

The chart pins `ghcr.io/doublegate/cyberchef-mcp_v2:<version>`, which is where this project's own
release workflow publishes. KSV-0125 fails any image from a registry outside a built-in allowlist,
and that allowlist does not include GHCR — so the finding is "you use your own registry".

Resolved by **naming the trusted registries** in `security/trivy/data/ksv0125.yaml` rather than
suppressing the check. That keeps it live: verified by pointing the chart at
`evil.example.com/attacker/image`, which still fails the scan.

## 3. Code scanning: KSV-0110, "workloads in the default namespace" (LOW) — **SUPPRESSED, with reason**

A false positive for a *distributable* chart. A Helm chart cannot know its namespace: the operator
supplies it with `helm install --namespace`, and `helm template` without one renders `default`,
which is what Trivy sees. Hardcoding `metadata.namespace` would be actively wrong — it would
override `--namespace` and force every installation into one namespace.

Suppressed in `security/trivy/.trivyignore.yaml`, with the reasoning in the file rather than in a
commit message.

## 4. The scanning gap this release nearly created

Both findings above were reported against `app/deploy/helm/...` — **inside the container image**.
The chart was being scanned only because `deploy/` was being copied into the runtime image.

v2.8.0 stopped shipping non-runtime trees, for size. That would have closed both alerts *by moving
the file*, and silently ended the chart's scanning altogether. A finding that disappears because the
file moved is not a finding that was addressed.

So the IaC is now scanned where it lives, deliberately: a new `trivy-iac-scan` step in
`security-scan.yml`, configured by `security/trivy/trivy.yaml`.

Three things were learned building it, each of which had failed silently first:

- **`ref-proj/` produced 42 of 43 findings** in the first full run, including four CRITICALs — all
  of them upstream GCHQ CyberChef's own files, kept only so the sync can three-way diff. Excluded.
  Reporting upstream's Dockerfiles as this project's posture would bury the one finding that is ours.
- **The config-file keys are not where the CLI flag names suggest**, and Trivy ignores unknown keys.
  `--config-data` is `rego.data` (not `misconfiguration.data`) and `--skip-dirs` is
  `scan.skip-dirs` (not top-level). The first version of the file was ignored entirely and the scan
  returned 43 findings — caught only by running the config file on its own instead of assuming it
  agreed with the CLI flags that had worked.
- **Ignore-file paths are relative to the SCAN ROOT.** CI scans the repository, giving
  `deploy/helm/.../templates/workload.yaml`; scanning the chart directly gives
  `templates/workload.yaml`. A glob for one matches nothing under the other, and the suppression
  looks correct while achieving nothing. Both forms are listed.

Verified live by mutation — an untrusted registry, a weakened `securityContext`, and a root
`USER` in the Dockerfile each still fail the scan.

## 5. `npm audit`: 4 low-severity, one root cause — **NO FIX EXISTS**

```text
crypto-browserify 3.12.1  (direct, and the latest published)
└─┬ browserify-sign 4.2.6 → elliptic 6.6.1
└─┬ create-ecdh 4.0.4     → elliptic 6.6.1
```

All four trace to **GHSA-848j-6mx2-7j84** (LOW), *"Elliptic Uses a Cryptographic Primitive with a
Risky Implementation"*, whose range is `<= 6.6.1` with **`firstPatchedVersion: NONE`** — it affects
every version ever published. `elliptic@6.6.1` is the latest, and the CRITICAL advisory in that
package (GHSA-vjh7-7g9h-fjfh) *is* patched in 6.6.1, which is what is installed.

**`npm audit fix --force` would make this worse.** Its proposed remedy is
`crypto-browserify@3.5.1`, flagged `isSemVerMajor: true` — a downgrade to a release from 2018 that
would not remove `elliptic` either. `crypto-browserify` is a direct dependency at `^3.12.1`,
matching upstream exactly.

Nothing to do: every package in the chain is at its latest version, and the remaining advisory has
no patch anywhere. `npm audit` runs `continue-on-error: true` in `security-scan.yml`, so it does not
gate the build. Re-check when `elliptic` publishes a fix.
