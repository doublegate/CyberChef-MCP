**Released:** 2026-11-26

## What changed, in one paragraph

Mostly a security dependency release. Every advisory below lives in a dependency or the container
base image, and is fixed by the version resolved in `package-lock.json` or by the base-image
digest in `Dockerfile.mcp`. Installing from npm with an existing lockfile needs one extra step; see
the hono note below. Relative to v4.2.0 there is one source change: **upstream CyberChef v11.5.0**
reaches a release for the first time, adding one operation, `Parse PGP Key`, and seven upstream
fixes (see [Upstream](#upstream-cyberchef-v1140---v1150)). Separately, **`RSA Verify` keeps
working**. It was disabled on `master` after v4.2.0 because of CVE-2026-85393 in node-forge, and is
restored here byte-for-byte, unchanged from v4.2.0, now on node-forge 1.4.4, which fixes the
flaw. New regression tests prove the forgery is rejected (see
[RSA Verify](#rsa-verify-is-restored)). Six
Dependabot pull requests are folded in: #176, #177, #181 and #182 through #185, and #186 and #187
through #188. This is also the first release of the runtime updates #170 landed on `master` after
v4.2.0. No configuration key, transport or protocol behaviour changes; see
[Compatibility](#compatibility). The version string is read at startup, so a running v4.2.1 server
reports `4.2.1` in `serverInfo`, the startup log and the `cyberchef_mcp_build_info` metric.

## RSA Verify is restored

**What happened.** CVE-2026-85393 (GHSA-86w9-cpqp-85rv, HIGH) is a signature-forgery flaw in
node-forge <= 1.4.0. RSA PKCS#1 v1.5 verification checked the element count of the outer
`DigestInfo` SEQUENCE but not of the nested `DigestAlgorithm` SEQUENCE. Unconsumed bytes inside that
nested structure still verified, which gives a low-exponent (e=3) key the room for a forged
signature over any message. It was an incomplete fix for CVE-2026-33894. On 2026-10-09, with no
fixed node-forge release available, commit 89cc60b9 replaced `RSA Verify`'s body on `master` with a
"temporarily disabled" error. That change never shipped: v4.2.0 predates it, so v4.2.0 users had the
operation working on vulnerable node-forge 1.4.0.

**What v4.2.1 does.**

- It ships node-forge **1.4.4** (`^1.4.4` floor). That release carries the upstream fix
  (digitalbazaar/forge#1152), which requires the nested `DigestAlgorithm` to contain only the OID
  and an optional NULL.
- It restores `src/core/operations/RSAVerify.mjs` **byte-for-byte from gchq/CyberChef v11.5.0**,
  which is also byte-identical to the file v4.2.0 shipped.
- It drops the hand edit. Under this fork's rules `src/core/**` is upstream-owned, and an edit there
  that is not a `patches/fork/` patch is silently reverted by the next sync: that is how the
  SafeRegex mitigation was lost. The next sync would have re-enabled `RSA Verify` unannounced.
  Restoring upstream's file makes that sync a no-op for this operation.

**How it is proven.** `tests/mcp/cve-regressions.test.mjs` gains nine tests. They sign with a real
key rather than reproduce a full e=3 forgery, which keeps the one property under test isolated: does
verification reject a `DigestAlgorithm` whose shape is anything other than the OID plus an
optional, empty NULL?

| Test | node-forge 1.4.0 | node-forge 1.4.4 |
|---|---|---|
| a genuine signature verifies | Verified OK | Verified OK |
| a genuine signature over a different message | Verification Failure | Verification Failure |
| control: `DigestAlgorithm` = OID, NULL | Verified OK | Verified OK |
| control: `DigestAlgorithm` = OID alone (parameters absent, allowed by RFC 8017) | Verified OK | Verified OK |
| OID, NULL, plus an extra OCTET STRING (the CVE-2026-85393 vector) | **Verified OK (vulnerable)** | **`OperationError`** |
| OID with non-NULL INTEGER parameters | **Verified OK (vulnerable)** | **`OperationError`** |
| OID with non-NULL OCTET STRING parameters | **Verified OK (vulnerable)** | **`OperationError`** |
| OID with a NULL that carries 32 value bytes | **Verified OK (vulnerable)** | **`OperationError`** |
| guard: an extra element on the **outer** `DigestInfo` (CVE-2026-33894) | `OperationError` | `OperationError` |

The table is measured, not inferred. The suite was run against node-forge 1.4.0 installed in place
(`npm install --no-save node-forge@1.4.0`), where the four malformed `DigestAlgorithm` cases fail
and the other five pass, and against the locked 1.4.4, where all nine pass. The last row is the
outer half of the same bug, fixed in 1.4.0 already. It guards the fix that CVE-2026-85393
completed, rather than distinguishing the two versions. The test key comes from Node's native
`crypto.generateKeyPairSync` and is imported into forge, so the suite has no pure-JS prime search on
its path. The controls exist so that a broken test
builder cannot make a rejection pass for the wrong reason. The rejections assert an
`OperationError` whose message names the `DigestInfo`, not just "some exception", so a bare `Error`
leaking to the MCP layer would also fail. Against the disabled operation that `master` carried,
every test fails, so the suite also fails if anyone disables the operation again without changing
the test.

## Upstream CyberChef v11.4.0 -> v11.5.0

#153 synced upstream v11.5.0 (released 2026-09-18) into `src/core/**` on 2026-10-09, after v4.2.0
was tagged. The sync is mechanical: an `rsync -a --delete` of the upstream tree, then the
`patches/fork/` patches re-applied, where a patch that stops applying fails the sync. So these are
upstream's changes, listed with upstream's pull requests:

| Change | Upstream | Effect here |
|---|---|---|
| **New operation `Parse PGP Key`** | gchq/CyberChef#2734 | New tool `cyberchef_parse_pgp_key`, in the `Public Key` category. Uses `openpgp` |
| Duplicate `RandomPrime.mjs` removed | #2764 | No operation lost: it was byte-identical to `GeneratePrime.mjs` and both declared `Pseudo-Random Prime Generator` |
| `LM Hash` no longer crashes on input that expands when upper-cased | #2787 | Error -> digest for such input |
| `Render Markdown` keeps anchors that already carry a `target` attribute | #2767 | Output change for those links only |
| `PEM to JWK` adds an opt-in `kid` (RFC 7638 thumbprint) | #2771 | New boolean argument, off by default. Default output measured identical to v4.2.0 for RSA (SPKI, PKCS#8, PKCS#1) and EC P-256 (SPKI, PKCS#8) keys |
| `MOD`, `Luhn Checksum` raise `OperationError`, not a bare `Error` | #2766 | Same failure, now a structured tool error |
| `Parse IP range` masks host bits in the network of a CIDR range | #2694 | Output change for CIDR input with host bits set |
| `Disassemble x86` accepts hexadecimal address arguments | #2721 | New accepted input form |
| Blank number arguments fall back to the declared default | #2707 | `Operation.mjs`: a `number` argument whose value is `NaN` (for example, left blank) takes the argument's default instead |
| Numeric `0` input is a value, not an empty dish, in the Node API | #2759 | `Dish.mjs` and `src/node/api.mjs`: input `0` is processed instead of being treated as empty |

Upstream's one SECURITY item in v11.5.0 (no autobake on a loaded recipe when an operation sets
`manualBake`) is in the web UI. `src/web` is not part of this server, so it does not apply here.

Operation count: **504 -> 505** (`Parse PGP Key`). `tools/list` on `all` goes from 545 to **546**
tools, measured at 427,123 bytes with `npm run measure:surfaces`. The `index` (23 tools, 15,620
bytes) and `curated` (120 tools, 109,548 bytes) surfaces are unchanged, so a default client sees
the same listing as on v4.2.0. The new operation is reachable there through `cyberchef_search`,

## Behaviour of the folded-in updates

None of these is a security fix, but some touch code paths whose output users check, so each was
read against the code that calls it.

**`js-sha3` 0.14.0 -> 0.16.0** (`SHA3`, `Keccak`, `Shake`). This is a 0.x minor bump, so it may
break things, and it brings two digest-affecting changes:

- 0.15.0 encodes unpaired UTF-16 surrogates in **string** input as U+FFFD, matching `TextEncoder`
  and Node.js `crypto`.
- 0.16.0 hashes multi-byte **typed arrays** (`Uint16Array`, `Uint32Array`, `Float32Array`, ...) by
  their underlying bytes, and fixes the digests of `DataView` and of `Int8Array` with negative
  values.

Neither change can alter a CyberChef digest. All three operations declare
`inputType = "ArrayBuffer"` and pass that buffer directly to `sha3_*`, `keccak*` or `shake*`. Both
versions treat an `ArrayBuffer` as raw bytes. The 18 SHA3, Keccak and Shake vector tests in
`tests/operations/tests/Hash.mjs` pass unchanged.

**`kbpgp` 2.1.19 -> 2.1.21** (PGP operations). The dropped `bzip-deflate` dependency is replaced by
a vendored decompressor, not removed: `lib/openpgp/packet/compressed.js` still handles
`C.compression.bzip`, now through `contrib/bzip_deflate`. The new code passes a `max_length` bound
into the inflater, which caps how far a BZIP2-compressed packet can expand. BZIP2-compressed PGP
messages still decode, with a decompression-bomb limit they did not have before.

**`openpgp` 6.3.2 -> 6.3.3** (`Parse PGP Key`). Upstream fixed brainpool and secp256k1 ECDSA signing
and verification under Node, which failed because a dependency was missing from the bundle
(openpgpjs/openpgpjs#2075, fixed by #2078). `Parse PGP Key` parses keys and never signs or
verifies, so its output does not change.

**`terser` 5.51.2 -> 5.51.4** (`JavaScript Minify`): patch releases. The operation has no
known-answer test in `tests/operations`, so it was exercised through the SDK client instead (see
[Verification](#verification)). **`jquery` 4.1.0** and **`postcss-loader` 8.2.2** are used only by the web app and its
build. Nothing under `src/core/operations` or `src/node` imports them.

## Supply-chain review

`openpgp` 6.3.3 is the first `openpgp` release in years to declare a runtime dependency. The new
dependency, `eckey-utils`, is a single-maintainer package, and that pattern is a known warning sign,
so it was traced before it was accepted:

- `openpgp@6.3.3` was published to npm by `larabr`, the openpgpjs maintainer who also published
  6.3.2. Its `gitHead` is `804cf464`, which matches the `v6.3.3` GitHub release.
- At that commit, upstream `package.json` declares `"eckey-utils": "^0.7.14"`. It was introduced by
  openpgpjs/openpgpjs#2078, which `larabr` wrote and merged. Before that it was a bundled
  development dependency.
- The `eckey-utils@0.7.14` tarball (ISC, 27 KB unpacked) has no install scripts and no
  dependencies. It never uses `child_process`, `http` or `fetch`.
- `^0.7.14` cannot resolve to the `eckey-utils` 1.x and 2.0 releases published on 2026-11-17 and
  2026-11-18, so those were not evaluated and cannot be installed through this range.
- The range is `openpgp`'s own, not this project's. The Docker image and `npm ci` install exactly
  0.7.14 from the lockfile. A fresh npm install of `cyberchef-mcp` without a lockfile resolves
  whatever `<0.8.0` release is newest at that moment, and a future 0.7.x was not reviewed here. Use
  the image, or commit your lockfile, if that matters to you.
- OSV lists no advisories for any of the six versions #188 resolves.

## Compatibility

This is a drop-in release over v4.2.0: nothing a v4.2.0 client relies on is removed or renamed.

**A note on the version number.** Strict SemVer would make this 4.3.0. The upstream sync adds a
tool (`cyberchef_parse_pgp_key`) and an optional argument (`cyberchef_pem_to_jwk`), and additive
functionality is a MINOR change. It ships as 4.2.1 deliberately, as the security release for the
v4.2 line. Both additions come from the upstream sync rather than from new fork features, both are
opt-in, and a client that pins `^4.2.0` or `~4.2.0` picks up the security fixes either way. Nothing
changes for a client that does not call the new tool or pass the new argument.

- **Tools and schemas:** additive only. `index` (23 tools) and `curated` (120) are unchanged. `all`
  gains `cyberchef_parse_pgp_key` (545 -> 546). `cyberchef_pem_to_jwk` gains one optional boolean
  argument whose default reproduces v4.2.0's output. All 505 operations and 19 registry tools are
  present, and the `cyberchef_` prefix is unchanged.
- **Behaviour:** `RSA Verify` verifies again, as it did in v4.2.0, now on fixed node-forge. The
  upstream fixes above change output only for the inputs each one names.
- **Protocol:** unchanged. The 2026-07-28 and 2025 eras both match the conformance baseline.
- **Configuration:** unchanged. There are no new, renamed or removed keys in `cyberchef.config.json`
  or the environment, and the precedence is still env > file > default.
- **Transports:** unchanged. `stdio`, Streamable HTTP and `socket` behave as before; the hono
  upgrade is internal to the HTTP transport.
- **Runtime:** Node `>=26 <27`. The image moves from Node v26.12.1 to v26.13.1.
- **Licence:** GPL-3.0-or-later, unchanged.

**How an operation's own error reaches an MCP client.** The forged-signature rejection arrives as
the tool's text result with `isError: false`, not as a protocol-level tool error. That holds for
every operation, and it is pre-existing behaviour, not part of this release. The recipe engine
(`src/core/Recipe.mjs`) turns an `OperationError` raised by an operation into that operation's
output text; v4.2.0 behaves the same, and so does, for example, `RSA Verify` with an empty key ("Please
enter a public key."). `isError: true` is reserved for failures the server itself detects, such as
an unknown operation, invalid arguments or the offline guard. For `RSA Verify`, an MCP client should
therefore treat only the exact text `Verified OK` as success. That has always been the operation's
contract, and the tests above pin it at the operation layer.

`js-sha3` 0.14.0 and 0.16.0 were also run side by side outside the server, on the inputs CyberChef
produces. They return identical digests for every `ArrayBuffer` input, and differ only for a string
that contains a lone surrogate, which CyberChef never passes to them.

A note on non-ASCII input, since it looks like a regression and is not one. Through MCP,
`SHA3("é")` hashes the single byte `0xE9`, not the UTF-8 bytes `C3 A9`. That conversion is
upstream CyberChef's `Utils.strToArrayBuffer`, which maps text whose code points are all below 256
to one byte per character. It happens before js-sha3 sees the input, it is the same on v4.2.0, and
this release does not change it.
