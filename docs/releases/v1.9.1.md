## The defect

`LRUCache.getCacheKey` hashed only the first 1,000 characters of the input:

```js
hash.update(input.substring(0, 1000));   // "Use first 1KB for hash"
```

Two different inputs sharing that prefix produce the **same key**, so the second caller receives
the first caller's answer. Reproduced against the shipped code:

```
a = "x".repeat(1000) + "SECRET-A"        (1,008 chars)
b = "x".repeat(1000) + "DIFFERENT-B"     (1,011 chars)

keys equal: true
lookup with b's key returned: "ANSWER-FOR-A"
```

Two consequences, the second being the serious one: a **silently wrong result** for valid input,
and on a shared HTTP server, **one caller receiving output computed from another caller's data**.
Since these operations are typically decode, decrypt, hash or parse, that output may be derived
from sensitive material.

Nothing about triggering it is exotic. The cache is on by default, inputs over 1,000 characters are
ordinary, and a shared prefix is the normal case for the same document with different trailing
content, for log lines, and for anything with a fixed header. No malice is required.

| | |
|---|---|
| **Affected** | v1.4.0 through v2.4.0 — introduced with the LRU cache in v1.4.0 |
| **Patched** | **v1.9.1** on this line; **v2.4.1** on the current line |
| **Advisory** | [GHSA-rmg9-8936-vx66](https://github.com/doublegate/CyberChef-MCP/security/advisories/GHSA-rmg9-8936-vx66), CVSS 5.9 |
| **Mitigation without upgrading** | `CYBERCHEF_CACHE_ENABLED=false` |
| **Affected only by the wrong-answer half** | Single-user stdio deployments — no second caller to receive the data |

The fix hashes the whole input plus its length. Full SHA-256 is 2.3 ms at 1 MB and 252 ms at the
100 MB input ceiling — negligible against the operation the cache guards, which scales with the
same input.

## Two release-machinery defects, fixed here because this release needed them

Both were latent and would have caused real damage on this release specifically.

**`latest` would have moved backwards.** Docker Hub uses a single repository across majors
(`parobek/cyberchef-mcp`), unlike GHCR which is per-major. `docker/metadata-action` defaults to
`latest=auto`, which tags `latest` for any non-prerelease semver tag and **does not compare
versions** — so publishing this v1.9.x patch would have pointed `latest` at the v1 image, handing
every unpinned user a two-major-version downgrade.

This was verified rather than assumed: v2.4.1 was tagged on a release branch rather than the
default branch and `latest` moved anyway, which also demonstrates that the
`enable={{is_default_branch}}` condition in the workflow was never what controlled it. The v1 line
now sets `latest=false` explicitly.

**The release asset and the vulnerability scans referenced `:latest`.** The workflow pulled, saved
and scanned `$IMAGE:latest` rather than the version it had just built — so a v1.9.x release could
have attached a **v2** tarball to its GitHub release and published Trivy results describing a build
this release never produced. Now pinned to the tag's own version.

## Upgrading

```bash
docker pull ghcr.io/doublegate/cyberchef-mcp_v1:1.9.1
```

Nothing is breaking. Cache entries are keyed differently, so the cache starts cold — which is the
intended effect, the old entries having been keyed by a value that did not identify their input.

**If you are considering v2.x instead:** it is a different licence (GPL-3.0-or-later), has breaking
changes documented in `docs/v2.0.0-breaking-changes.md`, and is where feature work happens. This
line receives security fixes only.
