## `cyberchef_pqc_identify` — the nineteenth registry tool

**Zero of the 504 operations touch ML-KEM, ML-DSA or SLH-DSA.** That was measured against
`OperationConfig.json` rather than assumed: no operation matches `kyber`, `dilithium`, `sphincs`,
`ml-kem`, `ml-dsa`, `slh-dsa`, `falcon`, `lattice` or `post-quantum`. A toolkit that parses RSA,
ECDSA, DSA and EdDSA and not the NIST standards has a gap a user will meet.

The new tool names the parameter set behind a key, signature or ciphertext — ML-KEM (FIPS 203),
ML-DSA (FIPS 204), SLH-DSA (FIPS 205), all eighteen sets.

### It identifies; it does not implement

Node's own `crypto` generates every one of the eighteen parameter sets from Node 24. This project
has no business shipping its own lattice arithmetic, and the RE-MEASURE ritual's "search the
ecosystem before you build" step is what surfaced that. It changed the build twice over:

- **Every test fixture is generated by Node at test time.** No hand-assembled DER anywhere. A
  hand-written blob tests the parser against its author's understanding of the format; a generated
  one tests it against an implementation that has to interoperate.
- **The OID and size table was extracted, not cited.** Every value came out of a key Node produced,
  and then agreed with the published FIPS figures — which is the cross-check, not the source.

### What it refuses to claim

Given DER — PEM, hex or base64, SPKI or PKCS#8 — it reads the algorithm OID, answers `definite`, and
reports the OID so the answer can be checked rather than trusted. Given raw bytes it has only a
length, and a length is evidence, not an identification. So it lists **every** candidate and
declines to choose:

- **1568 bytes is both an ML-KEM-1024 encapsulation key and an ML-KEM-1024 ciphertext.** A tool that
  answered one would be right half the time and confident always.
- **A 32-byte SLH-DSA public key is indistinguishable from a SHA-256 digest or an Ed25519 key**, and
  48 and 64 collide the same way.
- **The hash family is not recoverable from a raw signature at all.** `SHA2-128s` and `SHAKE-128s`
  signatures are both 7856 bytes, and that holds across every SLH-DSA size.

A non-match is reported as a non-match rather than as absence: 999 bytes matching nothing does not
mean the input is not post-quantum.

### The first extraction was wrong and looked right

The OID table was first pulled by scanning for the `0x06` tag byte near the start of the SPKI. It
gave correct answers for five of six algorithms, and this for the sixth:

```text
ml-kem-1024   1.8.11.6.9.96.840.1.101.3.4.4.3.3.262.33.0.2348.414852...
```

A `0x06` inside a length field, read as a tag. **Five plausible results and one absurd one is a
lucky failure mode** — had the sixth also looked plausible, a wrong OID would have shipped.
Replaced with a real DER walk, which agrees with the published values for all eighteen, and pinned
by a test that fails if the byte scan comes back.

## The coverage margin v3.10.0 warned about lasted one release

v3.10.0 measured statements at 95.06% against a threshold of 95, wrote down that the margin was
thin, and said what to do when it broke: cover the code, do not move the bar.

```text
before   94.99 statements   FAILS the 95 threshold
after    95.16 statements   exit 0
```

The deficit was the new tool, and the shape of it is the interesting part: `pqc-identify.mjs`
measured **91.39% statements against 98.64% lines**. Nearly every line ran. What did not run were
the parser's *rejection* paths — a truncated TLV, a PKCS#8 version INTEGER with nothing after it,
an `AlgorithmIdentifier` whose first element is not an OID, an OBJECT IDENTIFIER with an empty body
— and every `input_format` other than `Auto`.

Those are precisely the paths where a parser invents an answer, and this parser's predecessor did
invent one. The tests were owed regardless of the threshold, and writing them found a real defect:
**the tool threw a bare `Error` where every other registry tool throws `createInputError`**, so the
same class of bad input reached a client untyped, without the `INVALID_INPUT` code or the offending
field. Fixed, and pinned by a test asserting the code rather than the message.

## Four gates caught this release, and one of them was not on the list

Adding one tool moved five documented figures. Each gate named its own fix:

```text
registry-tool-docs       19 expected, 18 found, across 7 documents; 4 inventories missing the name
tool-surface-figures     table says 42 / 44,493, server serves 43 / 45,647
stdio-client-contract    a registry tool with no client-driven call fixture
test:coverage            statements 94.99% against a threshold of 95
```

The third is the one worth recording. `stdio-client-contract.test.mjs` derives its expected fixture
list **from the live registry** rather than from the fixture table beside it — its own comment
explains that an earlier version compared the table against itself, which is an identity that cannot
fail. That is the only reason a new tool with no client-driven call surfaced at all.

`registry-tool-docs` earned its keep the same way: it **discovers** which documents behave as
inventories instead of listing them, and so named `docs/guides/commands.md`, which no part of the
plan mentioned.

count will see 43 rather than 42 on `index`, 121 on `curated` and 546 on `all`.
