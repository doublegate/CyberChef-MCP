## F-01 — arm64 was blocked on hardware this repository already uses — **THE PLAN WAS WRONG**

The carried-forward list has said the same thing since v3.3.0, and v3.7.0 re-recorded it unchanged:

> **arm64 performance is still unmeasured.** The timings taken there came from QEMU on an amd64
> host and measure the emulator; real numbers need arm64 **hardware**.

That objection is obsolete, and has been for some time. `mcp-docker-build.yml` line 47:

```yaml
  build-arm64:
    runs-on: ubuntu-24.04-arm
```

GitHub-hosted arm64 runners, free for public repositories, **already in use in this repository** and
succeeding on every recent run. The hardware the note says is needed has been sitting in the CI
configuration of the same project.

The note was carried forward five times without being re-checked against the thing it claims is
missing. That is the failure mode the re-measurement ritual exists for, arriving from the other
direction than usual: normally a plan describes work that is already done, and here it describes a
blocker that is already gone.

There is even a comment three lines above that label explaining the runner-label security property
in detail — so the arm64 runner was not merely present, it had been reasoned about carefully. The
carried-forward note and the workflow have coexisted for releases without anyone connecting them,
which is what a list nobody re-measures does.

### Scope decision

**v3.8.0, a MINOR.** New measurement, a new registry tool and a design document; the arm64
benchmark reports and does not gate, following v3.5.0/v3.6.0's discipline of measuring a noise floor
before setting a threshold. No runtime behaviour changes for existing users. v4.0.0 stays
unscheduled — no MCP specification revision after 2026-07-28.

## F-03 — Two wrong numbers, both found in the output of gates run for something else

Neither was on the plan, and neither was found by looking. Both appeared in output produced while
verifying the release, which is the case for reading what a gate prints rather than only its exit
code.

### `describeSurface` reported tokens, and the wrong tokens

`npm run measure:surfaces` was re-run to confirm the release notes' surface figures. It printed the
server's own startup line alongside its measurement:

```text
tool surface: all (504/504 operations; ~86k tokens per tools/list)
  all         545     424810      415       106ms
```

Two defects in one line, visible only because the true measurement sat directly beneath the claim:

1. **It is a token figure**, in a repository whose own AGENTS.md row says *"Bytes, not tokens: no
   tokenizer has ever been in this repo and every historical `~N tokens` figure was bytes/4."* This
   line was one of those figures and had never been converted.
2. **It had drifted by a fifth even under its own convention.** 424,810 / 4 is ~106k, not 86k. The
   number was presumably right when the index shipped; v3.3.0's twelve registry tools moved it and
   nothing re-measured a string that nobody thought of as a measurement.

It is operator-visible — it is logged at startup to answer "why can the model not see this tool" —
so a wrong figure there is advice, not decoration. Now `~415 KB`, with the history in a comment so
the next reader does not re-derive it.

### The coverage row had lines and statements transposed

`npm run test:coverage` printed:

```text
Statements   : 95.54%    Branches : 89.52%    Functions : 96.53%    Lines : 96.60%
```

`AGENTS.md` said *"95.7% lines / 89.6% branches / 96.7% functions / 96.6% statements"* — the same
four numbers with **lines and statements swapped**. Confirmed as a transposition rather than a real
change by `vitest.config.mjs`, which records v2.7.0's actuals as `statements 95.78 ... lines 96.63`:
the same relationship, so the row has been wrong since it was written.

The sting is where it sat. `vitest.config.mjs` carries a paragraph about exactly this confusion:

> NOTE the order. Vitest takes these as named keys; the docs quote them in the conventional
> statements/branches/functions/lines order [...] They are not swapped -- a reviewer read them as
> swapped once, which is why this note exists.

The warning was written about the *threshold* tuple and never applied to the *actuals* quoted two
files away. The figures are now given in the order vitest prints them, and the threshold tuple beside
them is explicitly labelled with its different order rather than left to be inferred — because the
two orders sitting unlabelled next to each other is what made this survivable for six releases.

## F-04 — The benchmark workflow did not run on changes to the benchmark workflow

The arm64 job was written, committed, pushed, and opened as a pull request. The PR had **no
benchmark check on it at all**.

`performance-benchmarks.yml` filters its triggers by path:

```yaml
    paths:
      - 'src/node/mcp-server.mjs'
      - 'src/node/index.mjs'
      - 'src/core/**'
      - 'benchmarks/**'
```

Every entry names code the benchmarks *measure*. None names the workflow that measures it. So an
edit to this file does not run this file — and the one class of change whose correctness this
workflow is the only available judge of is precisely the class it never executed on.

The consequence for this release, stated plainly: **a new CI job would have merged having never run
once**, while the release notes described its behaviour in the present tense. That is the same
defect this project has now written about repeatedly under other names — a claim published without
the measurement that would support it — arriving this time in the shape of a job that had never
executed.

It was not found by review. It was found by looking for the benchmark result on the pull request
and there not being one. The filter is a sensible optimisation and the omission is easy to make;
what makes it costly is that its failure mode is **silence**, and a missing check reads exactly like
a check that passed unless someone counts.

### Fix

The workflow's own path is added to both filters. The PR then triggers it, which is how the arm64
job gets executed before it is merged rather than after.

### What this does not fix

The filter still omits `src/node/lib/**` and `src/node/tools/**`, deliberately. A benchmark run
costs two full dependency installs and several minutes on two architectures, and v3.4.0's study
established that this runner pool is heterogeneous enough that extra runs on unrelated changes buy
noise rather than signal. The rule this finding establishes is narrower and it is the one that was
actually violated: **a gate must trigger on changes to itself.**

## F-05 — Review found a tool contradicting itself, and a claim arithmetic alone refutes

Four review threads on PR #122, all four correct, all four verified against the code before being
answered.

### `self_consistent` was false for the commonest valid input in the world

`cert_chain` pushed the missing-root message into `problems`, and `self_consistent` was
`problems.length === 0`. So a server's ordinary `fullchain.pem` — leaf plus intermediate, no root —
came back:

```text
self_consistent: false
assessment:      "... a missing root is expected in a server bundle and is not a defect ..."
```

The tool contradicted itself inside a single response. A reader who believes the flag distrusts a
good bundle; a reader who believes the prose learns to ignore the flag. Neither is acceptable.

Worse, **the tests encoded the defect**. The test named "says a missing root is expected rather than
calling it a defect" asserted the text appeared in `problems` and never asserted `self_consistent`
at all — so the suite pinned the wrong half of the behaviour while its own name described the right
one. Notes and problems are now separate fields, `self_consistent` keys off defects alone, and both
directions are pinned so they cannot drift back together.

This is the third design change to this tool caused by a measurement or a reader rather than by
review-in-the-abstract, in one release. That is an argument for the tool, not against it: each
correction moved it from something plausible to something true.

### The surface figures were half-updated, and nothing gated them

Adding one registry tool moved every surface by one tool and a few thousand bytes. The **byte**
figures were re-measured and updated in all three live documents. The **tool counts** were not:

| Location | Said | Should have said |
|---|---|---|
| `AGENTS.md` | 41 / 42,901 · 119 / 106,147 · 544 / 423,305 | 42 / 44,406 · 120 / 107,652 · 545 / 424,810 |
| `tool-catalog.mjs` table | 544 / 119 / 41 tools, correct bytes | 545 / 120 / 42 |
| `README.md` | "545 tools" and "all 544" three sentences apart | 545 both times |
| `tool-catalog.mjs` round trip | "42,415 bytes ... 9.5x cheaper" | 46,184 bytes, 9.2x |

The last one needs no measurement to refute, only arithmetic: 42,415 is **smaller than the index
alone**, which the same header had just been updated to say is 44,406. A figure for "the index plus
one schema" cannot be less than the index.

`check:versions` did not catch any of it. It discovers and checks OPERATION counts across 37
locations and has never covered SURFACE counts — so a partial update reported itself as complete.
That is v3.7.0's lesson arriving for a different claim: *a check that covers some occurrences of a
claim reads as covering the claim.*

`tests/mcp/tool-surface-figures.test.mjs` closes the cheap half. It asserts the live documents agree
with the canonical table in `tool-catalog.mjs`, and that the round-trip figure exceeds the index it
contains. It was verified by reintroducing both real defects: the 545/544 drift fails the README
assertion, and the impossible 42,415 fails with `expected 42415 to be greater than 44406`.

**What it does not do, stated because the distinction is the value of the check:** it cannot tell
you the numbers are *right*. Three documents can be consistently stale and it will pass. Only
`npm run measure:surfaces` establishes truth, by driving a real client and counting bytes. This test
is deliberately the cheap half — no server, milliseconds — so it runs in the ordinary suite and
stops the figures diverging between measurements.

## F-06 — A second review pass, and the description was advertising a finding the tool cannot make

Three more threads after the first round was fixed. All three correct, and the first is the one that
matters.

### The tool description promised the unreachable branch

`cert_chain`'s `description` — the string the **model** reads when deciding whether to call it —
said the tool reports:

> ... or an issuer whose name matches but whose signature does not.

That is precisely the branch established as unreachable earlier in this same release, and removed
from the implementation and the header comment. The description was not updated with them.

This is worse than the stale header comment fixed in the same PR, and the difference is worth being
exact about. A comment misleads whoever reads the file. A tool description misleads the **caller**:
it advertises a class of finding the tool cannot produce, so a model that needs exactly that
detection will select this tool and receive silence. The output would not be wrong — it simply would
not contain the thing the description promised.

Three of this release's corrections to `cert_chain` are now the same correction arriving in
different places: implementation, header comment, and model-visible description each carried the
withdrawn claim, and each was fixed separately because nothing tied them together. The lesson is not
"check the description" but that a claim removed from code has to be chased everywhere it was
repeated — the same shape as v3.7.0's operation-count sweep and this release's own surface figures.

### The note asserted a root when it knew only that an issuer was absent

`!rootIsSelfSigned` establishes that the issuer of the TOP certificate is not in the bundle. It does
not establish that the absent certificate is a root. For a bare leaf the missing certificate is the
**intermediate**, and the note said "the root is not in this bundle" in that case too.

Reworded to say what the condition supports — the issuer above the top certificate is absent, most
often the root, possibly a missing intermediate, and this tool cannot tell which from outside.
Distinguishing them is not possible from the bundle alone, so the honest output names both.

### A test comment that contradicted its own assertion

The comment read "a bundle missing its root AND missing its intermediate must not be rescued into
`self_consistent`" and the assertion below it expected `self_consistent` to be **true**. The comment
described the second half of the test while sitting above the first. Split into two commented
halves, and the second now also asserts the note is present alongside the problem — which is the
case that would actually regress if the two fields were ever folded back together.

## F-07 — `checkIssued` does not verify signatures, and this tool was built on the claim that it does

The most serious finding of the release, raised by a reviewer disputing a claim this project had
already published in four documents and stated confidently in four review replies.

### The claim, and the measurement that appeared to support it

`cert_chain`'s first draft reported "the issuer name matches but the signature does not" as a
link-level warning. That was **withdrawn as unreachable** on the strength of a real measurement:

```text
real.subject === imposter.subject      true
leaf.checkIssued(real)                 true
leaf.checkIssued(imposter)             FALSE
```

The measurement is genuine and reproducible. The inference drawn from it was wrong.

### What actually happened

`X509Certificate.checkIssued()` compares issuer/subject names, **authority and subject key
identifiers**, and key usage. It never checks the signature. Inspecting the fixtures shows exactly
why the imposter was rejected:

```text
leaf   AKID : D2:5D:C6:09:...:BC:96
inter  SKID : D2:5D:C6:09:...:BC:96      <- matches, so checkIssued accepts
imposter SKID: 33:1C:DC:CA:...:E5:E8     <- differs, so checkIssued rejects
```

A metadata mismatch, mistaken for cryptography. The imposter was built to test one property (same
subject, different key) and happened to differ in a second (key identifier), and the second is what
did the rejecting.

### The disproof

Mint a certificate with the real intermediate's subject **and** a `subjectKeyIdentifier` equal to
the leaf's `authorityKeyIdentifier`, over a different key:

```text
leaf.checkIssued(skidImposter)         true
leaf.verify(skidImposter.publicKey)    FALSE
```

Committed as `tests/mcp/fixtures/cert-skid-imposter.pem`. The branch is reachable, and it is the
substitution signature the tool exists to surface.

### The consequence, which is worse than the wrong sentence

Edge selection took the **first** `checkIssued` match and stopped:

```js
if (issued) { issuedBy.set(i, j); break; }
```

So a certificate of that shape captures the edge, and the real issuer — present in the same bundle —
is never considered. The tool then reports a **broken chain for a bundle that is actually fine**,
which is the failure mode most likely to be acted on: a user seeing "signature does not verify"
about their own good chain.

Fixed by evaluating every candidate, preferring one whose signature verifies, and keeping a
metadata-only match only as a fallback so a substitution is still *reported* rather than silently
becoming an orphan. Verified by reverting the selection to first-match, at which point the new test
fails and the other sixteen still pass — the defect was invisible to every test written before it.

Two further checks, from the same review: an issuer must carry `basicConstraints CA:TRUE`, and a
self-signed top must verify against its own key.

### The transferable lesson

**A single negative result was taken as proof of a mechanism.** The observation ruled out one way of
failing and was read as establishing how the function works. Everything downstream inherited it: the
implementation, the header comment, the model-visible tool description, the release notes, the
CHANGELOG, the wiki, the ROADMAP row — and four confident replies to a reviewer on this very PR.

Worth stating plainly: the earlier rounds of review on this PR *improved the wrong design*. Threads
were answered, verified, and resolved, and the answers were sincere and incorrect, because they were
checked against a claim rather than against the library. The correct check was three lines of
`node -e` and was not run until someone insisted.

That is also the argument for the ceremony rather than against it. Nothing in this release's own
process caught it. A reviewer contradicting a stated claim did.
