## F-01 — arm64 was blocked on hardware this repository already uses — **THE PLAN WAS WRONG**

The carried-forward list has said the same thing since v3.3.0, and v3.7.0 re-recorded it unchanged:

> **arm64 performance is still unmeasured.** The timings taken there came from QEMU on an amd64
> host and measure the emulator; real numbers need arm64 **hardware**.

That objection is obsolete, and has been for some time. `mcp-docker-build.yml` line 47:

```yaml
  build-arm64:
    runs-on: ubuntu-24.04-arm
```

GitHub-hosted arm64 runners, free for public repositories, **already in use in this repository** and
succeeding on every recent run. The hardware the note says is needed has been sitting in the CI
configuration of the same project.

The note was carried forward five times without being re-checked against the thing it claims is
missing. That is the failure mode the re-measurement ritual exists for, arriving from the other
direction than usual: normally a plan describes work that is already done, and here it describes a
blocker that is already gone.

There is even a comment three lines above that label explaining the runner-label security property
in detail — so the arm64 runner was not merely present, it had been reasoned about carefully. The
carried-forward note and the workflow have coexisted for releases without anyone connecting them,
which is what a list nobody re-measures does.

### Scope decision

**v3.8.0, a MINOR.** New measurement, a new registry tool and a design document; the arm64
benchmark reports and does not gate, following v3.5.0/v3.6.0's discipline of measuring a noise floor
before setting a threshold. No runtime behaviour changes for existing users. v4.0.0 stays
unscheduled — no MCP specification revision after 2026-07-28.

## F-03 — Two wrong numbers, both found in the output of gates run for something else

Neither was on the plan, and neither was found by looking. Both appeared in output produced while
verifying the release, which is the case for reading what a gate prints rather than only its exit
code.

### `describeSurface` reported tokens, and the wrong tokens

`npm run measure:surfaces` was re-run to confirm the release notes' surface figures. It printed the
server's own startup line alongside its measurement:

```text
tool surface: all (504/504 operations; ~86k tokens per tools/list)
  all         545     424810      415       106ms
```

Two defects in one line, visible only because the true measurement sat directly beneath the claim:

1. **It is a token figure**, in a repository whose own AGENTS.md row says *"Bytes, not tokens: no
   tokenizer has ever been in this repo and every historical `~N tokens` figure was bytes/4."* This
   line was one of those figures and had never been converted.
2. **It had drifted by a fifth even under its own convention.** 424,810 / 4 is ~106k, not 86k. The
   number was presumably right when the index shipped; v3.3.0's twelve registry tools moved it and
   nothing re-measured a string that nobody thought of as a measurement.

It is operator-visible — it is logged at startup to answer "why can the model not see this tool" —
so a wrong figure there is advice, not decoration. Now `~415 KB`, with the history in a comment so
the next reader does not re-derive it.

### The coverage row had lines and statements transposed

`npm run test:coverage` printed:

```text
Statements   : 95.54%    Branches : 89.52%    Functions : 96.53%    Lines : 96.60%
```

`AGENTS.md` said *"95.7% lines / 89.6% branches / 96.7% functions / 96.6% statements"* — the same
four numbers with **lines and statements swapped**. Confirmed as a transposition rather than a real
change by `vitest.config.mjs`, which records v2.7.0's actuals as `statements 95.78 ... lines 96.63`:
the same relationship, so the row has been wrong since it was written.

The sting is where it sat. `vitest.config.mjs` carries a paragraph about exactly this confusion:

> NOTE the order. Vitest takes these as named keys; the docs quote them in the conventional
> statements/branches/functions/lines order [...] They are not swapped -- a reviewer read them as
> swapped once, which is why this note exists.

The warning was written about the *threshold* tuple and never applied to the *actuals* quoted two
files away. The figures are now given in the order vitest prints them, and the threshold tuple beside
them is explicitly labelled with its different order rather than left to be inferred — because the
two orders sitting unlabelled next to each other is what made this survivable for six releases.

## F-04 — The benchmark workflow did not run on changes to the benchmark workflow

The arm64 job was written, committed, pushed, and opened as a pull request. The PR had **no
benchmark check on it at all**.

`performance-benchmarks.yml` filters its triggers by path:

```yaml
    paths:
      - 'src/node/mcp-server.mjs'
      - 'src/node/index.mjs'
      - 'src/core/**'
      - 'benchmarks/**'
```

Every entry names code the benchmarks *measure*. None names the workflow that measures it. So an
edit to this file does not run this file — and the one class of change whose correctness this
workflow is the only available judge of is precisely the class it never executed on.

The consequence for this release, stated plainly: **a new CI job would have merged having never run
once**, while the release notes described its behaviour in the present tense. That is the same
defect this project has now written about repeatedly under other names — a claim published without
the measurement that would support it — arriving this time in the shape of a job that had never
executed.

It was not found by review. It was found by looking for the benchmark result on the pull request
and there not being one. The filter is a sensible optimisation and the omission is easy to make;
what makes it costly is that its failure mode is **silence**, and a missing check reads exactly like
a check that passed unless someone counts.

### Fix

The workflow's own path is added to both filters. The PR then triggers it, which is how the arm64
job gets executed before it is merged rather than after.

### What this does not fix

The filter still omits `src/node/lib/**` and `src/node/tools/**`, deliberately. A benchmark run
costs two full dependency installs and several minutes on two architectures, and v3.4.0's study
established that this runner pool is heterogeneous enough that extra runs on unrelated changes buy
noise rather than signal. The rule this finding establishes is narrower and it is the one that was
actually violated: **a gate must trigger on changes to itself.**
