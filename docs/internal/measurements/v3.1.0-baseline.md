# v3.1.0 measurement baseline

Captured 2026-09-04, against the released v3.1.0, **before** any v3.2.0 change. Method is recorded
with every number, because a number without its method cannot be reproduced or challenged.

This exists because v3.2.0 Track B makes the benchmarks able to fail, and a gate needs something to
gate against. It also found four documented claims that are wrong.

---

## Machine and method

One developer machine, otherwise idle. Node v26.8.1. Every figure is from execution, not from a
prior document. CI variance is **not** characterised here — see the tolerance note.

## Operation throughput

`npm run benchmark` — now also `--json`. Committed as `benchmarks/baseline.json`: the median of
four consecutive runs, with the first run of a cold process discarded.

| | |
|---|---|
| Tasks | 30 |
| Worst per-task spread across four runs | **9.8%** |
| Median per-task spread | **4.3%** |
| Gate tolerance | **25%** on median throughput, ≈2.5x the worst observed spread |

**The first attempt at this study was wrong by an order of magnitude**, and how it was wrong is the
useful part. It reported per-task spreads up to **84%** and would have justified a tolerance so
wide the gate could never fire. Two causes:

1. **A task-name collision.** `SHA2` is registered twice — once for 256, once for 512 — and both
   emitted tasks called `SHA2 (1KB)`. Printed side by side that reads as a repeat; consumed by
   anything keyed on the name it silently conflates two operations. The 84% "variance" was
   SHA-256 and SHA-512 taking turns in the same slot. Fixed: the tasks are now `SHA2-256` and
   `SHA2-512`.
2. **JIT warm-up on the first bench of a cold process.** `To Base64 (1KB)` measured 7,482 ops/s in
   the first run of a fresh process and 11,445–12,188 across later runs. It is the first benchmark
   registered, so it absorbs the warm-up. The baseline generator now discards run one.

Both were invisible in the printed tables and only appeared when the numbers were collected and
compared, which is the argument for collecting them.

## Cold start

Time from process spawn to the first `tools/list` result over stdio, through a real client, five
runs: **385, 395, 395, 395, 400 ms — median 395 ms.**

Worth stating plainly because v2.6.0's release notes quote **~185 ms**, and that figure measured
something narrower (server readiness, not a completed round trip through a client). Both are honest
measurements of different things; only one of them is what a client waits for. The 395 ms figure is
the one to regress against.

## Four documented claims that are wrong

Found by measuring rather than reading. Each is a live document, not a historical release note.

### 1. The image is not shell-free

`README.md` and `docs/wiki/Installation.md` both say the image contains **no shell**, and README
makes it a security argument — *"the attack surface is the point rather than the size — no shell,
no package manager"*.

```text
$ docker run --rm --entrypoint /bin/sh ghcr.io/doublegate/cyberchef-mcp_v3:3.1.0 -c '...'
sh:       /usr/bin/sh
ash:      /usr/bin/ash
busybox:  /usr/bin/busybox     BusyBox v1.38.0
npm:      /usr/bin/npm
node:     /usr/bin/node
apk:      absent
wget:     absent
curl:     absent
```

The runtime base is `cgr.dev/chainguard/node:latest`, a Wolfi image with BusyBox. The
"no package manager" half is true — `apk` is absent. The "no shell" half is false, and `npm` is
present too.

This is the most serious finding here, because it is a **security claim** a reader may rely on when
deciding what the blast radius of a compromise is.

### 2. Image size on disk

README says **726 MB on disk**. Measured: **453 MB**, which matches what AGENTS.md has said since
v2.8.0. The README figure predates the `npm prune --omit=dev` work.

### 3. Release tarball size

README says **~196 MB** gzipped. The published v3.1.0 asset is **141 MB**.

### 4. Production package count

AGENTS.md says **432 packages**. Two counting methods against the published image give **402**
(`find -maxdepth 3 -name package.json`) and **384** (walking directories that contain a
`package.json`, following `@scope`). All three numbers are defensible measurements of slightly
different questions, which is the actual defect: the document quotes a number without its method.

## What this baseline does not cover

- **CI variance.** Every figure here is one machine. The 25% tolerance is 2.5x the *local* worst
  case and is a first estimate, not a characterisation. Revisit once CI has produced enough runs.
- **Memory and allocation.** Nothing here profiles heap or GC, and v2.8.0's memory target was
  retired without a replacement measurement.
- **arm64.** All figures are amd64. The published image is multi-arch and the arm64 leg has never
  been benchmarked.
