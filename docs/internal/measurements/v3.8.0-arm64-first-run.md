# arm64, measured on hardware — the first run

**Captured 2026-09-04**, on PR #122, by the `benchmark-arm64` job added in v3.8.0. This is the
measurement the carried-forward list asked for from v3.3.0 to v3.7.0 while recording its blocker as
"needs arm64 **hardware**".

## The machine

```text
arch:   aarch64
kernel: 6.17.0-1022-azure
cpus:   4
model:  implementer 0x41 part 0xd49 (no model name field)
memory: 15.6 GB
node:   v26.8.1
```

Recorded because a benchmark whose machine is unrecorded is a number nobody can reuse — this project
has a baseline in its history that claimed the wrong machine. Node **v26.8.1** is the version the
published image ships, so this measures the runtime users actually get rather than the declared
floor.

`model:` came back **empty** on the very first run and is fixed in the same release. arm64
`/proc/cpuinfo` carries no `model name` field — that is an x86 convention — and the step's
`|| echo unknown` fallback could not fire, because `grep` matching nothing still leaves `xargs`
exiting 0. An empty field is worse than "unknown": it reads as a machine with no model rather than
as a question the step failed to answer. It now falls back to the implementer/part pair, which is
the closest thing arm64 offers to an identity, and the line above is the **verified** output of the
fixed step on a re-run rather than a description of what it should produce. `0x41` is ARM Ltd; the
part number is recorded raw rather than decoded to a marketing name, because a lookup table in a
CI step is one more thing that can go stale.

## What this is not

**It is not a comparison against amd64.** Those are different machines, and the entire v3.4.0–v3.6.0
line of work in this project was about not drawing conclusions from cross-host comparisons. The
amd64 job in the same workflow run measured a different host; subtracting one from the other would
reproduce exactly the mistake that took three releases to stop making.

**It is not a gate, and must not become one from this file.** One run establishes no noise floor. The
v3.6.0 gate required two separate studies before it was allowed to fail a build — a worst-case noise
floor over four runs on unchanged code, and a detection curve from a deliberately tunable slowdown —
and this project has set three thresholds from a first plausible measurement and had to move two of
them within days. This is run one of the accumulation that would have to precede any arm64
threshold.

**It is not a claim about arm64 being slower or faster.** The `Gzip (100KB)` row reads 2 ops/s, which
looks alarming and is the same figure shape the amd64 benchmarks produce for that task; nothing here
licenses a conclusion about it without the amd64 number from the same class of host, which does not
exist.

## What would make it a gate

The same thing that made the amd64 comparison one: repeated runs on unchanged code to establish the
spread, then a detection curve showing what size of real regression the threshold actually catches.
Until both exist, the job reports into the PR comment and the numbers accumulate.
