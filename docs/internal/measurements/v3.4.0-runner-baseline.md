# The runner-captured benchmark baseline, and the tolerance it supports

**Captured 2026-09-04. Supersedes the tolerance study in
[`v3.1.0-baseline.md`](v3.1.0-baseline.md), which measured a developer machine.**

This is the measurement that ends a three-release argument about one number. The regression
tolerance has been 25%, then 50%, and is now **20%** — and each move happened because the
measurement underneath it changed, not because the number felt wrong.

## What was wrong with every earlier baseline

Through v3.3.0 the committed baseline was captured on a developer machine while the gate ran on
GitHub's shared runners. The consequence was measured, not assumed:

```text
committed (developer machine) vs runner median, 30 tasks
  worst slower   -22.7%   Regular expression (100KB)
  worst faster   +43.1%   To Hex (100KB)
  median          -9.6%
```

The runner is faster than the baseline machine on most tasks by a machine-class margin. That has a
consequence worth stating rather than discovering later: **a regression smaller than the
cross-machine offset was not caught on CI**. If CI runs ~30% faster than the baseline machine, code
that got 25% slower still measures faster than baseline and passes.

It also produced two false failures in three CI runs — `Entropy (100KB)` at -25.3%, then
`Frequency distribution (100KB)` at -25.5%, a different task each time with nothing in the diff
touching either — which is what forced the tolerance out to 50% as a stopgap. Two cries of wolf in
three runs is how a gate gets disabled, and a disabled gate is what this whole line of work
replaced.

## The captures

`.github/workflows/benchmark-baseline.yml` ran for the first time on 2026-09-04, three times,
producing three independent captures on three runner instances. Each capture is itself the median
of four consecutive runs with the cold run discarded.

```text
run 33866915030   11:13 UTC
run 33868212825   11:29 UTC
run 33868225945   11:35 UTC     <- committed as benchmarks/baseline.json
```

All three carry all 30 tasks; the union and the intersection are both 30, so nothing is missing
and `benchmark:check`'s missing-task failure cannot fire spuriously against any of them.

> Every one of those runs reports **failure** in the Actions UI. That is the `open-pr` job hitting
> `GitHub Actions is not permitted to create or approve pull requests` — F-01 in the v3.4.0
> findings log. The `capture` job succeeded in all three and the artifacts are intact, which is why
> this study exists at all.

## Variance, measured two ways

```text
between the three captured medians (30 tasks)
  worst  6.7%    To Base64 (1KB)     10403.7 / 11081.0 / 11104.8
  median 1.5%
  mean   2.0%
  tasks over 25%: 0        tasks over 50%: 0

within one capture -- 4 runs on one instance, pooled over the three (n = 90)
  worst  15.2%
  median  3.6%
  mean    4.9%
  over 10%: 12 of 90       over 15%: 1 of 90
```

The first block is the one that decides the tolerance, because it is what the gate actually does:
compare a fresh median-of-four against a stored median-of-four, on a different instance. It already
contains both sources of error.

The second block is kept because it is the worse number and a threshold should clear the worse
number, not the convenient one.

## Simulating the gate

Each capture used as the baseline, the other two as the run under test — 6 orderings × 30 tasks =
180 comparisons:

```text
tolerance 10%    0 false failures
tolerance 15%    0 false failures
tolerance 20%    0 false failures
tolerance 25%    0 false failures
tolerance 50%    0 false failures
```

## Why 20% and not 10%

The data supports 10%. It is not chosen, for one reason: **three instances over a sixteen-minute
window is a narrow sample of a pool that is not homogeneous** and varies by day, by region, and by
whatever else is running on the host. Picking a threshold from the sample it was measured on is
precisely the mistake this project has made twice — most recently the `DIVISOR_MARGIN` study that
looked best at 1.10 over 72 cases and turned out worse than changing nothing over 400.

20% is:

- **3x** the worst observed cross-instance spread (6.7%);
- **above** the worst single-capture spread (15.2%), so even a genuinely noisy instance clears it;
- **2.5x tighter** than the 50% stopgap it replaces.

That last figure is the point of the exercise. The gate goes from catching factor-level regressions
to catching a one-fifth regression, which is the range real performance work actually moves.

## What still is not measured

- **arm64.** The published image is multi-arch, and no benchmark has ever run on arm64 hardware.
  The v3.3.0 timings came from QEMU on an amd64 host and measure the emulator. Unchanged here.
- **Longer-term runner drift.** Three captures sixteen minutes apart say nothing about what the
  pool does across weeks. `benchmark-baseline.yml` runs monthly; after a few cycles there will be
  enough to say whether 20% is conservative or about right, and the number should be revisited
  then rather than on the next release for its own sake.

## Reproducing this

```bash
gh run download <run-id> -n benchmark-baseline -D <dir>     # per capture
```

Then compare `tasks[*].throughputMedian` between captures for the cross-instance spread, and
`tasks[*].observedSpreadPct` within each for the single-instance spread. The gate simulation is the
same comparison the checker makes: `(other - base) / base * 100 < -tolerance`.
