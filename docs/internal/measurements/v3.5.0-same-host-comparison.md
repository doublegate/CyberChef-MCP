# Comparing on one host instead of estimating the host

**Measured 2026-09-04.** Supersedes the *approach* proposed in
[`v3.4.0-runner-baseline.md`](v3.4.0-runner-baseline.md), whose own data disproves it.

## The proposal this replaces, and why it fails

v3.4.0's findings log named the fix for a benchmark gate swamped by runner variance:

> **Normalise against a calibration task.** Measure one fixed, well-understood operation each run
> and scale the rest by it.

Tested against the four CI runs that motivated it, *before* building it. Normalising by a
calibration task is arithmetically the same as dividing out the run's median, so that is what is
computed:

```text
run           median delta vs baseline    residual spread AFTER normalising
33874729332          +101.4%                    -32.8% .. +33.7%
33875552658            -2.3%                     -7.8% ..  +4.0%
33876193748            +1.1%                    -39.7% .. +11.7%
33877632342            +2.2%                    -44.3% .. +26.5%
```

**The correction is worth about two percentage points.** Residuals of -39.7% and -44.3% against raw
deltas of -38.6% and -42.1%. The hosts do not differ by a scale factor; they differ in *profile* —
memory-bandwidth-bound tasks (`To Hex`, `Entropy`, `Frequency distribution` at 100KB) collapse while
CPU-bound `Regular expression` improves **on the same run**. No single constant corrects two
directions at once.

That table also carries a fact worth stating on its own: one run measured a median **+101.4%**
against the committed baseline. Across four runs the pool's median throughput varied by a factor of
two.

## What replaces it

Stop estimating the host. Remove it from the comparison: benchmark the **merge base** and the
**head** in one job on one runner, and compare those two. Whatever that host is, both sides got it.

## First measurements

Base = `8b486cb3` (v3.4.0), head = the v3.5.0 branch, which changes nothing in the benchmarked path.

**On a developer machine:**

```text
tasks compared: 30      median -0.2%      worst -5.5% (Gzip 100KB)      best +3.6%
```

**On a GitHub runner** — the environment that produced the -42% to +101% range above. Two runs of
PR #119, on different commits of the same branch:

```text
tasks compared: 30      median +0.5%      worst -2.2% (SHA2-256 10KB)     best +6.0%
tasks compared: 30      median +0.1%      worst -6.9% (AES Encrypt 100KB) best +9.9%
```

The second is noticeably wider than the first, which is exactly the point being made below about
single samples: had the threshold been set from the first, the second run would already be pressing
on it.

The second is the one that matters, because the runner pool is the problem. Per task, against the
same code:

```text
                        vs stored baseline (v3.4.0)     same host (this)
To Hex (100KB)                  -41.8%                       -2.0%
To Hex (10KB)                   -37.0%                       -1.4%
Frequency distribution (100KB)  -29.2%                       (within noise)
Regular expression (1KB)        +28.2%                       +6.0%
```

`To Hex (100KB)` is the clearest single case: a task that read as a **41.8% regression** against a
stored baseline, on code that does not touch it, reads as **-2.0%** when both sides are measured on
the same host. The signal is roughly **twenty times** tighter on the environment that broke the
previous approach.

## Why it does not gate yet

Because one measurement on one machine is exactly the evidence base that produced the 20% tolerance
in v3.4.0, and that number survived a few hours.

There are now **two** runner measurements, which is not a distribution either — and they already
disagree by enough to matter: worst-slower moved from -2.2% to -6.9% between two runs of the same
pull request. A threshold set from the first would have been under pressure by the second. That is
the whole argument in one observation.

Neither says anything yet about a busy runner, a different host class, or a pull request that
actually changes the benchmarked code — which is the case a threshold has to survive.

So `compare-runs.mjs` reports and does not fail; `check-regression.mjs` stays the blocking gate; and
the pull-request comment carries the same-host numbers above the fold so they accumulate where
someone will see them.

**The threshold gets set from those numbers, in a later release, and not before.** Writing that down
is the whole point: the previous three thresholds were each set from the first plausible
measurement, and two of them moved within days.

## What could still make it wrong

- **Order effects.** The base is benchmarked after the head, in the same process-free sequence but
  on a warmed machine (page cache, CPU governor, a busier container). If that biases the comparison
  it will show as a consistent sign in the accumulated data, which is the thing to watch for first.
- **The dependency guard.** `node_modules` is reused across the two checkouts, which is only valid
  while both commits install the same tree. The first version of that guard diffed `package.json`
  and `package-lock.json` wholesale and **skipped this very pull request**, because a release bumps
  the version and rewrites both files without changing a dependency — see F-04. It now compares the
  resolved tree, ignoring the lockfile's root entry. A genuine dependency change still gets no
  same-host number, correctly, since there is no honest one to give.
- **It only exists on pull requests.** A push to `master` has no merge base to compare against, so
  the stored-baseline gate remains the only check there.
