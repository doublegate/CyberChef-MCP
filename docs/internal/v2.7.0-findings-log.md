# v2.7.0 findings log

What was measured while building Phase 5's third release, including what the plan got wrong and
what I got wrong. Same purpose as the v2.2–v2.6 logs: the numbers and the reasoning, so a later
reader inherits the evidence rather than the conclusion.

---

## F-01 — Half the plan was already shipped, and the other half was mislabelled — **SCOPED**

**Found:** reading the plan against the code before writing anything, which is now the standing
habit after v2.5.0's and v2.6.0's F-01 each did the same thing.

`docs/planning/future-releases/release-v2.7.0.md` lists structured logging with Pino as item 3.
Pino has been the logger since v1.5.0 — `src/node/logger.mjs` imports it on line 10. Nothing to do.

The plan also describes `TelemetryCollector` as the metrics layer to build on. It is not a metrics
layer: it is a **10,000-entry ring buffer of individual executions**, opt-in and off by default.
Every aggregate the plan assumed existed had to be either derived at scrape time or built. That
distinction turned out to matter enormously — see F-04 and F-05.

**Scoped to:** Prometheus metrics, OpenTelemetry tracing, log correlation, and the operator-facing
assets (dashboard, alerts, deployment wiring) that make any of it usable.

---

## F-02 — The SDK costs more than the release before it saved — **REJECTED (plan item)**

**Found:** measuring before installing, prompted by v2.6.0 having just spent an entire release on
startup cost.

The plan asks for `@opentelemetry/sdk-node` integrated directly, plus exporters for "3+ backends
(Jaeger, Datadog, New Relic)". Measured on a clean tree:

```text
@opentelemetry/sdk-node + OTLP + Prometheus exporters   71 packages   50 MB   +100 ms startup
@opentelemetry/api alone                                 1 package   2.6 MB    +9 ms startup
```

v2.6.0 took cold start from ~1300 ms to ~185 ms. **Bundling the SDK hands back more than half of
that on every launch** — and nearly every launch of this server is an editor starting a subprocess
on stdio, where there is no collector and never will be.

The counter-argument would be that instrumentation you cannot switch off is useless. So that was
measured too:

```text
100,000 span + metric cycles, no SDK registered:   8 ms total   (0.08 microseconds each)
tracer.startSpan(...).isRecording():               false
```

The API is a genuine no-op. So the server depends on `@opentelemetry/api` and nothing else, creates
the spans and records the histogram, and the **operator supplies the SDK**:

```bash
node --import ./otel-bootstrap.mjs src/node/mcp-server.mjs
```

Measured after the change: cold start 147–164 ms across 6 runs. No regression.

The plan's "3+ backends" is also beaten by not implementing it. Because the operator picks the
exporter, **every OTLP backend works**, not three.

## F-03 — Recording only in the catch block — **MY BUG**

**Found:** writing the test that asserts a duration is recorded on success.

The first draft of `withServerSpan` called `recordDuration` inside its `catch` and nowhere else.
The success path ended the span and recorded nothing.

The consequence is worse than "missing data": the duration histogram would have collected **error
samples exclusively**, and there is nothing in a latency graph to reveal that that is what it
shows. A p95 of 40 ms would have been the p95 of the failures.

Moved to `finally`, recorded once on every path with `errorType` set or not. Pinned by two tests,
mutation-verified.

## F-04 — A failed tool call does not throw — **MY BUG**

**Found:** reading `errors.mjs` while wiring the span, not from a failing test.

MCP returns tool failures as an ordinary result with `isError: true`. `handleCallTool` catches
internally and *returns* `error.toMCPError()` for rate limits, quota, authorisation and every
meta-tool branch. A span that only watches for exceptions therefore reports **every failed
operation as a success** — which is exactly the case an operator is looking for.

Fixed by inspecting the returned result. The error code is recovered with a regex bounded to a bare
uppercase identifier (`^Error \[([A-Z][A-Z0-9_]*)\]`), which is the point of the bound: whatever an
operation puts in an error string, nothing but a member of the fixed code enum can reach a
telemetry backend. Verified with a deliberately hostile message containing a path and a password —
it yields `tool_error`, not the message.

## F-05 — The per-tool counters were not counters — **MY BUG, twice**

**Found:** designing the Grafana dashboard, which forced the question "is `rate()` valid on this?"

The first `/metrics` implementation derived per-tool counts by grouping `TelemetryCollector`'s
buffer at scrape time. Two independent faults:

**It falls.** The buffer is a 10,000-entry ring that drops its oldest entries. A derived count
therefore *decreases* on rollover — and Prometheus reads a falling counter as a process restart,
bridging the drop with a reset adjustment. Every `rate()` over it would have invented traffic that
never happened.

**It is empty by default.** `record()` returns early unless `CYBERCHEF_TELEMETRY_ENABLED=true`,
which is off by default and privacy-first. So `/metrics` on a default deployment would have
reported **zero tool calls forever**, under any load. An operator reads that as an idle server or a
broken endpoint. A monitoring surface that reads empty under load is worse than none, because it is
believed.

Fixed by adding dedicated monotonic counters to `TelemetryCollector`, incremented **before** the
opt-in gate. What telemetry makes opt-in is the per-call record — duration, sizes, timestamp, one
row per execution. A count of how many times a tool ran carries none of that, and the quota tracker
already counts total operations unconditionally; this is the same number broken out by tool.

`clear()` deliberately does not reset them: it is reachable from an MCP tool, and a counter a
caller can zero is not a counter.

## F-06 — Any caller could mint unbounded Prometheus labels — **MY BUG (security)**

**Found:** driving real traffic through a running server, in the output of the very first scrape.

```text
cyberchef_mcp_tool_calls_total{tool="cyberchef_definitely_not_a_tool"} 1
```

The tool name reaching the counter is the name the **caller** asked for. An unknown one is still
dispatched — it enters the `cyberchef_` branch, acquires quota, fails to resolve, and is recorded
as a failure.

Unbounded, anyone able to call this server can create arbitrary Prometheus label sets by invoking
`cyberchef_<random>` in a loop. That grows a `Map` in the server, and — far worse — explodes
cardinality in the monitoring system, where each label set is a new time series persisting for the
whole retention period. It takes out monitoring for every other service sharing that Prometheus.

Fixed with a hard cap of 1024 distinct tool labels, overflowing into a single `__other__` series.
The real catalogue is ~500 tools, so every legitimate name fits with room to spare. Overflow is
**bucketed, not dropped**: a flood of unknown tool names is precisely what an operator wants to see.

Verified: 5,000 attack calls collapse to one series while real tools keep counting.

## F-07 — Three `# HELP` lines for one metric fails the whole scrape — **MY BUG**

**Found:** reading my own first sample output.

The lifecycle states were emitted as three separate families in a loop, repeating
`# HELP cyberchef_mcp_lifecycle_state` three times. Prometheus rejects a duplicated declaration and
**fails the entire scrape**, not just the offending family — so every other metric on the endpoint
would have silently disappeared with it.

One family, three samples. Pinned by a test that asserts every name declares HELP and TYPE exactly
once, mutation-verified against the original loop.

## F-08 — Log correlation needs a context manager, which the API does not provide

**Found:** a test failing that I expected to pass.

`traceFields()` reads `trace.getActiveSpan()`, and `withServerSpan` sets the active span with
`context.with()`. Against the bare API that does nothing: `@opentelemetry/api` ships a **no-op
context manager** which runs the callback and stores nothing, so `getActiveSpan()` returns
undefined and correlation silently produces no fields.

Not a defect — with no SDK there are no traces to correlate a log line *to*, and every real SDK
registers `AsyncLocalStorageContextManager`. But it means correlation is a property of the SDK
being present, not of this module alone. Documented in `otel.mjs`, and the test supplies an
`AsyncLocalStorage`-backed manager so the assertion means something.

The correlation itself is a **pino `mixin`**, so it applies to every log line rather than to the
three request helpers. Threading ids through call sites correlates only the lines someone
remembered to change, and the useful line during an incident is invariably one of the others.

## F-09 — Two of my own dashboard tests were wrong, not the code

**Found:** the tests failing.

`/metrics/` returned 200 where I asserted 404. `normalizeEndpointPath` strips trailing slashes for
every route, so `/metrics/` resolving is **consistent**, not lax — and tightening it for this one
path would make `/metrics` the only endpoint on the server where a trailing slash is fatal. The
test was changed to assert the tolerance deliberately.

The drain test called `drain({delayMs: 0})` and then scraped, racing its own shutdown. The drain
delay is precisely the window that keeps the server answering during a drain; testing it with the
window shut proves nothing. Set to 500 ms.

A third: the alert-drift test regex-matched `expr:` and captured YAML's `>-` block-scalar indicator
as part of the expression, reporting a drift that did not exist. **A false failure is the worst
kind of test.** Replaced with a real YAML parse.

## F-10 — Verifying the observability assets, rather than reviewing them

**Found:** deciding that a dashboard nobody has run is a JSON file with opinions in it.

Configuration rots differently from code: it never throws. A dashboard querying a renamed metric
shows an empty panel; an alert copied into a Helm template drifts the first time only one side is
edited. None of that is caught by running the server.

So all of it was executed rather than read:

```text
promtool check rules alerts.yaml                    9 rules, SUCCESS
promtool parse of all 38 distinct dashboard queries 38 rules, SUCCESS
live Prometheus scraping a live server              up, 20 metric families
all 38 queries executed against real data           30 returned data
                                                     6 empty (OTel, no SDK — expected)
                                                     2 empty (annotations — see below)
                                                     0 PromQL errors
drain triggered, annotation query re-run            1 series, 2 samples captured
server restarted, resets() annotation re-run        1 series, 4 detections
server stopped, alert state polled                  CyberChefMCPDown -> pending
helm lint + every optional render path              clean; guards fire correctly
```

The two initially-empty annotation queries were empty because nothing had drained or restarted
during the test. Both were then verified by actually draining and actually restarting.

Four assets tests were mutation-verified: drifting a chart threshold, drifting a `for` duration,
renaming a server metric, and overlapping two panels each fail.

## F-11 — Why the dashboard is schema v1

**Found:** researching Grafana 12's dynamic dashboards before choosing.

Grafana 12 ships a v2 dashboard schema with `TabsLayout`, `RowsLayout` and conditional rendering,
which would suit this dashboard well. It is **experimental**, Grafana's own guidance is not to use
it in production, and — decisively — migration is **one-way**: a dashboard converted to v2 cannot be
converted back.

Shipping an artefact users import into their own Grafana is not the place for a one-way experimental
migration. v1 (`schemaVersion: 39`) imports cleanly into Grafana 10, 11 and 12. Pinned by a test so
the choice is deliberate rather than incidental.

The advanced *visualisations* were adopted regardless, since they are v1 panel types: a state
timeline for the lifecycle, a bucket heatmap with exemplars for latency, a joined table with gauge
and colour-background cells, a horizontal bar chart, threshold-dashed overlays, and annotation
queries. Panel option keys were taken from Grafana's own `panelcfg.gen.ts` schemas rather than from
memory — which is how `options.footer` was caught as having been refactored out of the table panel.

## F-12 — No latency alert, and no per-tenant alert

Both absences are decisions, and both are pinned by tests so they read as decisions.

**Latency.** This server has no meaningful latency SLO. A base64 decode and a bcrypt comparison are
both "one operation"; any single threshold is useless for the fast ones or a permanent page for the
slow ones. That is also why the dashboard leads with a **heatmap** rather than percentile lines —
the distribution is genuinely multi-modal, and a p95 averages three populations into a number
describing none of them. Percentiles are the right thing to alert on; the distribution is the right
thing to diagnose from, so both are present and neither is an alert.

**Per-tenant.** Tenant identity is not in the metrics at all. `/metrics` is unauthenticated by
necessity — a scraper carries no bearer token — so a tenant label is tenant identity leaking into a
surface nobody access-controlled for it, made permanent by cardinality. Tenant *count* is exposed;
names are not. Per-tenant attribution comes from the audit log, which is access-controlled.

## F-13 — The cardinality cap was exhaustible — **REVIEW FINDING, my bug**

**Found:** CodeRabbit on PR #106, and it is a sharper version of F-06 than I had.

F-06 capped distinct tool labels at 1024 with overflow bucketed. That bounds the label count, but
it does not bound *who gets the slots*. An attacker calling `cyberchef_<random>` 1024 times before
real traffic arrives fills every slot, and **legitimate tools then collapse into `__other__`** —
the attack degrades exactly the metrics the cap was meant to protect.

The real fix is to resolve the name against the dispatch catalogue *before* it becomes a dimension.
`toolDimension()` in `mcp-server.mjs` checks all three kinds this server dispatches — registry
tools, meta-tools, operations — mirroring `annotationsForToolName`, because a dimension that
disagreed with the authorisation decision about what a name *is* would be its own bug. An unknown
name never occupies a slot.

The cap stays as defence in depth: `TelemetryCollector` is constructible on its own.

Verified live: 40 bogus tool calls produce exactly one `__other__` series while the real tool keeps
its own, and the mutation that reverts to a bare cap fails two tests.

## F-14 — The OpenTelemetry tool dimension had no bound at all — **REVIEW FINDING, my bug**

**Found:** CodeRabbit on PR #106.

F-06 bounded the Prometheus labels. It did not bound the **span**. `withServerSpan` took
`request.params.name` verbatim into the span name and into the duration histogram's attributes, so
the same caller-controlled cardinality attack landed on the tracing backend instead — where it is
arguably worse, because a span name is high-cardinality by construction and backends index it.

Fixing the Prometheus path and leaving the span path open is the characteristic shape of a partial
mitigation: the fix was applied where the bug was *observed* rather than where the untrusted value
*enters*. `toolDimension()` is now applied at the single boundary both consume.

## F-15 — `/metrics` sat in front of the DNS-rebinding check — **REVIEW FINDING, my bug (security)**

**Found:** CodeRabbit on PR #106.

I routed `/metrics` beside the health probes, which are deliberately ahead of `hostAllowed()`. For
the probes that is right: a kubelet addresses the pod by an IP the allowlist does not name, and the
probes disclose nothing but a status string.

A scrape is the opposite — equally unauthenticated, genuinely informative. So a DNS-rebound browser
request could read an internal server's traffic profile through an attacker-controlled `Host`
header: the exact attack the allowlist exists for, reached through the one route not behind it.

The lesson is about the *reason* rather than the position. I copied the probes' placement along with
their justification, without checking that the justification still held for a route that says a
great deal more.

**And the first test I wrote for it passed for the wrong reason.** `Host` is a forbidden header
name, so `fetch` silently drops the override and sends the real authority — the "attacker" host was
never presented, and the 403 came from `127.0.0.1:PORT` not being in the allowlist either. Rewritten
against `node:http`, which can set it.

## F-16 — Two more of my tests asserted nothing — **REVIEW FINDING**

**Found:** CodeRabbit on PR #106. Both are the failure class this project has been bitten by before.

**The rollover test.** It asserted `expect(buffer.length).toBeLessThanOrEqual(5)` to show the ring
had rolled over. Telemetry buffering is off by default, so the buffer was **empty** and the
assertion passed against 0 — proving that a rollover which never happened did not break anything.
Now re-imports the module with `CYBERCHEF_TELEMETRY_ENABLED=true` stubbed and asserts the buffer
holds exactly 5 of 50.

**The escaping test.** It read a body whose labels were all clean, so it never drove a reserved
character through `escapeLabel` at all. The comment claimed the property was "asserted on the
escaping function's effect"; the effect was never produced. Swapping the backslash and quote
replacements — which changes the output — left it green. Verified by making that swap.

Also from the same review: the renderer interpolated collector fields directly, so a partial
collector rendered `cyberchef_mcp_operations_total undefined` — and Prometheus rejects the **whole**
scrape on one bad line. Now coerced to `NaN`/`±Inf`, and the test parser enforces the numeric
grammar instead of `.+`, which is why it could not catch this before.

## F-17 — Alerts mixed every deployment together — **REVIEW FINDING**

**Found:** CodeRabbit on PR #106, then extended by a test I wrote in response to it.

Only `CyberChefMCPDown` was scoped to a job; the rest used bare `sum()`. One Prometheus commonly
scrapes staging beside production, or a canary beside a stable release — so a healthy production
masked a staging fleet with nothing serving, and a normal rollout in one deployment read as version
skew across all of them.

Every aggregate is now `by (job)`, which also puts the job in the alert labels so the page says
which deployment. I then wrote a test asserting *every* aggregate in the file is job-scoped, and
**it immediately caught one CodeRabbit had not named**: `CyberChefMCPCacheThrashing` joined
`on (instance)` across jobs. Fixed to `(job, instance)`.

Worth recording as method: acting on a review finding by pinning the *general* property, rather than
patching the specific lines cited, is what found the extra one.

## F-18 — The cardinality fix added CPU cost on the attack path — **REVIEW FINDING, round 2**

**Found:** CodeRabbit's second pass, on the fix from F-13.

`toolDimension()` resolved a name with `Object.keys(OperationConfig).some(k => sanitizeToolName(k) === name)`
— sanitizing all 504 keys on every call. Measured:

```text
20,000 unresolved lookups:  4455 ms   (223 microseconds each)
```

And it runs **twice** per `tools/call` (once for the span, once for the counters), beside a third
identical scan in the dispatch itself and a fourth in `annotationsForToolName`.

The worst case is what makes this more than a micro-optimisation: an **unknown** name scans the
whole catalogue before failing, so the defence against a cardinality attack introduced CPU
amplification on exactly the attack path it exists to blunt.

One module-level `Map` from sanitized name to `OperationConfig` key, shared by all four call sites.
`OperationConfig` is generated at startup and never mutated, so there is nothing for the index to go
stale against.

```text
200,000 unresolved lookups:  50.8 ms   (0.254 microseconds each)   ~880x
```

Confirmed by the 2,289 operation tests, since the dispatch lookup changed with it.

## F-19 — Test cleanup outside `finally` — **REVIEW FINDING, round 2**

**Found:** CodeRabbit's second pass, on the fix from F-16.

The rollover test stubs `CYBERCHEF_TELEMETRY_ENABLED` and resets the module graph, then restores
both at the end of the body. A failing assertion skips the restore, leaking an enabled flag and a
reset graph into every later test in the file — turning one honest failure into an order-dependent
run, which is much harder to diagnose than the failure that caused it.

Moved into `finally`. Verified by deliberately breaking the assertion: exactly one test fails, the
other 21 still pass.

Worth noting the shape: this is a bug in the *fix* for a test that was itself asserting nothing.
Test infrastructure earns the same care as the code it guards.
