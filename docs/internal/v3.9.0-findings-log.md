## F-02 — Issue #129 says a release is "available" that this repository already ships

[#129](https://github.com/doublegate/CyberChef-MCP/issues/129), opened by `upstream-monitor.yml` on
2026-09-06, is titled **"New CyberChef release v11.4.0 available"** and reports one new operation
(`ParsePGPKey.mjs`) and thirty modified ones.

Measured:

```text
package.json cyberchefUpstreamVersion   11.4.0
gchq/CyberChef latest release           v11.4.0  (published 2026-08-18)
```

This repository is **already on v11.4.0**. Diffing the operation set against the v11.4.0 tag:

```text
upstream v11.4.0: 505 .mjs      local: 506 .mjs
in local, not upstream:  index.mjs      (generated by grunt, gitignored)
in upstream, not local:  (none)
```

Every one of upstream's 505 operation files is present. The set is identical.

And `ParsePGPKey.mjs`, the "new operation", **is not in the v11.4.0 tag at all** --
`GET /repos/gchq/CyberChef/contents/src/core/operations/ParsePGPKey.mjs?ref=v11.4.0` returns 404.

### Why the workflow says otherwise

`upstream-monitor.yml` reads two different refs and prints them as one:

| Line | What it does | Ref |
|---|---|---|
| 40 | `git pull origin master` | **master** |
| 61 | `LATEST_TAG=$(git describe --tags --abbrev=0)` | **the newest tag** |
| 98, 108 | diffs operations against the clone's working tree | **master** |

So the headline is a tag name and the numbers underneath describe unreleased upstream master. The
issue is not wrong about there being a difference -- there is one, `ParsePGPKey` and thirty
modified files are real work on upstream `master`. It is wrong about what that difference *is*: it
presents post-release drift as an unadopted release.

This is the failure mode this repository keeps finding in its own checks, and the same one v3.8.0's
F-04 found in the benchmark workflow: not a check that fails to run, but a check whose output means
something other than what it says. A maintainer reading #129 would start an upstream sync that has
nothing to sync.

**Fixed this release.** The comparison is pinned to the same ref the headline names, and the issue
body distinguishes "a new release exists" from "master has moved since the release you are on".

## F-03 — `magic` ranks a decoded plaintext below the container it came out of

Filed as [#130](https://github.com/doublegate/CyberChef-MCP/issues/130) before this release opened,
from a live exercise of the 3.8.0 image.

A three-layer payload (`Gzip` -> `To Base64` -> `To Hex`) returns four candidates, with the fully
decoded plaintext at **rank 3**, beneath two partial decodes -- one of which is raw gzip bytes.

Recomputing every term of the comparator at `src/core/lib/Magic.mjs:328`:

| Recipe | lang score | after clamps | +len | +entropy | final |
|---|---|---|---|---|---|
| `From Hex -> From Base64` | 421,308.72 | **500** (gzip clamp) | 2 | 6.62 | **508.62** |
| `From Hex` | 4,853.05 | 4,753.05 | 1 | 5.79 | 4,759.84 |
| `From Hex -> From Base64 -> Gunzip` | 5,575.92 | 5,475.92 | 3 | 4.52 | **5,483.44** |
| (none) | 6,924.19 | 6,824.19 | 0 | 3.58 | 6,827.77 |

Two effects, and the first reading of this bug got the cause wrong:

1. **The file-type clamp decides rank 1.** `if (a.fileType && aScore > 500) aScore = 500` collapses
   421,308 to 500. Any candidate matching a file signature lands near 508 while a text candidate
   keeps a chi-squared score in the thousands, so a detected *intermediate container* outranks the
   decoded content of that container -- systematically, and worse the deeper the nesting.
2. **The chi-squared scorer rated base64 above English**, 4,853 against 5,576, deciding rank 2
   versus rank 3. That is the estimator weakness already documented at `src/node/lib/magic.mjs:126`
   surfacing in the ordering rather than in a label.

**Recipe length is not the cause.** It contributes 3 against 1 -- two points of a 723-point gap --
and entropy actually favours the correct answer. The `aScore += a.recipe.length` line is a
plausible-looking line that fits the symptom, and reading the mechanism off it without doing the
arithmetic is how the wrong cause got asserted. The table above is what settled it.

`src/core/lib/Magic.mjs` is upstream verbatim; no `patches/fork/*.patch` touches it. Fixed in the
MCP layer, where this project owns the code.

## F-08 — vitest 5 landed inside this project's own cooldown

`vitest` and `@vitest/coverage-v8` went to **5.0.0 on 2026-09-03**, seven days ago. There is no
Dependabot PR for it because `.github/dependabot.yml` sets `semver-major-days: 14`, with a written
rationale: *"nothing here is urgent enough to justify being the first to find out."*

Taking it at day 7 overrides the project's own stated policy, so it needs a better reason than
"latest". The reason is that the cooldown exists to avoid being the first to find out, and running
the full suite **is** finding out -- a devDependency test runner is exactly the case where the
evidence is cheap and immediate, unlike the cryptography and parser libraries the policy was
written for.

Read against this repository's configuration, the vitest 5 breaking changes are mostly inert:

| Change | Effect here |
|---|---|
| `coverage.thresholds.perFile` no longer inherits to globs | **None.** `perFile` is set nowhere, deliberately, and `vitest.config.mjs` carries three paragraphs explaining why. |
| `coverage.include`/`exclude` match relative paths, no "contains" matching | The real risk. Every entry is already relative or a `**` glob, but coverage numbers decide a gate, so this is settled by running it. |
| `clearMocks` defaults to `true` | Risk. Settled by running it. |
| Unawaited async assertions now fail | Would surface a latent defect rather than create one. |
| Vite >= 6.4.0 required | Satisfied: 8.2.2 installed. |
| Node >= 22.12.0; engines `^22.12.0 \|\| ^24.0.0 \|\| >=26.0.0` | Satisfied at both CI ends, 24 and 26. Note it excludes Node 25, which this project does not test. |
| `test.sequential` removed | Not used anywhere in `tests/`. |

Decision: **attempt it and let the suite decide.** The outcome is recorded in F-09 rather than
predicted here.

## F-10 — The upstream monitor could never report "up to date"

Found while fixing F-02, and larger than F-02.

The `Get current version` step read the wrong field:

```bash
CYBERCHEF_VERSION=$(node -p "require('./package.json').version")     # 3.8.0 -- this fork's semver
```

`package.json` carries **two** versions, and has since v2.2.0: `version` (this fork, 3.8.0) and
`cyberchefUpstreamVersion` (the upstream base, 11.4.0). The comparison step then does:

```bash
CURRENT="v${CYBERCHEF_VERSION}"        # "v3.8.0"
if [ "$LATEST" != "$CURRENT" ]; then   # "v11.4.0" != "v3.8.0"  -- ALWAYS true
```

So `new_version=true` on **every run, forever**. The monitor is not flaky and it is not
occasionally wrong; it is structurally incapable of reporting the "Already up-to-date" branch its
own code contains. The dead branch is right there in the file and has never once executed.

The same field also generated the issue's "next steps" link:

```text
https://github.com/gchq/CyberChef/compare/v3.8.0...v11.4.0
```

`v3.8.0` is not a ref in `gchq/CyberChef`. The link has been broken in every issue this workflow has
ever opened.

Both fixed. Together with F-02 this is one workflow making three different claims from two wrong
sources -- and the reason it survived is that nobody re-reads a bot's output closely when the
headline looks plausible.

## F-11 — The first version of the #130 fix regressed a case that was already correct

The re-ranking rule (F-03) was first written as: promote any candidate whose recipe extends
another's and which produced UTF-8 text. That is the broad reading of the issue's own suggestion,
and it is wrong.

Measured on the single-byte-XOR payload, which ranked **correctly** before the change:

```text
before   rank 1  From Base64 -> XOR                    "The key is a single byte and the analyst..."
after    rank 1  From Base64 -> XOR -> From Hexdump    "X"
         rank 2  From Base64 -> XOR                    "The key is a single byte and the analyst..."
```

`From Hexdump` extends the correct recipe and returns a single character at entropy 0. It is
incidental UTF-8, not a decoding, and the broad rule promoted it over the answer. A fix for a
ranking bug had introduced a ranking bug, in the opposite direction.

The rule is now anchored on the **container**: promotion happens only past a candidate that
produced a detected file type. That is what makes it mean "you decoded the container" rather than
"you ran one more operation".

Requiring a positive language probability instead was considered and **checked rather than
assumed** -- it would also have been wrong, because the correct answer in the issue's own payload
scores no language at all (every `languageScores` probability is 0), so a language test would
suppress the exact promotion the fix exists to make.

Three regression tests pin all of it, including the order-preserving claim. Verified by disabling
the re-rank: the headline test fails, the two guard tests pass either way, which is what a guard
test should do.

## F-12 — v3.8.0 published surface figures that its own artefact contradicts

The surface figures moved this release -- 44,406 -> 44,493 for the index, and +87 uniformly across
all three surfaces. The obvious assumption is that v3.9.0 changed something. It did not.

A/B against the **published v3.8.0 image**, through a real MCP client, same method as
`npm run measure:surfaces`:

```text
ghcr.io/doublegate/cyberchef-mcp_v3:3.8.0   index: 42 tools, 44493 bytes
this working tree (v3.9.0)                   index: 42 tools, 44493 bytes
per-tool byte maps                           IDENTICAL
```

The shipped v3.8.0 artefact serves 44,493. Its release notes say *"Surfaces re-measured: 42 tools /
44,406 bytes"*. **The number was already wrong at the tag** -- measured during development, changed
before the tag, never re-measured. Which is, word for word, the failure the `AGENTS.md` row itself
warns about:

> Every figure here was 325 bytes low through v3.3.0 -- recorded during its development and never
> re-measured before the tag, **which is this row's own warning happening to this row**.

It happened to that row again, one release later.

### Why the gate did not catch it

`tests/mcp/tool-surface-figures.test.mjs` compares every document against the canonical table in
`tool-catalog.mjs`'s header. That establishes **agreement, not truth**. When the table itself is
stale, every document agrees with a stale number and all four tests pass -- which is precisely what
`registry-tool-docs.test.mjs` warns about in its own header, about this very file:

> `tool-surface-figures` can only establish that documents agree with each other -- three documents
> can be consistently stale and it passes.

The warning was written in v3.8.0. The thing it warned about was already true in v3.8.0.

**Fixed by measuring.** A fifth test spawns a real client against each of the three surfaces and
compares the live byte count to the recorded table, exactly. No tolerance: these are deterministic
serialisations of a fixed catalogue, and a tolerance would let this same drift accumulate under it.
Verified by reverting the table to 44,406 -- it fails with `table says 44406, server serves 44493
(+87)` and names the command that fixes it.

The published v3.8.0 figures are left as they are, in the CHANGELOG and that release's notes. They
record what was claimed at the time, and rewriting history to hide a wrong number is worse than the
wrong number.
