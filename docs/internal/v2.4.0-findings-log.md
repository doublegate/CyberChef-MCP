# v2.4.0 running findings log

Live record of defects, gaps and decisions found while building v2.4.0. Each entry states how it was
found, what is actually wrong, and the disposition.

Status key: **OPEN** - **FIXED** (landed in v2.4.0) - **DOCUMENTED** (a decision, not a defect) -
**WONTFIX** (with reason).

Earlier logs: [v2.3.0](v2.3.0-findings-log.md), [v2.2.0](v2.2.0-findings-log.md).

---

## F-01 - "Sandboxed execution" is not achievable as the roadmap words it - **DOCUMENTED**

**Found:** starting the v2.4.0 theme, by checking what a sandbox would actually have to be before
writing a loader.

**The roadmap line** is *"Plugin system, sandboxed execution, plugin registry"*, and
`docs/planning/ext-proj-int/` specifies a `ToolLoader` for "dynamic tool discovery and loading".

**`node:vm` cannot sandbox a plugin, and the reason is specific to this case.** Node's documentation
says it is not a security mechanism; what makes that decisive here is that the obvious
counter-argument -- *"we will only pass in a narrow API"* -- is exactly what fails:

```js
const ctx = vm.createContext({ bake: hostBake });        // the one capability a tool needs
vm.runInContext('bake.constructor("return process")()', ctx);
// -> the real process object: pid, cwd(), env
```

Measured on Node 26.8.1. A host function carries its own realm, and `Function.prototype.constructor`
reaches that realm's `Function`. **Every useful tool needs at least one capability** -- this
registry's entire purpose is tools that compose operations, which means handing them `bake` -- so
the narrow-API defence is unavailable by construction. A vm context with no capabilities sandboxes
code that can do nothing.

Worker threads do not close the gap: they bound **CPU**, not **authority**, and share the process's
filesystem and network. `worker-pool.mjs` is concurrency, not isolation, and reading it as isolation
would be a mistake.

**Disposition:** the registry ships; the loader does not. Tools are registered by explicit import
from a manifest in this repository -- first-party code at the same trust level as the rest of the
server. Recorded as
[ADR 0002](../adr/0002-tool-registry-is-not-a-plugin-loader.md), including the conditions under
which third-party plugins get reconsidered, so the decision is visible rather than implied by an
absent feature. The roadmap line is corrected rather than quietly dropped -- the rule the withdrawal
of DEP001/007/008 set in v2.0.0.

## F-02 - Chi-square is the obvious score for XOR key length, and it is wrong - **FIXED**

**Found:** prototyping the first registry tool before writing it as a tool.

**Actually wrong.** Scoring each candidate key length by the chi-square of its columns against a
uniform distribution is the natural choice and produces a tool that always answers **1**:

```text
key="K"    (1)  -> 1   OK
key="sec"  (3)  -> 1   MISS
key="hunter"(6) -> 1   MISS
key="correcthorse"(12) -> 1   MISS
key="0123456789abcdef"(16) -> 1   MISS
```

Chi-square grows with sample size, and a shorter candidate length produces longer columns, so the
score is dominated by column length rather than by structure. Index of coincidence -- the
probability that two bytes drawn from a column are equal -- is normalised by construction. Same five
inputs, five correct answers.

**Worth recording because the failure is silent**: the chi-square version returns a confident
number for every input, and the number is wrong in four cases out of five. Only testing against
known keys reveals it.

## F-03 - A threshold tuned on one sample looked perfect and was not - **FIXED**

**Found:** the first end-to-end run of the tool over MCP returned 24 for a 6-byte key.

Every multiple of the true key length scores about as well as the true length, so the rule is *the
smallest length within a band of the best score*. The band was set to 90% on one sample, where it
scored 21/21.

Across a wider matrix -- ten key lengths, three input sizes, three plaintext kinds -- five rules:

```text
smallest >= 80% of best      84/90     <- chosen
smallest divisor of leaders  82/90
smallest >= 90% of best      77/90
gcd of leaders >= 90%        77/90
gcd of the top five          42/90
```

**The first corpus was also wrong**, and finding that mattered more than the threshold. Two of the
three plaintexts were a single short line repeated, so the plaintext had a strong period of its own
and the method locked onto that instead of the key's -- scoring 60/90 and making every rule look
bad. With realistic multi-line samples the same rules score 77-84.

**Disposition:** 80%, with the measurement recorded in the source, and the residual limitation
stated in the tool's own description rather than left for a user to discover: least reliable on
short inputs and on plaintext with its own strong period, such as fixed-width log lines.

## F-04 - Two defects the tests found in the tool's output contract - **FIXED**

1. **The reported candidates could omit the answer.** `candidates` was the top five by score, while
   `key_length` is the smallest within the band -- frequently not in that five. A `key_length` that
   does not appear in the candidate list printed beside it is a contradiction the caller has to
   resolve. The chosen length is now always present and marked `chosen: true`.
2. **A guard for an impossible case.** A test asserting that an 8-byte input is rejected failed
   because the input succeeds: 8 bytes is four samples of a length-1 key, which qualifies, so the
   candidate list is never empty and the `chosen === null` branch is unreachable. Rather than keep
   code claiming to handle a situation that cannot arise -- coverable only by faking it -- the guard
   is replaced by the invariant, stated, with the condition under which it would need revisiting.

## F-05 - A new source directory was invisible to coverage, again - **FIXED**

**Found:** checking why the branch figure barely moved after adding 300 lines of new code.

`src/node/tools/**` was not in `vitest.config.mjs`'s coverage `include` list, so the registry and
its first tool were measured at nothing while appearing in no report. **This is exactly how
`src/node/worker.mjs` went unmeasured for six releases** -- our code, on a real path, absent from
the list.

Added, and it measures **98.31 / 92.95 / 100 / 100**.

The general lesson is that the include list is an allowlist, so *adding a directory is a step in
adding a directory*. Worth a check in the release gate rather than a note here.

## F-06 - A relocation that stopped the server booting - **FIXED**

Lifting the meta-tool array to module scope as `META_TOOLS` -- needed so the registry can reserve
those names and refuse to shadow `cyberchef_bake` -- put `buildRegistry()` above the `const
META_TOOLS` initialiser, inside its temporal dead zone:

```text
ReferenceError: Cannot access 'META_TOOLS' before initialization
```

The server did not start at all. Caught immediately because the smoke test runs the real binary
rather than importing a module; a unit test that imported only the registry would have passed.

## F-07 - A known-answer test whose known answer was wrong - **FIXED**

**Found:** `hash_identify` failed to recognise a sha512crypt hash that I had written into the test
from memory.

The instinct is to widen the pattern. The pattern was right: sha512crypt's digest is exactly 86
characters, and the vector I had typed carried 84. Counting it took one line and settled which side
was wrong:

```text
digest len in my test vector: 84
```

Replaced with a hash generated on the spot -- `openssl passwd -6 -salt usesomesillystri password` --
and it matched immediately. Written down because the failure mode is not the typo, it is the
reflex: a red known-answer test invites you to change the code, and half the time the oracle is
what is broken. **Generate the vector, or cite where it came from. Never recall it.**

The `$6$rounds=N$` form is a separate branch of the same pattern and is now tested separately, with
a comment saying the digest there is spliced rather than real, since only the structure is under
test.

## F-08 - Two lint rules that make a snake_case output key unassignable - **WORKED AROUND**

`camelcase: {properties: "always"}` and `dot-notation: "error"` are both on. Together they leave no
way to *assign* a snake_case property after an object exists:

- `result.plaintext_int = x` -> camelcase error
- `result["plaintext_int"] = x` -> dot-notation error

Quoted keys inside an object literal are exempt from both, so the tool builds its result in literals
and uses `Object.assign(result, { "plaintext_int": ... })` for the conditional fields. That is why
those blocks are shaped the way they are; it is not stylistic preference, and rewriting them into
plain assignments will fail the lint gate.

Worth knowing before writing the next tool, because the output keys are snake_case by convention --
they are read by a model, and match the argument names.

## F-09 - Every numeric argument was bounded and every string one was not - **FIXED**

**Found:** by the Antigravity reviewer on PR #100, and it was right.

Each of the four tools bounds its numeric arguments carefully -- `fermat_iterations` at 10,000,000,
`max_key_length` at 256, `length` at 1 MB, `subsequence_length` at 8. Not one string argument had a
`.max()`. The schemas *look* careful, which is what made the gap easy to miss: the obvious fields
are all capped.

Measuring it settled which bound actually matters, and it was not the one already there:

```text
fermat, 1,000,000 iterations, 65-bit modulus            582 ms
fermat,       100 iterations, 262,144-bit modulus    72,125 ms
```

**Cost is driven by the size of the numbers, not by the iteration count.** So `fermat_iterations`,
the argument that looks like the safety bound, bounds nothing: 100 iterations against a 64 KB hex
string blocked the event loop for 72 seconds -- from one call, on a server whose every operation
tool is held to a 30-second timeout.

`xor_key_length` had the same shape with a gentler slope: the scan is O(input x max_key_length), so
128 KB costs 374 ms and 1 MB costs 3.2 s. Against the server's general 100 MB input ceiling that is
about five minutes.

`hash_identify` did **not**. The review suggested its `/^[0-9a-f]+$/i` fallback "could hang on
massive inputs"; it cannot. Every pattern is anchored and over a single character class, so there
is no backtracking to exploit, and 8 MB of junk costs 56 ms. It is bounded anyway, at 4 KB -- on the
grounds that no hash is 8 MB, not on the grounds that it is slow.

Three changes, in order of how much they matter:

1. **Bounds on every string argument**, each with a stated reason rather than a round number.
   `MAX_OPERAND_CHARS = 5000` admits a 16,384-bit key in hex or decimal; `xor_key_length` takes
   1 MB, measured at 3.2 s worst case.
2. **A bit-length guard**, because the character bound is only a proxy: 4,990 decimal digits is
   16,577 bits -- inside the character limit and outside the real one.
3. **The registry path now gets the same timeout as an operation**, with `maxRetries: 0`. Retrying
   a timed-out analysis repeats exactly the work that caused the timeout.

And a fourth that makes the third mean anything: **the Fermat loop now yields**. A synchronous loop
cannot be timed out -- `Promise.race` never gets a turn, so the timeout would resolve only after the
work it was meant to bound had finished. A bound that cannot be enforced is not a bound.

Verified end-to-end through a real client: **72,125 ms → 2 ms**, returned as a structured
`INVALID_INPUT`, with a genuine RSA-4096 modulus still accepted.

Two general lessons. **A schema is not "validated" because its numbers have limits** -- the
unbounded field is the one nobody looked at. And **bound the quantity that drives cost, not the
one that looks like a limit**; here they were different by four orders of magnitude.

## F-10 - A dead branch kept for a case that would corrupt output - **FIXED**

The same review noted that `typeof result === "string" ? result : JSON.stringify(result)` on the
registry dispatch path is dead, since all four tools return objects.

It is worse than dead. `JSON.stringify` of a bare string returns it *wrapped in quotes*, so the
branch was not a convenience but a guard against a silent corruption -- and one no test could reach.
Removed, with the invariant stated: a registry tool returns an object, and a tool that wants to
return text returns a field containing it. Same reasoning as F-04.

## F-11 - A user-controlled exponent that kills the process, not just slows it - **FIXED**

**Found:** by Copilot on PR #100.

`integerRoot(c, e)` computes `hi ** k`. `k` is the public exponent, which the caller supplies, and
raising to a huge power is not slow -- it is fatal:

```text
RangeError: Maximum BigInt size exceeded
    at integerRoot (rsa-attack.mjs:131)
```

Reproduced with a 400-digit exponent, comfortably inside the 5,000-character bound added in F-09.
The caller got an internal V8 error rather than an answer, and the process burned memory building
enormous BigInts on the way there. **F-09's bounds did not cover this**, because the dangerous
quantity is not the operand's size but the fact that it is used as an *exponent*.

The obvious fix -- bound `e` globally -- is wrong, and that is the interesting part. A **large** `e`
is precisely the signature Wiener's attack looks for: a small private exponent implies a large
public one, so capping `e` would disable the attack most likely to succeed. The guard belongs on
the small-e attack alone, which is meaningful only for e = 3 and occasionally 5 or 17 anyway.

Skipped rather than silently omitted: "the small-e attack found nothing" and "the small-e attack was
never run" are different answers, and only the second is true, so `attempted` now says which.

## F-12 - Two comments that described code that was never written - **FIXED**

Also from PR #100, and both the same species as the THIRD-PARTY-NOTICES correction this release
already carries -- prose asserting something the code does not do.

1. `deBruijn` carried "written iteratively: an explicit stack rather than recursion because a long
   pattern over a small alphabet nests deeply enough to matter." The function is plainly recursive,
   and the stated *reason* is wrong too: depth is bounded by the subsequence length (capped at 8),
   not by the pattern length, so a 1 MB pattern nests no deeper than an 8-byte one. Recursion is
   correct here; the comment invented a justification for a design decision nobody made.
2. `docs/guides/commands.md` documented `xor_key_length` as defaulting to `input_format: Hex` and
   `max_key_length: 40`. The schema says `Raw` and `32`. **Written from memory rather than read off
   the schema -- the same mistake as F-07, four days later, in the same release.** This one is
   worse than a wrong number: a caller trusting the docs would omit `input_format` for hex input,
   and analysing hex text as raw bytes returns a confident wrong key length rather than an error.

Also corrected: the release notes claimed the registry guards against "506 operation tools" where
`OperationConfig` has **504**, and three documents said the tool scores "forty" candidate lengths
where the default ceiling is 32.

**The pattern across F-07, F-12 and the notices rewrite is one thing:** every number and behaviour
claim in prose needs to come from the artefact, not from recollection of it. Three separate
instances in one release is not bad luck.

One review claim did not survive checking, and is recorded because rejecting it correctly matters
as much as adopting the rest. CodeRabbit reported the default index as "23 → 27", reasoning that
`META_TOOLS` holds 23 entries and no operation tool is in the index. Measured through a real
client: **28**, because `cyberchef_magic` is an operation tool deliberately exposed at every
surface -- 23 meta + 1 + 4 registry. The published figure of 24 → 28 was right.

## F-13 - Three tools that answered confidently and wrongly - **FIXED**

CodeRabbit's second pass on PR #100 found three correctness defects that the tests did not. All
three were reproduced before being believed, and all three share one shape: **the tool returned an
answer where it should have refused one.** That is the exact failure every one of these tools was
written to prevent, which is why it is worth recording rather than just fixing.

**1. `phi(n)` was wrong when the two factors are equal.** `n = p^2` is not hypothetical here --
Fermat returns `p === q` for it on the *first* iteration, because `a = isqrt(n)` gives `b^2 = 0`.
`phi(p^2)` is `p(p-1)`, not `(p-1)^2`. Measured:

```text
round-trip: 368518651580054785   expected 424242   WRONG
```

A private exponent that looks like a private exponent and decrypts to garbage.

**2. A non-exclusive pattern suppressed the ambiguity behind it.** The Cisco IOS type 7 pattern is
two decimal digits followed by hex, which any ordinary digest beginning `01`..`99` satisfies by
coincidence. `0123456789abcdef0123456789abcdef` -- a perfectly normal MD5-length string -- was
reported as `Cisco IOS type 7`, `confidence: structural`, `ambiguous: false`, one candidate, with
the note *"Identified by structure, so this is reliable."*

The tool's own headline property is that it does not pretend a bare hex digest is one algorithm.
It broke that property through a pattern that *looked* structural. Formats now carry a `weak` flag,
and a match that is not exclusive no longer suppresses the length candidates.

**3. A fragment shorter than the uniqueness window got an offset anyway.** Uniqueness is a property
of length-`n` windows only. With `n = 4`, `"aa"` occurs **282 times** in a 1024-byte pattern, and
`indexOf` returned the first as *the* offset -- with the note "Offset 0: that many bytes before the
value you recovered." A confident wrong overflow offset is the single thing this tool exists to
prevent. Now refused, naming the knob to turn.

Two smaller ones from the same pass, both about blaming the right thing:

- Malformed hex under an explicit `fragment_format: Hex` fell through to "does not appear in the
  pattern", sending the caller to check the pattern length and alphabet, which were fine.
- `byCategory` used a plain object, so a tool in a category named `__proto__` or `constructor` read
  an inherited value and threw on `.push`. `Object.create(null)`.

**The lesson is about test design, not about these three bugs.** Every one of them lives in a case
the tests did not think to construct: a square modulus, a digest that collides with a structural
pattern, a fragment below the window. The suite tested the cases the tools were *for*. Reviewing
each tool for "what input makes this return a confident wrong answer" is a different exercise from
"does it work", and it is the one that found these.

## F-14 - Documents that disagreed with the document they linked to - **FIXED**

Three more prose corrections, all found by CodeRabbit on PR #100, and the first is the interesting
one.

**The roadmap and release notes named a worker thread as a "real isolate"** that would make a
plugin loader buildable. ADR 0002 -- the document both of them link to, in the same sentence --
says the opposite and says it plainly: *"Worker threads do not close the gap either. They bound CPU,
not authority."* Two summaries of an ADR contradicted the ADR. Both now say what it says: process
isolation plus an explicit capability allowlist.

**The ADR over-claimed its own measurement.** It said the vm escape reaches "pid, cwd(), env,
child_process by require". `require` is module-scoped, not global, and is not reachable that way:

```text
typeof require inside the context: undefined
require("child_process")        : ReferenceError: require is not defined
```

`process` alone is reached, and `process` alone is enough to make the point. In a document whose
entire authority rests on having measured rather than argued, an unmeasured extra clause is the
worst possible sentence to leave in.

**And the README kept two stale copies** the docs pass missed: a 70%/75% coverage threshold from
before v2.3.0 raised it, and "798 tests across 25 files". It also conflated the statements and
lines thresholds, which are 95 and 96 rather than one number.

## Method note

F-02, F-03 and F-04 all come from the same discipline and are the reason this tool is worth
trusting: **prototype the algorithm against known answers before wrapping it as a tool.** Each of
the three would have shipped as a confident wrong number, and none would have been visible from
reading the code -- the chi-square version, the 90% band and the truncated candidate list all look
correct on the page.
