# v4.0.0 findings log

Written during development, in the order the findings arrived. F-01 states what the plan got wrong
before any code.

---

## F-01 — The plan gave v4.0.0 no way to happen, and the trigger watch says so out loud

### The measurement, run first

```text
draft changelog     EMPTY ("Changes since the most recent release will accumulate here.")
current revision    2026-07-28, no successor
SDK                 @modelcontextprotocol/{server,node,client} all 2.0.0
conformance         0.2.0-alpha.11
server.json schema  2025-12-11 still newest; every 2026-* date 404s

Nothing fired. v4.0.0 stays unscheduled; ship the next minor.
```

Every trigger unfired, for the fourth release running. Under `v4.0.0-plan.md` as written, that
settles it: do not cut a major.

**This release cuts one anyway, and the reason is that the plan is wrong — not the measurement.**

### What the plan got wrong

`docs/planning/v4/v4.0.0-plan.md` defines four triggers, A through D. Every one of them is an
**external** event in the MCP specification: tasks entering core, tool-result contracts
standardising, progressive discovery standardising, streamable HTTP over stdio.

The principle underneath that was sound and still is. SemVer says MAJOR means something broke, and
inventing a break to reach a round number is worse than staying on v3 — which is exactly why
v3.9.0, v3.10.0 and v3.11.0 correctly shipped v4 charter content as v3 minors.

The error is that the trigger set is **exhaustively external**, so the project has no internal path
to a major at all. Three consequences, all of which have now happened:

1. **v4.0.0 waits on an event that may never arrive.** The specification owes this project nothing.
2. **Removable surface accumulates with no mechanism that can remove it**, because removal is
   breaking and breaking requires a major.
3. **The version number stops carrying information.** v3.x has run to eleven minors; a reader
   cannot tell from the number that anything was ever retired, because nothing ever was.

A major version is not only a response to someone else's breaking change. It is also the mechanism
a project uses to retire its own past, and the plan modelled only the first kind.

### The evidence that the second kind is now due, measured not recalled

**The deprecation system's only live warning is a WITHDRAWN code.** Calling `cyberchef_bake`
normally — no unusual arguments, no legacy shapes — produces exactly one deprecation record:

```json
{
  "code": "DEP007",
  "feature": "Meta-tool cyberchef_bake",
  "description": "WITHDRAWN: cyberchef_bake is NOT being renamed. It keeps its name.",
  "alternative": "No action required.",
  "removalVersion": null,
  "withdrawn": true
}
```

So the live behaviour of the machinery is: **warn about a change that was cancelled, for a migration
to a version that shipped nine minors ago, and tell the caller no action is required.** That is not
a deprecation system; it is an artefact of one.

**Of the eight DEP codes, three are withdrawn and the other five describe work that shipped or was
abandoned:**

| Code | Says | Actually |
|---|---|---|
| DEP001, DEP007, DEP008 | the `cyberchef_` prefix / `bake` / `search` will be renamed | **withdrawn in v2.0.0**; the prefix is permanent |
| DEP002 | "Recipe schema will be enhanced with Zod v4 validation in v2.0.0" | shipped |
| DEP003 | "Error responses will include structured error codes in v2.0.0" | shipped |
| DEP004 | "Configuration will use unified config file + env vars in v2.0.0" | shipped in v2.10.0 |
| DEP005 | "Positional arguments will be replaced with named object arguments" | **never happened and will not**; both forms are supported and tested |
| DEP006 | "Recipe operations using simple arrays will require explicit operation objects" | same |

DEP005 and DEP006 are the sharpest: they announce removals this project has since decided **against**
and documents the opposite of, in `AGENTS.md` and in the FAQ ("Both argument forms work").

**What it costs, measured through a real client rather than estimated:**

```text
surface    with the migration tools      without        saved
index      43 tools /  45,963 bytes      41 /  44,968     995
curated   121 tools / 109,209 bytes     119 / 108,214     995
all       546 tools / 426,367 bytes     544 / 425,372     995
```

995 bytes on **every** `tools/list`, on every surface, for two tools that help a caller migrate to
v2.0.0. For scale: `cyberchef_pqc_identify`, the entire new tool v3.11.0 shipped, cost 1,470 bytes.
This project is paying two thirds of a real feature, on every request, to describe a completed
migration.

Behind them, `src/node/deprecation.mjs` is **522 lines** with **580 lines of tests**.

### The correction

A fifth trigger, internal, added to the plan and to `scripts/check-v4-triggers.mjs` so it is
executed rather than remembered — the same argument that made the other triggers a script:

> **T-13 — accumulated removals.** A major is due when deprecated surface that is still advertised
> to callers describes migrations that have completed, been withdrawn, or been decided against.
> Measured, not felt: a count of live-but-obsolete deprecation codes and the bytes their tooling
> costs on `tools/list`.

The kill criterion from the original plan is **not** repealed, and this release does not repeal it.
"A major exists because the protocol forced one" remains true of triggers A–D. What changes is that
it is no longer the *only* reason a major may exist.

*A plan that can only be satisfied by someone else is not a plan.*

## F-02 — What the removal actually cost, and what it bought

Executed as scoped. The numbers are measured, not projected:

```text
surface    before (v3.11.0)        after (v4.0.0)       delta
index      43 /  45,963 bytes      41 /  44,968          -2 tools,  -995 bytes
curated   121 / 109,209 bytes     119 / 108,214          -2 tools,  -995 bytes
all       546 / 426,367 bytes     544 / 425,372          -2 tools,  -995 bytes

round trip   index + one schema    46,746 bytes          9.1x cheaper than `all` (was 8.9x)
settings     64 in 15 sections     62 in 14 sections     the `compatibility` section
source       deprecation.mjs       gone                  522 lines
tests        deprecation + migrate gone                  1,188 lines across 3 files
```

**The round-trip multiplier improved for the first time since v3.2.0.** It has fallen at every
release that added a registry tool — 18.2x, then 9.5x, 9.2x, 9.0x, 8.9x — because a registry tool
has no navigation path and must sit in the index. Removing two tools that navigate to nothing moved
it back up to **9.1x**. That is the mechanism working in the direction it was designed for.

### The CLI went too, and the reason is that its premise was false

`cyberchef-migrate` was a published `bin`, so removing it is a real break. It converts v1-format
recipes to v2 — and **both formats work**, which was verified through a real client rather than
assumed:

```text
v1 positional args   [{op:"To Base64", args:["A-Za-z0-9+/="]}]   ->  "SGk="
v1 bare string op    ["To Base64"]                               ->  "SGk="
v2 named args        [{op:"To Base64", args:{alphabet:"..."}}]    ->  "SGk="
```

All three identical. The tool converted a working format into another working format, for a
migration whose target shipped nine minors ago.

### The image is RENAMED, and the gate caught that I had not done it

`bump-version.mjs` moved the version and left the image at `cyberchef-mcp_v3:4.0.0` — a tag that
will never be pushed, because `mcp-release.yml` derives the GHCR package from the tag's major.
`check:versions` failed on five locations at once:

```text
FAIL  deploy/helm/cyberchef-mcp/values.yaml (image.repository major): 3.x.x, expected 4.x.x
FAIL  server.json (packages[0].identifier major): 3.x.x, expected 4.x.x
FAIL  deploy/compose/docker-compose.yml (image reference 1..3 package major): 3.x.x, expected 4.x.x
```

This is precisely the v3.0.0 defect that made the check assert the major rather than only the
version, and it is the first major since. **The gate that was built for a once-every-few-years event
worked the first time that event recurred** — which is worth recording, because most such gates are
never exercised again after the release that motivated them.

## F-03 — A test that mutates a source file is a race, and the suite is parallel

The T-13 gate had to be verified by planting the real defect. The first version planted it in
`src/node/mcp-server.mjs` and restored it in a `finally`. It passed alone, passed under
`test:coverage`, and failed in the full suite:

```text
FAIL  tool-surface-figures > serves exactly the tool counts and byte sizes the table records
      expected 'curated tools: table says 119, server serves 120' to be ''
```

**Vitest runs test files in parallel**, and `tool-surface-figures.test.mjs` boots a real server by
spawning `src/node/mcp-server.mjs` from disk. It read the planted copy — with the extra tool — and
measured one tool too many. The failure was in a file I had not touched, blaming a figure I had
correctly updated.

Fixed by copying the script and the three files it reads into a temp directory and planting there,
so the real tree is never written to. The restore-in-`finally` was not the problem; **the window
was**, and a window is invisible to a single-file run.

*Anything a test writes, another test file may be reading at that moment.*
