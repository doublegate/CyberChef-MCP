What was measured before writing anything, including what the charter got wrong and what I got
wrong. Same purpose as the v2.2–v3.2 logs.

## F-01 — The charter's own kill criterion fires on the phase it proposed next — **RE-SCOPED**

The v3.3.0 charter is the `ext-proj-int` programme, and its first kill criterion is explicit:

> A phase's tools duplicate operations upstream has since added — re-check `OperationConfig` first;
> the catalogue grew 440 → 504 during v2.x.

Checked, against the generated config rather than against the plan:

| Sprint 2.1 tool | Upstream today |
|---|---|
| `cyberchef_encoding_morse` | **From Morse Code, To Morse Code** |
| `cyberchef_encoding_braille` | **From Braille, To Braille** |
| `cyberchef_encoding_ascii85` | **From Base85, To Base85** — ASCII85 *is* Base85 |
| `cyberchef_cipher_enigma` | **Enigma** |
| `cyberchef_cipher_affine` | **Affine Cipher Encode/Decode** |
| `cyberchef_cipher_bacon` | **Bacon Cipher Encode/Decode** |
| `cyberchef_encoding_baudot` | not present |
| `cyberchef_cipher_playfair` | not present |
| `cyberchef_cipher_polybius` | not present |

**Six of nine already exist as operations.** Building them as registry tools would not add
capability; it would add nine names to a catalogue whose whole surface design exists to keep names
findable, and six of them would shadow operations that already work. Registration *throws* on a
shadowing name, so three of those six would not even start the server.

**The three that are genuinely absent shipped** — Playfair, Polybius and Baudot, plus ADFGVX, in
one `classical_cipher` tool rather than four names. And the re-scope did not end the release: it
ended the *charter's* version of it. Reading the reference projects for what they actually do,
rather than reading the plan for what it says they do, produced twelve tools instead of nine, none
of which shadows anything. See F-05 onward.

Sprint 2.2 fails a different constraint, one the charter itself states two sections later:

> Preset tools use `preset_*`; `recipe_*` belongs to the v1.6.0 management tools.

Its table names `cyberchef_recipe_list` and `cyberchef_recipe_search`. **`cyberchef_recipe_list`
is a shipped v1.6.0 tool.** The plan document contradicts the constraint written to protect it, and
the collision is the kind that throws at startup rather than degrading quietly.

So Phase 2 as scoped is roughly one third viable. That is not an argument against the programme —
it is the argument for the kill criterion, which is why it was written down and why re-checking it
is step one of the ritual.

**The re-scope.** v3.3.0 ships the **carried-forward items** — concrete, measured, and promised at
the close of v3.2.0 — and leaves the tool programme to a release that re-derives its phase against
the current catalogue rather than against a December 2025 table. Those items are not filler: two of
them are gates this project shipped in a knowingly-incomplete state one release ago.

**SemVer:** additive. Better error text, a new workflow, new measurement. MINOR.

## F-02 — Every failure got the same three suggestions, and they contradicted the error — **FIXED**

The charter carried "error suggestions keyed by operation rather than by code" from v2.9.0, twice
deferred. Measured through a real client, an unknown-argument error arrives like this:

```text
Error [INVALID_INPUT]: Unknown argument for "AES Encrypt": input_type

Context:
  - accepted: ["key","iv","mode","input_arg","output", …]
  - hint: "Valid arguments: key, iv, mode, input_arg, output, additional_authenticated_data, include_iv_in_outp..."

Suggestions:
  1. Verify input data format and encoding
  2. Check for special characters or invalid byte sequences
  3. Ensure input matches the operation's expected format
```

Two defects, and the second is worse than "generic".

**The advice contradicts the error.** The failure is a wrong *argument name*; the advice is about
data format and special characters. `ErrorSuggestions` is keyed by error CODE, so all 504
operations share three lines for every `INVALID_INPUT`. Advice that points away from the fix is
worse than no advice, because it is the model's next action — here it sends the caller to inspect
an input that was fine.

**The truncation cut the fix.** A flat 100-character cap on context values chopped `hint` mid-word
at `include_iv_in_outp..."` — the one field that says what to do. "Truncate with guidance" is the
principle from the same charter, and a guidance field is exactly the wrong thing to truncate.

Both fixed, and the result is smaller as well as better: **663 → 540 bytes**. Generic suggestions
are *suppressed* rather than deleted, so an error with nothing more specific to say still says
something — a `Gunzip` failure on non-gzip input has no hint and keeps all three lines.

## F-03 — The gate shipped at a stopgap, and the stopgap now has a workflow

v3.2.0's regression gate ships at a **50%** tolerance, and F-13 recorded honestly that this is what
a cross-machine baseline can support rather than what the measurement wants: the baseline was
captured on a developer machine, the gate runs on a GitHub runner, and against the same baseline
that runner produced deltas from −25.5% to +99.1% and two false failures at 25%.

`benchmark-baseline.yml` captures the baseline **where the gate runs**, so the comparison is like
with like and the tolerance can come back down to what the runner's own variance supports.

Three decisions in it worth stating, because each is the difference between a baseline and a moving
target:

- **Manual and scheduled, never on push.** A baseline that regenerates on every commit can never
  report a regression.
- **It opens a pull request, not a push.** Moving a gate's reference point silently is
  indistinguishable from switching the gate off.
- **Same method as the local capture** — five runs, the first discarded — so the two are comparable
  and the cold-run artefact from F-03 of v3.2.0 does not reappear on the runner.

The tolerance itself is deliberately *not* lowered in this release. It should move once a
runner-captured baseline exists, on that measurement, not on the expectation of one.

## F-04 — arm64 works, and remains unbenchmarked — **HALF ANSWERED, HONESTLY**

The carried-forward item said *"every performance figure this project publishes is amd64, and the
published image is multi-arch."* True, and it stays true after this release, but for a reason worth
writing down rather than repeating the same line next time.

Driving the **published** v3.2.0 image on both platforms through a real MCP client:

```text
linux/amd64   boot + tools/list    775 ms
  To Base64 (10KB)   1.7 ms      MD5 (10KB)      1.7 ms
  Gzip (10KB)        5.7 ms      Entropy (10KB)  0.6 ms

linux/arm64   boot + tools/list  10412 ms
  To Base64 (10KB)  25.8 ms      MD5 (10KB)     32.4 ms
  Gzip (10KB)       59.9 ms      Entropy (10KB)  8.1 ms
```

**Those arm64 numbers measure QEMU, not arm64.** The host is amd64; the arm64 image runs under
binary translation, and a 13x boot and 10–19x per-operation penalty is the emulator's, not the
platform's. Publishing them as arm64 performance would be worse than publishing nothing — it would
be a measured-looking number about the wrong thing, which is the failure this whole line of releases
keeps writing up.

What they **do** establish, and what nobody had checked: the arm64 image **works end to end through
a real MCP client**. v2.8.0 shipped it and CI asserts that the optional `@napi-rs/nice` arm64 binary
resolved, but no test had ever connected a client to the arm64 image and run a recipe. It boots,
lists tools, and bakes correctly on all four operations.

So the gap narrows from "unverified and unmeasured" to "verified, unmeasured", and closing the rest
needs arm64 **hardware** — a native runner, or a machine. Carried forward with that stated, so the
next attempt does not repeat this one and think it succeeded.

## F-05 — Three reference tools document intelligence that does not execute — **DESIGN INPUT**

The `ext-proj-int` charter treats Ciphey and Ares as designs to port. Read as code rather than as
README, all three of their "intelligent" search layers are absent, unused or mis-scaled:

| Claim | What the code does |
|---|---|
| Ciphey uses A* search | `basemods/Searchers/__init__.py` is one line and does not import `astar`. The module is dead, and non-functional anyway: `self.text` is read and never assigned. |
| Ares uses A* with decoder popularity | It runs A*, but **both production call sites pass `&None` for `next_decoder`** (`astar.rs:306`, `astar.rs:386`); only unit tests pass `Some`. Decoder popularity, success-rate adaptation and the uncommon-pairing penalty therefore never fire, and the heuristic collapses to depth plus a string-quality tiebreak. |
| Brandon does a chi-squared test | Its 40-line docstring describes one; `check()` is a dictionary-proportion test and nothing else. |

Ares also carries `railfence` popularity **5.0** on a 0–1 scale, which would compute
`1.0 - 5.0 = -4.0` and dominate the queue — a latent bug masked only by the `&None` defect above.

What actually carries both tools is the boring pruning: a minimum length, a printable-ratio reject,
and exact deduplication. **That is the finding that shaped `plaintext_check`**: it answers in the
order the cheap checks resolve and does not pretend to a ranking model that would not run.

CyberChef's own `Magic` is the incumbent and has the opposite profile — it has the hard depth cap
(3) neither of them has, and lacks both of the things that do the work: it has **no visited set at
all** and no structural quality gate. Its `_chiSqr` is also fed percentages rather than counts, so
it is scale-free and ignores sample size, and its prune test `probability > 0` is a floating-point
underflow boundary rather than a tuned threshold. Recorded rather than fixed: `Magic` is
`src/core`, which is mirrored from upstream.

## F-06 — A statistic you can compute is not a statistic you can decide on — **FIXED**

`plaintext_check` called a 52-letter ROT13 sentence "not plaintext" with moderate confidence, on an
index of coincidence of 0.0332.

That is not uncertain, it is **backwards**. A monoalphabetic substitution *preserves* the index of
coincidence — it is a permutation invariant — so ROT13 of English reads English's IoC, not a
cipher's. The same text at 312 letters measures 0.0487 and does not trip the branch at all.

The 50-letter floor quoted for IoC (Thonky, and it is the only sourced figure — the frequently
repeated "a few hundred characters" has no primary source) is the length at which the statistic
becomes **computable**. Deciding on it needs about 200. Conflating the two floors is what produced
a confident wrong answer, and the fix is one line plus a test that pins the exact regression.

The same distinction has a second consequence, recorded in `vigenere_break`: in a key-length search
the relevant N is the **coset** length, not the message length. A 300-letter message tested at k=8
gives cosets of 37 letters, already below the floor — so a tool gating on total length silently
produces unreliable per-coset numbers and a confident answer built on them.

## F-07 — Quadgrams from a small corpus are worse than trigrams, not better — **MEASURED**

The obvious way to build a language model for `substitution_break` is quadgrams, because Practical
Cryptography's `english_quadgrams.txt` is the standard and quadgrams separate English from
wrong-key output by about four decades where letter frequency does not.

That file is 389,373 entries over 4.2 billion samples, 3.3 MB, third-party data of uncertain
licence, and its host has been unreachable. So the model here is built from this repository's own
English prose: 1,328,077 letters. Built **both** ways from that corpus and measured on 300-letter
ciphertexts:

```text
trigram model      67.9% of letters recovered
quadgram model     56.1%
```

Quadgrams are worse, and the reason is the corpus size rather than the n-gram order: at 11.75%
coverage of quadgram space the floor dominates and the signal thins, against 54.3% coverage for
trigrams. Which is the general rule stated in the other direction — a threshold calibrated against
one model is meaningless against the other, and so is a model of one order built from a corpus
sized for another.

The released model's measured accuracy, on four held-out passages at 120 restarts:

```text
100 letters    63.3% of letters recovered
150 letters    83.6%
250 letters    91.2%
350 letters    95.9%
```

Reported in the tool's own description as recovering *most* of the mapping and leaving a letter
pair or two swapped, because only 9 of 12 reach 95% of letters at 350 and claiming a solve
would be the dishonest reading of a 95.9% mean.

## F-08 — The generator was eating its own output — **FIXED**

`scripts/build-english-trigrams.mjs` gathers comment text from `src/node/**` with `/\/\*[\s\S]*?\*\/|\/\/.*/`.
Base64 contains `//`, so the `//.*` branch matched inside the generated table's own encoded bytes
and read them back in as English prose.

Two consecutive runs produced corpora differing by fifty letters, which is how it was found — the
script is meant to be idempotent and was not. Excluding its own output fixed it; excluding
`src/node/index.mjs` fixed a second determinism problem, since that file is generated by grunt and
gitignored, so the table would otherwise depend on whether the build had been run.

A committed data blob that cannot be regenerated byte-for-byte is not a data file, it is a mystery.

## F-09 — Index of coincidence is a filter, not a judge — **FIXED**

`vigenere_break` first committed to the smallest key length whose cosets cleared an IoC bar, on the
sound reasoning that every multiple of the true length scores as well or better. Practical
Cryptography's own worked example is the evidence: key `CIPHERS`, period 7 scores 0.0910 and period
14 scores **0.0988**, so an argmax answers 14 for a seven-letter key.

Committing to one length cost two of ten measured cases. Solving a *shortlist* of lengths in full
and letting the plaintext's trigram score decide — with a shorter length winning any tie, because a
multiple decrypts identically — recovered both, and costs 26 chi-squared evaluations per position.

The score is now 9 of 10. The tenth is a 14-letter key against 240 letters of ciphertext, which is
17 letters per coset where the statistic needs about 50, and the tool reports its own failure
rather than a key.

## F-10 — OpenSSL 3 will not give you MD4, and NTLM needs it — **WORKED AROUND**

`createHash("md4")` throws `ERR_OSSL_EVP_UNSUPPORTED` on any modern Node build: OpenSSL 3 moved MD4
to the legacy provider, which Node does not load.

NTLM is MD4 of the UTF-16LE password, so a hash-cracking tool either implements MD4 or does not
offer NTLM — and NTLM is the case most worth having, being unsalted, fast, and still what a Windows
domain hands you. `hash_crack` therefore carries an MD4 implementation, checked against all seven
RFC 1320 test vectors and against a real NTLM hash.

## F-11 — Twelve registry tools cost 20.3 KB on the default surface, and there is no way around it — **ACCEPTED, MEASURED**

| surface | v3.2.0 | v3.3.0 |
|---|---|---|
| `index` (default) | 28 tools, 20,297 bytes | **40 tools, 40,637 bytes** |
| `curated` | 106, 83,543 | **118, 103,883** |
| `all` | 531, 400,701 | **543, 421,041** |

The default payload doubled. Registry tools have no navigation path — `cyberchef_bake` runs recipes
of **operations**, and the three navigation tools walk `OperationConfig` — so a registry tool that
is not listed cannot be called at all. Listing must never be stricter than dispatch, so they are all
in the index.

The arithmetic, since a findings log is measurement evidence and has to survive being checked:
the twelve tools added **24.1 KB** before trimming (44,434 bytes measured against v3.2.0's 20,297).
Trimming the prose out of tool and field descriptions recovered **3.8 KB** of that, leaving
**20.3 KB** — 40,637 bytes against 20,297. The rest is schema structure that has to be there for
the tool to be callable.

The alternative was considered and rejected: one indexed dispatcher taking a tool name and a
free-form `args` object would cut most of the remainder and reintroduce exactly the defect v2.1.0
was spent fixing — a tool whose schema tells a client nothing. `index + one operation schema` is still
**9.9x cheaper than `all`**, which is the property the surface exists to provide.

## F-12 — The navigation tools could not see the tools they sit next to — **FIXED**

Found by probing the finished server through a real client rather than by reading it.

A caller sees `cyberchef_hash_crack` in `tools/list`, asks `cyberchef_describe_operation` about it,
and is told:

```text
No such operation. Use cyberchef_search to find the exact name.
```

Both halves are wrong for that input. It *does* exist — its complete schema is in the list the
caller just read — and `cyberchef_search` will not find it either, because `help()` searches
`OperationConfig` and registry tools are deliberately not in it. This is the F-02 defect in a
different place: advice that points away from the fix.

The search hole is the larger of the two. Searching **"playfair"** returned zero matches and
"try a shorter or more general keyword", for a capability that had been sitting in `tools/list`
since the release began. The index surface's whole design rests on search being how a caller finds
things, so a search that structurally cannot return sixteen of the tools on offer is a hole in the
design and not a missing nicety.

Both fixed. `describe_operation` now names a registry tool as one and says its schema is already
loaded; `search` returns an `analysis_tools` section alongside `operations`, marked "not an
operation: call it directly rather than putting it in a recipe".

## F-13 — Sixteen tools, one client-driven test each — **ADDED**

Every one of the twelve new tools had been exercised by calling `run()` directly. That is exactly
the gap v2.1.0 was spent closing: a direct `run()` call touches none of the schema conversion, the
capability hand-off, the timeout wrapper or the content block, and three releases once shipped with
every tool carrying an empty `inputSchema` while a suite of direct calls stayed green.

`stdio-client-contract.test.mjs` now drives **all sixteen** through the SDK client with a minimal
valid payload each, and a separate test asserts the fixture list matches the registry — so adding a
registry tool without adding a case fails there rather than in production. Two fixtures were wrong
on the first run (`cyclic_pattern` needs `mode`, `hash_statistics` returns `entries` not `total`),
which is the point: written-out payloads exercise something, and generated ones satisfy the schema
and prove nothing.

## F-14 — One legal call held the server for 29 seconds — **FIXED**

`entropy_scan`'s cost is bounded by `(bytes - window) / step`, not by the input size, and the
schema permitted 8 MB with a one-byte step. That is 8,388,593 windows. Measured:

```text
8 MB, window 16, step 1     29,219 ms
```

Against a 30-second operation timeout. The call is legal, it is synchronous, and the timeout
cannot fire while it runs — so it starves every other request on a shared server and there is no
way to interrupt it.

Refused above 500,000 windows rather than silently downsampled, because quietly widening the step
would answer a question at a resolution the caller did not choose, and the refusal names the
`step_bytes` that would fit. 500,000 is about 1.2 seconds, and it is also far more than anyone
reads: `max_regions` caps the output at 256, so a scan producing millions of windows is measuring
detail that never leaves the function.

Yields added to every remaining loop that is O(input) rather than O(1) — in `entropy_scan`,
`corpus_diff` and `crib_drag`. Measured longest event-loop block at each tool's schema maximum,
before and after:

| tool, at its maximum | before | after |
|---|---|---|
| `entropy_scan` (8 MB, step at the cap) | 1,129 ms | **399 ms** |
| `corpus_diff` (512 x 64 KB) | 193 ms | 224 ms |
| `crib_drag` (256 KB, 256-byte crib) | ~4,000 ms | **301 ms** |

## F-15 — A per-character callback was the largest block of synchronous work in the codebase — **FIXED**

Profiling what was left of `entropy_scan`'s 991 ms block found it was not the scan at all:

```text
Uint8Array.from(value, ch => ch.charCodeAt(0) & 0xff)    675 ms
new Uint8Array(Buffer.from(value, "latin1"))              14 ms      (byte-identical)
```

48x, on 8 MB. latin1 takes the low byte of each UTF-16 code unit, which is exactly what the mapper
was doing one character at a time; the callback is the entire cost.

The pattern appeared in four tools — `entropy_scan`, `corpus_diff`, `crib_drag` and
`xor_key_length` — and is replaced in all of them.

## F-16 — A bounds test that named four tools stopped covering the twelve that came after — **FIXED**

`tool-registry.test.mjs` had a test called *"bounds every string argument on every tool"*. It named
four tools by hand. Twelve more were added in this release and it kept passing, which is the same
shape as the gap it was originally written for: *"a schema that looks careful because the obvious
fields are capped."*

Replaced with a structural walk over every registry tool's schema, asserting that no string field
and no array is unbounded. It immediately found three:

```text
corpus_diff.analyses     (array length)
rsa_attack.attacks       (array length)
rsa_multi_key.attacks    (array length)
```

`rsa_attack.attacks` has been unbounded since v2.4.0, through nine releases and the hand-written
test that claimed to cover it. All three are enum arrays, so the natural bound is the number of
members — asking for the same attack twice is not asking for more.

The walk cannot reach inside an array of OBJECTS, which is what `rsa_multi_key.keys` is, so that
one is asserted directly alongside it. An assertion that silently checks nothing is worse than no
assertion, and a structural test is exactly where that happens.

## F-17 — The bot review found two crashes and a silently wrong private key — **FIXED**

Thirty-eight review comments on the release PR. Every one was reproduced before it was accepted or
rejected; eight were defects a test would not have caught because no test asked those questions.

**Two crashes, from inputs the schema accepts.**

```text
rsa_attack   modulus "97"                RangeError: Division by zero
rsa_multi_key  moduli 15 and 45          TypeError: Cannot mix BigInt and other types
```

The first: `smallFactors` found 97 dividing 97 and returned `{p: 97, q: 1}`, so `phi = (p-1)(q-1)`
was 0 and `modInverse(e, 0n)` divided by zero. The second: Håstad's coprimality check was
`g > 1n && g < n_i`, which is false when one modulus DIVIDES another, so `crt` was reached with
moduli that are not pairwise coprime and multiplied by a null inverse.

**And one silently wrong answer, which is worse than either.**

```text
rsa_attack   modulus "105" (= 3 x 5 x 7)
             p = 3, q = 35, private_exponent = 9, plaintext_int = 71
```

`q` is composite, so phi(105) is 48 and not 2 x 34 = 68 — but `modInverse(65537, 68)` succeeds, so
the tool returned a real-looking private exponent that decrypts nothing, and a plaintext field
derived from it. This is the same defect the `p === q` note in that file already records, in a
second place. Both factors are now tested for primality with **random-base** Miller-Rabin before
phi is computed, and a partial factorisation is reported as one.

Six more, all reproduced:

| | Was |
|---|---|
| `entropy_scan` region merge | `last.end === w.offset` never merges when step < window, so one 2 KB blob came back as **29 regions** competing for the same `max_regions` slots |
| `entropy_scan` yield counter | keyed on `blocks.length`, which stays 0 for an all-zero input, so it yielded on **every** block |
| Base64 decoding, three tools | `Buffer.from(v, "base64")` ignores non-alphabet characters, so `"hello world!!"` decoded to 7 bytes and every statistic was computed on them |
| `crib_drag` empty `ciphertext_b` | passed the schema, was treated as absent, and silently answered a different question |
| `hash_crack` mixed batch | an unsupported length was reported **uncracked**, which reads as a password that survived a search it was never in |
| `hash_statistics` NetNTLM | `user::domain:...` split on the first colon and reported a passwordless account |

The NetNTLM fix took two attempts, and the second is the interesting one. Detecting `::` is wrong:
a disabled shadow line is `daemon:*:19000:0:99999:7:::` and a genuinely passwordless one is
`user::19000:0:...`, and the second has `::` at exactly the position a NetNTLM record does. Only
the full pattern separates them, so the detection now reuses `hash_identify`'s own regexes.

## F-18 — `vigenere_break` reported a key and a score for two different keys — **FIXED**

The trigram rescore captured `original` once, before the loop over a position's five alternatives.
If the second alternative improved the score and the third did not, the third's failure wrote
`original` back — reverting an accepted correction while `score` still held the improved value.

So the reported key and the reported score described different keys, and the key was the wrong one:
the half a caller acts on. It survived because the tool still recovered 9 of 10 test keys — the
rescore corrects roughly one position per solve, and the bug needed two accepted corrections at the
same position to show.

Also from the same review: the "no key length has enough letters" error was unreachable (the
40-letter floor guarantees `k = 1` produces a coset twice the 20-letter minimum), and the test named
for it asserted that both its cases **succeed**. A test whose name and body disagree is worse than
no test, because it reads as coverage. Both removed, and the invariant asserted instead.

## F-19 — Two tests could not fail, and neither could a third — **FIXED**

The same review, on the tests rather than on the code.

**The registry-coverage test was an identity.** It kept the advertised names that appear in
`REGISTRY_CALLS`, then asserted that set equals `REGISTRY_CALLS`. A new registry tool with no
fixture would have sailed straight through the test written to catch exactly that. Derived from
`buildRegistry().list()` now, with a second assertion that every derived name is actually
advertised — so the fixtures cannot describe a tool the server does not serve either.

**The byte-offset test never touched the buffer it was named for.** It called `chiSquared`, which
reads the letter-frequency array and nothing else, so a wrong `byteOffset` in `english.mjs` would
have left it green. It now asserts against `TRIGRAM_LOGP` directly: 17,576 entries, and `THE`
scoring three decades above `QKX`.

**The shuffle used `sort(() => Math.random() - 0.5)`**, which is not a valid comparator —
inconsistent between calls, so the permutation is biased and engine-dependent and can leave much
of the original order intact. Seeded Fisher-Yates instead.

Also: `examples/**` was executed by CI and never LINTED, which is the same gap `benchmarks/**` and
`conformance/**` had before v3.2.0 — the grunt task globs `src/node/**` and `tests/**` only. Added
to both the glob and the `no-console` exemption.

## F-20 — The generator could write a wrong table and report success — **FIXED**

Two failure modes ended in the same place and neither was detected. An empty corpus makes `max`
zero, `counts[i] / max` is NaN, and assignment into a `Uint16Array` silently converts NaN to 0 — so
the output was an all-zero table with `lost` at 0 and a normal summary line. And both replacements
into the generated module are anchored on its current formatting, so a reformat would leave the
file untouched and still report success.

Both now refuse to write. The docblock says this script is meant to be copied into another
repository with a path substituted, which is exactly the case where the walk returns nothing.

Regenerating after the review's fixes also moved the corpus — the model is built from this
repository's own prose, and this release added a great deal of it. 1,328,077 letters, 9,606
distinct trigrams, and the accuracy re-measured rather than assumed to hold:

```text
100 letters    63.3% of letters recovered   (was 50.2%)
150 letters    83.6%                        (was 82.9%)
250 letters    91.2%                        (was 90.7%)
350 letters    95.9%                        (was 94.6%)
```

Every published figure updated to match. A measurement that moves and is not re-published is a
measurement nobody can check.
