# v3.5.0 findings log

Written under [`docs/planning/v3/RE-MEASURE.md`](../planning/v3/RE-MEASURE.md). F-01 is written
before any code, and states what the plan got wrong.

---

## F-01 — The gate written yesterday encodes a deprecated schema — **THE PLAN WAS WRONG**

v3.4.0 fixed `server.json`, which had never been validated by anything: it declared the 2025-07-09
schema while being written to 2025-09-29. The fix moved the declaration to 2025-09-29 and added
`npm run check:server-json`, a hand-transcribed gate.

**The current schema is 2025-12-11.** The gate shipped one version behind, and the release notes
said the file now "validates" without qualifying against what.

This was findable at the time, and the ritual says exactly how: *"Search the ecosystem for the thing
you are about to build, by name, on the registry."* I did not. The schema versions came from curling
two URLs I guessed at, and both existed, which made the guess look like a measurement. The official
`mcp-publisher` CLI — a published binary, the tool the registry documents — reports it in one line:

```text
$ mcp-publisher validate
⚠️  Deprecated schema detected: .../2025-09-29/server.schema.json
   Expected current schema: .../2025-12-11/server.schema.json
✅ server.json is valid
```

Two releases in a row have now made the same class of error against this one file. v3.4.0's was
*"nothing had ever read a file whose purpose is to be machine-read"*; this one is *"the thing that
reads it was written by hand when an official reader existed."* The lesson generalises past
`server.json`: **this project already knows that an official oracle beats an in-tree check** — it is
written down for the conformance suite, where the same mistake cost v3.0.0 a release that claimed
conformance on its own tests. The rule was not applied here because `server.json` did not look like
the kind of thing that has an oracle.

### What actually changed between the two schemas

Read from the schemas, not the changelog — which says of 2025-12-11 only *"Migration: No changes
required"*, true for the document and false for a checker:

```text
definitions added     Icon, LocalTransport, RemoteTransport
definitions removed   Server            (merged into ServerDetail)
Package.required      [registryType, identifier, version, transport]
                   -> [registryType, identifier, transport]        version is now OPTIONAL
Package.transport     -> $ref LocalTransport = anyOf(Stdio, StreamableHttp, Sse)
ServerDetail          + title (max 100), icons, _meta, remotes
```

The rules `check-server-json.mjs` transcribes for `name`, `description`, `version` and the transport
types are **unchanged**, so it was not reporting anything false. It was, however, stricter than the
schema on `Package.version` and unaware of three new definitions — and, more to the point, it had no
way to know it was stale. That is the defect worth fixing, not the version string.

### Scope decision

**v3.5.0, a MINOR.** Nothing here is breaking: the schema migration needs no change to the document,
the checker becomes less strict rather than more, and everything else is additive. v4.0.0 stays
unscheduled — its own kill criterion is *"if the specification does not force a breaking change, do
not cut a major"*, and there is no MCP specification revision after 2026-07-28 (checked: the spec
repository lists `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25`, `2026-07-28`, `draft`).

## F-02 — The fix F-13 recorded would not have worked — **MEASURED, RE-SCOPED**

v3.4.0's F-13 reverted the benchmark tolerance to 50% and named the real fix:

> **Normalise against a calibration task.** Measure one fixed, well-understood operation each run
> and scale the rest by it. This targets host-class difference directly, which is the thing that
> actually broke this, and it is the one worth building.

It is tested here against the four CI runs that produced F-13, before building it. Normalising by a
calibration task is arithmetically the same as dividing out the run's median, so that is what is
computed:

```text
run           median delta vs baseline    residual spread AFTER normalising
33874729332          +101.4%                    -32.8% .. +33.7%
33875552658            -2.3%                     -7.8% ..  +4.0%
33876193748            +1.1%                    -39.7% .. +11.7%
33877632342            +2.2%                    -44.3% .. +26.5%
```

**Normalisation removes almost nothing.** The residual on the two failing runs is -39.7% and
-44.3%, against raw deltas of -38.6% and -42.1% — the correction is worth about two points. The
hosts do not differ by a scale factor; they differ in *profile*. Memory-bandwidth-bound tasks
(`To Hex`, `Entropy`, `Frequency distribution` at 100KB) collapse while CPU-bound
`Regular expression` improves **on the same run**, and no single constant corrects two directions
at once.

The same table carries a second fact worth stating plainly: one run measured a **median +101.4%**
against the committed baseline. Across four runs the pool's median throughput varied by a factor of
two. A per-task threshold against a stored baseline cannot separate a 40% regression from that.

### What the data does support

The variance that matters is *between* hosts. Within one host it is small — v3.4.0 measured a
worst-case 15.2% and a median 3.6% across four separate process runs on one instance.

So the fix is not a better constant, and not a wider tolerance. It is to **stop comparing across
hosts**: benchmark the merge base and the head *in the same job, on the same runner*, and compare
those two. Host variance then cancels exactly rather than being estimated and subtracted, and the
usable tolerance drops to what one host's own noise justifies.

That is a real change to how the gate works rather than to a number in a file, and it is v3.5.0's
second item. The stored baseline stays for context and for the missing-task check; it stops being
the thing a pass or fail is decided on.

## F-03 — Registry publication, unblocked by v3.4.0 and never done — **SHIPPED**

v3.4.0 added both ownership proofs and verified them: `mcpName` in `package.json`, and an
`io.modelcontextprotocol.server.name` annotation read back off a built image. Both are live on the
published v3.4.0 artefacts. The registry still lists nothing:

```text
$ curl registry.modelcontextprotocol.io/v0/servers?search=cyberchef
{"servers":[],"metadata":{"count":0}}
```

The proofs are what makes a publish *possible*; publishing is a separate act, and nothing did it.
That is the same shape as the npm record that sat absent for seven published versions — a
precondition satisfied and the thing it was a precondition for never performed.

`publish-mcp.yml` does it, on the version tag. Three points are deliberate:

**No stored credential.** `mcp-publisher login github-oidc` exchanges a short-lived,
workflow-scoped identity token for registry credentials, so `id-token: write` on one job replaces a
long-lived secret. Nothing long-lived is stored, so nothing long-lived can leak.

**It waits for the artefacts it points at.** The registry hosts metadata, not packages: it records
that `cyberchef-mcp@3.5.0` exists on npm and `ghcr.io/...:3.5.0` on GHCR. `mcp-release.yml`
publishes those on the *same tag*, so publishing the listing first produces an entry that resolves
to nothing. The job polls npm for up to ten minutes and fails rather than listing a version that is
not there.

**It reads the registry back.** `mcp-publisher publish` exiting 0 is not evidence the listing is
live, and this project has the rule already — the OCI annotation is verified by inspecting a built
image, the tag by counting its headings. Same here: the job queries the registry for its own name
and version and fails if it cannot find them.

One guard is worth naming because it protects against a failure that reads as something else: the
job runs `check:server-json` and `check:versions` *before* authenticating. A drifted `mcpName` or a
version the packages do not carry would otherwise surface at the registry as a rejection that looks
like an authentication problem.

### The injection pattern the security hook caught

The first draft interpolated `${{ github.event.inputs.reason }}` directly into a `run:` body.
`${{ }}` is substituted into the shell *source* before bash parses it, so a value containing
`$(...)` executes. Dispatching this workflow already requires write access, so it was defence in
depth rather than a hole — but the unsafe form is the one that gets copied into a workflow where the
input is not trusted, and it costs one `env:` line to not write it. Passed through the environment
instead.

## F-04 — The same-host guard skipped every release PR, on its first run — **FIXED**

The same-host comparison reuses one `node_modules` across two checkouts, so it must first establish
that both commits would install the same tree. The first version of that guard was:

```bash
git diff --quiet "$BASE_SHA" HEAD -- package-lock.json package.json
```

CI skipped the comparison on the very first pull request that used it — this one — and the comment
said so:

> _No same-host comparison: this was a push, or the dependency lockfile differs between the merge
> base and the head._

The guard was right by its own rule and **the rule was wrong**. A release pull request bumps the
version, which rewrites `package.json` and `package-lock.json` without changing a single dependency.
So the guard fired on exactly the pull requests where the comparison is most wanted, and would have
gone on doing that at every release, quietly, while looking like correct caution.

Fixed by comparing the resolved dependency **tree** rather than the files. `deps-identical.mjs`
hashes every `packages` entry from the lockfile **except the root `""` entry** — the root describes
this package itself, and its `version` is the field a release bumps — plus the declared
`dependencies`/`devDependencies` and the `lockfileVersion`. Verified in all three directions:

```text
this PR (version bump only)     identical    exit 0
one tampered resolved version   differ       exit 1
malformed lockfile              cannot tell  exit 2   -> treated as "do not compare"
```

Exit 2 is deliberately not folded into "differs": a parse failure says nothing about the
dependencies, and a guard that reports "different" when it means "I could not read it" is making a
claim it has not established.

**This is the value of shipping it as reporting rather than as a gate.** The defect surfaced as a
skipped comparison on a pull request instead of as a mysterious pass on a release. A gate that
silently stops checking is the failure this project keeps finding — `check:versions` exists because
a pattern stopped matching, and `check-server-json.mjs` fails on an unknown schema for the same
reason. This one announced itself because its output is read rather than merely acted on.

## F-05 — Seven review findings, all valid — **FIXED**

No dispute this time. Each verified against the code before being answered.

| Finding | Why it was real |
|---|---|
| `${{ github.base_ref }}` interpolated into a shell body | The same pattern the security hook caught in `publish-mcp.yml` and that I then did not check for in the workflow edited an hour earlier. `base_ref` is the target branch and so is not attacker-controlled the way `head_ref` is — but the unsafe form is what gets copied into the workflow where it is. Passed through `env:` and quoted. |
| No deployment environment on the OIDC publish job | Substantive. The registry maps the OIDC `repository_owner` claim to `io.github.doublegate/*`, so any repository writer dispatching this workflow can publish or overwrite entries in that namespace — a strictly wider set than "who may cut a release". `environment: mcp-registry-publish` added. |
| The registry read-back matched name and version independently | Real defect. Two greps over a *search* response, which holds several servers, pass when the name is in one record and the version in another. Parsed now, requiring both in one record. |
| `compare-runs.mjs` silently dropped a zero-baseline task | The comment called it "a broken run" and then dropped it, while the summary still said "30 tasks compared". That is the shape of every quietly-shrinking check this project has found. Listed explicitly now, excluded from the figures and named. |
| `deltas.at(-1)` when every task regresses | Printed `worst faster: +-2.0%` and listed negative deltas under "Largest speedups" — a report contradicting itself in the run where it matters most. Split by direction; each side prints `n/a` when empty. Verified with an all-regress fixture. |
| Three dates in the future | `2026-09-05` written on `2026-09-04`, in the ROADMAP, CHANGELOG, the measurement document and the schema retrieval date. Corrected. |

### The one worth keeping in mind

`environment:` is the half that lives in the repository. The other half is settings and cannot be
committed: **required reviewers, and deployment branches restricted to `v*`**, under
Settings → Environments → `mcp-registry-publish`. Until that is configured GitHub creates the
environment unprotected on first use and the line changes nothing. It is the hook, not the
protection — said plainly in the workflow so that reading it does not create false confidence.

## F-06 — The publish job's wait could never finish — **FIXED, POST-TAG**

`publish-mcp.yml` ran for the first time on the v3.5.0 tag and was **cancelled**, at the step that
waits for the npm package its listing points at.

Two mistakes, and the first is the embarrassing one:

**The job budget was smaller than the budget it contained.** `timeout-minutes: 10` around a poll of
`30 × 20s` — exactly ten minutes. The poll could never exhaust, so the carefully worded error
message written for "npm never appeared" was unreachable, and a slow publish ended as an
unexplained cancellation instead. *A job budget must exceed the budgets inside it, or the steps' own
error handling is dead code.*

**The budget was sized for the wrong thing.** It assumed the wait was npm propagation. The actual
timeline says otherwise:

```text
20:04:24   publish-mcp.yml starts polling npm
20:12:42   mcp-release.yml finishes publishing to npm
```

Both workflows trigger on the same tag and run in **parallel**, and `mcp-release.yml` builds and
pushes multi-arch images *before* it publishes npm. So the wait is dominated by an image build, not
by propagation — and the poll died with the package about eighteen seconds away.

Now `75 × 20s` inside a 35-minute job, sized from that measured timeline rather than from an
assumption about npm.

### What went right

The wait step itself did exactly its job. `cyberchef-mcp@3.5.0` genuinely was not on npm when the
poll ran, and the workflow **refused to publish a registry listing pointing at a version that did
not exist** — the failure mode it was written to prevent. The subsequent steps were skipped, nothing
was published, and the registry was left untouched rather than left holding a broken entry.

A gate that fails for the wrong reason while still preventing the right harm is a better outcome
than one that passes, and the fix is to the budget rather than to the check.

## F-07 — There is a layer stricter than the official validator — **FIXED**

The re-run got past the wait and was rejected by the registry itself:

```text
status 400: registry validation failed for package 0 (doublegate/cyberchef-mcp_v3):
OCI packages must not have 'registryBaseUrl' field
 - use canonical reference in 'identifier' instead (e.g. 'docker.io/owner/image:1.0.0')
```

**Neither the schema nor `mcp-publisher validate` expresses this rule.** The 2025-12-11 schema
permits `registryBaseUrl` on any package and constrains `identifier` only to `string`; the official
validator reported `✅ server.json is valid` before the publish, and still does for a document with
the offending field. Only the publish endpoint enforces it.

That is the more useful half of the finding, and it corrects something F-01 asserted. F-01's lesson
was "an official oracle beats an in-tree check". True, and incomplete — there are **three** layers,
not two:

```text
schema        what the document may contain
validate      what the official tool checks     <- what F-01 called the oracle
publish       what the registry accepts         <- the only authoritative one
```

`mcp-publisher validate` is a better oracle than a hand-transcribed checker and it is not the
authority. The only way to learn a publish-time rule is to publish, which is precisely why the rule
is now written down in a gate rather than left to be rediscovered.

### The fix

An OCI `identifier` is a canonical reference carrying the tag, and the entry therefore has no
`registryBaseUrl` and no `version`:

```json
{ "registryType": "oci", "identifier": "ghcr.io/doublegate/cyberchef-mcp_v3:3.5.0",
  "transport": { "type": "stdio" } }
```

Both gates learned the rule. `check-server-json.mjs` asserts that an OCI package has no
`registryBaseUrl` and that its identifier is a canonical reference, with two fixtures — one for each
half, each a document this repository actually shipped. `check-version-consistency.mjs` now asserts
the **tag** of the OCI identifier, which is a stronger claim than the major it checked before, and
stops requiring a `version` field that is now legitimately absent.

### What went right, again

Nothing was published. The registry rejected the document rather than accepting a malformed entry,
and the `Confirm the listing is live` step never ran because the publish failed first. Two failed
attempts, and the registry's state is still exactly what it was — which is the property that makes a
failed release cheap.
