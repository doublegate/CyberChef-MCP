Written during development, in the order the findings arrived. F-01 states what the charter got
wrong before any code, per [`docs/planning/v3/RE-MEASURE.md`](../planning/v3/RE-MEASURE.md).

## F-01 — The charter is right, and the strongest evidence for it is external and was not in it

Eight releases have opened this log by finding the plan wrong. This one mostly does not, which has
not happened before and is worth stating plainly rather than dressing up. The headline measurement
reproduces, all four navigation claims hold, and the design is unchanged. What the ritual did find
is a **published external measurement that reframes the charter's own kill criterion**, and four
smaller corrections.

### The measurement, re-run first

`npm run measure:surfaces`, through a real MCP client, 2026-09-11:

```text
surface     tools      bytes
index         41      44968      <- charter says 44,968.  MATCHES
curated      119     108214      <- charter says 108,214. MATCHES
all          544     425372      <- charter says 425,372. MATCHES
```

The crossover arithmetic therefore stands, including the `1.01x` correction made during review of
the plan itself.

### Correction 1 — the index split is off, and the two errors cancel

The charter breaks the index into navigation and registry bytes. Measured through a client, with
registry tools identified from `buildRegistry()` rather than by name pattern:

| | charter | measured | delta |
|---|---|---|---|
| registry tools (19) | 30,663 | **30,683** | +20 |
| navigation + meta (22) | 14,305 | **14,276** | -29 |
| total | 44,968 | 44,968 | 0 |

The total is exact and both parts are wrong, in opposite directions, by amounts that nearly cancel.
That is the most dangerous shape for a wrong number: every check that looks at the total passes.
Average registry tool is **1,615 bytes**, not 1,614.

### Correction 2 — all four navigation claims hold, but two survived a bad probe first

Verified through a real client against `pqc_identify`:

| Path | Charter says | Measured |
|---|---|---|
| `cyberchef_search` | finds it | **TRUE** — separate `analysis_tools` array with a summary |
| `cyberchef_describe_operation` | refuses | **TRUE** — *"is a registry tool, not an operation … Its full schema is already in `tools/list`"* |
| `cyberchef_bake` | cannot run it | **TRUE** — `Unknown operation: pqc_identify` |
| `cyberchef_categories` | does not mention it | **TRUE** — 16 categories, all operation categories, none analysis |

Recorded because it nearly went the other way: the first probe passed `operation:` (singular) to
`describe_operation`, whose parameter is `operations:`, and got an `INVALID_INPUT` that looked like
the expected refusal but was a different refusal entirely. The same probe tested `categories` with
a regex that matched the word "analysis" in its `usage` text rather than in a category name, and
reported the charter wrong. **Both charter claims were right and my instrument was wrong**, in
opposite directions, within one run. A probe that produces the expected answer for the wrong reason
is worse than one that fails.

### Correction 3 — the local Node is below the floor this project declared one release ago

```text
node on PATH   v24.21.0     <- fnm default
engines        >=26 <27     <- set by v4.0.0
/usr/bin/node  v26.8.1
```

v4.0.0's entire premise was that floor and ceiling one major apart means **one runtime to test, and
it is the one that ships**. The default shell here does not run it. Every command in this session
before this finding ran on 24. Nothing broke, which is precisely why it would not have been
noticed: the failure mode is a v26-only API passing review because it was never executed. All
verification for this release runs on `/usr/bin/node` (26.8.1), and CI tests 26 regardless.

### Correction 4 — there is a fifth closed progressive-discovery SEP

The charter lists four (SEP-1862 closed unmerged, SEP-1928 dormant, SEP-1300 rejected, SEP-1881
closed). **SEP-1888, "Progressive Disclosure for Typed Library Discovery & Introspection"**, filed
2025-11-24, is also **closed**, with `Sponsor: TBD` and no maintainer commitment.

It does not weaken the charter, it strengthens it — and it is worth reading rather than counting,
because its proposed shape is a `<library>.searchTools` meta-tool with an operations mode and a
types mode. That is, independently, the design in this charter: search finds the tool, a second
call fetches its schema, a dispatcher runs it. **Five attempts, five closed, and the fifth
converged on the same answer this charter reached.**

### The finding that matters — the kill criterion is refuted by published measurement

The charter's second kill criterion is:

> **Measured model behaviour degrades.** If a tool behind one extra hop is materially less likely to
> be used when it should be, the index cost was buying something real.

Written as a risk this release runs. Anthropic's Tool Search Tool documentation measures the
opposite, and measures it on the exact axis:

> Claude's ability to pick the right tool **degrades once you exceed 30–50 available tools**.
> Because tool search loads only a focused set of relevant tools on demand, selection accuracy
> stays high even across thousands of tools.

**This server's index is 41 tools. That is inside the band.** The status quo is the degraded
condition, and v4.1.0 moved below it -- **23 tools shipped**, against a projection of 22. The kill criterion is not merely
unlikely to fire; the evidence points the other way, and the release that does nothing is the one
carrying the measured risk.

Two further points from the same source, both checkable:

- **It does not replace this work, and the reason is one sentence:** *"You still send every tool's
  full definition in the `tools` array on every request, including the deferred ones."* Tool Search
  is a **context-window** optimisation. The bytes still cross the wire. `tools/list` cost is
  untouched by it, on every client, which is the cost this charter measures.
- **It is a Claude-platform feature, not an MCP one.** For MCP specifically, deferral is set on the
  `mcp_toolset` entry, whole-server by default — a *client* decision this server cannot make or
  rely on. A server that needs a smaller surface has to produce one.

Incidental confirmation of an unrelated decision: the same page advises *"Use consistent namespacing
in tool names: prefix by service or resource … so one search matches the whole group."* The
`cyberchef_` prefix, whose removal was announced in v1.8.0 and **withdrawn in v2.0.0**, is that
recommendation. The withdrawal is now externally supported rather than merely defended.

### Ecosystem search (ritual step 3)

`npm search` for the thing about to be built:

| Package | What it is | Why it is not this |
|---|---|---|
| `mcpflow-router` | *"MCP tool router with smart-search and on-demand loading"* | A **proxy between client and servers**. Solves the aggregation case, not the single-server case, and adds a hop this server would not control |
| `@mcpfusion/skills`, `@vurb/skills` | Agent Skills over MCP, *"progressive disclosure (search → load → read)"* | Distributes skills, not a server's own tools |

The pattern is validated by the ecosystem and the implementations are all **out-of-process
aggregators**. Nothing here is adoptable in-server, and nothing to vendor.

### SDK source, read rather than its changelog (ritual step 2)

`@modelcontextprotocol/server` **2.0.0 is current on npm and is what is installed** — no newer
release to adopt. It declares a `listChanged` capability flag and provides **no** tool-resolution,
tool-search, dynamic enable/disable, or dispatcher mechanism. Grep for `tools/resolve`,
`toolResolve`, `removeTool`, `updateTool` returns nothing. Building this in-server remains the only
route, which is what the charter says.

### Scope decision

**Unchanged, and v4.1.0 is correct under SemVer.** Registry tools leaving `index` changes what
`tools/list` returns at the default surface, which is observable — but every one of them stays
reachable, by name, through `cyberchef_analyse`, and `CYBERCHEF_TOOL_SURFACE=curated|all` continues
to list them outright. Nothing is removed and no call that worked stops working, so this is
additive: MINOR, not MAJOR. The bar v4.0.0 set for a major was **T-13**, surface advertised to
callers describing a migration that has completed or been withdrawn. Nothing here meets it.

## F-02 — The charter's crossover is arithmetically impossible, and a natural experiment proved it

F-01 said the charter survived largely intact. Building the Sprint 1.1 ceiling gate disproved its
central claim within the hour, and the disproof was accidental: the gate was being verified the way
this project requires — by reintroducing the real defect — and the defect refused to reproduce.

### The claim

> At **59 total registry tools the index costs more than `curated`**.

This figure reordered the entire v4 line. It is why v4.1.0 exists, why the tool programme was given
a prerequisite, and it appears in the charter, `v4.x-plan.md`, `DECISION-GATES.md`, two phase
to-dos and `AGENTS.md`.

### The experiment

Forty synthetic registry tools were injected to make the gate fail. The headroom half failed as
designed. **The ordering half did not fail**, so the surfaces were measured directly:

```text
              index     curated       all     curated - index
before        44,968    108,214   425,372          63,246
after +40    121,408    184,654   501,812          63,246
delta        +76,440    +76,440   +76,440               0
```

Every surface grew by exactly the same 76,440 bytes. **The gap is unchanged to the byte.**

### Why, and it is one line of code

`handleListTools` builds registry tools with this comment already attached:

> *Always exposed, regardless of `CYBERCHEF_TOOL_SURFACE` — that setting exists to keep 504
> operation schemas out of the default payload, and there are a handful of these.*

Registry tools are on **every** surface. `CYBERCHEF_TOOL_SURFACE` selects how many *operation*
schemas to pre-load and has never governed registry tools at all. So adding one grows `index`,
`curated` and `all` equally, and `curated − index` is a constant determined solely by the 79
curated operation schemas.

**The index cannot cross `curated` by adding registry tools. Not at 59, not at 590.** The crossover
table projected a growing index against a frozen `curated`, when both move together.

### What this does and does not invalidate

Dead:

- "at 59 registry tools the index costs more than `curated`" — impossible;
- the `+20 / +40 / +80 / +120` crossover table, every row;
- "the ext-proj-int ceiling is 59 tools" — there is no such ceiling;
- the `1.01x` correction made to that table during review of #135. That was a real arithmetic
  error inside a table that should not exist. Fixing a number in an invalid table is the most
  convincing kind of wrong, and it passed a full bot-review ceremony and a merge.

Alive, and the reason this charter still ships:

- **19 registry tools are 30,683 of the index's 44,968 bytes — 68%.** Measured, unchanged, and the
  real finding all along.
- **Absolute growth is severe.** At the measured 1,615 bytes each, the `ext-proj-int` programme's
  80–120 further tools puts the index at roughly **174k–239k bytes** — not "more than curated", but
  four to five times what it costs today, on the surface whose entire purpose is being small.
- **The tool-count argument is stronger than the byte argument and was not in the charter.** F-01
  found Anthropic measures tool-selection accuracy degrading past **30–50 tools**. The index is
  **41**. Adding 80 registry tools makes it 121 — and unlike the byte crossover, this one applies
  to `curated` and `all` as well, because the tools are on every surface.

### The correct framing

The charter asked "when does the index stop being cheaper than the preset?" — which has no answer,
because the comparison is between two quantities that move together. The question with an answer
is: **what does the index cost in absolute terms, and how many tools does it list?** On both, the
registry tools are 68% of the problem and do not need to be there.

v4.1.0's scope is unchanged. Its justification is now a measurement instead of an arithmetic error,
and the ceiling gate is rewritten around a figure that can actually move.

## F-03 — The gate that had to be rebuilt, and the one leak it exposed

### The gate

Sprint 1.1's ceiling gate was built, verified-by-defect, and **deleted the same hour** because the
defect it was written to catch cannot occur (F-02). What replaced it asserts properties that can
actually move:

| Assertion | Fails when |
|---|---|
| `index` lists no registry tool | one leaks back onto the default surface |
| `curated` and `all` list every one | the gate is "satisfied" by deleting tools |
| `index` stays under 30 tools | the surface re-enters the measured accuracy-degradation band |
| `index` < `curated` | kept, but stated correctly: about operation schemas, carrying no projection |

Two of the four failed when written, which was the specification for sprints 1.2–1.4.

### The leak, which is the more interesting half

`tests/mcp/auth.test.mjs`'s `callTool` helper opened an HTTP session per call via `initialize` and
never closed it. `CYBERCHEF_MAX_SESSIONS` defaults to **100**.

The dispatcher authorisation tests are the first in this file to loop over every registry tool —
19 tools x 2 directions, twice — which pushed it past the cap. The symptom was not a capacity
error where the calls were made. It was **`-32001 Session not found` on an unrelated assertion
several tests later**, which read exactly like an authorisation failure in the feature under
development.

Two things worth keeping from it:

1. **A leak with a threshold is invisible until something crosses it.** The helper has leaked since
   it was written. Nothing was wrong with the tests that exposed it; they were simply the first to
   be large enough.
2. **The fix was already documented by the thing being tested.** The server's own capacity message
   reads *"Retry later, or close an idle session with DELETE"* — the helper now does exactly that.
