# v3.11.0 findings log

Written during development, in the order the findings arrived. F-01 states what the plan got wrong
before any code.

---

## F-01 — The charter asked for v4.2.0; v4.1.0 was already shipped, and Node can do most of the work

Two findings, one about scope and one that changes how the work is built.

### The charter sequence had already moved

The request was to develop **v4.1.0**. Its charter is complete: both items are on `master` and
verified by content, not by filename —

```text
main-module guard (isEntryPoint)          present
regression test (entry-point.test.mjs)    present
four teardowns restored                   present
pipeline race (sibling_state)             present
```

— and the charter's own banner already records that it shipped as **v3.10.0**. So this release
executes the next live charter, [v4.2.0](../planning/v4/charters/v4.2.0.md), the `ext-proj-int`
programme. It ships as **v3.11.0** for the reason F-01 of the previous release gives: the v4 numbers
are a reading order, and a v4 charter executed before v4.0.0 lands as a v3 minor.

### The gap is real, re-measured

```text
operations matching kyber|dilithium|sphincs|ml-kem|ml-dsa|slh-dsa|falcon|lattice|post-quantum: NONE
total operations: 504        registry tools: 18
```

Zero of 504. A toolkit that covers RSA, ECDSA, DSA and EdDSA and not the NIST post-quantum standards
has a gap a user will meet.

### **Node 24 already implements them, and that changes the build**

The ritual's step 2 is "read the dependency's source, not its changelog", and step 3 is "search the
ecosystem for the thing you are about to build". Both paid here:

```text
generateKeyPairSync("ml-dsa-44")        SUPPORTED
generateKeyPairSync("ml-kem-1024")      SUPPORTED
generateKeyPairSync("slh-dsa-sha2-128s") SUPPORTED
```

Node's own `crypto` generates all eighteen parameter sets. That matters twice over:

1. **Fixtures are real.** Every test key and signature in this release is generated by Node rather
   than hand-assembled, so the tool is tested against bytes a real implementation produced.
2. **The identification table is measured, not cited.** Every OID and size below was extracted from
   a key Node generated, then cross-checked against the published FIPS figures. They agree.

### The table, derived rather than quoted

| Algorithm | OID | raw public key | signature / ciphertext |
|---|---|---|---|
| ML-DSA-44 / 65 / 87 | `…3.4.3.17` / `.18` / `.19` | 1312 / 1952 / 2592 | 2420 / 3309 / 4627 |
| ML-KEM-512 / 768 / 1024 | `…3.4.4.1` / `.2` / `.3` | 800 / 1184 / 1568 | ct 768 / 1088 / 1568 |
| SLH-DSA (12 sets) | `…3.4.3.20` … `.31` | 32 / 48 / 64 | 7856 … 49856 |

**Two ambiguities that the tool must report rather than resolve**, both found by looking at the
numbers rather than by reasoning about them:

- **ML-KEM-1024's encapsulation key and its ciphertext are both 1568 bytes.** Length alone cannot
  tell a public key from a ciphertext for that parameter set.
- **SLH-DSA public keys are 32, 48 or 64 bytes** — the same lengths as a SHA-256, SHA-384 or SHA-512
  digest, and as an Ed25519 key. Length alone is worthless there; only an OID identifies them. And
  the `sha2` and `shake` families share every signature size (7856 for both 128s variants), so a
  raw signature gives the parameter set but **not** the hash family.

A tool that answered those from length would be confidently wrong, which is the failure
`cert_chain` shipped with in v3.8.0 and had to be corrected for.

### The first extraction was wrong, and looked right

The OID table was first pulled with a byte scan for the `0x06` tag inside the first 40 bytes of the
SPKI. It produced correct answers for five of six algorithms and this for the sixth:

```text
ml-kem-1024   1.8.11.6.9.96.840.1.101.3.4.4.3.3.262.33.0.2348.414852...
```

A `0x06` byte inside a length field, read as a tag. Five plausible results and one obviously absurd
one is a lucky failure mode — had the sixth also been plausible, a wrong OID would have shipped.
Replaced with a real DER walk (`SEQUENCE` → `AlgorithmIdentifier` → `OBJECT IDENTIFIER`), which
agrees with the published values for all eighteen.

## F-02 — Four gates caught the release, and the one I had not anticipated was the strongest

Adding one registry tool moved five documented figures — the registry-tool count, the three surface
tuples, and coverage. **Four** gates fired between them, and each named its own fix rather than only
its fault:

```text
registry-tool-docs       19 expected, 18 found, in 7 documents; 4 inventories missing the name
tool-surface-figures     table says 42/44,493, server serves 43/45,813
stdio-client-contract    a registry tool with no client-driven call fixture
test:coverage            statements 94.99% against a threshold of 95
```

The third entry is the one worth recording, because it was the only one I had not expected to fire.
`stdio-client-contract.test.mjs` derives the expected fixture list **from the live registry**, not
from the fixture table beside it — its own comment explains that an earlier version compared the
table against itself, which is an identity and could not fail. That is the only reason a new tool
with no client-driven call was caught at all, and it is the difference between a check and a
tautology.

`registry-tool-docs` earned its keep the same way: it **discovers** which documents behave as
inventories rather than listing them, so it named `docs/guides/commands.md` — a file no part of my
plan mentioned.

## F-03 — The thin coverage margin was hit on the very next release

v3.10.0 measured statements at 95.06% against a threshold of 95 and wrote down that the margin was
thin, that it would be tripped, and what to do when it was: cover `mcp-server.mjs`, do not move the
bar. The margin lasted exactly one release.

```text
before   94.99 statements   FAILS the 95 threshold
after    95.13 statements   exit 0
```

The deficit was not `mcp-server.mjs` and not anything old: it was the new tool. `pqc-identify.mjs`
measured **91.39% statements against 98.64% lines**, and that gap is the diagnosis. Nearly every
line ran; what did not run were the parser's *rejection* paths and the explicit-format branches —
a truncated TLV, a PKCS#8 version INTEGER with nothing after it, an `AlgorithmIdentifier` whose
first element is not an OID, an OBJECT IDENTIFIER with an empty body, and `input_format` set to
anything but `Auto`.

Those are exactly the paths where a parser invents an answer. The first version of this tool's OID
extraction *did* invent one. So the tests were owed regardless of coverage, and writing them found
a real defect:

**The tool threw a bare `Error` where every other registry tool throws `createInputError`.** Same
class of mistake, two different shapes on the wire — one carrying the `INVALID_INPUT` code and the
offending field, one carrying an untyped string. Fixed, and pinned by a test that asserts the code
rather than the message.

*A coverage threshold that is calibrated against a true number tells you where you did not look.
This one did, on the first opportunity it had.*
