# v3.10.0 findings log

Written during development, in the order the findings arrived. F-01 states what the plan got wrong,
before any code.

---

## F-01 — This is v3.10.0, not v4.1.0, and the charter's own name hid that

The work in this release is the [`v4.1.0` charter](../planning/v4/charters/v4.1.0.md). The release
it ships in is **v3.10.0**, and the reason is arithmetic the charter directory never stated.

`docs/planning/v4/v4.0.0-plan.md` concludes — on a measurement repeated at the start of this release
— that **v4.0.0 must not be cut**:

```text
draft changelog     EMPTY ("Changes since the most recent release will accumulate here.")
current revision    2026-07-28, no successor
SDK                 @modelcontextprotocol/{server,node,client} all 2.0.0
conformance         0.2.0-alpha.11
server.json schema  2025-12-11 still newest; every 2026-* date 404s
```

All four of v4.0.0's triggers are unfired, so its kill criterion fires instead.

**But `4.1.0` cannot precede `4.0.0`.** A charter directory numbered `v4.1.0 … v4.9.0` quietly
assumes the major it explicitly tells you not to cut. The numbering was a reading order — the
directory's README says exactly that — and it still read as a schedule the moment someone executed
one. That is the same failure the whole directory was shaped against, in the shape of a filename.

So: the charter's **content** ships, as **v3.10.0**. v2.x ran to eleven minors; v3.x now runs to
eleven too, which the ROADMAP treats as evidence of health rather than drift.

**Corrected in the charters rather than left for the next reader.** Each `v4.x` charter now carries
a banner: the number is an ordering, the release it lands in is decided at execution time by
SemVer, and a v4 charter executed before v4.0.0 ships as a v3 minor.

### Scope, re-measured before building

| Item | Claimed | Measured now |
|---|---|---|
| `runServer()` runs on bare import | F-13, v3.9.0 | **True.** Importing the module in a bare script emits 3 startup log lines. |
| Four test files leak a temp directory to survive it | F-13 | **True.** `rate-limit-dispatch`, `prompts-resources`, `in-process-handlers`, `tenancy` all still carry the "NOT removed, deliberately" workaround. |
| The release pipeline races itself | v4.1.0 charter, second item | **True, and it cost this project a release.** `publish-mcp.yml` waits 25 minutes for an npm publish that is the *last step* of a job whose median is 9 minutes but whose tail is unbounded — v3.9.0's build hung twice at 33 minutes. |
| The trigger watch is manual | `to-dos/00-PHASE-0-TRIGGER-WATCH.md` | **True.** Twelve checks, all by hand, and two of them (T-11, T-12) were missing until the day after the file was written. |

Nothing in the charter was already built, which makes this the first release since v2.5.0 where F-01
does not open by deleting scope.

## F-02 — The coverage figure was partly the defect executing itself

Fixing the entry point dropped coverage below the gate:

```text
before   96.56 lines / 89.61 branches / 96.6 functions / 95.53 statements   (v3.9.0)
after    95.91 lines / 89.08 branches / 96.48 functions / 94.94 statements   FAILS 96/89/96/95
```

Nothing was deleted and no test was removed. The cause is that `runServer()` used to be invoked on
**every test import** — that was the defect — so its body and its `catch` counted as covered in
every run. About **0.6% of this project's line coverage was the bug running itself.**

The thresholds were therefore calibrated, in part, against a number the defect inflated.

### Fixed honestly, not by lowering the bar

Two changes, neither of which is "adjust the threshold":

1. **`isEntryPoint` is exported and unit-tested in-process** — six cases covering the decision
   rather than the spawn: argv[1] as the module, as a symlink, as a relative path, as another file,
   absent entirely, and pointing at something that does not exist.
2. **The invocation block is marked `/* v8 ignore */` with the reason.** It *is* exercised — by
   `entry-point.test.mjs`, in child processes, which is the only way to observe a module's
   import-time behaviour once the worker has already imported it. v8 instruments the vitest worker
   only, so those runs are invisible to it. The file already uses this marker for signal wiring, so
   the convention is established rather than invented here.

```text
after the fix   96.02 lines / 89.13 branches / 96.6 functions / 95.06 statements   exit 0
```

**The margin is thin and that is worth saying out loud**: statements clear the gate by 0.06 and
lines by 0.02. A future change of any size may trip it. The right response when that happens is to
cover `mcp-server.mjs` (81.5% statements, and the file `vitest.config.mjs` already names as carrying
the deficit), **not** to move the threshold — the threshold is now calibrated against a figure that
is true, which it was not before.

## F-03 — Three self-inflicted false greens while building the fix

Recorded because each is the same shape as the defects this line of work keeps finding, and because
two of them passed while the code was wrong.

| # | What | Why it looked right |
|---|---|---|
| 1 | The test helper used `execFileSync` | It surfaces stderr **only on a non-zero exit**, and this server logs to stderr by design — stdout is the JSON-RPC channel. The headline test asserted on output it was discarding, and **passed while the defect was present**. |
| 2 | The same test asserted `runServer` and `serveStdio` were exported | Neither is. It **failed against correct code** until the export list was actually read, which is the mirror image of 1. |
| 3 | The first teardown restoration searched for an indented `});` | The top-level `beforeAll` closes at column 0, so the new `afterAll` landed **inside the first `describe`** and deleted the storage directory while five later describes were still using it. Tests passed; `/tmp` still leaked 2 directories per run, which is how it was caught. |

Number 3 is the useful one: the tests passing was not evidence, and counting `/tmp` before and
after was. **40 → 42 became 40 → 40.**

## F-04 — `fetch()` of the specification site returns an error shell

The trigger watch fetches two pages from `modelcontextprotocol.io`. A plain `fetch` of the HTML
route returns a Next.js/Mintlify **error shell** — `<html id="__next_error__">` — not the page. The
regex therefore matched nothing.

The first version of the script printed that as:

```text
  --   T-2   a revision after 2026-07-28 is Current   current revision is unparsed
```

`--` is the same mark it prints when the page says nothing has changed. **Cannot measure** and
**nothing changed** are different facts, and only one of them is reassuring.

Both are fixed: the `.md` routes (which 307 to the real markdown, and `fetch` follows redirects),
and an unreadable page now **throws** with exit code 2 rather than recording a miss. All three exit
codes — 0 nothing fired, 1 fired, 2 could not measure — were verified by simulation rather than
assumed.

## F-05 — I wrote a fixed-budget flake into the test that proves the fix

The first full-suite run after adding `entry-point.test.mjs` failed one test. The second passed.
An intermittent failure is worse than a consistent one, so it was worth finding rather than re-running.

The cause was mine, and it is the same mistake this project has spent three releases finding in
other people's code. The two child-process tests spawned a server and then **slept a flat 12
seconds** before checking for `Running on stdio transport`. `vitest.config.mjs` records, in a
comment written for exactly this hazard:

> Booting a suite's server builds the tool surface over 504 operations, which on this machine lands
> at **9.5-10s** for the heavier files.

A two-second margin against a ten-second boot, in a suite that runs files in parallel. That is not a
flaky test, it is a **race with a coin-flip outcome** — the same shape as `publish-mcp.yml`'s
25-minute budget against an unbounded build, which this very release fixed two commits earlier.

Replaced with polling for the marker, capped at 60 seconds. Both tests went from **12,050ms to
534ms** — 22x faster *and* reliable, because a poll exits when the thing happens rather than when
the clock says it probably has.

Two full-suite runs at 1725/1725 after the change.

**The general form, since this keeps recurring**: a fixed wait encodes an assumption about how long
something takes, and every such assumption is a bet that gets re-rolled on every run, on hardware
nobody controls. Poll for the condition, and bound the poll.
