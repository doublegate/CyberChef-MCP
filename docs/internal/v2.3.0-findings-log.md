## F-01 - npm publishing was blocked by a broken dependency, not by packaging - **FIXED**

**Found:** picking up v2.2.0's F-14, which deferred npm publishing because
`npm 12 blocks dependency install scripts by default`, and this project needed one. The deferral was
right; the diagnosis stopped one level short of the cause.

**Actually wrong, and it is worse than "needs a postinstall".** `crypto-api@0.8.5` - the latest
published version - **cannot be loaded as published**, in two independent ways:

1. Its `package.json` declares `"main": "index"`, and the tarball contains **no `index.js`**. The
   `files` allowlist names `index.js`, `index.min.js` and `index.min.js.map`; none were ever
   included. `require("crypto-api")` fails outright, so there is no bundle to fall back on.
2. Its ESM sources use **extensionless relative imports** (`from "./hasher/has160"`), which Node's
   resolver rejects, so `import "crypto-api/src/crypto-api.mjs"` dies on the first transitive
   import.

Upstream CyberChef works around (2) by rewriting the specifiers inside `node_modules` from
`postinstall`. That is fine for a checkout and impossible for a published package. So the blocker
was never packaging: it was a dependency that has to be patched to be usable at all.

**Fixed by removing the need for the patch.** `crypto-api` is vendored at `src/vendor/crypto-api/`
(MIT, 24 files, 224 KB, byte-identical apart from appending `.mjs` to relative specifiers in 16 of
them), the seven `src/core/**` importers are repointed at it by
`patches/fork/08-crypto-api-vendored.patch`, and the `crypto-api` step is gone from
`scripts/patch-dependencies.mjs`. Provenance, the exact modification, and the condition for deleting
the tree again are in `src/vendor/crypto-api/README.md`; the licence row is in
`THIRD-PARTY-NOTICES.md`.

**A second blocker, found only because the first was fixed: `terser` was a devDependency.**
`src/core/operations/JavaScriptMinify.mjs` imports it statically and `src/node/index.mjs` imports
every operation, so it is a hard runtime requirement. It survived as a devDependency because
upstream bundles the web app with webpack and never ships `src/core` unbundled - this fork does.
Moved to `dependencies`. A scan of every bare import in `src/{core,node}` found no other case.

**Verified end to end, not asserted.** `npm pack`, then `npm install --ignore-scripts` of the
tarball into an empty project on npm 12.0.2, then the installed `cyberchef-mcp` binary over stdio:
`initialize` returns `cyberchef-mcp 2.2.0`, `cyberchef_md5("abc")` returns the canonical digest, and
a `SM3 -> To Upper case` recipe - which runs through the vendored crypto-api - returns the canonical
`66C7F0F4...`. That is the exact path that failed before, with the exact error F-14 recorded.

**The method is the transferable part.** F-14 was found by packing and installing rather than by
reading `package.json`; F-01's second blocker was found the same way, one layer down. A package
manifest that looks correct says nothing about whether the package runs.

## F-02 - 17 image operations returned Node's shared buffer pool, not the image - **FIXED**

**Found:** the F-01 consumer probe called `Generate QR Code` and an image filter to check that
nothing else was missing from the published tarball. The filter failed with `Invalid file type.` -
and then failed identically on the local tree, so it was never a packaging problem.

**Actually wrong.** Every one of these operations ended `run()` with

```js
return imageBuffer.buffer;
```

where `imageBuffer` is a Node `Buffer`. A `Buffer` is a **view**: for a small allocation Node hands
back a window into a shared pool, so `.buffer` is not the image. Measured directly:

```text
Buffer  length 70   byteOffset 32
backing ArrayBuffer byteLength 65599
first 8 of buf        : 137,80,78,71,13,10,26,10     <- the PNG
first 8 of buf.buffer : 72,18,133,107,250,127,0,0    <- whatever else was in the pool
```

Two consequences, and the second is the serious one:

- **The image is unreadable.** `present()` does `new Uint8Array(data)` from offset 0, `isImage()`
  finds no magic bytes, and the operation throws `Invalid file type.` The throw is in the
  **presenter**, after `run()` has already succeeded, which is why the message points nowhere near
  the cause and why this survived so long.
- **The surplus 65 KB is other allocations.** It is whatever the process most recently placed in
  that pool. On a server handling more than one caller - which is what this project is - that is
  other callers' data, returned verbatim to whoever asked for an image. This is an information
  disclosure, not only a correctness bug.

**This is upstream's defect, and upstream has already ruled on it.** `GenerateImage.mjs` carries

```js
// see https://nodejs.org/docs/latest-v24.x/api/buffer.html#bufbyteoffset
// for why we can't just return result.buffer
return result.buffer.slice(result.byteOffset, result.byteOffset + result.byteLength);
```

so the fix is upstream's own, applied to one operation and not to the 17 siblings.
`lib/QRCode.mjs` and `BSONSerialise.mjs` slice correctly too - which is why QR codes worked in
v2.2.0 while every image *filter* did not.

**Fixed** by `patches/fork/09-image-ops-return-pooled-buffer.patch`, which applies upstream's own
form to all 17 sites: `AddTextToImage`, `BlurImage`, `ContainImage`, `ConvertImageFormat`,
`CoverImage`, `CropImage`, `DitherImage`, `FlipImage`, `ImageBrightnessContrast`, `ImageFilter`,
`ImageHueSaturationLightness`, `ImageOpacity`, `InvertImage`, `NormaliseImage`, `ResizeImage`,
`RotateImage`, `SharpenImage`.

**Scope was measured, not assumed.** Every other `return <var>.buffer` in `src/core` was probed by
running the operation and counting output bytes: `Gzip` 41, `Raw Inflate` 11, `LZ4 Compress` 26,
`LZ4` round trip 11, `Drop bytes` 5, `Bit shift left` 11, `AMF Encode` 14. All exact. Those build
their own typed arrays, so `byteOffset` is 0 and the backing store is the right size; only the
jimp-backed operations receive a pooled `Buffer`. The defect is exactly 17 operations wide.

**Pinned** by `tests/mcp/image-operations.test.mjs` (19 tests): all 17 operations over the MCP path
must yield an `image` content block whose payload carries real magic bytes and is under 8 KB, plus
two assertions at the operation boundary - that `run()` returns an ArrayBuffer sized to the image,
and that `present()` accepts what `run()` returned.

**Worth reporting upstream** together with the existing list in issue #73.

## F-03 - `Add Text To Image` had never worked in this fork - **FIXED**

**Found:** it was the one operation in F-02's new test that still failed after patch 09, with
`Error preparing fonts. (Cannot find module '/src/web/static/fonts/bmfonts/RobotoBlack72White.fnt')`.

**Actually wrong.** The operation loads four bitmap fonts through webpack-only `import()` of
`.fnt`/`.png` under `src/web/static/fonts/bmfonts/`, then builds an absolute URL from
`self.docURL`. This fork **removed `src/web/` in v1.7.1** and runs under plain Node, where neither
the webpack loader nor a document URL exists. So the operation failed on every call, in every
release since v1.7.1, while remaining advertised in `tools/list` - the same shape as v2.2.0's F-05:
a capability the server offers and cannot deliver.

Restoring the assets alone would not have fixed it. Node cannot `import()` a `.fnt`, and there is
still no `self.docURL` to resolve against.

**Fixed** by vendoring the four fonts and their page atlases at `src/vendor/bmfonts/` (Apache-2.0,
© Crown Copyright, rendered from Roboto/Roboto Mono/Roboto Slab, also Apache-2.0; 324 KB) and by
`patches/fork/10-add-text-to-image-node-fonts.patch`, which replaces the import block with a
face-to-filename map and calls `loadFont(<path to the vendored .fnt>)`. jimp accepts a filesystem
path in Node and resolves each font's page atlas relative to its descriptor.

**Verified** by rendering: an 8x8 fixture resized to 200x60 with "CHEF" centred in Roboto Black
comes back as a 7,669-byte PNG with the text legibly drawn.

## F-04 - The SDK v2 migration is far smaller than the plan assumed - **FIXED**

**Found:** starting plan PR 6b, which the plan itself calls "the second-largest technical risk after
PR 6" and which budgets a rewrite of the two `setRequestHandler` callbacks into per-tool
`registerTool` registrations.

**What the plan got wrong, measured against the published packages rather than inferred.** Three
corrections, in increasing order of how much work they save:

1. **`LATEST_PROTOCOL_VERSION` is 2025-11-25 in *both* generations.** SDK v2's exported constant and
   `SUPPORTED_PROTOCOL_VERSIONS` are identical to legacy 1.30.0's. Read on its own, that says the
   migration buys no protocol currency at all. It is misleading: revision 2026-07-28 is not in that
   list because it is not negotiated through `initialize`. It is reached through a per-request
   `_meta` envelope claim and a `server/discover` probe, and the constant only ever described the
   legacy handshake.
2. **`registerTool` is not required to reach the modern era.** The low-level `Server` -- the API
   this server already uses -- carries `_ondiscover` and serves 2026-07-28 perfectly well. Proven
   with a spike: the same low-level server answered a v2 client pinned to 2026-07-28 *and* a v1-SDK
   client on 2025-11-25. So the `registerTool` rewrite is a separate, optional refactor for
   testability, not a prerequisite for the protocol. That removes the entire "second-largest risk".
3. **The era decision lives in the entry, not the transport.** A bare `StdioServerTransport` plus
   `server.connect()` serves the 2025 era *only*: a modern-pinned client fails with
   `ERA_NEGOTIATION_FAILED` because nothing answers `server/discover`. `serveStdio(factory)`
   classifies the opening exchange and pins one instance per connection. This is the one structural
   change the migration actually needs, and no amount of reading the changelog would have surfaced
   it -- the bare-transport spike is what did.

**What the migration therefore came to.** Swap the packages; change seven `setRequestHandler` calls
from a Zod request schema to a method string (v2's signature is
`setRequestHandler(method, handler)`); route stdio through `serveStdio` instead of connecting a
transport; swap `StreamableHTTPServerTransport` for `NodeStreamableHTTPServerTransport`, whose
options are identical field for field. 977 tests pass, including the 38 HTTP-session tests and the
in-process handler suite, which drive v1-generation transports against the v2 server unchanged.

**Two things that had to be fixed to keep the tests honest.**

- **`createTransport` now returns `transport: null` for stdio**, as it already did for HTTP: there is
  nothing left for `runServer()` to connect, and connecting would bypass the entry that makes the
  modern era reachable. The two tests asserting the old shape were rewritten to assert the new one
  and to complete an actual round trip, which they never did before.
- **`serveStdio` defaults to the process's own stdin/stdout**, which a test runner must not hand
  over. `createTransport` now accepts an injected `transport`, which is also the SDK's documented
  seam for a stdio binding over a socket rather than a pipe.

- **`tests/mcp/http-transport-sessions.test.mjs` was building a v1 `Server`** and connecting it to
  the now-v2 HTTP transport. It passed -- the generations are wire-compatible -- while no longer
  testing the pairing production uses. Migrated to a v2 server.

**Pinned** by `tests/mcp/protocol-eras.test.mjs`, which spawns the real binary twice: once for a
client pinning 2026-07-28 (asserting the negotiated revision *and* the `_meta` envelope on the
result, not just that the call succeeded) and once for a v1-SDK client (asserting a populated
`inputSchema`, because an SDK swap is exactly the change that could reintroduce v2.1.0's empty-schema
regression). Both hit the same handler registrations, so the eras cannot drift apart silently.

**HTTP followed, in F-05.**

## F-05 - The modern era over HTTP, and the validation gap it opens - **FIXED**

**Found:** finishing what F-04 started. stdio served 2026-07-28; HTTP still served only the 2025
era, so the same server answered different protocol revisions depending on how you reached it.

**What was needed.** `createMcpHandler(factory, { legacy: "reject" })` serves the modern revision
per request; `isLegacyRequest` decides which leg a request belongs to. The SDK documents exactly the
shape this server already had:

```js
const probe = await toWebRequest(req, req.body);
await ((await isLegacyRequest(probe)) ? legacy(req, res) : modern(req, res, req.body));
```

which fits because the handler already reads the body once and passes it on as `parsedBody`.
Classifying from the request alone would clone an already-used body and throw, so the parsed value
is passed to both.

`legacy: "reject"` matters and is not the default. The entry will otherwise serve its own
*stateless* 2025 fallback, which would be a second, unaccounted route to the same tools -- bypassing
the session accounting, the idle sweeper and the capacity limit that the sessionful wiring has. One
factory backs both legs, so the eras cannot drift apart in what they expose.

**The security part is the part worth writing down.** The modern entry is **deliberately
validation-free** -- the SDK says so in as many words, and expects the caller to put Origin/Host
checks in front of it. The sessionful transport gets that protection from
`enableDnsRebindingProtection`, which the entry does not have. Dropping the modern leg in without
its own check would therefore have left a DNS-rebindable path to the same server, reachable simply
by adding a `_meta` claim to a request -- a hole opened by a *feature*, in a file whose whole
purpose is that the HTTP surface is safe. The same allowlist (`effectiveAllowedHosts()`) now gates
both legs, and a test forges a Host against the modern path specifically: if it ever returns 200 the
check has been lost.

**Pinned** by `tests/mcp/http-protocol-eras.test.mjs`. Two of the four cases drive a **real** v2
client over Streamable HTTP rather than a hand-built envelope -- the first attempt hand-wrote the
`_meta` claim and the entry rejected it for a missing `clientCapabilities` key, which is the useful
signal: a hand-built envelope tests my ability to construct one, not the server. The remaining two
use a minimal claim on purpose, because routing and the Host check are both decided *before* the
envelope is validated. One case asserts `sessions.size === 0` after modern traffic, because a modern
leg that quietly opened sessions would make the capacity limit count two different kinds of thing.

## F-06 - v2.3.0's own roadmap theme names a transport that does not exist - **DOCUMENTED**

**Found:** starting the last item of the Advanced Transports theme, by checking what SDK v2 offers
before writing a transport.

**Actually wrong.** The roadmap row reads "WebSocket, Streamable HTTP, SSE (deprecated)". Measured:

- **Streamable HTTP** shipped in v2.0.0 and now serves both eras (F-05). Already done.
- **SSE** (the HTTP+SSE transport of 2024-11-05) is deprecated by the specification, and SEP-2596's
  grandfathering policy makes it **eligible for removal**. Building it now would add a transport the
  spec is deleting.
- **WebSocket is not an MCP transport at all.** The specification defines stdio and Streamable HTTP
  and nothing else. SDK v2 ships no WebSocket transport in `@modelcontextprotocol/server`,
  `@modelcontextprotocol/node` or `@modelcontextprotocol/client` -- zero occurrences of the string
  across all three packages. A WebSocket transport here would be a private extension that no
  existing client could speak, which is the opposite of what a transport is for.

So two thirds of the theme is either done or actively harmful to build, and the remaining third is
not implementable as written. This is not a small correction: it is the release's headline theme.

**Disposition: DOCUMENTED, not silently dropped** -- the same rule the withdrawal of
DEP001/007/008 established in v2.0.0. `docs/planning/ROADMAP.md` now carries the corrected row and
a note giving this reasoning, so nobody re-derives it or waits for a WebSocket transport that is
not coming.

**What the theme was actually reaching for** -- transport reach beyond a local pipe -- does have a
spec-sanctioned form: the stdio binding over a Unix domain socket or TCP stream, which the SDK
documents explicitly ("a `StdioServerTransport` constructed over a Unix domain socket or TCP
stream, per the stdio binding's custom-transport guidance"). `createTransport` already accepts an
injected transport, added in F-04 for the tests, which is exactly the seam it needs. It is **not
built**, and is the obvious candidate to replace the WebSocket line.

## F-07 - The socket transport, and two things the kernel will not tell you - **FIXED**

**Found:** building the successor to F-06's dead WebSocket line.

**What it is.** `CYBERCHEF_TRANSPORT=socket` serves the stdio binding over a Unix domain socket or a
loopback TCP stream -- the SDK's own documented custom-transport route, so an existing client speaks
it with no private extension. Each connection gets its own `serveStdio` entry, which pins ONE server
instance for that connection's lifetime, so this inherits issue #36's isolation without needing
session ids: the socket *is* the session.

**Three deliberate refusals, because this transport has no authentication.** The stdio binding's
security model is "the peer already has your process". On a Unix socket that is filesystem
permissions; on TCP it is nothing at all.

- **A non-loopback TCP bind is refused** unless `CYBERCHEF_SOCKET_ALLOW_REMOTE=true`. The failure
  mode otherwise is an unauthenticated MCP server exposing 504 operations to anyone who can route to
  the port -- and the loopback check covers the whole `127.0.0.0/8` block, not just `127.0.0.1`.
- **The Unix socket is `chmod 0600`**, not left to the umask. A socket's access control *is* its
  file mode; a permissive umask would let any local user drive the server.
- **A stale socket file is probed before removal.** Existence cannot distinguish a crashed
  process's leftover from a running server or from somebody's data, so it connects first: refused
  means stale and it is unlinked; anything else, or a path that is not a socket, fails loudly.
  Deleting the wrong file here would be silent destruction.

**Two failures the kernel reports uselessly, both hit while building this.**

1. **`sun_path` is a fixed 108-byte field** (104 on macOS). An ordinary 128-character path under a
   temp directory produced a bare `listen EINVAL: invalid argument` naming the path and nothing
   else. Nothing in that message points at length. The length is now checked up front and the error
   says so.
2. **`pkill -f mcp-server.mjs` killed the shell running it**, because `-f` matches full command
   lines and the shell's own contained the pattern. That cost two debugging cycles and made a
   working smoke test look like a hang -- the server log proved the round trip had succeeded all
   along. Use a recorded PID.

**A flake that was a real fragility, found by adding these tests.** Two suites failed at *file*
level on the first full run afterwards. They were not broken: `vitest.config.mjs` set
`testTimeout: 10000` and never set `hookTimeout`, so `beforeAll` -- where a suite builds its
504-operation tool surface -- inherited the same 10s. The heaviest files sit at 9.5-9.9s on this
machine, so one more parallel suite tipped them over. A hook timeout reports as a whole-file
failure and looks nothing like "the runner was busy", which is why it read as a real break. Both
timeouts are now 30s, with the reasoning recorded in the config, and the suite ran clean twice.

**Pinned** by `tests/mcp/socket-transport.test.mjs` (12 tests), including two clients proving they
get *different* server instances -- issue #36's defect arriving by a different door -- the 0600
mode, the non-loopback refusal, the not-a-socket refusal, the live-server refusal, and the path
length.

## F-08 - A failing operation on the progress path hung the request - **FIXED**

**Found:** chasing an uncovered branch in `streaming.mjs`, lines 277-278.

**Actually wrong.** `streamOperationWithProgress` ended its bake with

```js
bakeFunction(input, recipe).then(result => { clearInterval(interval); resolve(result); })
                           .catch(err => { clearInterval(interval); throw err; });
```

`throw` inside the `.catch` callback of a promise nobody holds does two things, neither visible from
reading it: the rejection is **unhandled**, and `resolve` is **never called**, so the `await
progressPromise` two lines below waits forever. A failing operation on the progress path therefore
hung the request until its timeout instead of reporting the error.

Not dead code: `streaming.mjs:374` and `:489` route progress-capable operations straight into it.

**The existing test documented the defect without recognising it.** `tests/mcp/streaming.test.mjs`
carried the comment *"Create a mock that throws synchronously to avoid unhandled promise
rejection"* -- a test written around the bug. A real `bake` is async and **rejects**; it does not
throw synchronously. The one case that mattered was the one the test avoided.

**Fixed** by rejecting rather than throwing, with the rejection handler as `then`'s second argument
rather than a chained `.catch`, so it cannot observe an error thrown by the fulfilment handler and
settle twice.

**Proved, not assumed.** Against a snapshot of the old code the new test **times out at 30s**;
against the fix it passes in 6ms. That is the hang, measured.

## F-09 - The coverage gate could not fail, and two files hid behind ten - **FIXED**

**Found:** plan PR 6c.

**Actually wrong.** Thresholds were `75/70/90/75` while actual coverage was `93.5/84.7/93.0/94.4`.
A gate set twenty points below actual cannot fail, which is the same as not having one -- and
`codecov.yml` was worse: `project.target: 70%`, `patch.target: 75%`, `range: 70..90`, so a 94%
project painted solid green with nothing left to aim at.

**What was done.**

- Tests for the reachable gaps, not tests for the number: the toggleString and argSelector schema
  branches, `resolveArgValue`'s option correction, the recipe validator's type checks, every prompt
  rendering, the resource-shape fallbacks, telemetry's disabled path and ring buffer, the socket
  connection lifecycle, and `bakeOnCore`'s error and presentation paths.
- **`src/node/worker.mjs` is measured for the first time.** It was absent from the include list, so
  it appeared in no report while being our own code on the worker-threads path. It is a plain async
  function; calling it directly exercises what the worker thread runs, no worker thread needed. It
  now reports 100/75/100/100.
- The signal-handler block in `runServer()` is `/* v8 ignore */`d **with a reason**: the handlers
  end in `process.exit()`, so exercising them in-process kills the test runner, and mocking
  `process.exit` would assert that the mocks were called rather than that the server shuts down.
  What *is* testable -- `closeAll`, which does the actual closing -- has its own tests.

**Result: 93.48/84.68/93.01/94.36 -> 95.51/88.65/96.34/96.35.**

**Two tiers rather than `perFile: true`, and the reason is specific.** `src/node/lib/**` aggregates
to 99.1/94.4/100 and is held there; the global bar sits just under actual. `perFile` is not on
because two files carry the whole deficit -- `mcp-server.mjs` at 72.5% branches and
`transports.mjs` -- and both are dominated by SDK error callbacks and per-request handler bodies
that only become individually testable after the `registerTool` decomposition. F-04 established
that decomposition is **not** needed for the protocol, so forcing it now would be a large rewrite
bought purely to move a number. The per-glob tier delivers what `perFile` was wanted for -- a weak
module cannot hide behind healthy ones -- for the half of the tree where it is achievable today.
`autoUpdate` stays off: it silently ratchets a regression gate into a rubber stamp.

**The gate was verified to fail.** Raising the branch bar to 99 against a snapshot produced exit
code 1. A gate never seen failing is not known to work.

**`codecov.yml` corrected**: project 70% -> 95%, patch 75% -> **100%** with a zero threshold (new
code arrives covered -- the project figure moves slowly and forgives an uncovered addition, while
patch coverage is the only check that sees it on its own), `range` 70..90 -> 90..97, the `mcp-tests`
flag widened from two paths to all fork-owned `src/node/**` (twelve of our own modules were absent
from flag reporting while appearing in the totals), the dead `core-tests` and `node-api` flags
deleted since only `mcp-tests` is ever uploaded, and `profiling.critical_files_paths` removed --
it configured a Codecov feature that no longer exists, which is inert configuration describing a
capability the project does not have, the same shape of claim this release spent its time deleting
from the code.

## F-10 - `argSelector` arguments were validated by nobody - **FIXED**

## F-11 - Two things CodeQL found in this release's own code - **FIXED**

**Found:** the v2.3.0 release PR (#98), which reported 2 new alerts against the master baseline.

**1. `js/insecure-temporary-file`, HIGH, and it was mine.** `tests/mcp/socket-transport.test.mjs`
wrote to a predictable name under `os.tmpdir()` built from the process id. `os.tmpdir()` is
shared and world-writable, and that name is entirely predictable, so a local user can pre-create a
symlink at it and redirect what the test writes. The socket paths had the same shape, softened only
by `Math.random()`.

Fixed by creating one `fs.mkdtempSync` directory per test file: `mkdtemp` returns a directory only
this process can enter, so nothing inside it is guessable or pre-creatable, and one recursive remove
cleans up everything. It also shortens the socket paths, which matters given the 108-byte `sun_path`
limit from F-07.

**2. `js/useless-assignment-to-local` in `src/vendor/crypto-api/hasher/snefru.mjs`.** Vendored
third-party code, already exempt from this repository's linter and from coverage for the same
reason it should be exempt here: it is not ours to change, and an alert on it is a finding that can
neither be acted on nor sensibly dismissed one by one. `src/vendor/**` is now in the CodeQL config's
`paths-ignore`, with the reasoning recorded there. **`src/core/vendor/**` stays analysed** -- its
alerts have been individually dispositioned and hiding them would lose that record.

## F-12 - The patch-coverage target was aspirational, and it failed on its own release - **FIXED**

**Found:** the same PR. `codecov/patch` reported **93.12% of diff hit, target 100%**.

**What happened is the gate working.** F-09 set patch coverage to 100% on the reasoning that patch
is the only check that sees an addition on its own. The first PR it ran against was this release's,
and it fired.

**The right response to a firing gate is to cover the code, and that came first.** Four uncovered
additions turned out to be plainly testable and are now tested: a non-numeric
`CYBERCHEF_SOCKET_PORT`, the connection cap dropping a connection past the limit, a forged Host on
the modern HTTP path, and a request with no Host header at all. Coverage rose to
**95.71/88.79/96.34/96.57** and patch to ~91.6%.

**What remained was not laziness.** Ten added lines: SDK `onerror` callbacks, `closeAll`
teardown-failure branches, and `stat` errors other than `ENOENT`. Reaching them means faking a
filesystem or SDK failure, which asserts that the mocks were called rather than that the code works
-- the same "a number, not a guarantee" the `/* v8 ignore */` reasons already name.

**So the target is now 90%, measured rather than chosen**, and the residual is named in
`codecov.yml` so the number is auditable. A target nobody can hit is a check people learn to
override, which is the same failure as a check that cannot fail -- the one this file had at 75%.

## F-13 - What the CodeRabbit review found in this release's own code - **FIXED**

**Found:** the release PR. Seventeen threads; the two that mattered are defects I wrote, and both
were invisible from reading the code I wrote.

**1. `closeAll()` never closed the pinned `Server` instances.** The socket transport's teardown was

```js
for (const entry of [...connections]) entry.socket.destroy();
connections.clear();
```

`destroy()` emits `"close"` **asynchronously**, so `connections.clear()` ran first; when `drop()`
later fired, `connections.delete(entry)` returned `false` and it returned *before* calling
`handle.close()`. Every per-connection `Server` stayed alive after `closeAll()` resolved. In
`runServer()` the process exits immediately afterwards so the blast radius is bounded, but the tests
and any embedded caller keep running. Fixed by closing the handles explicitly instead of relying on
the socket's own close listener -- the guard was written to prevent double-drop and quietly became
the thing preventing the drop.

**2. A umask window before the socket's `chmod`.** `listen()` creates the Unix socket with the
process umask and the `chmodSync(path, 0o600)` ran on the next line. Between the two, a permissive
umask published a world-writable socket -- and a connection accepted in that window survives the
mode change. Fixed by tightening the umask around the bind and restoring it immediately; the chmod
stays as a belt-and-braces assertion of the final mode. CWE-732, and it is exactly the shape of the
F-05 finding: a security property asserted a moment after the moment it was needed.

**3. `src/vendor/crypto-api/index.mjs` could not load under any Node.** It reads
`import CryptoApi from './crypto-api'` followed by `module.exports = CryptoApi` -- an ES import
with a CommonJS export, naming a file that does not exist. My rewrite pass missed it because it
matched `from "..."` with double quotes and a trailing semicolon, and this file uses neither.
Nothing imports it; the consumers name `crypto-api.mjs`, `hasher/sm3.mjs` and `encoder/hex.mjs`
directly. **Deleted rather than repaired**: it is part of why the published package is unusable, and
carrying a file that cannot be loaded would be shipping the defect we vendored around.

**4. Two claims of mine that were not true, corrected rather than defended.**

- The release notes gave a hand-written JSON-RPC one-liner as the **authoritative** verification.
  That contradicts this project's most expensive lesson: raw JSON-RPC does no schema validation,
  which is how three releases shipped with every tool carrying an empty `inputSchema` while probes
  like that reported success. The notes now put a real MCP client first and keep the one-liner
  explicitly as a container smoke test.
- `vitest.config.mjs` claimed the per-glob tier "delivers the property `perFile` was wanted for".
  It does not: without `perFile: true` inside the glob object, the numbers are checked against the
  glob's **aggregate**. The claim is removed. `perFile` is still not set on that tier, and now for a
  stated reason: it would be floored by `prompts.mjs` at 72% branches, whose uncovered branches are
  `?? ""` fallbacks that `getPrompt` makes unreachable -- so a per-file tier would be a *weaker*
  gate than the 94% aggregate, not a stronger one.

**5. Real, and cheap: three tests that were missing.** A prompt rendered with its **optional**
argument omitted (`decode-chain`'s `hint` -- the earlier test supplied every declared argument and
so never took that path), the unknown-font rejection patch 10 introduced, and telemetry's
disabled-path test isolated from the environment, since `TELEMETRY_ENABLED` is evaluated when
`config.mjs` loads and a developer with `CYBERCHEF_TELEMETRY_ENABLED=true` would have seen it fail
for a reason unrelated to the code. Verified by running it with that variable set.

**6. Declined, with reasons.** Findings against `src/vendor/crypto-api/encoder/utf.mjs` (lone
surrogates encoded as U+10000 rather than U+FFFD) and `tools/tools.mjs` (a 64-bit rotation by zero
combining halves) are real descriptions of upstream's code. They are **not ours to change**: the
tree is vendored verbatim, editing it defeats the point of vendoring and would be silently dropped
by any re-vendor, and neither is reachable from this server -- every hash vector in the suite passes,
including the SM3, HAS-160, RIPEMD and Whirlpool vectors that route through those helpers. Recorded
here so the decision is visible rather than implied by silence.

## Method note

F-01, F-02 and F-03 are one chain, and each was found only because the previous one was fixed: the
consumer install exposed the vendoring need, the vendoring probe exposed the buffer pool, and the
buffer-pool test exposed the fonts. None would have surfaced from reading the code. The pattern that
keeps working is to exercise the product the way a user reaches it - a real install, a real client -
and to let each fix's verification step run wider than the fix.
