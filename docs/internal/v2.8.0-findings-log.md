# v2.8.0 findings log

What was measured while building Phase 6's first release, including what the plan got wrong and
what I got wrong. Same purpose as the v2.2–v2.7 logs: the numbers and the reasoning, so a later
reader inherits the evidence rather than the conclusion.

---

## F-01 — Half the plan was delivered by v2.6.0 — **SCOPED**

**Found:** measuring the plan's stated baselines before writing anything, which is now the standing
habit after v2.5.0, v2.6.0 and v2.7.0 each found the same thing.

`docs/planning/future-releases/release-v2.8.0.md` was last updated December 2025 and its "current"
column describes a server that no longer exists.

| Plan says "currently" | Plan target | Measured today |
|---|---|---|
| Cold start ~3s | <1s | **158 ms** (mean of 4) |
| Memory idle ~150MB | <100MB | **96 MB RSS** after import |
| Lazy loading: to build | — | **already shipped in v2.6.0** (`lib/node-api.mjs`) |
| Startup optimization: to build | — | **already shipped in v2.6.0** |

Three of the plan's eight features — lazy loading (item 3), startup optimization (item 4), and the
memory target — are done, and the cold-start target is beaten by six times before this release
starts. v2.6.0 took startup from ~1300 ms to ~185 ms by deferring the 505-operation barrel; that is
precisely the "OperationLoader" the plan sketches.

The plan's code samples are also stale in ways that matter: they build on `node:22-alpine` (this
project is `>=24 <27` on Chainguard), and they `COPY --from=builder /app/dist` (there is no `dist/`
— `npm run build` is `grunt configTests`, which generates config, not a bundle).

**Scoped to what is actually missing:** arm64, image size, and offline honesty.

## F-03 — 885 of 1190 packages in the runtime image are dev-only — **the v2.0.0 plan called this and it was never done**

`Dockerfile.mcp` runs `npm ci` (everything) and then `rm -rf` on a **hardcoded list of nine package
globs**. There are 1190 packages in the image.

```text
installed tree:  1310 paths
production-only:  425 paths      -> 885 dev-only paths shipping in the runtime image
```

Among them: `typescript` (24MB), `@rolldown` (19MB), `@octokit` (18MB),
`@codecov/bundler-plugin-core` (14MB), `@babel` (14MB), `lightningcss` (10MB). A hardcoded list
cannot keep pace with a 1300-package tree, which is exactly what the v2.0.0 plan predicted:

> *"devDependencies are shipping in the runtime image. Trivy found `vitest` under
> `app/node_modules/` in the scanned container... Replace that list with `npm prune --omit=dev`."*

That was written for PR 7 and never landed. Measured by building it:

```text
before:  node_modules 589 MB, 1190 packages
after:   node_modules 345 MB,  432 packages     -> -244 MB, -41%
```

This is a security result as much as a size one: every dev dependency in the runtime image is
attack surface and a standing Trivy finding.

## F-04 — A local build ships 240MB of Docusaurus deps and the developer's saved recipes

**Found:** the prune experiment produced a *bigger* image than the published one, which made no
sense until I looked inside.

`.dockerignore` contains `node_modules`. Docker matches those patterns against the path **from the
context root**, so it excludes `./node_modules` and nothing else — `docs-site/node_modules` is
copied in whole:

```text
local build:  /app/docs-site  249 MB   (of which node_modules 240 MB)
CI build:     absent
```

CI never sees this because it checks out clean, so **a local build and a CI build produce
materially different images and nobody would notice.**

Worse than size, in the same copy:

```text
-rw-------  /app/recipes.json
-rw-------  /app/recipes.json.backup
```

The saved-recipe store. Anyone building this image locally bakes **their own saved recipes** into
it, and would publish them if they pushed it. Mode 0600 on disk is irrelevant once it is a layer.

## F-05 — arm/v7 is not available, so the plan's Raspberry Pi 3 target cannot be met

The plan asks for `linux/amd64`, `linux/arm64` and `linux/arm/v7`. The base image publishes two:

```text
cgr.dev/chainguard/node:latest
  Platform:  linux/amd64
  Platform:  linux/arm64
```

arm64 is the valuable one regardless — Apple Silicon, AWS Graviton, Raspberry Pi 4/5 — and the
release currently ships **amd64 only** (`platforms: linux/amd64` in `mcp-release.yml`). arm/v7 is
reported as unavailable rather than quietly dropped.

## F-06 — "Offline mode" is mostly already true, and the plan's table is wrong about why

The plan lists five network dependencies. Measured against the code:

| Plan claims | Reality |
|---|---|
| Core operations: no network | Correct — **502 of 504** touch nothing |
| Plugin loading: NPM registry | **There is no plugin loader.** ADR 0002; `node:vm` is not a boundary |
| Telemetry: OTLP export | The server exports nothing — it depends on the OTel **API** only (v2.7.0) |
| Auth validation: IdP | Already bounded in v2.6.0: 5s deadline plus a circuit breaker |
| Health checks: optional | Local only already |

Exactly **two** operations reach the network: `HTTPRequest` and `DNSOverHTTPS`. So the work is not
building offline capability — it is already there — but making it *explicit and fail-closed*, so an
air-gapped deployment refuses those two rather than hanging until the OS gives up.

## F-07 — QEMU cost: I predicted 30-60 minutes, it is 4m46s — **MY ESTIMATE WAS WRONG**

**Found:** measuring instead of acting on the estimate.

I argued for restructuring the release workflow into a native-runner matrix — three jobs, push by
digest, merge a manifest list — on the grounds that emulating a 1300-package npm install would take
30-60 minutes and risk the release. Measured locally with binfmt installed:

```text
linux/arm64 under QEMU:   4m 46s
linux/amd64 native:      ~4m 30s
```

Almost no difference, and the reason is the previous commit: **the production tree after the prune
is pure JavaScript and WebAssembly.** Nothing compiles under emulation, and nearly all the elapsed
time is npm's I/O, which QEMU barely taxes. Before the prune the tree carried
`@rolldown/binding-linux-x64-gnu` and `lightningcss-linux-x64-gnu`; those would not have built for
arm64 at all.

So the matrix was rejected on the number rather than adopted on the guess, and the number is
recorded in the workflow so a future reader can re-measure rather than re-argue.

**The check that actually matters is not "it built".** `@napi-rs/nice` (via `piscina`) ships its
platform binaries as OPTIONAL dependencies, so an install that silently resolved the wrong one
still produces a working image that fails later, in the worker pool, on someone else's machine.
Verified explicitly:

```text
/app/node_modules/@napi-rs/nice-linux-arm64-gnu     <- correct
```

and asserted on every pull request by a native-arm job.

## F-08 — Offline mode is a guard on the RECIPE, not on the tool name

**Found:** tracing the call graph before placing the guard, having been bitten by the same shape in
v2.5.0.

The obvious implementation refuses network-annotated *tools*. It would be useless:
`cyberchef_bake` is not a network tool, and `bake({recipe: [{op: "HTTP request"}]})` is a network
call. That is exactly the v2.5.0 authorisation bypass — the scope check sat below the meta-tool
branches, so bake skipped it entirely while every unit test passed.

There is also **no single choke point**. Three entries reach the engine:

| entry | reached by |
|---|---|
| `bakeOnCore` | `cyberchef_bake`, `cyberchef_batch`, registry tools, streaming |
| `executeInWorker` | a direct operation tool, worker pool enabled |
| `bake` (Node API) | saved-recipe execute **and** test |

So the check takes a normalised recipe and is called at all four sites, the direct-operation guard
sits **above** the worker/streaming split (one check rather than two that drift), and the suite
walks each path by name. Four mutations verified, including moving the guard below the split.

**One bug of mine, caught by reading rather than by a test:** the first version passed `recipeName`
to the guard in `recipe-manager.mjs`. There is no such binding there — it is a property key on a log
object — so every saved-recipe execution would have thrown a `ReferenceError`.

## F-09 — <50MB is not reachable, and saying so is the deliverable

The plan targets an image under 50 MB. After the prune:

```text
image        453 MB
node_modules 345 MB   of which @jimp 89 MB, tesseract.js-core 44 MB
```

`@jimp` and `tesseract.js-core` are **production** dependencies of real operations — image
manipulation and OCR. A server exposing 504 operations including those cannot be a 50 MB image; the
target was set against a baseline (~200 MB) that was itself wrong by 3.4x.

30% is what was actually available without dropping capability, and it was taken. The remaining
target is reported as unreachable with the numbers rather than quietly missed.

## F-10 — Web-app leftovers: 19 MB, measured and **DEFERRED**

Five production dependencies have **zero imports anywhere in `src/`** — inherited from upstream
CyberChef's web app, which this fork stripped in v1.7.1:

```text
bootstrap                  10 MB
jquery                      4 MB
bootstrap-material-design   3 MB
bootstrap-colorpicker       1 MB
snackbarjs                  1 MB
                    TOTAL  19 MB   =  4.2% of the image
```

Not removed, deliberately. The change is not one line: `scripts/patch-dependencies.mjs` still
patches `snackbarjs`, `Gruntfile.js` and `webpack.config.js` reference the others, and editing the
dependency manifest of a fork whose upstream declares them invites a conflict at the next sync.

Checked whether it was a security question rather than a size one, which would change the answer:

```text
npm audit --omit=dev      4 low-severity advisories, none on these five
Dependabot open alerts    0
```

So it is 4.2% for a multi-file change across the fork boundary, in a release that already took 30%.
Recorded with the numbers so a later release can act on it deliberately rather than rediscover it.

## F-11 — Resource profiles would be config theatre

The plan proposes `minimal` / `balanced` / `performance` profiles as a new configuration layer. Two
of the five fields in its schema describe things that do not exist:

- `lazyLoading: true|false` — lazy loading is unconditional since v2.6.0; there is no switch.
- `maxOperations: 100` — there is no per-deployment operation limit, and adding one would make
  operations unreachable rather than cheaper.

The other three (`cacheSize`, `telemetry`, `memoryLimit`) are already environment variables and
Helm values. A profile system would therefore be a new indirection over settings that exist, whose
distinguishing features are fictional.

The real need behind it — "what should I set on a small box?" — is a documentation question, and it
is answered as one: a table of recommended settings per deployment size, in the edge deployment
guide. No new configuration layer.
