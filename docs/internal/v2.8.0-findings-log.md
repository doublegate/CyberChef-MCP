# v2.8.0 findings log

What was measured while building Phase 6's first release, including what the plan got wrong and
what I got wrong. Same purpose as the v2.2–v2.7 logs: the numbers and the reasoning, so a later
reader inherits the evidence rather than the conclusion.

---

## F-01 — Half the plan was delivered by v2.6.0 — **SCOPED**

**Found:** measuring the plan's stated baselines before writing anything, which is now the standing
habit after v2.5.0, v2.6.0 and v2.7.0 each found the same thing.

`docs/planning/future-releases/release-v2.8.0.md` was last updated December 2025 and its "current"
column describes a server that no longer exists.

| Plan says "currently" | Plan target | Measured today |
|---|---|---|
| Cold start ~3s | <1s | **158 ms** (mean of 4) |
| Memory idle ~150MB | <100MB | **96 MB RSS** after import |
| Lazy loading: to build | — | **already shipped in v2.6.0** (`lib/node-api.mjs`) |
| Startup optimization: to build | — | **already shipped in v2.6.0** |

Three of the plan's eight features — lazy loading (item 3), startup optimization (item 4), and the
memory target — are done, and the cold-start target is beaten by six times before this release
starts. v2.6.0 took startup from ~1300 ms to ~185 ms by deferring the 505-operation barrel; that is
precisely the "OperationLoader" the plan sketches.

The plan's code samples are also stale in ways that matter: they build on `node:22-alpine` (this
project is `>=24 <27` on Chainguard), and they `COPY --from=builder /app/dist` (there is no `dist/`
— `npm run build` is `grunt configTests`, which generates config, not a bundle).

**Scoped to what is actually missing:** arm64, image size, and offline honesty.

## F-02 — The image is 674MB, not "~200MB", and 87% of it is `node_modules`

**Found:** measuring the published artefact rather than trusting the plan's figure.

```text
ghcr.io/doublegate/cyberchef-mcp_v2:2.7.0     643 MB image   /app 616 MB   1190 packages
  /app/node_modules   589 MB   <- 87% of /app
  /app/src             18 MB
  /app/images           8 MB   <- banner JPEGs, no runtime use
```

The plan's baseline is wrong by 3.4x, which matters because its target (<50MB) was set against it.

## F-03 — 885 of 1190 packages in the runtime image are dev-only — **the v2.0.0 plan called this and it was never done**

`Dockerfile.mcp` runs `npm ci` (everything) and then `rm -rf` on a **hardcoded list of nine package
globs**. There are 1190 packages in the image.

```text
installed tree:  1310 paths
production-only:  425 paths      -> 885 dev-only paths shipping in the runtime image
```

Among them: `typescript` (24MB), `@rolldown` (19MB), `@octokit` (18MB),
`@codecov/bundler-plugin-core` (14MB), `@babel` (14MB), `lightningcss` (10MB). A hardcoded list
cannot keep pace with a 1300-package tree, which is exactly what the v2.0.0 plan predicted:

> *"devDependencies are shipping in the runtime image. Trivy found `vitest` under
> `app/node_modules/` in the scanned container... Replace that list with `npm prune --omit=dev`."*

That was written for PR 7 and never landed. Measured by building it:

```text
before:  node_modules 589 MB, 1190 packages
after:   node_modules 345 MB,  432 packages     -> -244 MB, -41%
```

This is a security result as much as a size one: every dev dependency in the runtime image is
attack surface and a standing Trivy finding.

## F-04 — A local build ships 240MB of Docusaurus deps and the developer's saved recipes

**Found:** the prune experiment produced a *bigger* image than the published one, which made no
sense until I looked inside.

`.dockerignore` contains `node_modules`. Docker matches those patterns against the path **from the
context root**, so it excludes `./node_modules` and nothing else — `docs-site/node_modules` is
copied in whole:

```text
local build:  /app/docs-site  249 MB   (of which node_modules 240 MB)
CI build:     absent
```

CI never sees this because it checks out clean, so **a local build and a CI build produce
materially different images and nobody would notice.**

Worse than size, in the same copy:

```text
-rw-------  /app/recipes.json
-rw-------  /app/recipes.json.backup
```

The saved-recipe store. Anyone building this image locally bakes **their own saved recipes** into
it, and would publish them if they pushed it. Mode 0600 on disk is irrelevant once it is a layer.

## F-05 — arm/v7 is not available, so the plan's Raspberry Pi 3 target cannot be met

The plan asks for `linux/amd64`, `linux/arm64` and `linux/arm/v7`. The base image publishes two:

```text
cgr.dev/chainguard/node:latest
  Platform:  linux/amd64
  Platform:  linux/arm64
```

arm64 is the valuable one regardless — Apple Silicon, AWS Graviton, Raspberry Pi 4/5 — and the
release currently ships **amd64 only** (`platforms: linux/amd64` in `mcp-release.yml`). arm/v7 is
reported as unavailable rather than quietly dropped.

## F-06 — "Offline mode" is mostly already true, and the plan's table is wrong about why

The plan lists five network dependencies. Measured against the code:

| Plan claims | Reality |
|---|---|
| Core operations: no network | Correct — **502 of 504** touch nothing |
| Plugin loading: NPM registry | **There is no plugin loader.** ADR 0002; `node:vm` is not a boundary |
| Telemetry: OTLP export | The server exports nothing — it depends on the OTel **API** only (v2.7.0) |
| Auth validation: IdP | Already bounded in v2.6.0: 5s deadline plus a circuit breaker |
| Health checks: optional | Local only already |

Exactly **two** operations reach the network: `HTTPRequest` and `DNSOverHTTPS`. So the work is not
building offline capability — it is already there — but making it *explicit and fail-closed*, so an
air-gapped deployment refuses those two rather than hanging until the OS gives up.
