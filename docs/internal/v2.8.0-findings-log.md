# v2.8.0 findings log

What was measured while building Phase 6's first release, including what the plan got wrong and
what I got wrong. Same purpose as the v2.2–v2.7 logs: the numbers and the reasoning, so a later
reader inherits the evidence rather than the conclusion.

---

## F-01 — Half the plan was delivered by v2.6.0 — **SCOPED**

**Found:** measuring the plan's stated baselines before writing anything, which is now the standing
habit after v2.5.0, v2.6.0 and v2.7.0 each found the same thing.

`docs/planning/future-releases/release-v2.8.0.md` was last updated December 2025 and its "current"
column describes a server that no longer exists.

| Plan says "currently" | Plan target | Measured today |
|---|---|---|
| Cold start ~3s | <1s | **158 ms** (mean of 4) |
| Memory idle ~150MB | <100MB | **96 MB RSS** after import |
| Lazy loading: to build | — | **already shipped in v2.6.0** (`lib/node-api.mjs`) |
| Startup optimization: to build | — | **already shipped in v2.6.0** |

Three of the plan's eight features — lazy loading (item 3), startup optimization (item 4), and the
memory target — are done, and the cold-start target is beaten by six times before this release
starts. v2.6.0 took startup from ~1300 ms to ~185 ms by deferring the 505-operation barrel; that is
precisely the "OperationLoader" the plan sketches.

The plan's code samples are also stale in ways that matter: they build on `node:22-alpine` (this
project is `>=24 <27` on Chainguard), and they `COPY --from=builder /app/dist` (there is no `dist/`
— `npm run build` is `grunt configTests`, which generates config, not a bundle).

**Scoped to what is actually missing:** arm64, image size, and offline honesty.

## F-03 — 885 of 1190 packages in the runtime image are dev-only — **the v2.0.0 plan called this and it was never done**

`Dockerfile.mcp` runs `npm ci` (everything) and then `rm -rf` on a **hardcoded list of nine package
globs**. There are 1190 packages in the image.

```text
installed tree:  1310 paths
production-only:  425 paths      -> 885 dev-only paths shipping in the runtime image
```

Among them: `typescript` (24MB), `@rolldown` (19MB), `@octokit` (18MB),
`@codecov/bundler-plugin-core` (14MB), `@babel` (14MB), `lightningcss` (10MB). A hardcoded list
cannot keep pace with a 1300-package tree, which is exactly what the v2.0.0 plan predicted:

> *"devDependencies are shipping in the runtime image. Trivy found `vitest` under
> `app/node_modules/` in the scanned container... Replace that list with `npm prune --omit=dev`."*

That was written for PR 7 and never landed. Measured by building it:

```text
before:  node_modules 589 MB, 1190 packages
after:   node_modules 345 MB,  432 packages     -> -244 MB, -41%
```

This is a security result as much as a size one: every dev dependency in the runtime image is
attack surface and a standing Trivy finding.

## F-04 — A local build ships 240MB of Docusaurus deps and the developer's saved recipes

**Found:** the prune experiment produced a *bigger* image than the published one, which made no
sense until I looked inside.

`.dockerignore` contains `node_modules`. Docker matches those patterns against the path **from the
context root**, so it excludes `./node_modules` and nothing else — `docs-site/node_modules` is
copied in whole:

```text
local build:  /app/docs-site  249 MB   (of which node_modules 240 MB)
CI build:     absent
```

CI never sees this because it checks out clean, so **a local build and a CI build produce
materially different images and nobody would notice.**

Worse than size, in the same copy:

```text
-rw-------  /app/recipes.json
-rw-------  /app/recipes.json.backup
```

The saved-recipe store. Anyone building this image locally bakes **their own saved recipes** into
it, and would publish them if they pushed it. Mode 0600 on disk is irrelevant once it is a layer.

## F-06 — "Offline mode" is mostly already true, and the plan's table is wrong about why

The plan lists five network dependencies. Measured against the code:

| Plan claims | Reality |
|---|---|
| Core operations: no network | Correct — **502 of 504** touch nothing |
| Plugin loading: NPM registry | **There is no plugin loader.** ADR 0002; `node:vm` is not a boundary |
| Telemetry: OTLP export | The server exports nothing — it depends on the OTel **API** only (v2.7.0) |
| Auth validation: IdP | Already bounded in v2.6.0: 5s deadline plus a circuit breaker |
| Health checks: optional | Local only already |

Exactly **two** operations reach the network: `HTTPRequest` and `DNSOverHTTPS`. So the work is not
building offline capability — it is already there — but making it *explicit and fail-closed*, so an
air-gapped deployment refuses those two rather than hanging until the OS gives up.

## F-07 — QEMU cost: I predicted 30-60 minutes, it is 4m46s — **MY ESTIMATE WAS WRONG**

**Found:** measuring instead of acting on the estimate.

I argued for restructuring the release workflow into a native-runner matrix — three jobs, push by
digest, merge a manifest list — on the grounds that emulating a 1300-package npm install would take
30-60 minutes and risk the release. Measured locally with binfmt installed:

```text
linux/arm64 under QEMU:   4m 46s
linux/amd64 native:      ~4m 30s
```

Almost no difference, and the reason is the previous commit: **the production tree after the prune
is pure JavaScript and WebAssembly.** Nothing compiles under emulation, and nearly all the elapsed
time is npm's I/O, which QEMU barely taxes. Before the prune the tree carried
`@rolldown/binding-linux-x64-gnu` and `lightningcss-linux-x64-gnu`; those would not have built for
arm64 at all.

So the matrix was rejected on the number rather than adopted on the guess, and the number is
recorded in the workflow so a future reader can re-measure rather than re-argue.

**The check that actually matters is not "it built".** `@napi-rs/nice` (via `piscina`) ships its
platform binaries as OPTIONAL dependencies, so an install that silently resolved the wrong one
still produces a working image that fails later, in the worker pool, on someone else's machine.
Verified explicitly:

```text
/app/node_modules/@napi-rs/nice-linux-arm64-gnu     <- correct
```

and asserted on every pull request by a native-arm job.

## F-08 — Offline mode is a guard on the RECIPE, not on the tool name

**Found:** tracing the call graph before placing the guard, having been bitten by the same shape in
v2.5.0.

The obvious implementation refuses network-annotated *tools*. It would be useless:
`cyberchef_bake` is not a network tool, and `bake({recipe: [{op: "HTTP request"}]})` is a network
call. That is exactly the v2.5.0 authorisation bypass — the scope check sat below the meta-tool
branches, so bake skipped it entirely while every unit test passed.

There is also **no single choke point**. Three entries reach the engine:

| entry | reached by |
|---|---|
| `bakeOnCore` | `cyberchef_bake`, `cyberchef_batch`, registry tools, streaming |
| `executeInWorker` | a direct operation tool, worker pool enabled |
| `bake` (Node API) | saved-recipe execute **and** test |

So the check takes a normalised recipe and is called at all four sites, the direct-operation guard
sits **above** the worker/streaming split (one check rather than two that drift), and the suite
walks each path by name. Four mutations verified, including moving the guard below the split.

**One bug of mine, caught by reading rather than by a test:** the first version passed `recipeName`
to the guard in `recipe-manager.mjs`. There is no such binding there — it is a property key on a log
object — so every saved-recipe execution would have thrown a `ReferenceError`.

## F-09 — <50MB is not reachable, and saying so is the deliverable

The plan targets an image under 50 MB. After the prune:

```text
image        453 MB
node_modules 345 MB   of which @jimp 89 MB, tesseract.js-core 44 MB
```

`@jimp` and `tesseract.js-core` are **production** dependencies of real operations — image
manipulation and OCR. A server exposing 504 operations including those cannot be a 50 MB image; the
target was set against a baseline (~200 MB) that was itself wrong by 3.4x.

30% is what was actually available without dropping capability, and it was taken. The remaining
target is reported as unreachable with the numbers rather than quietly missed.

## F-11 — Resource profiles would be config theatre

The plan proposes `minimal` / `balanced` / `performance` profiles as a new configuration layer. Two
of the five fields in its schema describe things that do not exist:

- `lazyLoading: true|false` — lazy loading is unconditional since v2.6.0; there is no switch.
- `maxOperations: 100` — there is no per-deployment operation limit, and adding one would make
  operations unreachable rather than cheaper.

The other three (`cacheSize`, `telemetry`, `memoryLimit`) are already environment variables and
Helm values. A profile system would therefore be a new indirection over settings that exist, whose
distinguishing features are fictional.

The real need behind it — "what should I set on a small box?" — is a documentation question, and it
is answered as one: a table of recommended settings per deployment size, in the edge deployment
guide. No new configuration layer.

## F-12 — The offline guard was above the split but below the CACHE — **REVIEW FINDING, my bug**

**Found:** CodeRabbit on PR #108, and it is the sharpest finding of the release.

F-08 records placing the direct-operation guard "above the worker/streaming split so one check
covers both legs". That was the wrong ceiling. A **cache hit returns from a branch above the
split**, so with `CYBERCHEF_CACHE_ENABLED` (the default) a cached `HTTP request` was served with
offline mode on. Reproduced before fixing:

```text
offline: true
cache still returns the networked result: "CACHED-RESPONSE-BODY-FROM-WHEN-WE-WERE-ONLINE"
```

This is worse than an ordinary bypass. The value returned is **a real response from the network**,
handed to a caller who has been told this deployment cannot reach one — so an air-gapped operator
sees evidence that it can.

The generalisable lesson: the ceiling is not "before execution", it is **before anything that can
answer the request**. A cache answers without executing, and I did not count it as a path.

**And the first test I wrote for it passed with the bug reintroduced.** It warmed the cache with a
hand-built key, then asserted a refusal — but the key did not match the one the handler computes
(the real `recipeArgs` for `HTTP request` are its resolved defaults, not `[]`), so there was never a
cache hit. The refusal it saw came from the guard on the ordinary miss path: a test for cache
ordering that never involved the cache.

Rewritten to assert the **ordering** directly — spy on `operationCache.get` and require it was never
called — which is true regardless of how the key is constructed, and is precisely the detail that
made the first attempt useless. Both the source-order test and the runtime test now fail when the
guard is moved back.

That is twice in this project that a guard was placed correctly with respect to the thing I was
thinking about (v2.5.0: meta-tool branches; here: the worker split) and incorrectly with respect to
a path I had not enumerated.

## F-13 — Review findings that were not defects

Recorded because "verify before answering" produced two of these, and a log of only the confirmed
findings would misrepresent the review.

**`/bin/sh` in the distroless runtime — marked Critical, empirically false.** The claim was that the
runtime image has no shell, so the arm64 binding check fails before it can inspect anything. The
image is Chainguard `node:latest`, which does ship a shell, and the CI job had already printed the
answer on a real ARM runner:

```text
build-arm64  Verify npm resolved the arm64 native binding   binding: /app/node_modules/@napi-rs/nice-linux-arm64-gnu
```

Confirmed locally as well. No change made.

**Self-hosted runners could claim `ubuntu-24.04-arm`.** Structurally true — Actions has no
"hosted-only" qualifier — but not actual here: the repository's one self-hosted runner carries
`self-hosted, Linux, X64, agy` and is x64, so it cannot match an arm64 label. There is no code
change that fixes this; the mitigation is a policy about how runners are registered, so that policy
is now stated in the workflow where someone adding a runner will read it.

## F-14 — The Snyk PR would have broken an operation, silently

**Found:** verifying a proposed security upgrade before merging it.

PR #107 upgraded `@xmldom/xmldom` 0.8.15 → 0.9.12. Two reasons it was wrong, either sufficient:

**We were already patched.** Every advisory for this package has *two* patched versions, one per
release line — `0.8.15` and `0.9.12` for the newest, `0.8.13` and `0.9.10` for the rest. `npm audit`
reported nothing against the installed tree because there was nothing.

**And it breaks `XPath expression`.** `XPathExpression.mjs:53` passes `errorHandler`, which 0.9
removed. Reproduced on that exact code path:

```text
0.8.15:  parsed OK -> root
0.9.12:  THREW -> errorHandler object is no longer supported, switch to onError!
```

The construction is inside a `try` whose `catch` raises `OperationError("Invalid input XML.")` — so
the operation would not crash. It would report **"Invalid input XML." for every input**, including
valid XML. A silent wrong answer, which is worse than a failure.

Generalisable: an automated dependency PR carries a claim ("this fixes a vulnerability") and a
consequence (a version change). Both need checking, and here **neither held**.

## F-15 — A size fix nearly ended a security scan

**Found:** reading the paths on the two open code-scanning alerts.

Both were reported against `app/deploy/helm/...` — **inside the container image**. The Helm chart
was being scanned only because `deploy/` was being copied into the runtime image (F-04's territory).

This release stops shipping non-runtime trees. That would have closed both alerts **by moving the
file**, and silently ended the chart's scanning altogether. The Security tab would have gone green
and the coverage would have gone with it.

A finding that disappears because the file moved is not a finding that was addressed. The IaC is now
scanned where it lives, deliberately, and the two standing findings are configured rather than left
to vanish: KSV-0125 by *naming the trusted registries* (so the check stays live — verified by
pointing the chart at `evil.example.com`, which still fails), KSV-0110 by suppression with the
reasoning in the file, since a distributable chart cannot know its namespace.

Three things failed silently while building it, all caught by testing rather than reading:

1. **`ref-proj/` produced 42 of 43 findings**, including four CRITICALs — upstream's files, not
   ours. Excluded.
2. **Trivy's config-file keys are not where the CLI flag names suggest**, and unknown keys are
   ignored. `--config-data` is `rego.data`, `--skip-dirs` is `scan.skip-dirs`. My first file used
   `misconfiguration.data` and a top-level `skip-dirs`; both were ignored and the scan returned 43
   findings. Caught only by running the config file **on its own** rather than assuming it agreed
   with the CLI flags I had tested with.
3. **Ignore-file paths are relative to the scan root**, which differs between the CI scan (`.`) and
   a direct chart scan. A glob for one matches nothing under the other, and the suppression looks
   correct while doing nothing. Both forms are listed now.

## F-17 — The performance benchmarks were measured on an unsupported Node

**Found:** sweeping every workflow log for warnings after the tag, rather than only reading the
red/green.

`performance-benchmarks.yml` still pinned `node-version: '22'` while `package.json` declares
`engines: >=24 <27`. Every benchmark run printed:

```text
npm warn EBADENGINE package: 'cyberchef-mcp@2.8.0',
npm warn EBADENGINE required: { node: '>=24 <27' }, current: { node: 'v22.23.2' }
```

**Worse than a warning.** The numbers posted to every pull request were measured on a runtime this
project does not support, against a V8 two majors behind the one it ships. A performance benchmark
run on the wrong engine is not a benchmark — it is a different measurement wearing the same label.

The v2.0.0 plan called for moving "all 7 workflows" to Node 24. This was the one that was missed,
and it stayed missed for eight releases because a warning is not a failure and nobody reads a green
job's log.

This was written when the fix was "make it 24 like everything else", and that turned out to be the
wrong fix — see F-20. Testing 24 everywhere would have left the runtime that actually ships
untested, which is the same bug pointed the other way.

**The configuration that actually shipped**, for anyone reading this entry rather than F-20:

| workflow | Node |
|---|---|
| `core-ci`, `pull_requests` (core-test, mcp-test) | **matrix: 24 and 26** |
| `performance-benchmarks`, `mcp-release`, `security-scan`, `docs-site`, `upstream-sync`, `upstream-monitor`, `rollback` | **26** |
| `engines` in `package.json` | `>=24 <27`, unchanged |

## F-19 — The remaining warnings, and why they stay

Swept every workflow log. What is left is benign, and saying which is the point:

**`EBADENGINE` for `@astronautlabs/amf@0.0.6`** (production, `AMF Encode`/`AMF Decode`). It declares
`engines: {node: "^14"}` — stale author metadata. `0.0.6` is the latest published version, so there
is nothing to upgrade to, and upstream CyberChef declares it too. Verified the operations actually
work on Node 26.8.1 rather than assuming:

```text
AMF Encode  object -> OK (14 bytes)   string -> OK (7 bytes)   number -> OK (9 bytes)
```

(Noted in passing: the operations suite contains **zero** AMF test cases. Upstream's gap, in an
upstream-mirrored tree, so not this release's to close — but worth knowing that the verification
above is currently the only coverage AMF has.)

**Four deprecated production packages**: `crypto-js`, `jsrsasign`, `bootstrap-colorpicker`,
`popper.js`. The first two are genuine upstream operation dependencies with no drop-in replacement.
The other two are web-app leftovers already measured in F-10 — and this strengthens that entry: they
are not merely 19 MB of dead weight, they are *deprecated* dead weight. Still not worth the
fork-boundary cost in this release, now recorded with the extra reason.

**Everything else is not a warning.** `if-no-files-found: warn` is an input value being echoed; the
`git hint:` lines are runner noise about default branch naming; the `WARNING:` in the non-root check
is the script's own message text; and the `level:"warn"` lines in the test log are the audit trail
and capacity limiter being exercised *on purpose* by tests that assert those paths fire. Chasing
those would be chasing the word rather than the condition.

## F-20 — Making it 24 was the wrong fix; we were shipping 26

**Found:** immediately after F-17, on being offered a blanket bump to Node 26 — which forced the
question of what the right target actually is.

F-17 fixed a benchmark job pinned to Node 22 by moving it to 24, "matching every other workflow".
Every other workflow was also wrong:

```text
image ships   Node 26.8.1
CI tests      Node 24
engines       >=24 <27
```

**The runtime that actually ships had never been tested**, and nothing reported it, because 24 is a
perfectly valid version to test on — it is simply not the one users get. A green pipeline said
nothing about the thing being shipped.

And a blanket move to 26 would have inverted the bug rather than fixed it: 24 is a supported version
for anyone installing from npm, so testing only 26 leaves the declared floor untested — precisely
what was already wrong.

The test gates now run **both boundaries** (24 = the floor, 26 = what ships) with `fail-fast: false`,
because when the Node version is the variable under test, "which ones broke" is the entire result.
Everything that is not a test gate runs 26, matching the artefact it builds, publishes, measures or
audits. `engines` is unchanged — narrowing it would drop Node 24 consumers, a breaking change that
does not belong in a patch release.

The lesson is about the shape of the first fix: "make it consistent with the others" is a repair
that never asks whether the others are right.

## F-21 — "Node 22 compatibility" named a version for a version-independent patch

**Found:** review of PR #109, after I renamed one step and missed five other places.

Six files described the `SlowBuffer` substitutions as "Node 22 compatibility patches". `SlowBuffer`
was **removed** from Node — the patch is required on every version this project supports and on
later ones too. Naming a version implied the opposite: that moving off 22 would retire it.

That is an actively harmful comment rather than merely a stale one, because it tells a future
debugger the patch is legacy cruft safe to delete. Renamed to name the cause (`SlowBuffer`) rather
than a version that has nothing to do with it.

One "Node 22" reference was deliberately kept, in `mcp-release.yml`: it is a historical note
recording that the Docker Hub description once *claimed* Node 22 for an image running Node 25. That
one is about the past and is accurate.
