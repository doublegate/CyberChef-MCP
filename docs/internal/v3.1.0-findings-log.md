# v3.1.0 findings log

What was measured before writing anything, including what the charter got wrong and what I got
wrong. Same purpose as the v2.2–v3.0 logs: the numbers and the reasoning, so a later reader
inherits the evidence rather than the conclusion.

---

## F-01 — The charter's kill criterion fired, and the thing it named already existed — **RE-SCOPED**

By convention F-01 measures the plan against the running server before any code is written.
[`RE-MEASURE.md`](../planning/v3/RE-MEASURE.md) makes it mandatory, and the
[v3.1.0 charter](../planning/v3/charters/v3.1.0-evaluation-harness.md) states its own first kill
criterion:

> The MCP ecosystem ships a conformance/eval harness that covers this — check MCP-Bench, MCP-Atlas
> and the SDK's conformance work before building.

**It does, in part.** `@modelcontextprotocol/conformance` is an official package — *"a framework
for testing MCP client and server implementations against the specification"* — with a
`conformance` binary, 26 published versions, and a `--expected-failures` baseline mechanism built
in. Nothing in this repository referenced it.

The dates are the uncomfortable part:

```text
0.1.16          2026-03-30    scenarios for 2025-03-26 / 2025-06-18 / 2025-11-25
0.2.0-alpha.11  2026-08-07    adds 2026-07-28, including `caching`, `server-stateless`,
                              `sep-2164-resource-not-found`, `http-header-validation`
v3.0.0          2026-09-03    shipped "MCP 2026-07-28 conformance", verified entirely by
                              hand-written tests
```

**An official suite with scenarios for the exact SEPs v3.0.0 implemented was published four weeks
before v3.0.0 shipped, and nobody looked.** Module 20's rule is that accuracy-critical behaviour is
verified against *an independent, external oracle, not self-asserted*, and a conformance release
verified only by its own tests is the definition of self-asserted. `RE-MEASURE.md` step 2 says
"read the dependency's source, not its changelog"; it does not say "check whether the ecosystem
has shipped the tool you are about to hand-build", and that omission is what this cost.

### So the charter is re-scoped, not killed

Conformance and evaluation are different axes and only one of them is covered:

| Axis | Covered by the ecosystem? | v3.1.0 |
|---|---|---|
| Protocol conformance against the spec | **Yes** — `@modelcontextprotocol/conformance` | **Adopt it.** Do not rebuild it. |
| Tool quality: token cost, task success, redundant calls | **No** | Build the harness the charter asked for |

Both belong in the same release under one heading — *measured, not asserted* — and the split is
what makes it honest: the half somebody else already built is adopted, and only the half nobody
covers is written here.

**SemVer:** additive. A CI gate, a devDependency-or-`npx` tool, a measurement script, and one
SHOULD-compliance fix (F-03) that adds a field to an error payload. No behaviour a caller depends
on changes. MINOR is correct.

## F-02 — What the external oracle actually says — **11/11 applicable, then 27/27**

Ran, rather than reasoned about. Server on Streamable HTTP, suite pointed at `/mcp`.

**2025 era** (`0.1.16`, the negotiated version was `2025-11-25`): **11 passed, 21 failed**, and the
raw number is worthless without the classification, which is why it is here rather than in a
release note:

| Bucket | Count | What it means |
|---|---|---|
| Fixture-dependent | 10 | The scenario calls the SDK reference server's own fixtures — `test_simple_prompt`, `test://static-text`, a tool that returns an image. Not applicable to any server with its own surface. |
| Undeclared capability | 5 | `logging/setLevel`, `completion/complete`, `resources/subscribe`, `resources/unsubscribe` answer `-32601`. **Correct**: this server declares `tools`, `prompts`, `resources` and nothing else, and the capability gates the method. |
| Client-side interaction | 6 | Elicitation, sampling, progress — all driven by the fixture tool the scenario calls. |

**Zero of the 21 is a defect in this server.** Every fixture-independent scenario passed:
`server-initialize`, `ping`, `tools-list`, `tools-call-simple-text`, `tools-call-error`,
`resources-list`, `prompts-list`, `server-sse-multiple-streams`, `dns-rebinding-protection`.

**2026-07-28 era** (`0.2.0-alpha.11`), the scenarios that map onto v3.0.0's work, run individually
because they sit outside the default `active` suite:

```text
caching                       7/7   SUCCESS   SEP-2549 ttlMs/cacheScope on all five list methods
server-stateless             12/12  SUCCESS   SEP-2575 _meta validation, server/discover,
                                              capabilities-match-handlers, unsupported-version error
http-header-validation       12/12  SUCCESS   SEP-2243 Mcp-Method/Mcp-Name, -32020 HeaderMismatch
sep-2164-resource-not-found   3/3   SUCCESS   + 1 WARNING, see F-03
json-schema-2020-12           1/2   fixture   wants a `json_schema_2020_12_tool` that does not exist
http-custom-header-server-... 1/6   fixture   wants tools carrying `x-mcp-header` annotations
```

`caching` is the one worth pausing on. v3.0.0 chose those TTLs by argument — the two zeros because
no `listChanged` capability is declared — and an independent implementation of the SEP now agrees
that all five list methods carry the fields, that every `ttlMs` is a non-negative integer, and that
every `cacheScope` is exactly `public` or `private`. That is the first time any claim in this
project about protocol behaviour has been confirmed by something this project did not write.

## F-03 — The oracle found a real defect in v3.0.0's own code — **FIXED**

```text
WARNING  sep-2164-data-uri
         Error data.uri is undefined, expected
         "test://nonexistent-resource-for-conformance-testing". This is a SHOULD requirement.
```

`readResource` takes two `-32602` paths. The missing-recipe path carries `data.uri` — v3.0.0 added
it deliberately. The **unsupported-scheme** and **empty-id** paths carry `data.supported` and a
hint, and omit the URI entirely.

That was a deliberate choice, and the v3.0.0 findings log records it as one: *"two distinct
-32602s, distinguishable by whether `data.uri` is present"*. The spec says otherwise — the
requested URI SHOULD be in `data` for **any** of them — and the design goal survives the fix
intact, because the two cases are equally distinguishable by whether `data.supported` is present.
Including the URI in both is strictly better: it satisfies the SHOULD *and* keeps the distinction.

**1,426 in-tree tests did not find this**, and could not have: they assert the shape this server
was written to produce. Only an oracle that encodes the specification independently asks the
question the other way round. That is the whole argument for F-01's re-scope, arriving four hours
after the argument was written.

## F-04 — The module that argues for the index surface has stale numbers in its header

`tool-catalog.mjs` opens with the measurement that justifies progressive disclosure. Measured again
today, through a real client, counting the exact bytes of the `tools/list` result:

| Surface | Header claims | Measured 2026-09-03 |
|---|---|---|
| `index` | ~24 tools, ~10 KB, ~2,500 tokens | **28 tools, 20,297 bytes** |
| `curated` | 99 tools, 66 KB, ~16,600 tokens | **106 tools, 83,543 bytes** |
| `all` | 524 tools, 345 KB, ~86,000 tokens | **531 tools, 400,701 bytes** |

Every number moved, and the index — the one the design rests on — is **2x** its documented size.
The argument still holds by a wide margin (20 KB against 391 KB), which is exactly why nobody
noticed: a claim that stays directionally true is the hardest kind to keep numerically true.

Two further things this exposes:

1. **No token counter exists in this repository.** Every `~N tokens` figure in the codebase and in
   `AGENTS.md` is bytes÷4. For JSON schema text that is optimistic — punctuation and identifiers
   tokenize denser than prose — so the real figures are probably higher than any of them.
2. `AGENTS.md` and `tool-catalog.mjs` disagreed with each other, and both were written by measuring
   once and never again. A number in prose is a claim with no test behind it.

## F-05 — A required argument was not required, and the error told the caller the wrong thing — **FIXED**

Found by the first run of the surface benchmark, which reported a `cyberchef_describe_operation`
result of **197 bytes**. A schema for `To Base64` is not 197 bytes. What came back was:

```json
{"operations":[{"operation":"","error":"No such operation. Use cyberchef_search to find the exact name."}]}
```

I had called it with `{operation: "To Base64"}`. The schema says `operations` — plural, and
`required`. Two separate faults, and the second is the server's:

1. **Mine.** The singular is the name a model guesses, and it is the name this repository's own
   prose uses: `mcp-server.mjs` line 408 reads *"cyberchef_describe_operation for the argument
   names"*, and the tool is itself called `describe_operation`. Guessing wrong here is the default
   outcome, not a slip.
2. **The server's.** A required argument was not enforced. `describeOperations(undefined)`
   stringifies to `""`, matches no operation, and produces an error that tells the caller the
   operation it never named does not exist, and points it at a search tool it does not need. The
   argument that was actually missing is never mentioned. `isError` was not set either.

v2.2.0 made **unknown** arguments an error rather than a silent default. This is the same defect
from the other side — a **missing required** argument silently defaulted — and it survived because
the two look nothing alike. The neighbouring `cyberchef_list_operations` already had the right
shape; `describe_operation` now matches it, naming the expected argument and echoing the keys the
caller did send.

The tool-quality axis of this release found this in its first ten minutes, before any task set
existed. That is the argument for the axis, made by accident.

## F-06 — What v3.1.0 deliberately did not build

The charter asked for a task-level evaluation harness: accuracy against ground truth, tool calls
made, redundant-call patterns, a held-out set. This release builds the measurement infrastructure
and **not** the model-in-the-loop scoring, for a reason the charter itself anticipates in its
second kill criterion.

Scoring "did the model use the tools well" requires a model in the loop. That means an API key in
CI, a per-run cost, and a number that moves when the model changes underneath it — for a repository
whose entire gating philosophy is that a flaky number must not be a gate.
`performance-benchmarks.yml` already occupies the honest version of that position, saying in its
own output that it *"cannot fail on a regression"*.

So the split is:

| Measurable deterministically | Needs a model |
|---|---|
| Protocol conformance (external oracle, gating) | Task accuracy against ground truth |
| Wire bytes per surface (exact, reproducible) | Tool calls made, redundant-call patterns |
| The index's round-trip trade (18.2x, measured) | Whether a description is *clear* |

Everything in the left column ships here and gates. The right column stays a charter, and it
should be re-scoped again before it is executed rather than inherited from this log — the same rule
that produced this release instead of the one that was written down.
