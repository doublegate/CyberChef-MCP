# v3.2.0 findings log

What was measured before writing anything, including what the charter got wrong and what I got
wrong. Same purpose as the v2.2–v3.1 logs: the numbers and the reasoning, so a later reader
inherits the evidence rather than the conclusion.

The full pre-release capture is [`measurements/v3.1.0-baseline.md`](measurements/v3.1.0-baseline.md),
taken against the released v3.1.0 before any of this changed.

---

## F-01 — The charter's feature track was aimed at the wrong tools — **RE-SCOPED FROM DATA**

Track A proposed a `response_format: concise | detailed` enum across the high-volume tools, citing
a measured 65% reduction. The charter's own instruction was to extend the harness and measure this
catalogue first, because *"the published numbers come from servers with a handful of verbose tools;
a server whose results are mostly short binary transforms may not behave the same way, and that
would be the finding worth writing up."*

It was. `npm run measure:results`, through a real client:

```text
case                            bytes
short transform                    55
analysis                           57
error: missing argument           448
error: unknown operation          457
magic (unknown data)            1,688
describe one operation          3,115
category index                  5,529
describe five operations        7,603
list one category              18,057
search                         27,060
large transform (64 KB in)     87,423
```

**Median 3,115 bytes.** A format enum across 504 operation tools buys nothing: their results are
the data the caller asked for, and the two largest cases are a 64 KB payload (incompressible by
definition — it *is* the answer) and one outlier.

The outlier is the finding, and a generic flag would not have fixed it. See F-08.

**SemVer:** additive. New scripts and gates, one tool result summarised with an opt-in flag
restoring the old shape, one security-relevant documentation correction. Nothing a caller depends
on breaks. MINOR is correct.

## F-02 — The image is not shell-free, and the docs made that a security argument — **FIXED**

The sharpest finding, and it came from a routine baseline capture rather than from looking for it.

`README.md` and `docs/wiki/Installation.md` both said the image contains **no shell**, README
framing it as the point: *"the attack surface is the point rather than the size — no shell, no
package manager, and a Wolfi base rebuilt daily."*

```text
$ docker run --rm --entrypoint /bin/sh ghcr.io/doublegate/cyberchef-mcp_v3:3.1.0 -c '...'
sh       /usr/bin/sh          apk      absent
ash      /usr/bin/ash         wget     absent
busybox  /usr/bin/busybox     curl     absent
npm      /usr/bin/npm         BusyBox v1.38.0, ID=wolfi
```

The "no package manager" half is true. The "no shell" half is false, `npm` is present, and the base
is `cgr.dev/chainguard/node:latest` — not the distroless variant the docs called it.

This matters more than a wrong number because **a reader may have sized the blast radius of a
container compromise on it**. Both documents now say what is present and say that they used to say
otherwise. Whether to move to a genuinely shell-free base is a real question with real risk, and it
belongs in a release that measures it rather than in the commit that discovers the error.

Three further numbers, all in live documents:

```text
README   image on disk        726 MB  ->  453 MB    (predates the v2.8.0 `npm prune` work)
README   gzipped tarball     ~196 MB  ->  141 MB    (the published release asset)
AGENTS   production packages      432 ->  402 / 384 depending on the counting method
```

The package count is the instructive one: 402 by `find -maxdepth 3 -name package.json`, 384 by
walking directories that contain one, and all three figures are defensible answers to slightly
different questions. **The defect is a document quoting a number without its method**, not the
number itself.

## F-03 — The first variance study was wrong by an order of magnitude — **CORRECTED**

Making the benchmarks able to fail (Track B) needs a tolerance, and a tolerance has to be measured
rather than picked. The first attempt measured per-task spread across three runs and reported:

```text
SHA2 (100KB)  84%      To Base64 (100KB)  45%
SHA2 (10KB)   71%      To Base64 (1KB)    32%
```

Numbers like that justify a tolerance so wide the gate can never fire — which is how a gate gets
built that satisfies a checklist and catches nothing. Two causes, both invisible in the printed
tables and both only findable once the numbers were collected rather than printed:

1. **A task-name collision.** `SHA2` is registered twice, once for 256 and once for 512, and both
   emitted tasks called `SHA2 (1KB)`. Printed side by side that reads as a repeat; keyed by name it
   silently conflates two operations. The 84% "variance" was SHA-256 and SHA-512 taking turns in
   one slot.
2. **JIT warm-up on the first bench of a cold process.** `To Base64 (1KB)` measured 7,482 ops/s in
   a fresh process and 11,445–12,188 across later runs. It is the first benchmark registered, so it
   absorbs the warm-up.

With names disambiguated and the cold run discarded, four runs give a **worst spread of 9.8% and a
median of 4.3%**. The tolerance is 25% — about 2.5x the worst observed — because a regression that
matters is a factor, not a few percent, and a gate tuned to a few percent on a shared runner is a
gate that gets disabled within two releases.

Recorded because the wrong answer was more plausible than the right one: 84% variance on a
JIT-compiled workload is *believable*, and believing it would have produced a useless gate with a
measurement to justify it.

## F-05 — Nothing rendered the chart this project publishes — **FIXED**

Found in v3.1.0 (F-10) and fixed here. No workflow linted, rendered or installed
`deploy/helm/cyberchef-mcp`, and v3.1.0's own `image.digest` addition was verified by rendering it
through a container **by hand** — the manual step a gate exists to replace.

`helm-chart.yml` lints `--strict` and renders four values paths, asserting both directions of the
digest logic: a digest wins over the tag, **and** the default still renders the tag. A template
that always rendered a digest would pass the first assertion and be wrong.

It does not install, and the debt statement was corrected rather than left overstating the scope.
`--dry-run=server` catches admission and API-version rejections a local render cannot, but this
chart's ServiceMonitor needs the Prometheus operator CRDs — a bare cluster would reject a valid
manifest, and a gate that fails on correct input is a gate people disable.

## F-06 — Three documents said 505 where the config says 504 — **FIXED AND GATED**

`check:versions` covered versions and package majors. It did not cover derived counts, and nothing
did:

```text
deploy/helm/cyberchef-mcp/templates/prometheusrule.yaml   "loads all 505 operations"
README.md                                                 "import of all 505 operations"
docs/wiki/Release-History.md                              "440 -> 505 operations"
```

The first is the one that matters: it is the alert description an operator reads while diagnosing a
restart loop, so the wrong number arrives at the worst moment.

The count is now read from the generated `OperationConfig.json` rather than hardcoded — a check that
must be hand-edited on every upstream sync is a check that gets edited wrongly — and the locations
are skipped when the config has not been generated, so the script still runs on a fresh clone.

## F-07 — No defect in the metadata, and no guard either — **GUARDED**

Every tool name, description, argument name and dropdown option a model reads comes from
`OperationConfig.json`, generated from a tree this fork mirrors from upstream verbatim. That is a
path from an upstream commit to text a model treats as instruction, and **the fork's review of a
sync is a diff review** — so the one thing a reviewer cannot catch is the one thing worth screening
for. A Unicode TAG-block sequence renders as nothing in a diff.

```text
7,408 strings across 504 operations
  TAG-block   0      bidi override  0
  control     0      zero-width     0
  non-ASCII  89      (accents, Greek, mathematical symbols -- all legitimate)
```

Ordinary non-ASCII is tolerated deliberately: a rule banning it would fail the first sync that adds
a cipher name with a diacritic, and then the rule gets removed rather than the metadata fixed. The
guard is against text a reviewer **cannot see**, not text a reviewer might not expect.

Two things keep it from passing vacuously, which is what a screening test is most prone to: the
input string count is asserted, and every screen is proven against a synthesised positive and a
clean negative — so a mistyped range cannot look identical to a clean tree.

In `upstream-sync.yml` it is a **blocking** step, unlike the suite beside it, which records
pass/fail and lets the PR open for a human. That is right for a broken test and wrong for metadata
whose entire property is that the human cannot see it.

## F-08 — Search returned more than `describe_operation` — **FIXED**

The outlier from F-01, and the reason a generic format flag was the wrong plan.

`cyberchef_search` returned raw `help()` output: the full `OperationConfig` entry for every match —
module, HTML description, infoURL, input and output types, and every argument with its defaults.

```text
"base64"  14 matches   27,060 bytes
"aes"     21 matches   35,642 bytes
```

For comparison, `describe_operation` for **five** operations is 7,603 bytes. So the discovery tool
returned several times what the detail tool returns, for operations the caller had not chosen yet.
That is the index surface paid twice, by the one tool sitting outside the hierarchy the rest of the
design commits to: `list_operations` returns names and one-liners, `describe_operation` is the one
place a full schema is paid for.

```text
"base64"  27,060 -> 3,087 bytes   (-88.6%)
```

`detailed: true` restores the old payload, opt-in rather than default, because the default is what
every model pays. The tool description now states what the flag costs, which is the "truncate with
guidance" principle from Track A applied to the one place it earns its keep.
