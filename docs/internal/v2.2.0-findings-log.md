# v2.2.0 running findings log

Live record of defects, gaps and improvement opportunities found while exercising the shipped
v2.1.x server. Each entry states how it was found, what is actually wrong, and the disposition.

Status key: **OPEN** (not yet fixed) - **FIXED** (landed in v2.2.0) - **WONTFIX** (with reason).

---

## F-01 - The coverage gate has been red on `master` since the v2.1.0 merge - **FIXED**

**Found:** PR 96 (`release/v2.1.1`) reported one failing check, `test`. All 805 tests passed; the
job failed on the coverage thresholds, all four of them.

**Actually wrong:** commit `865e217a` (the v2.1.0 merge) added ~800 lines of new
`src/node/lib/*.mjs` and 252 lines to `mcp-server.mjs`. The tests that exercise them
(`stdio-client-contract`, `examples`) drive the server as a **child process**, and v8 attributes
nothing a child does to the parent. So `tool-catalog.mjs` measured 2.17% while being thoroughly
exercised, and the global lines/statements/branches/functions all fell under their floors.

Two facts made this worse than a number going down:

- **`handler-dispatch.test.mjs` does not dispatch handlers.** Its header claims it "Tests all
  handler branches in the CallTool request handler"; it imports ~30 re-exported helpers and asserts
  on those. `createMcpServer()` was called by **no test in the suite**, so the entire tool-call
  handler (lines ~466-1090, 263 of 309 statements) counted as dead code.
- **PR 92 never ran the `test` job**, so v2.1.0 was merged and tagged with this gate already red on
  the default branch.

**Disposition:** added `tests/mcp/in-process-handlers.test.mjs`, which connects a real MCP `Client`
to `createMcpServer()` over `InMemoryTransport.createLinkedPair()`. Genuine protocol round trips in
one process, so every dispatch branch is both exercised and measured. Not fixed by lowering the
threshold, and not by mocking.

## F-02 - A draft recipe cannot be validated - **FIXED**

**Found:** calling `cyberchef_recipe_validate` with `{name, operations}` while writing F-01's tests.

**Actually wrong:** it rejects with `invalid_type` on `id` and `version`:

```
"Invalid input: expected string, received undefined"  path: ["id"]
"Invalid input: expected string, received undefined"  path: ["version"]
```

`id` and `version` are **server-assigned**. Requiring them means the tool can only validate a recipe
that has already been saved - which is the case where validation is least useful. The natural use
("check this before I store it") is impossible.

`cyberchef_recipe_test` has the same requirement and additionally returns it as a hard error rather
than the structured `{valid:false, error}` that `recipe_validate` returns, so the two disagree about
how a bad recipe is reported.

**Disposition:** FIXED. `DraftRecipeSchema` makes the four server-assigned fields (`id`,
`version`, `created`, `updated`) optional, and `validateRecipe` takes a `{draft: true}` option that
the validate/test tools pass. A recipe read back out of storage is still validated strictly, where
a missing `id` means the record is damaged rather than unsaved.

Nothing that decides whether a recipe is *correct* was relaxed - operation names, arguments and the
composition graph all run against `operations`, which stays required. Verified: a draft now
validates (`valid: true`) and tests (`SGVsbG8=`), while a bad operation name and an empty operation
list are still rejected with structured errors.

## F-03 - `Generate QR Code` returns an empty string - **FIXED**

**Found:** probing image operations for the v2.2.0 multi-modal theme.

**Actually wrong:** the operation produces `<img src="data:image/png;base64,...">` (606 chars, a
valid PNG). v2.1.0 converts `html`-output operations to plain text with
`Utils.unescapeHtml(Utils.stripHtmlTags(...))`, which deletes the entire tag and leaves `""`.

Not a v2.1.0 regression - v2.0.0 returned `{}` for the same call, because it `JSON.stringify`'d the
Dish. The operation has never worked over MCP; only the failure mode changed.

The same applies to every image-producing operation (`Render Image`, `Rotate Image`, and the rest of
the `html`-output image set).

**Disposition:** FIXED. `src/node/lib/content-blocks.mjs` returns an MCP `image` block when an
html operation's markup carries a data-URI image, and reduces the markup to text only when it does
not - so `Magic` stays readable while the picture survives. An image is also detected by magic
number, which covers `From Base64` of a PNG, where no markup is ever produced.

Verified end to end: `Generate QR Code` now returns `type=image mimeType=image/png` with 572 bytes
of base64; `Render Image` likewise; `Magic` still returns plain text.

## F-04 - Binary output is returned as mojibake - **FIXED (opt-in)**

**Found:** the same probe. `cyberchef_bake` with `Gzip` on `hello world` returns 41 characters of
Latin-1 mojibake beginning with the gzip magic rendered as text.

**Actually wrong - and less wrong than it looks.** The presentation is unreadable, but it was
measured rather than assumed, and the measurement changes the disposition: the latin1 mapping is
**byte-for-byte reversible**, verified over a gzip payload with `str.charCodeAt(i) === bytes[i]` for
every byte. So no data is lost; a client that knows the convention recovers the payload exactly.

This is therefore a readability problem, not a correctness one, and it is treated differently from
F-03. 76 operations declare `ArrayBuffer` or `byteArray` output, and changing the default for all of
them - to fix something that is not actually broken - is a worse trade than an opt-in.

**Disposition:** FIXED as an opt-in. `CYBERCHEF_BINARY_OUTPUT=base64` returns base64 instead; the
default is unchanged. Binary that *is* an image is promoted to an `image` block regardless, since
that case genuinely was broken (F-03).

## F-05 - `--openssl-legacy-provider` is inert in the shipped image - **FIXED**

**Found:** the discipline battery against the published `ghcr.io/doublegate/cyberchef-mcp_v2:2.1.0`
container. `Generate all hashes` returns:

```
Error [INVALID_INPUT]: Generate all hashes - error:0308010C:digital envelope routines::unsupported
```

**Actually wrong:** the v2.1.0 release notes say this was fixed by setting
`--openssl-legacy-provider` in `npm run mcp` and in the image's `NODE_OPTIONS`. The variable **is**
set - `podman inspect` confirms `NODE_OPTIONS=--openssl-legacy-provider` - and it does nothing,
because the Chainguard runtime has **no legacy provider module to load**:

```
$ podman run --rm --entrypoint /usr/bin/node <image> -e "require('crypto').createHash('md4')"
Unable to load legacy provider.
node v26.8.1   openssl 3.6.4
   md4 FAIL error:0308010C   md5 OK   ripemd160 OK   whirlpool FAIL
```

A filesystem walk of the whole image finds **no** `*legacy*.so`. So the flag emits a warning on
every container start and changes nothing. This is the same shape as the SafeRegex incident: a
mitigation documented as active that the shipped artefact does not carry.

**Blast radius is one operation, not the twenty it looks like.** Testing all 21 members of
`Generate all hashes` individually in the container: **20 pass**, including `MD4`, `NT Hash` and
`Whirlpool` - CyberChef implements those in JavaScript, so OpenSSL never enters. Only **`LM Hash`**
fails, because it delegates to `ntlm@0.1.3`, whose `smbhash.lmhash` calls
`crypto.createCipheriv('DES-ECB', ...)` (`node_modules/ntlm/lib/smbhash.js:46`), and single DES is
legacy-only under OpenSSL 3.

**Disposition:** drop the OpenSSL dependency instead of trying to satisfy it. `node-forge` (1.4.0,
already a direct dependency) does DES-ECB in pure JavaScript, and a fork patch to `LMHash.mjs`
reproduces both canonical vectors exactly:

```
LM("password") = E52CAC67419A9A224A3B108F3FA6CB6D   (matches)
LM("")         = AAD3B435B51404EEAAD3B435B51404EE   (matches)
```

That works in any environment rather than only where a legacy provider happens to be installed.

**Verified in a rebuilt container**, which is where it failed: `LM Hash` returns
`E52CAC67419A9A224A3B108F3FA6CB6D` and `Generate all hashes` returns all 44 lines with no error.
The full 62-case battery is now **62/62** against the new image.

The flag itself is removed from `Dockerfile.mcp` and both npm scripts. It was load-bearing nowhere:
this development host also lacks the legacy provider, and all 2,289 operation tests plus 241 Node
API tests pass without it. The `docs/guides/user_guide.md` claim that it is "not optional" is
corrected, and `docs/releases/v2.1.0.md` carries an inline correction so the false claim is not left
standing in the published record.

## F-06 - `Generate all hashes` is all-or-nothing - **OPEN**

**Found:** the same failure. One unavailable algorithm out of 21 threw, and the caller lost **all
twenty hashes that computed correctly**.

**Actually wrong:** the operation has no per-algorithm error handling, so any single failure
propagates out of the whole operation. For a tool whose entire value is "give me every hash of
this", that is the worst possible failure mode - the twenty results the analyst wanted are
discarded because of one they did not.

**Disposition:** compute each algorithm independently and report per-algorithm failures inline,
so an unavailable hash costs its own line rather than the whole answer. Worth doing on its own
merits even once F-05 removes the only current trigger.

## N-01 - Not a defect: stdio framing under concurrency

Recorded because it looked exactly like a serious server bug and cost real time.

Driving 62 concurrent calls, one 7,783-byte `XOR Brute Force` response arrived as 10 unparseable
fragments, deterministically. The server is correct: captured in binary it is **one valid JSON
document, valid UTF-8, with exactly one trailing newline**.

The harness was wrong. Python's `subprocess(text=True)` decodes and then `str.splitlines()` splits
on **U+0085, U+2028 and U+2029** as well as `\n` - and JSON only escapes below `0x20`, so those
characters appear literally in any response carrying high bytes. Splitting on `chr(10)` alone fixes
it.

Worth keeping: any client that frames MCP stdio with a Unicode-aware line splitter will corrupt
responses from binary-producing operations, and will blame the server.

## F-07 - The coverage gate cannot run on a pull request - **FIXED**

**Found:** after pushing F-01's fix to PR 96, the `test` check did not turn green - it **disappeared
from the PR entirely**, and no `MCP Server CI` run existed for the commit.

**Actually wrong:** two independent gaps that together mean the MCP suite and the coverage gate were
never a merge requirement.

1. **`core-ci.yml` has no `pull_request` trigger at all.** It runs on push to `master` and
   `release/**`. A PR from an ordinary feature branch therefore never runs the MCP tests or
   `test:coverage`; the checks that appeared on PR 96 came from the *push* to its release branch,
   which only happens because release branches are in the push filter.
2. **Its `paths:` filter omits `tests/**` and `vitest.config.mjs`.** It lists `src/core/**`,
   `src/node/**`, `package.json` and `.github/workflows/**`. So a test-only commit cannot trigger
   the gate - which is why the commit that *fixed* the thresholds could not demonstrate it, and,
   worse, a change that breaks a test while touching nothing else would pass unnoticed.

`pull_requests.yml` does run on PRs, but only `lint`, `npm test` (core) and `testnodeconsumer` - no
MCP tests, no coverage.

This is the mechanism behind F-01: v2.1.0 was reviewed, merged and tagged while all four coverage
thresholds were failing, because the job that checks them never ran on its PR and only went red
afterwards, on the push to master. A gate that cannot fail before a merge is not a gate.

**Disposition:** FIXED.

- `pull_requests.yml` gains an `mcp-test` job running `npx grunt configTests` then
  `npm run test:coverage`, so every PR is gated on the MCP suite and all four thresholds.
- `core-ci.yml`'s `paths:` filter gains `tests/**`, `vitest.config.mjs`, `Gruntfile.js` and
  `package-lock.json` - everything the gate's result actually depends on.

## F-08 - A misspelled argument is silently ignored - **FIXED**

**Found:** running a battery of complex multi-stage recipes drawn from the upstream corpus. The
"three rounds of base64 via Label+Jump" case returned **one** round decoded and reported no error:

```
input   YUhSMGNEb3ZMM04wWVdkbE1pNWxlR0Z0Y0d4bEwzQmhlV3h2WVdRdVltbHU=  (after one decode)
expected  http://stage2.example/payload.bin                            (after three)
```

**Actually wrong:** the recipe passed `{label: "top", maximum_jumps: 2}`. `Jump`'s real argument
names are `label_name` and `maximum_jumps_if_jumping_backwards`. Both keys matched nothing, both
were **silently dropped**, and the defaults were used instead:

```
{label: "top", maximum_jumps: 2}   ->  ["", 10]     // empty label: no jump ever happens
{label_name: "top", maximum_jumps_if_jumping_backwards: 2}  ->  ["top", 2]
```

So the recipe ran, returned data, and was wrong, with nothing to indicate it. Both paths had the
defect - `toPositionalArgs` in the recipe path and the direct operation-tool path in
`mcp-server.mjs` - because both iterate the operation's argument definitions and never look at what
the caller actually sent.

This is not an unlikely mistake. CyberChef's UI labels sanitise into forms nobody would guess
(`Maximum jumps (if jumping backwards)` -> `maximum_jumps_if_jumping_backwards`), so a caller
working from the operation's *documentation* rather than from `cyberchef_describe_operation` will
hit it. And for a server used in forensic and malware work, a confidently wrong answer is the worst
failure mode available - worse than an error, because nothing prompts a second look.

**Disposition:** FIXED. `assertKnownArgs` rejects any key the operation does not have, naming both
the offending keys and the accepted ones:

```
Unknown arguments for "Jump": label, maximum_jumps
  accepted: ["label_name", "maximum_jumps_if_jumping_backwards"]
  hint: Valid arguments: ... Use cyberchef_describe_operation for types and defaults.
```

Applied to both paths. The raw CyberChef label (`{"Label name": "top"}`) is still accepted, so a
recipe written against the UI keeps working, and the `input` data parameter is excluded from the
check because it is this server's addition rather than one of the operation's own.

## F-09 - `cyberchef_bake` advertised only positional arguments - **FIXED**

**Found:** wiring the container into Claude Code as a real MCP server and reading the schema the
client actually loaded for `cyberchef_bake`:

```json
"args": {"description": "Arguments for the operation", "items": {}, "type": "array"}
```

**Actually wrong:** array only. The implementation has accepted **named** arguments since DEP005,
and named arguments are the entire reason a model can use these operations correctly - they are what
v2.1.0's whole tool-usability effort was built on. So the advertised contract contradicted both the
implementation and the design.

Two consequences:

- A client that validates outbound arguments against `inputSchema` **cannot send the supported
  form at all**. It happens to work from Claude Code because that does not strictly validate
  outbound arguments, which is precisely the kind of accident that hides a contract bug.
- `cyberchef_recipe_create` declares the same concept as `z.record(z.any())` - an object - two tools
  away. The server disagreed with itself about how a recipe step is written.

**Disposition:** FIXED. `args` is now `z.union([z.record(z.string(), z.any()), z.array(z.any())])`,
so the schema advertises `anyOf: [object, array]` - named listed first, since it is the primary
form - with a description pointing at `cyberchef_describe_operation` for the argument names. All
three forms verified through a real client: named, positional and omitted all return `SGVsbG8=`.

Worth noting how it was found: only by connecting a real MCP client and reading the schema it
loaded. Neither the test suite nor the container harness had ever compared the *advertised* argument
shape against the *accepted* one - the same blind spot, in a new place, that let 524 empty schemas
ship for three releases.

## F-10 - `Play Media` loses its audio the same way images were lost - **FIXED**

**Found:** looking for the rest of the v2.2.0 multi-modal theme after F-03, by asking which other
operations put a payload inside markup.

**Actually wrong:** `Play Media` emits

```
<audio src='data:audio/x-wav;base64,UklGRogAAABXQVZF...' type='audio/x-wav' controls>
```

296 characters of markup carrying the whole recording. The html-to-text conversion reduced it to
**23 characters of player chrome** and deleted the audio. Identical to F-03 in every respect except
which tag the payload rode in.

MCP has an `audio` content block alongside `image`, so the fix is the same shape as F-03's:

**Disposition:** FIXED. One extractor now covers `<img>`, `<audio>` and `<video>` rather than three
near-copies, and the block type is chosen from the payload's MIME type. Magic-number sniffing gained
WAV, MP3 (ID3) and OGG, so binary audio is promoted too - the path `From Base64` of a WAV takes,
where no markup exists.

RIFF needed care: `RIFF....WAVE` is audio and `RIFF....WEBP` is an image, and the first four bytes
are identical. A prefix table would have had to guess, so the form type is read separately, and a
buffer truncated before it decides nothing rather than guessing.

**Video is the honest exception.** MCP has no video content block, so the data URI is returned as
text - unreadable, but *recoverable*, which is the entire difference between that and stripping it.
Returning an `image` block for a video would be worse than returning nothing.

Verified through a real client: `Play Media` returns `type=audio mimeType=audio/x-wav`, while the
QR code still returns an image and `Magic` still returns plain text.

## F-11 - Relative links in release notes 404 on the Releases page - **FIXED**

**Found:** raised by Copilot on PR 96, verified against the workflow, fixed for that one file and
deferred here for the durable fix.

**Actually wrong:** `mcp-release.yml` publishes `docs/releases/<tag>.md` as the GitHub Release body
(`--notes-file`). A release body renders on the Releases page, not inside the tree, so
`[text](../security/foo.md)` 404s for every reader of the release - the audience the file exists
for. Already-published notes carry **8 broken links in v2.0.0 and 3 in v2.1.0**; v2.1.1's were
caught only because a reviewer happened to look.

**Disposition:** FIXED at publish time rather than per-file, so a future note cannot reintroduce it:
the author writes the link that works in the repository, and `scripts/absolutise-release-links.py`
makes it work on the release page too, pinned to the tag.

**Two mistakes made while writing this fix**, both caught before shipping and both now pinned by
tests, because neither is obvious:

1. **A `sed` version was wrong for the commonest case.** It dropped every leading `../` and
   prepended the repository root. But `../guides/tutorial.md` sits beside the notes under `docs/`,
   so it resolves to `docs/guides/tutorial.md`, not `guides/tutorial.md`. Only `../../` happened to
   land correctly - which is why the first test run *looked* fine. Paths are resolved now, not
   pattern-stripped.

2. **An inline heredoc would have broken every release.** The logic started as
   `python3 - <<'PY'` inside the workflow. Within a YAML block scalar the terminator keeps its
   indentation, and a quoted heredoc ends only on a line that is exactly the delimiter - so the
   heredoc ran to end of file and `bash -n` reported "unexpected end of file". Extracting the
   workflow step and running `bash -n` on it is what caught this; nothing else would have, until a
   release failed.

Moved to a script, which also makes it testable: `tests/mcp/release-links.test.mjs` runs it as a
subprocess from the existing vitest gate, since the release job has no `setup-node` and Python
avoids adding one. Nine cases, including the two mistakes above, directory trailing slashes,
anchors, external URLs, and a link that escapes the repository root (left alone for a human rather
than published as a URL that cannot resolve).

## F-12 - `recipes.json` was gitignored and tracked at the same time - **FIXED**

**Found:** `git status` after running the new example showed `M recipes.json` — a file `.gitignore`
explicitly lists.

**Actually wrong:** `.gitignore` has no effect on a file already tracked, and `recipes.json` was
committed in v1.6.0. So the default recipe store sat in the repository, and any run of the server
or an example from a checkout modified it. Exactly the defect PR 57 fixed for
`src/core/config/OperationConfig.json`, in a second place.

Two smaller things fell out of the same look:

- **The ignore list missed the suffix the code actually writes.** `recipe-storage.mjs:219` writes
  `${filePath}.backup`; `.gitignore` listed `.bak`. So the backup file the server creates was never
  ignored — and the comment directly above that block warns the store "may hold keys and IVs, since
  a saved recipe carries its arguments".
- **The examples wrote into the checkout.** `CYBERCHEF_RECIPE_STORAGE` defaults to
  `./recipes.json`, and only example 05 pointed it elsewhere. Any other example that saved a recipe
  wrote user data into the repository root.

**Disposition:** FIXED. `recipes.json` untracked (`git rm --cached`; the file stays on disk),
`.backup` added to `.gitignore`, and `connect()` in `examples/_lib.mjs` now points every example at
a temp directory, so no example can write into a checkout. Verified: running example 09 leaves
`recipes.json` byte-identical.

## F-13 - The examples still passed the inert OpenSSL flag - **FIXED**

**Found:** reading `examples/_lib.mjs` while fixing F-12.

**Actually wrong:** `connect()` spawned the server with `--openssl-legacy-provider`, carrying a
comment that said the flag was needed or `Generate all hashes` "returns its input unchanged rather
than erroring". Wrong twice over, and F-05 had already established both halves: the flag is inert on
any Node without a legacy provider module, and the one operation that reached OpenSSL now computes
DES in JavaScript.

Left behind when F-05 removed the flag from `Dockerfile.mcp` and both npm scripts — a reminder that
"remove the flag" means every place that passes it, not only the places that are obviously builds.

**Disposition:** FIXED. Flag removed, comment replaced with what is actually true. Also corrected
`call()`'s doc comment, which claimed "every CyberChef tool returns a single text block" — no longer
so, now that image and audio operations return blocks carrying `data` and no `text`.
