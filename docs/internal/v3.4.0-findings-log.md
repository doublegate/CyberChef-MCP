# v3.4.0 findings log

What was measured before writing anything, including what the plan got wrong and what I got wrong.
Same purpose as the v2.2–v3.3 logs.

---

## F-01 — The workflow added so a tolerance could come down had never run, and fails when it does — **FIXED**

v3.3.0 added `benchmark-baseline.yml` for one stated reason: the regression gate ships at a **50%**
tolerance, that number is a stopgap for a baseline captured on a developer machine and compared
against a GitHub runner, and the charter said plainly it *"should come down on the first
runner-captured measurement, not on the expectation of one."*

The first thing this release measured was whether that measurement exists.

```text
gh run list --workflow=benchmark-baseline.yml
(no runs)
```

**It had never run.** Manual and monthly-scheduled, added 2026-09-04, and the schedule had not yet
come round — so the whole reason it exists was still outstanding, and nothing said so, because a
workflow that has never run reports nothing at all.

Dispatched it. The `capture` job succeeded and pushed the branch. The `open-pr` job failed:

```text
##[error]GitHub Actions is not permitted to create or approve pull requests.
```

Confirmed at the source:

```json
{"can_approve_pull_request_reviews": false, "default_workflow_permissions": "read"}
```

The workflow's own design note explains why it opens a pull request: *"moving a gate's reference
point silently is indistinguishable from switching the gate off."* That reasoning is right and the
mechanism was the one thing the repository forbids — a constraint this project had already hit
twice, in `upstream-sync.yml` and `upstream-monitor.yml`, and written down.

Two defects in one workflow, and both are the same defect underneath: **it was written and never
executed.** A workflow that has not run is not a workflow, it is a plan in YAML.

## F-02 — The runner-captured measurement, and what it licenses — **MEASURED**

The capture that F-01 finally produced, against the committed developer-machine baseline:

```text
cross-machine drift      worst slower -23.1%   worst faster +43.6%   median -10.5%
runner's own spread      max 15.2%   median 3.6%     (4 runs, one instance)
```

The second row is the one that decides the tolerance. Once the baseline is captured **on the
runner**, the gate no longer has to absorb the cross-machine gap in the first row — only the
runner's own run-to-run variance.

That is also why 25% failed in v3.3.0 and why it is not simply reinstated here. The two false
failures then (`Entropy (100KB)` -25.3%, `Frequency distribution (100KB)` -25.5%) were
cross-machine, and a runner-captured baseline removes their cause. But 15.2% comes from **one
runner instance**, and GitHub's pool is not homogeneous; picking a tolerance from one sample is the
mistake this project has made twice already, most recently the `DIVISOR_MARGIN` study that looked
best at 1.10 over 72 cases and turned out worse than changing nothing over 400.

So: three captures, cross-instance, before the number moves.

## F-03 — Three Forensics operations were dead through the whole fork — **FIXED**

`Unzip`, `Untar` and `Extract Files` output `List<File>`. Through this server, none of them has
ever worked. Not degraded — dead, since v1.0.0, while all three stayed advertised in `tools/list`
and every suite stayed green.

Two independent defects stack, which is why it survived so long: fixing either one alone leaves the
operation still broken, in a different way.

### Defect 1 — `Utils.readFile` rejects the type its own signature promises

`src/core/Utils.mjs:1231`. The JSDoc example is literally
`await Utils.readFile(new File(["hello"], "test"))`, and the Node branch was:

```js
return Buffer.from(file).buffer;
```

`Buffer.from` accepts a string, `Buffer`, `ArrayBuffer` or array-like. The `src/node/File.mjs` shim
is none of those, so this throws `ERR_INVALID_ARG_TYPE`. `Chef.bake` presents every dish
unconditionally and `displayFilesAsHTML` reaches here once per member — so the operation threw
**inside the presenter, after `run()` had already succeeded**, and the caller saw an error naming a
type conversion rather than the archive.

Fixed by `patches/fork/11-utils-readfile-accepts-file.patch`. `src/core/**` is mirrored, so a
hand-edit here would be reverted by the next sync and stay reverted — which is precisely what
happened to the SafeRegex mitigation, documented at
`docs/security/2026-08-30-saferegex-reverted-by-upstream-sync.md`. The patch is verified to apply
against a pristine `git show HEAD:` copy and reproduce the working tree byte for byte.

`.buffer` is also sliced to the view's own window rather than returned whole, for the reason
`patches/fork/09` documents: a small `Buffer` is a window onto a shared 8 KB pool, and returning
the pool leaks unrelated memory to the caller. It presented here as `RangeError: offset is out of
bounds`.

### Defect 2 — the global `File` shim is never installed in this process

Five operations construct a **bare global** `File` — `Unzip`, `Untar`, `Tar`, `Zip`,
`Split Colour Channels` — and **not one of them imports it**. In a browser that is the platform's
`File`. On Node the shim at `src/node/File.mjs` stands in, and the only assignment in the tree is:

```
src/node/index.mjs:516    global.File = File;
```

That is the **generated bridge**, which this server deliberately does not import eagerly — the note
at the top of `mcp-server.mjs` explains why (it pulls all 504 operation implementations at
startup). The optimisation is right; its side effect went with it.

So `new File(...)` inside an operation resolved to **Node's own global `File`** — a `Blob` subclass
with no `.data`, whose bytes are reachable only through an async `arrayBuffer()`. The result is the
worst available failure mode: `Unzip` parsed the central directory correctly and returned members
with the **right names and zero bytes each**. That does not read as a defect. It reads as an empty
archive.

Fixed in `src/node/lib/core-recipe.mjs`, which every bake path goes through. The worker path
already gets the shim from the bridge it does import.

### Why eleven releases of a green suite never saw it

**Defect 2 cannot be reproduced in-process.** Every earlier probe — and every existing test that
touches baking — imports `bakeOnCore`, and `core-recipe.mjs` now installs the shim on import. Before
the fix, any harness that had loaded the bridge for any reason put the shim back, and the bug
vanished. Six separate hypotheses were ruled out (module duplication, the retry wrapper, caching,
`bootstrap-config`, worker dispatch, recipe normalisation — the last verified by diffing
`toCoreRecipe` output between contexts, which was byte-identical) before the difference turned out
to be the one thing an in-process test cannot vary: whether the bridge had been loaded at all.

This is the same blind spot as the three releases that shipped 524 tools with an empty
`inputSchema`, and it has the same answer. `tests/mcp/list-file-output.test.mjs` spawns the real
server and speaks to it through the official SDK client. Verified as a regression test rather than
assumed: with the shim commented out, **4 of its 6 assertions fail** — and the 2 that pass are
exactly the two that check names and the absence of markup, which defect 2 never broke.

### Scope

`Tar`, `Zip` and `Split Colour Channels` construct the same global `File` and are fixed by the same
change. The rendering of `List<File>` results is a separate decision, made in `core-recipe.mjs` and
documented there: the dish leaves the value as an array of per-file arrays on Node — deliberate
upstream behaviour that `tests/node/tests/NodeDish.mjs:226` asserts — and the presenter emits a
browser file-list table with names, sizes, two button labels, and the contents nowhere in it.
Neither gives a caller what they unzipped an archive to get.

## F-04 — `server.json` had never been validated by anything — **FIXED**

The file exists to be machine-read by the MCP registry. Nothing read it. Validated for the first
time in v3.4.0, it failed against the schema it declares in **six** places:

```text
/description                 153 characters, against a 100-character limit
/packages/0, /packages/1     missing `registry_type`; `registryType` not permitted
                             missing `registry_base_url`; `registryBaseUrl` not permitted
```

The cause is not a typo. The file was **written to** the 2025-09-29 schema, which is camelCase, and
**declared** the 2025-07-09 schema, which is snake_case. Both URLs resolve, both are real schemas,
and the document is internally consistent — so nothing about reading it suggests a problem. Against
the schema it was actually written to, exactly one error remains, and that one is real: the
description was 53 characters over the limit.

Fixed by declaring the schema the file is written to and shortening the description to 93
characters. `npm run check:server-json` is now the gate, wired into `core-ci.yml` and
`pull_requests.yml` beside `check:versions`.

**Why not `ajv`.** It is in `node_modules` only as a transitive dependency of something else, so a
gate built on it disappears the day that dependency drops it — silently, at a moment unrelated to
this file. More decisively, validating against the live schema URL would make the gate need the
network, and this project ships an explicit offline posture and an air-gapped deployment guide. The
rules are transcribed instead, with the retrieval date recorded, and the checker **fails when
`$schema` names a version whose rules it does not have**. That last part is the whole design: a
checker that silently checks the wrong rules is precisely the defect it was written for.

### The registry ownership proofs, both absent

Publishing to the registry needs proof of ownership per package type
(`modelcontextprotocol/registry`, `docs/modelcontextprotocol-io/package-types.mdx`, retrieved
2026-09-04):

- **npm** — `mcpName` in `package.json`, which MUST equal `name` in `server.json`.
- **OCI** — an `io.modelcontextprotocol.server.name` annotation on the image, same rule.

Neither existed. Measured rather than inferred: `npm view cyberchef-mcp mcpName` is empty across
**all eleven published versions** (2.5.0 through 3.3.0), and
`registry.modelcontextprotocol.io/v0/servers?search=cyberchef` returns `{"count": 0}`. A registry
publish today would be rejected on both packages.

Both are now present, and `check:server-json` asserts all three copies of the identifier agree —
one identifier in three files is three chances to drift, which is the same shape as the version
drift that produced `check-version-consistency.mjs`.

The OCI annotation is verified by **reading it off a built image**, not by reviewing the Dockerfile:

```text
$ docker inspect cyberchef-mcp --format '{{index .Config.Labels "io.modelcontextprotocol.server.name"}}'
io.github.doublegate/cyberchef-mcp
```

Registry publication itself is a separate, outward-facing act and is not done here.

## F-05 — `--requirements` does not replace `--suite all` for this server — **NO CHANGE**

The conformance CLI's own help says `--requirements <revision>` "Replaces --suite and
--spec-version", and the installed version (`0.2.0-alpha.11`, already the newest) has it. The
obvious move is to switch. Measured, it is the wrong move.

```text
--suite all                    40 scenarios   45 passed, 23 failed, all baselined
--requirements 2026-07-28      13 server scenarios, 10 of which are `tasks-*`
```

Set difference, both directions:

```text
in --suite all but not in --requirements     (none)
in --requirements but not in --suite all     13 -- 10 tasks-*, plus json-schema-2020-12
                                             and the two http-header-validation scenarios
```

This server **deliberately declines tasks**, with the reasoning recorded at `SERVER_CAPABILITIES`
and a negative test as a tripwire: tasks need state outliving the request and this server has none
by design. So switching would trade 40 scenarios for 13, ten of which exist to test a capability
that is intentionally absent and would go straight into the baseline — while losing the
`resources`, `prompts` and `caching` scenarios that are the ones actually validating v3.0.0's work.

`--suite` is still present on both the `client` and `server` subcommands in alpha.11. The gate stays
as it is. Recorded because the next person to read that help text will have the same idea, and
because if `--suite` is ever removed the replacement is not a flag swap — it is a decision about
whether ten baselined tasks scenarios are worth the three non-tasks ones they bring.
