# v2.9.0 findings log

What was measured while building Phase 6's second release, including what the plan got wrong and
what I got wrong. Same purpose as the v2.2–v2.8 logs: the numbers and the reasoning, so a later
reader inherits the evidence rather than the conclusion.

---

## F-01 — Four of the plan's seven features already exist — **SCOPED**

**Found:** measuring the plan against the running server before writing anything, which is now the
standing habit after v2.5.0 through v2.8.0 each found the same thing.

| Plan feature | Reality |
|---|---|
| 2. Context-aware operation suggestions | **`Magic`**, shipped, exposed as `cyberchef_magic` |
| 3. Auto-recipe generation from examples | **`Magic` at depth 3**, which is multi-step inference |
| 5. Intelligent error correction | **`errors.mjs`** has `ErrorSuggestions` keyed by code |
| 6. LLM-powered documentation | **`cyberchef_describe_operation`**, shipped |

The plan proposes building a suggestion engine, a multi-step recipe inferrer, an error-fix mapper
and a documentation tool. All four are in the tool list today.

## F-02 — The flagship feature is shipped, and broken for its only consumer

**Found:** calling `cyberchef_magic` and reading what comes back.

`Magic` is described in `tool-catalog.mjs` as *"the entry point for unknown data"* and is kept in
**every** tool surface for that reason. Here is what an MCP client actually receives:

```text
            Recipe (click to load)
            Result snippet
            Properties

            From_Base64('A-Za-z0-9+/=',true,false)

            Hello World
            Valid UTF8
Entropy: 2.85
```

That is an HTML `<table>` with the tags stripped. It contains **"Recipe (click to load)"** — an
instruction to click something, sent to a program that has no browser and no mouse.

**And the structured data exists.** `src/core/operations/Magic.mjs`:

```js
dish.set(options, Dish.JSON);      // run() produces JSON
```

with a separate `present()` that renders HTML for the web UI. This server bakes with
`returnType: "string"`, which asks for the *presented* form — so it throws the JSON away and
receives the rendering.

Each discarded entry carries exactly what an agent needs:

```json
{
  "recipe": [{ "op": "From Base64", "args": ["A-Za-z0-9+/=", true, false] }],
  "data": "Hello World",
  "entropy": 2.845,
  "isUTF8": true,
  "fileType": null,
  "matchingOps": [],
  "useful": false,
  "matchesCrib": null
}
```

`recipe` is **directly executable** — it can be passed to `cyberchef_bake` unchanged. Instead the
caller gets a sentence telling it to click.

This is the release. The capability the plan wants to build is present; what is missing is that it
speaks to a browser.

## F-03 — `Magic`'s arguments are exposed with no descriptions — **FIXED**

The tool schema advertises four arguments and describes none of them:

```text
depth: number
intensive_mode: boolean
extensive_language_support: boolean
crib_known_plaintext_string_or_regex: string
```

`crib` is the most useful argument the operation has — a known-plaintext string that filters
candidate decodings down to the ones that actually produce it — and an agent has no way to learn
that from the schema. `depth` controls how many operations deep the search goes, and a caller
cannot tell whether 1 or 10 is sensible.

**Resolution.** A curated table in `tool-schema.mjs`, keyed `"<Operation>|<Argument>"`, consulted
by `mapArgsToZod`.

The obvious implementation was a parser, and measuring killed it. CyberChef operations document
their arguments inside the operation description as `<u>Depth:</u> ...`, so extracting that
automatically looked like a general fix. It is not: **7 of 504 operations use the convention**,
yielding 14 arguments whose heading matches an argument name. A fragile HTML parser over prose
upstream is free to reword, for fourteen descriptions — and it would still have missed the
argument that prompted this finding, because `Magic` documents its crib as running prose rather
than under a heading.

The cost is real and is paid on every `tools/list`, because `Magic` is the one operation in
`ALWAYS_EXPOSED`. Measured, and the first draft was too verbose:

```text
first draft   cyberchef_magic  1,750 B of a 20,685 B index   8.5%
tightened     cyberchef_magic  1,354 B of a 20,289 B index   6.7%
```

The comment in `tool-surface.mjs` claiming Magic's schema is "a few hundred bytes ... well under a
percent" was true when written and false after this change, so it now carries the number above.
That is the kind of stale-by-a-side-effect claim this project keeps finding, and the fix is to put
the measurement in the comment rather than an adjective.

## F-04 — "Natural language to recipe" belongs in the client, not the server — **REJECTED (plan item)**

The plan's P0 feature is `cyberchef_create_recipe_from_description`: the server converts a natural
language description into a recipe.

**The caller is already a language model.** It has the tool catalogue, `cyberchef_search` across all
504 operations, and far better language understanding than anything this server could host.

The plan's own pseudocode gives the game away — *"use operation knowledge base / match intent to
operations"*. That is keyword matching, which is `cyberchef_search`, already shipped. Tested against
the plan's own worked example:

```text
search("base64")      -> From Base64, Show Base64 offsets, To Base64
search("decompress")  -> Bzip2 Decompress, LZ4 Decompress, LZMA Decompress
search("extract urls")-> Extract URLs
```

Every operation in the plan's expected output is found by an existing tool.

The only other reading is that the server should *call* an LLM — which would add a network
dependency, an API key, per-call cost and non-determinism to a security toolkit, and would directly
contradict the offline work v2.8.0 just shipped.

So the answer is not to build language understanding into the server. It is to give the model that
already has it **material it can use** — which is F-02.

## F-05 — Magic's recommended recipe could not be executed — **FIXED**

The defect that decided this release's shape, and it is worse than "the output was ugly".

`Magic` renders its results through `Utils.generatePrettyRecipe`, which produces the web app's
display form. `bake` rejects it:

```text
input:  From_Base64('A-Za-z0-9+/=',true,false)
bake:   Couldn't find an operation with name 'From_Base64('A-Za-z0-9+/=',true,false)'.
```

So the single most actionable field Magic produced was the one field a caller could not use. To act
on Magic's own suggestion a model had to reverse-engineer the pretty form back into
`[{op: "From Base64", args: [...]}]`, guessing that underscores become spaces and that the quoted
arguments map positionally — a hallucination invitation sitting in the happy path.

What a client actually received, verbatim, from the published v2.8.1 image:

```text
    Recipe (click to load)
    Result snippet
    Properties
        From_Base64('A-Za-z0-9+/=',true,false)
        The quick brown fox
        Valid UTF8
Entropy: 3.89
```

That is the web app's results **table** with its markup stripped — including "Recipe (click to
load)", a UI affordance with no meaning whatsoever over MCP.

Fixed by `src/node/lib/magic.mjs`, which calls `speculativeExecution` directly and renders both a
plain-text report and shaped `structuredContent`. The recipe is emitted in executable form only.
The round trip is now a test: every recommended recipe is fed back to `bake` and the best one must
reproduce the plaintext the report advertised.

## F-06 — The language estimate was confidently wrong, and my first gate did not catch it

Worth recording because the first implementation looked correct and was not.

`detectLanguage` is a chi-squared comparison of byte frequencies. Its scores are ALWAYS populated
and ALWAYS sorted, so `languageScores[0]` names a language even for a PNG. The web presenter gates
on `probability > 0`, and copying that gate is what I did first. Measured:

```text
"Attack at dawn"                (14 B, English)  -> German, probability 1.35e-8
"just some ordinary words here" (29 B, English)  -> Polish, probability 1, English 4th
a representative French sample  (100 B)          -> English
the same French sample          (40 B and 160 B) -> French, correctly
```

A probability of 1.35e-8 passes `> 0`. So the report's first version stated **"language German"**
for English text — and in a plain-text report an assistant relays verbatim, that reads as a
determination rather than as a weak statistic.

Accuracy does not rise monotonically with length, so a length cutoff would discard correct answers
while still admitting wrong ones. The fix is therefore wording, not thresholding: the report says
"estimated language German (or English, Dutch)", carries the runners-up, and closes with a line
saying the estimate is sometimes wrong and the decoded text should be read before repeating it.

## F-07 — `cyberchef_json_beautify` returned invalid JSON — **FIXED**

Found while checking whether F-05 was one operation's problem or a class. It is a class, and this
member of it is data corruption rather than formatting.

44 operations declare a `presentType` that differs from their `outputType`. `bakeOnCore` asks the
engine for the presented form, which is correct for the ones whose payload lives ONLY in the markup
— `Generate QR Code` emits `<img src="data:image/png;base64,...">` and the bytes exist nowhere
else. For the rest the presentation is a browser artefact.

`JSON Beautify` renders an object key as bare text inside
`<li>name<span class="json-colon">:</span>`, so the quotes around every key are markup structure
rather than characters. Reducing that to text gave:

```text
in:   {"name":"alice","age":30}
out:  {name: "alice",age: 30}      <- does not parse
```

A "beautify" that emits unparseable output, with the indentation it exists to add also gone. Two
more in the same class:

| operation | presented | raw dish |
|---|---|---|
| `JSON Beautify` | 689 B of markup, invalid | 53 B of correctly indented JSON |
| `Text Encoding Brute Force` | 9,842 B table, headers fused to values (`EncodingValueUTF-8 (65001)Hello`) | 7,650 B of valid JSON |
| `Frequency distribution` | 15,669 B opening with `<canvas id='chart-area'>` | 5,865 B of valid JSON |

Fixed in `bakeOnCore`: `Chef.bake` already returns `dish` — *"a raw version of the dish,
unpresented"* — from the same execution, so preferring it costs no second bake. The swap happens
only when the presented value contains markup AND carries no media, and it is resolved **before the
cache**, because a decision made downstream of the cache applies to a miss and not to a hit — which
is exactly how `cyberchef_generate_qr_code` once returned an image on the first call and text on
every call after it.

Both directions are pinned by tests: the data operations must return data, and `Generate QR Code`
must still return an image block. One cost accepted and recorded: `Index of Coincidence` drops from
1,072 B to the bare number `0.021848739495798318`, losing static explanatory prose that surrounded
a `<canvas>` element. The number is the answer; the prose is boilerplate an assistant can supply.

## F-08 — Three review findings, two of them mine, one test that proved nothing

Recorded because the review caught things the suite did not, and because one of them is the more
interesting kind of mistake: a test that passed for the wrong reason.

**The Magic branch removed a timeout that Magic already had.** Before this release `Magic` ran
through `executeWithStreamingProgress` and was bounded by `OPERATION_TIMEOUT`. The first version of
the dispatch branch returned above that wrapper — taking the bound off the single most expensive
operation in the catalogue, where `depth` and `intensive` each multiply the work, while it held a
quota slot. Now wrapped, with `maxRetries: 0`, because `speculativeExecution` is deterministic over
its input and a retry after a genuine timeout re-runs identical work.

CodeRabbit also asked for worker-pool routing, which was **declined**: `executeInWorker` takes
`(input, recipe, timeout)` and returns a baked dish, so routing a library call returning a
structured object through it needs a second worker entry point and a serialisation contract — real
work with its own failure modes, and not something to bundle into a release about output shape.
`ENABLE_WORKERS` is off by default, and the restored timeout bounds the case that actually hurt.

**A malformed crib was reported as an operation failure.** `new RegExp(crib, "i")` threw a bare
`SyntaxError` with no `code`, so the error layer classified the caller's own bad argument as the
operation breaking:

```text
crib "(unclosed"  ->  SyntaxError: Invalid regular expression: /(unclosed/i: Unterminated group
```

Now a structured `INVALID_INPUT` quoting the engine's diagnosis, since "Unterminated group" is the
part that tells the caller how to fix it. Note the ordering: `assertSafeRegexArg` runs *before*
compilation, so a catastrophic pattern never reaches `new RegExp` and this branch only sees
genuinely malformed ones.

**The argument-order test could not have failed.** It asserted `shaped.options.intensive`, which is
built from the requested options *after* the call — an echo of the input. Proven worthless by
mutation rather than by argument:

```text
MUTANT: speculativeExecution(depth, intensive, extLang, ...)   <- the two swapped
  before   PASSED   <- the test named for this bug did not detect it
  after    FAILED   AssertionError: expected false to be true
```

It now asserts the effect. Single-byte XOR is recoverable only by the brute-force pass `intensive`
enables, with the non-intensive control asserted alongside so the positive result means something:

```text
{}                  candidates= 0   recovers plaintext: false
{intensive: true}   candidates=20   recovers plaintext: true
{extLang: true}     candidates= 0   recovers plaintext: false
```

## F-09 — The unexplained flake had a cause, and I had made it more likely

Reported in the previous summary as "one failure in six runs, could not identify". CI found it.

The Docker smoke test failed with:

```text
Recipe storage changed underneath this process: expected generation 0 but found 1.
Another process is writing the same file.
```

`mcp-docker-build.yml` starts the server detached and then `docker exec`s a **second** server into
the same container. Both default their recipe store to `./recipes.json`, so the replica generation
guard correctly refuses. A race, which is why it passed for as long as the exec won it.

The same latent race is in the test suite, and adding `magic-report.test.mjs` made it more likely:
**five** suites spawn a server, none of them set `CYBERCHEF_RECIPE_STORAGE`, and vitest runs test
files in parallel — so every spawned server was writing the same `./recipes.json`. A fifth
concurrent writer is almost certainly the failure I saw once and could not reproduce.

Each spawner now gets its own store, and the workflow probe takes the guard's own advice. Three
consecutive clean local runs since, which is not proof for a race but is the evidence available.

**The lesson worth keeping:** an unexplained single failure in an otherwise green suite is a
finding, not noise. Reporting it as unidentified rather than dismissing it is what made it possible
to connect to the CI failure two hours later.

## F-10 — A CodeQL alert that will keep coming back

`js/redos` fires on `tests/mcp/magic-report.test.mjs`, where `(a+)+$` is passed as Magic's crib to
assert that `assertSafeRegexArg` **rejects** it. The dataflow is accurate: the literal does reach
`new RegExp(crib, "i")` in `runMagic`, and the guard that throws first is a runtime check CodeQL
cannot see.

Note that the same patterns in `tests/mcp/safe-regex.test.mjs` are NOT flagged, because there they
only reach the parser — which is why this alert is new rather than long-standing.

Dismissed as `used in tests` (#543, then #544 when the line moved by one). **It re-fires as a NEW
alert whenever that line shifts**, because dismissals are per-alert and identity includes location.
Suppressing `js/redos` repo-wide was rejected: it is a real rule that protects `src/node/**`, and
`query-filters` cannot be scoped to a path. Obfuscating the literal to satisfy the scanner was also
rejected — it would make the fixture dishonest about what it is testing.

So the maintenance cost is a re-dismissal when that line moves. Recorded so the next person does
not treat a familiar alert number as a new finding.
