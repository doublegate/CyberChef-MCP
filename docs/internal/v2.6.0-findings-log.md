# v2.6.0 findings log

What was measured while building Phase 5's second release, including what the plan got wrong and
what I got wrong. Same purpose as the v2.2–v2.5 logs: the numbers and the reasoning, so a later
reader inherits the evidence rather than the conclusion.

---

## F-01 - The plan's centrepiece solves a problem the protocol deleted - **SCOPED**

**Found:** reading the current specification before writing anything, which is now the standing
habit after v2.5.0's F-01 did the same thing.

The plan is built on externalising **session state** to Redis: "sessions: in-memory → Redis",
session affinity, sticky sessions, session migration, session recovery after failover. MCP protocol
revision `2026-07-28` — implemented by this server since v2.3.0 — removed sessions from the
protocol:

> *"Revision 2026-07-28 changed the behavior of Streamable HTTP. Changes included: Removal of the
> GET stream endpoint. **Removal of protocol-level sessions.**"*
>
> *"servers could assign a session via the `Mcp-Session-Id` header … **None of these mechanisms are
> part of this revision.**"*
>
> *"An `Mcp-Session-Id` header on a request: **ignore it, and do not mint or echo session IDs.**"*

Verified against this server rather than assumed: the modern path is `createMcpHandler(...,
{legacy: "reject"})`, so session state exists only on the legacy 2025-era route. The modern request
path is already stateless.

So plan features 1 (partly) and 6 (entirely) evaporate, along with the Redis dependency, the
session store, and every "sticky routing" concern. **Had this been built from the plan, the release
would have added a database dependency to coordinate state the protocol no longer has.**

**The plan's state table is also just wrong** in a way that matters: it lists recipes as living in
SQLite. They are a JSON file. The state that actually blocks horizontal scaling was mislabelled in
the document that was supposed to plan for it.

## F-02 - 88% of startup was one import, and the first fix measured nothing - **FIXED**

Cold start was ~1300 ms. Profiling rather than guessing:

```text
src/node/index.mjs            1159 ms   <- imports all 505 operation implementations
  src/core/operations/index   1132 ms
src/core/Chef.mjs               20 ms   <- what tool calls actually use
src/node/lib/tool-catalog.mjs   12 ms   <- what tools/list actually uses
```

Nothing on the hot path needs it: `tools/list` is built from `OperationConfig.json`, and every
operation call goes through `bakeOnCore` → `Chef.mjs`. The Node API was reached from three places
only — `help` for `cyberchef_search`, `help` for the batch search branch, and `bake` for recipe
execution.

Deferred behind a memoised `loadNodeApi()`: **1300 ms → 185 ms**, mean of eight runs. First
`cyberchef_search` pays 1119 ms once; subsequent calls are 3 ms. The cost moved from *every launch*
to *first use of one of three tools*, and the common case never pays it.

**Two mistakes worth keeping.**

*The first fix measured zero improvement.* Two of the three call sites were converted and cold start
did not move at all. The third was `lib/batch.mjs`, missed because the search for importers used a
broken `grep --include` that silently matched nothing. Fixing two-thirds of a problem and measuring
no change is a good outcome — it says the model is wrong — but only if the measurement is actually
taken. The regression guard is therefore structural (assert the module has not been loaded) rather
than a wall-clock budget, which would measure the CI runner and go flaky.

*The warm-up made it worse.* Pre-importing after `connect` — the plan's "warm pool" idea, in-process
— was implemented and measured:

```text
lazy, no warm-up        186 ms
lazy + background warm 1300 ms
eager (before)         1300 ms
```

Module loading blocks the event loop, so "in the background" is not something it can be: the
warm-up does the same 1.1 s of work in front of the request already queued behind it. Removed.
**The plan's target was "<1 s cold start (with warm pools)"; it was beaten fivefold by deleting the
cost instead of hiding it.**

## F-03 - Liveness and readiness are not interchangeable - **DESIGN**

The health endpoints exist to answer one question — should this process get traffic — and the
design turns on a distinction that is commonly implemented backwards.

A failing **liveness** probe means *restart me*. A failing **readiness** probe means *route around
me*. During a graceful drain the server is deliberately refusing new traffic while finishing
in-flight work, so it is **not ready** and **entirely alive**. A liveness probe that tracks
readiness gets the pod killed mid-drain — the exact outcome the drain exists to prevent.

So `/health/live` returns 200 in every state including `draining`, and only `/health/ready` flips.
Verified by mutation: making liveness track readiness fails two tests.

They are also **unauthenticated**, because a kubelet probe carries no bearer token and gating them
would make them useless to their only caller — the same reasoning that makes RFC 9728 discovery
unauthenticated. Being unauthenticated, they are deliberately uninformative: a status string and
nothing else. No version, no configuration, no counts. An unauthenticated endpoint that reports
internal state is a reconnaissance surface, and "it is only health data" is how that ships.

## F-04 - Two replicas silently ate each other's recipes - **FIXED**

Recipe storage is a JSON file, so it is per-process unless deliberately shared. Two replicas
sharing one file both load, both modify, and both save. Measured before the fix:

```text
A saved. A sees: [ 'saved-by-A' ]
B saved WITHOUT complaint
on disk now:     [ 'saved-by-B' ]      <- A's recipe is gone
```

A user saves a recipe, it is accepted, and it is gone. No error, no log line, nothing.

The file now carries a `generation`, bumped per save and compared against the on-disk value
immediately before the commit, so a stale writer is refused with an error that says what to change.

**It is a conflict detector, not a lock, and is not sold as one.** There is a window between the
check and the rename, and Node has no portable advisory locking. Adding a database or a lock daemon
to a security toolkit to coordinate one JSON document is the wrong trade — which is the same
judgement that kept Redis out of this release. A test pins the limitation so it stays part of the
contract rather than only a comment.

The constraint itself is **documented rather than engineered away**: per-replica volumes or a
single replica, the chart refuses anything else, and the HTTP transport says so at startup.

## F-05 - The chart refuses what the server would reject - **DESIGN**

Three configurations render as valid YAML, deploy cleanly, and then fail:

- a shared recipe volume across replicas — conflicting writes, so saves fail;
- `auth.enabled` without `auth.resource` — that value is what the token audience is checked against
  (RFC 8707), so a mismatch rejects **every** otherwise-valid token, and the symptom looks exactly
  like "authentication is broken";
- `tenancy.enabled` without `auth.enabled` — the server refuses to start, so the pod crashloops.

All three now fail at `helm template` time with an error that explains the cause. A chart that
renders a configuration the server will reject has moved the failure from a place with a good error
message to a place with none.

## F-06 - A circuit breaker nobody used, and the one place it belonged - **FIXED**

The plan asks for circuit breakers. `retry.mjs` already exported a `CircuitBreaker` with
CLOSED/OPEN/HALF_OPEN states and a test suite — and the only `new CircuitBreaker` in the repository
was **in its own test**. Nothing in `src/` instantiated it.

That is the `SafeRegex.mjs` shape again: v1.4.1 added that module to close 11 ReDoS alerts, a later
sync reverted every call site, and three documents went on describing a protection that no longer
existed. Here the class was never wired up at all.

**I first recorded this as "leave it alone", and that was wrong.** The reasoning — a breaker
protects calls to a failing dependency, and this server's work is local CPU — was right about the
operations and forgot the one genuine dependency: the authorization server. Measuring it settled
the question.

`fetchJwks` caches successes for five minutes and failures **not at all**, and `discoverJwksUri`
tries **two** metadata URLs. So an issuer outage amplified every incoming request into two outbound
ones, none of which had a deadline, because Node's `fetch` has no default timeout. Against a
black-holed host — accepts the connection, never answers, which is what a firewall drop looks like
— each of those hangs until the OS gives up, holding a socket and a pending verification per
request.

Measured, 20 verifications against a down issuer:

```text
before:  40 outbound fetch attempts     (2 per request, growing with traffic)
after:   10 outbound fetch attempts     (then the breaker opens; the rest make none)
```

The shape matters more than the ratio: before, the cost grew with traffic — a stampede against a
service that is already unhealthy, at the moment it can least afford one. After, it is bounded at
ten regardless of load.

Two fixes, and the smaller one is arguably the more important: **every request to the authorization
server now has a 5 s deadline**, and the breaker stops the retry storm. A breaker without a timeout
would still let five requests hang for minutes before opening.

Deliberately generous settings — five consecutive failures to open, 30 s before a single probe. An
authorization server that flickers must not lock this server out, and one that is genuinely down
must not be hammered. A failed probe reopens the circuit, which a test asserts explicitly: one
lucky request must not reopen the floodgates against a server that is still down.

**The reusable point:** "this code is unused" and "this code is unnecessary" are different claims,
and I conflated them. The right question was not *should we delete it* but *is there a dependency
here that can fail and stay failed* — and there was one, in the file added the release before.

## F-07 - A lockfile that drifted while nobody was looking - **FIXED**

`package-lock.json` came back 2,661 lines changed after an `npm install` run to restore the
dependency set following a branch switch. Not an upgrade anyone asked for: `package.json` uses
caret ranges and npm resolved newer patch and minor versions.

248 entries changed — 216 dev-only, 32 runtime, all patch/minor transitive bumps, no direct
dependency and no major moved. Committed rather than reverted, because those are the versions the
release was tested against and restoring the older file would make the committed state differ from
what was verified; committed **separately**, because dependency churn and behaviour changes should
not share a diff.

The general point: a lockfile can change without any intent behind it, and the change is invisible
unless something looks. `git status` at the end of a work session is the only thing that caught it.

## F-08 - The README told people to pull an image that does not exist - **FIXED**

**Found:** checking that the chart's image tag matched what the release workflow publishes, and
following the check one step further into the README.

Two of the four install paths were broken, and both were in the first thing a new user reads:

```text
hub.docker.com/v2/repositories/doublegate/cyberchef-mcp/  ->  HTTP 404
hub.docker.com/v2/repositories/parobek/cyberchef-mcp/     ->  HTTP 200
```

The Docker Hub repository is named from `secrets.DOCKERHUB_USERNAME`, which is `parobek`. The
README said `docker pull doublegate/cyberchef-mcp:latest`, matching the GitHub org rather than the
Docker Hub account. `docker manifest inspect` confirms the failure rather than inferring it.

The offline path was wrong in a second way. Step 3 said to tag
`ghcr.io/doublegate/cyberchef-mcp_v2:v2.6.0` after a `docker load`, but the workflow saves the
tarball with

```yaml
docker save "$DOCKERHUB_REGISTRY/$DOCKERHUB_IMAGE_NAME:latest" | gzip > ...
```

so the loaded image is `parobek/cyberchef-mcp:latest` — a different registry, a different
repository and a different tag. No `v`-prefixed GHCR tag is published at all:
`ghcr.io/doublegate/cyberchef-mcp_v2:2.5.0` exists and `:v2.5.0` does not.

Both fixed, and every remaining docker reference in the README verified to resolve with
`docker manifest inspect` rather than by reading.

**Historical release notes are left alone.** The same references appear in v1.4.3 through v1.7.3,
and they may have been correct when written — the tag scheme changed (the eight orphaned
`release-v*` Docker Hub tags predate the `{{version}}` scheme) and the Docker Hub account name
comes from a secret that could have changed too. Rewriting published release notes to match today
would falsify the record, which is the same rule applied to the superseded plan documents in
v2.5.0: annotate history, do not edit it.

**How it survived:** the offline path costs a 206 MB download to test, and the Docker Hub path
looks plausible because the GitHub org really is `doublegate`. Neither is exercised by CI. The only
reason it surfaced now is that the Helm chart forced the question "what is actually published?" —
which is an argument for deployment manifests as a form of documentation test.
