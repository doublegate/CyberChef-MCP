Every findings log since v2.5.0 has opened by reporting the plan wrong. This one cannot.

v3.5.0 shipped the same-host benchmark comparison as **reporting only**, and said explicitly why:

> The threshold gets set from those numbers, in a later release, and not before.

That is the entire plan for v3.6.0, it is unambiguous, and the data it asked for now exists. There
is no re-scoping to do, which has not happened before and is worth recording as plainly as the eight
corrections were.

The ecosystem was checked as the ritual requires, and nothing moved:

```text
@modelcontextprotocol/server     2.0.0        unchanged
conformance                      alpha.11     unchanged
server.json schema               2025-12-11   current; `mcp-publisher validate` clean
MCP spec revisions               nothing after 2026-07-28
chainguard/node:latest-slim      v25.9.0      the base-image trigger has NOT fired
```

So every "wait for the trigger" item stays parked, and v3.6.0 is the threshold plus the work needed
to justify it.

### Scope decision

**v3.6.0, a MINOR.** A gate becoming stricter changes what fails CI, not what the server does; no
runtime behaviour, tool, or surface changes. v4.0.0 stays unscheduled — its kill criterion is "if
the specification does not force a breaking change, do not cut a major", and there is still no MCP
specification revision after 2026-07-28.

## F-02 — The comparison had never been tested against a regression — **MEASURED**

Four same-host measurements accumulated on v3.5.0's own pull request, all on code that changes
nothing in the benchmarked path:

```text
median +0.5%    worst slower -2.2%   worst faster +6.0%
median -0.1%    worst slower -1.7%   worst faster +3.1%
median +0.1%    worst slower -6.9%   worst faster +9.9%
median -0.1%    worst slower -7.6%   worst faster +2.0%
```

That is the **noise floor**: worst observed same-host slowdown on unchanged code is **-7.6%**. A
fifth datapoint from a developer machine, two runs of identical code, gives -1.8%.

**But a noise floor is only half of what a threshold needs.** The other half had never been
measured, in this project or in the previous two attempts at this gate: *does the comparison detect
a real regression, and at what size?* A threshold set from noise alone answers "what will not fire"
and says nothing about "what will".

### The experiment

A worktree of the current HEAD with a deliberate, tunable slowdown in `To Hex` — the operation redoes
a measured fraction of its own work and discards it. Its own work rather than a sleep or a busy
loop, so the slowdown carries the operation's real performance profile. Compared against the same
worktree unmodified, on one machine:

```text
nominal extra work   To Hex 1KB   To Hex 10KB   To Hex 100KB   worst UNTOUCHED task
              0%          0.0%          0.0%           0.0%          0.0%
             10%         -4.5%         -7.4%          -8.2%         -3.7%
             25%        -11.1%        -16.3%         -20.2%         -3.1%
             50%        -19.8%        -27.7%         -32.8%         -2.5%
```

Two results, and the second is the more useful one.

**The comparison detects, and roughly linearly.** 25% extra work reads as -20.2% on the largest
input; 50% reads as -32.8%.

**The regression stays localised.** Only the three `To Hex` tasks move. Every untouched task stays
within -3.7% at every magnitude, which is inside the noise floor. So the comparison attributes a
slowdown to the thing that got slower rather than smearing it across the suite — the property that
makes a per-task threshold meaningful at all.

### What the two halves together say

```text
noise floor (CI, unchanged code, 4 runs)    worst -7.6%
detection (local, 25% extra work)                 -20.2%
detection (local, 50% extra work)                 -32.8%
```

A per-task threshold has to sit above the noise floor and below the smallest regression worth
catching. **25%** is 3.3x the worst observed same-host noise, matching the 2.5-3x margin this
project's own precedent uses.

**What that actually catches, in both framings, because conflating them is how a gate's reach gets
overstated:**

```text
the gate fires when a task is MORE THAN 25% SLOWER
in the experiment that took ~33% extra work   (interpolating -20.2% at 25% and -32.8% at 50%)
```

Verified against the experiment's own data rather than asserted — the gate was run over every
fixture from this measurement:

```text
identical code                pass
two runner captures           pass
10% extra work  (-8.2%)       pass, reported
25% extra work  (-20.2%)      pass, reported     <- a quarter more work does NOT fail
50% extra work  (-32.8%)      FAIL
a zero-throughput task        FAIL               <- a broken run is not a clean one
```

**A quarter of the work added to an operation does not fail this build.** That is narrower than the
previous two thresholds were quoted as achieving, and it is the accurate statement. The full
comparison is printed on every run, pass or fail, precisely so the numbers below the threshold are
readable — a pass is not proof there is no regression, and the gate's own output says so.

The first draft of this section said 25% "clears the -20.2% of a 25% regression only narrowly",
which is wrong in the direction that matters: -20.2% is *inside* the threshold and passes. Caught by
running the gate against the fixtures instead of reasoning about the numbers, which is the same
discipline that produced the detection curve in the first place.

### Why this is not the v3.4.0 mistake again

v3.4.0 set 20% from three captures taken sixteen minutes apart, and CI disproved it within the hour.
The obvious worry is that four runs from one pull request is the same sampling error.

The difference is structural rather than statistical. v3.4.0's failure cause was **host-class
variation** — memory-bandwidth-bound tasks collapsing on one host while CPU-bound ones improved.
The same-host comparison is immune to that *by construction*: both sides run on the same host, in
the same job. What is left is within-host noise, and two independent estimates of it agree in
magnitude (CI -7.6%, developer machine -1.8%).

It is still four runs. The gate is therefore built so that being wrong is cheap and visible: it
fails on a **per-task** threshold, the full comparison is printed either way, and the stored-baseline
gate continues to run. If it produces a false failure, the report next to it says so in numbers.
