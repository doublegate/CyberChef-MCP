# v3.0.0 findings log

What was measured before writing anything, including what the plan got wrong and what I got wrong.
Same purpose as the v2.2–v2.10 logs: the numbers and the reasoning, so a later reader inherits the
evidence rather than the conclusion.

---

## F-01 — The planned v3.0.0 was empty, and had been for three releases — **RE-DERIVED**

By convention F-01 measures the plan against the running server before any code is written.
`docs/planning/future-releases/release-v3.0.0.md` (December 2025) lists six breaking changes:

| Planned breaking change | Measured |
|---|---|
| 1. Tool naming convention (`cyberchef_` removal) | **Withdrawn permanently** in v2.0.0 |
| 2. Recipe schema v2 (named arguments) | **Shipped** — `args: {alphabet: "…"}` bakes today |
| 3. Structured error responses | **Shipped** — code + context + `toMCPError` |
| 4. Unified configuration | **Shipped in v2.10.0** |
| 5. Plugin API v2 | **Superseded by ADR 0002** — there is deliberately no plugin loader |
| 6. "MCP Protocol 2027 / SDK v3.x" | No such SDK exists; SDK v2.0.0 is current and installed |

Six for six. The ROADMAP already said so in a correction dated 2026-09-03 — *"v3.0.0's scope needs
re-deriving before it is planned rather than executed"* — which is what this release did.

The replacement scope is **MCP 2026-07-28 conformance plus the breaking cleanups conformance
forces**, derived by reading the specification changelog against the server.

## F-02 — A missing resource answered "Internal Error" — **FIXED**

The sharpest finding, and not the one the plan predicted.

`ErrorCodes` in `errors.mjs` are STRINGS (`"INVALID_INPUT"`). The SDK dispatcher keeps a thrown
error's code only when it is a safe integer and substitutes Internal Error otherwise. So every
`resources/read` failure answered **-32603 with no `data`**. Measured through a real client:

```text
recipe://00000000-0000-4000-8000-000000000000   code=-32603 data=undefined
file:///etc/passwd                              code=-32603 data=undefined
```

A caller could not distinguish *"that resource does not exist"* from *"the server broke"* — and the
spec is explicit that resource-not-found is -32602. After:

```text
recipe://00000000-0000-4000-8000-000000000000   code=-32602 data={"uri":"recipe://0000…"}
file:///etc/passwd                              code=-32602 data={"supported":"recipe://<id>", …}
recipe://                                       code=-32602 data={"supported":"recipe://<id>"}
```

Two distinct -32602s, distinguishable by whether `data.uri` is present — which is the shape the SDK
documents clients to recognise resource-not-found by.

**The workaround whose reason expired.** The comment at that throw said context had to go in the
MESSAGE because the SDK carried *"`message` alone, with `data` null"*. True of the SDK it was
written against. The modern codec carries `data`, so the constraint had quietly lifted and nobody
had noticed — the same shape as the `cyberchef.config.json` promise v2.10.0 fixed, in the opposite
direction: there, documentation outlived the code; here, a workaround outlived the defect.

`getRecipe` keeps its string code deliberately. It is also called from `cyberchef_recipe_get`, where
the result is a tool result rather than a JSON-RPC error, and there the string code is correct. The
translation happens at the resource boundary.

## F-03 — `cyberchef_bake` cost more than the operations it runs — **FIXED**

The primary breaking change, and it started as a much smaller task.

`visibleTools()` has existed since v2.5.0, with a unit test asserting it works, and **nothing called
it**. Every token was listed the whole surface and learned what it could not do by being refused.
Tested-but-unwired is a worse state than absent: the green test says the capability is there.

Wiring it turned out to be blocked on something else. `cyberchef_bake`, `cyberchef_batch` and
`cyberchef_recipe_execute` are annotated `openWorldHint: true` because a recipe *may* contain
`HTTP request`, and `requiredScopes` checks that hint first — so all three demanded
`cyberchef:network` for every call, including recipes that never leave the process. Measured across
the catalogue:

```text
502 of 504 operation tools require only cyberchef:read
  2 of 504 require cyberchef:network   (HTTP request, DNS over HTTPS)
```

So `cyberchef_to_base64` cost `read`, while `cyberchef_bake` running **that same operation** cost
`network`. The same work through a different door, priced differently — and the cheaper door is the
one exposing 504 separate tools, so the expensive one bought nothing.

Two adjacent tests in `auth.test.mjs` asserted both halves of that incoherence without anyone
noticing they contradicted each other:

```text
line 947  "lets a read-scoped token run a pure operation"      cyberchef_to_base64  -> allowed
line 953  "REFUSES a read-scoped token a tool that needs write" bake([To Base64])   -> refused
```

Scopes for `bake` and `batch` now come from the recipe submitted, reusing the granularity the
offline guard settled on in v2.8.0 — *"the guard is on the recipe, not the tool name"*. Strongest
wins, so one networked operation still costs `network`.

`cyberchef_recipe_execute` is deliberately excluded: it carries only an id, and resolving it would
mean moving the authorisation check after a storage read, which is exactly the v2.5.0 bypass shape.

## F-04 — I listed a tool more strictly than I enforced it — **caught before commit**

While implementing F-03 I made recipe-carrying tools list at the tool's own `readOnlyHint`, which is
`false` for `bake`, so the listed floor came out as `write`. Dispatch, meanwhile, admitted a benign
recipe at `read`.

That is backwards. A `read` token would have been **hidden a tool it could successfully invoke** —
the exact inversion of the reason the list is filtered at all, which `rbac.mjs` states as *"hiding
what is unusable is kinder to the model than explaining it afterwards"*. Listing stricter than
dispatch is not caution; it is misinformation.

The floor is now `read`, which is what the cheapest recipe actually costs at dispatch. List and
enforcement agree.

## F-05 — Cache hints were already conformant, and maximally useless — **FIXED**

The plan treated `ttlMs`/`cacheScope` (SEP-2549) as unimplemented because neither string appears
anywhere in `src/node/`. Reading the SDK instead of the server corrected that: it fills both at the
2026-era encode seam for a closed set of six methods, defaulting to `{ttlMs: 0, cacheScope:
"private"}`.

So the server was **conformant and telling every client to cache nothing**. The work was choosing
values, not implementing a field — one option at the two construction sites:

```text
tools/list                600000 public   (300000 private when auth is on)
prompts/list             3600000 public
resources/templates/list 3600000 public
resources/list                 0 private
resources/read                 0 private
server/discover           600000 public
```

The two zeros are the honest ones. Saved recipes change on any caller's write and are partitioned by
tenant, and this server declares **no** `listChanged` capability and emits no notification — so the
TTL is the only invalidation signal a client has. Any non-zero value would serve a stale list with
no way to know.

**Why the constructor option and not the handlers.** The legacy codec passes a result through
unchanged, so a handler-returned `ttlMs` would leak onto the **2025 wire** that every deployed
v1-SDK client speaks. The option is invisible to that era by construction. Verified in both
directions — and the first probe, which used the legacy client and reported `undefined`, was the
no-leak property rather than a bug.

## F-06 — Two things I asserted that were wrong

Recorded because both were mine and both reached a written plan.

**"`visibleTools` is dead code, referenced nowhere else."** The grep behind that was scoped to
`src/node/` and the conclusion was stated as if it were repo-wide. It is imported and asserted in
`tests/mcp/auth.test.mjs:28,101-103`. The correct description — tested but unwired — is materially
different and materially worse, and the plan said the weaker thing.

**"`tools/list` has no deterministic order."** Only the operation tier comes from object key order;
`META_TOOLS` is an array literal and `toolRegistry.list()` is `[...Map.values()]`, both already
stable per build. The gap was that nothing *pinned* it, which is a smaller and more accurate claim
than the one I made.

## F-07 — A dated fuse in the release pipeline — **FIXED**

`mcp-release.yml` guarded npm publish with `if: startsWith(github.ref_name, 'v2.')` on **three**
steps. The comment above them states the intent — exclude the v1.9.x line, whose `postinstall`
cannot survive a tarball install — but it is written as an allowlist of the then-current major, so
it excluded every major after it too.

A `v3.0.0` tag would have pushed the image to GHCR `_v3` correctly (that step resolves any numeric
major) and then **skipped npm entirely, with no failure and no warning**, because a skipped `if:` is
a green step. Unobservable until the one tag that trips it.

Now written as the exclusion it always meant, and simulated across majors before committing, since
there is no other way to see it:

```text
ref        old(v2 allowlist)  new(v1 exclusion)  intent
v1.9.2     skip npm           skip npm           skip npm
v2.10.0    publish            publish            publish
v3.0.0     skip npm           publish            publish   <- fixed
v4.0.0     skip npm           publish            publish   <- fixed
```

## F-08 — Tasks and extensions, assessed and declined — **WONTFIX, with reasons**

2026-07-28 moves long-running work into `io.modelcontextprotocol/tasks` and adds an `extensions`
capability field. Neither is declared, and the reasoning sits at `SERVER_CAPABILITIES` rather than
only here:

1. **Already solved differently.** `streaming.mjs` plus progress notifications cover long
   operations; CyberChef operations run in seconds, and a polling model buys nothing for work that
   finishes before a client could poll twice.
2. **Nowhere to put the state.** Tasks need state outliving the request, and this server
   deliberately has none — HTTP builds a `Server` per session, stdio pins one per connection.
   Adding a process-wide store re-opens the isolation issue #36 was filed for.
3. **The server's own rule forbids it.** A capability listed there MUST have a handler; tasks is a
   subsystem, not a declaration.

An empty `extensions: {}` is omitted rather than added for completeness: it advertises nothing and
would read as an intent that does not exist.

The negative test is a tripwire — the SDK is pinned `^2.0.0`, and a 2.x minor that began
auto-declaring either would otherwise ship silently and promise handlers that are not there.

## F-09 — Deprecation alignment: nothing to do, verified rather than assumed

2026-07-28 deprecates Roots, Sampling, Logging, the HTTP+SSE transport, and OAuth Dynamic Client
Registration. Checked one at a time:

```text
roots/list              0 files      sampling/createMessage  0 files
logging/setLevel        0 files      SSEServerTransport      0 files
```

DCR does not apply. `lib/auth.mjs` is purely an OAuth 2.1 **resource** server — it verifies JWTs
against a JWKS and publishes RFC 9728 metadata, and references zero authorization-server endpoints.
DCR and its replacement, Client ID Metadata Documents, are authorization-server and client concerns.

Recorded because "we do not use it" is a claim worth checking once rather than repeating.

## F-10 — A major bump renames the image, and nothing in the repository knew — **FIXED**

The second dated fuse, found while doing the version bump rather than while planning it. Same shape
as F-07 and a worse blast radius.

`mcp-release.yml` derives the GHCR package name from the tag's major:

```yaml
echo "name=${GITHUB_REPOSITORY_OWNER}/cyberchef-mcp_v${major}" >> "$GITHUB_OUTPUT"
```

So `v3.0.0` publishes to `cyberchef-mcp_v3`, and the `_v2` package is not superseded in place — it
simply stops receiving pushes. Correct, deliberate, documented in the v2.0.0 release notes, and
**referenced nowhere that a bump would touch**. Measured across the repository: 40 files carried a
`cyberchef-mcp_v2` reference.

The sharpest one is in the chart this project publishes:

```yaml
image:
  repository: ghcr.io/doublegate/cyberchef-mcp_v2   # not bumped
  tag: "3.0.0"                                      # bumped
```

`repository` and `tag` are two halves of one reference. Moving one resolves to
`cyberchef-mcp_v2:3.0.0` — an image that will never be pushed. A `helm install` of the published
chart would have failed to pull, at the first release where anyone tried it.

**And `check:versions` was green.** It verified `image.tag` and never looked at `image.repository`,
which is worse than not checking at all: a report that says `ok` next to a half-updated reference
is read as verification. The gate written in v2.10.0 *because a prose checklist cannot fail a
build* had the same weakness one level down.

Its own compose pattern was a third instance:

```js
find: text => [...text.matchAll(/cyberchef-mcp_v2:([0-9]+\.[0-9]+\.[0-9]+)/g)]
```

Literal `_v2`. At v3.0.0 that matches nothing, and by the checker's own rule a location matching
nothing is a failure — so it would have failed with *"the pattern has stopped matching"* rather
than naming the actual problem. A check that only works for the major it was written in has an
expiry date, which is the property F-07 was about.

Now the major in the package name is asserted everywhere one appears — `docker-compose.yml`,
`values.yaml`, `server.json` — and both new checks were proven by drifting each file and watching
the run go red, rather than by reading them.

**`server.json` had been stale since v2.4.1.** Six releases, no report, because it is not published
from CI and nothing was looking at it. It is in the gate now:

```text
server.json (version)                     2.4.1  ->  3.0.0
server.json (packages[0].identifier)      _v2    ->  _v3
```

## F-11 — The archive move was refused by its own measurement

The plan said to move genuinely dead plans to `docs/planning/archive/`. Measuring first changed the
answer, so the directory ships holding only a README explaining why it is empty.

**Every one of the 62 planning documents is referenced from at least two files outside
`docs/planning/`** — mostly `CHANGELOG.md`, `docs/releases/*.md` and `docs-site/`. Moving one
either breaks a published URL or requires editing release notes to describe a directory layout that
did not exist when they were written, which is rewriting history — the one thing the plan's own
risks section said not to do.

So 26 documents were annotated in place instead. The banner is the part that does the work: a
reader arrives at these files through a link, not by browsing a directory listing, and a dated
banner at the top of the file they opened tells them what the move was supposed to.

Recorded because "the plan said to move them" would otherwise read as an unexplained omission, and
because the test to re-run before concluding otherwise is worth keeping:

```bash
grep -rl --include='*.md' -F "$(basename "$FILE")" . \
  | grep -v '^./docs/planning/' | grep -v '^./node_modules'
```
