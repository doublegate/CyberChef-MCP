## F-01 — The defect is real, but the gate the charter implies would fire on a false positive

### The measurement, run first

The charter counts *"23 `if (name === "cyberchef_…")` branches in handleCallTool"* against one
`META_TOOLS` literal. Measured on this tree:

```text
META_TOOLS declarations                      22
`if (name === "cyberchef_…")` occurrences    24
  ... of which, inside `recipeScopesFor`      2   (cyberchef_bake, cyberchef_batch -- scope
                                                   resolution, not dispatch)
top-level dispatch branches                  21
```

Three numbers, none of them 23, and the arithmetic explains the drift: the charter's count was
taken before v4.0.0 removed `cyberchef_migration_preview` and `cyberchef_deprecation_stats` and
before v4.1.0 added `cyberchef_analyse`.

### The finding that changes the design

Comparing the two sets the way the charter describes produces:

```text
declared with NO handler    : cyberchef_analyse
handled with NO declaration : none
```

**`cyberchef_analyse` is not undispatched. It is fully callable, and the v4.1.0 suite proves it
byte-for-byte against a direct call.** It has no `if (name === "cyberchef_analyse")` branch because
it resolves *inside* the registry-tool block — `if (!registryTool && name === "cyberchef_analyse")`
— which is deliberate: sharing one body with the direct call is what makes "behaves identically"
checkable rather than aspirational.

So the syntactic check the charter implies **fails on its first run, against a tool that works.**

That is not a small detail. A gate whose first output is a false positive is a gate people learn to
override, which this repository has written down before — `codecov.yml` argues the same point about
an unreachable target. And the cause is structural rather than incidental: dispatch shapes differ
*for reasons*, and they should.

| Tool | Dispatch shape | Why |
|---|---|---|
| 21 meta-tools | top-level `if (name === …)` | ordinary |
| `cyberchef_analyse` | inside the registry block | shares one body with the direct call |
| `cyberchef_bake`, `cyberchef_batch` | branch **plus** an entry in `recipeScopesFor` | priced by the recipe submitted |
| `cyberchef_magic` | **an operation**, not a meta-tool | force-exposed on every surface |

### `cyberchef_magic` is a third case the charter does not mention

The index lists **23** tools: 22 `META_TOOLS` plus `cyberchef_magic`, which is an entry in
`OperationConfig` dispatched through the operation path (`opName === "Magic"`) and pinned into every
surface. It is neither declared in the literal nor dispatched by a meta-tool branch.

Any "one table" that does not account for it will either omit the most important navigation tool on
the surface or report it as an orphan. The charter's two-way check has a third direction.

### Re-scope, and the order matters

The charter's kill criterion says the refactor does not happen unless the full meta-tool surface can
be asserted through a real client before and after. Read literally that makes the **gate the
prerequisite, not the deliverable** — so it is built first, and it is built on **behaviour rather
than syntax**:

1. every tool `tools/list` advertises is callable, verified by calling it and asserting the failure
   is not "unknown tool";
2. every meta-tool reachable by dispatch is advertised;
3. `cyberchef_magic` is present on every surface, stated as its own case rather than left to a
   pattern that cannot see it.

A behavioural gate is immune to the false positive above *because it asks the question the charter
actually cares about* — "can a caller use what we advertised?" — instead of a proxy for it.

### Scope decision

**v4.2.0, MINOR, unchanged in intent.** The consolidation still lands; the gate lands first and the
refactor happens behind it. If the refactor cannot be proven behaviour-preserving the gate is still
worth shipping on its own, which is the outcome the kill criterion already contemplates.

### Everything else the ritual checked

- **Outstanding work**: a sweep for `TODO`/`FIXME`/`XXX`/`HACK`/stub markers across `src/node`,

## F-02 — The gate already existed, and the "uniform" group was 8 of 10

Two findings, both from doing the work rather than planning it, and both landing on the charter's
central claims.

### The parity gate was built in v3.7.0

The charter says *"The dispatch table has never had its version."* It has.
`tests/mcp/meta-tool-parity.test.mjs` exists, was written in v3.7.0, and asserts exactly the two
directions this release set out to gate — with its own header recording the same v3.0.0
carried-forward item as the motivation.

So v4.2.0's headline deliverable was **already shipped**, and the release began by building a
second one. The consolidation release had duplicated a check. That is the same defect it exists to
remove, one level up.

It is not wasted, because of *how* it was already solved. The v3.7.0 gate is **syntactic** — it
greps `if (name === "cyberchef_…")` and compares the set against the `META_TOOLS` literal — and
F-01 predicted, before any code, that a syntactic check would be fragile. The prediction landed
harder than expected: the refactor this very charter asks for **breaks it**, because eight tools
dispatched from a table have no branch to grep. A gate that forbids the change it was written to
protect is not a gate, it is a lock.

`meta-tool-parity.test.mjs` is therefore **superseded and removed**, not patched. Patching it to
also read the table would leave two overlapping checks, the more fragile one authoritative. Its one
assertion that behaviour cannot reach — a meta-tool shadowing a *registry* tool, which
`ToolRegistry.register` catches in the other direction only — is carried into
`dispatch-table.test.mjs`, and strengthened: it now derives registry names from
`ToolRegistry.exposedName` rather than from a filename regex.

### "They differ only in the method called" was wrong for 2 of 10

The ten recipe branches look identical. Two are not, and neither difference is visible from the
shape:

| Tool | What was hidden |
|---|---|
| `cyberchef_recipe_execute` | Calls `validateInputSize(args.input)` **first**, and returns the recipe's own string result when there is one instead of a JSON envelope |
| `cyberchef_recipe_export` | `exportRecipe` already returns a **string**; the table's `JSON.stringify` encoded it twice, so callers got `"{\n \"id\": …}"` instead of the document — and it round-trips through `recipe_import`, so this broke a pair rather than only cosmetics |

Folding them in silently dropped an input-size guard and changed two output shapes. Both were
caught by `in-process-handlers.test.mjs` and an executable example — **not by the new gate**, which
asks only whether a tool is reachable, and both remained perfectly reachable while answering
differently.

That is worth stating plainly rather than filing as a near-miss. The charter's kill criterion says
*"a tidier dispatch that answers differently is a regression with good intentions"*, and the
regression happened on the first attempt. What prevented it shipping was the pre-existing suite,
not the consolidation's own safety net.

The table therefore holds **8 of 10**, and the two exceptions keep their branches with the reason
written where the next person will remove them. A table with two special cases inside it would be
a table of exceptions, which is the two-sources problem wearing a different hat.

### Measured

```text
                          before        after
dispatch `if` occurrences     24           16
tools dispatched by table      0            8
mcp-server.mjs statements  85.40%       85.56%   (357/418 -> 338/395)
mcp-server.mjs branches    68.04%       70.39%   (164/241 -> 164/233)
mcp-server.mjs functions   91.48%       92.85%
total statements           95.30%       95.50%
total branches             89.31%       89.88%
```

The sprint asks whether coverage moved, on the theory that a consolidation which does not move it
has probably moved complexity rather than removed it. It moved the right way and for the right
reason: **25 fewer statements and 10 fewer branches to cover**, with the covered count essentially
unchanged. The uncovered remainder is in the heterogeneous branches, which is where it should be.
