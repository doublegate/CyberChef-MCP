## F-01 — The defect is real, but the gate the charter implies would fire on a false positive

### The measurement, run first

The charter counts *"23 `if (name === "cyberchef_…")` branches in handleCallTool"* against one
`META_TOOLS` literal. Measured on this tree:

```text
META_TOOLS declarations                      22
`if (name === "cyberchef_…")` occurrences    24
  ... of which, inside `recipeScopesFor`      2   (cyberchef_bake, cyberchef_batch -- scope
                                                   resolution, not dispatch)
top-level dispatch branches                  21
```

Three numbers, none of them 23, and the arithmetic explains the drift: the charter's count was
taken before v4.0.0 removed `cyberchef_migration_preview` and `cyberchef_deprecation_stats` and
before v4.1.0 added `cyberchef_analyse`.

### The finding that changes the design

Comparing the two sets the way the charter describes produces:

```text
declared with NO handler    : cyberchef_analyse
handled with NO declaration : none
```

**`cyberchef_analyse` is not undispatched. It is fully callable, and the v4.1.0 suite proves it
byte-for-byte against a direct call.** It has no `if (name === "cyberchef_analyse")` branch because
it resolves *inside* the registry-tool block — `if (!registryTool && name === "cyberchef_analyse")`
— which is deliberate: sharing one body with the direct call is what makes "behaves identically"
checkable rather than aspirational.

So the syntactic check the charter implies **fails on its first run, against a tool that works.**

That is not a small detail. A gate whose first output is a false positive is a gate people learn to
override, which this repository has written down before — `codecov.yml` argues the same point about
an unreachable target. And the cause is structural rather than incidental: dispatch shapes differ
*for reasons*, and they should.

| Tool | Dispatch shape | Why |
|---|---|---|
| 21 meta-tools | top-level `if (name === …)` | ordinary |
| `cyberchef_analyse` | inside the registry block | shares one body with the direct call |
| `cyberchef_bake`, `cyberchef_batch` | branch **plus** an entry in `recipeScopesFor` | priced by the recipe submitted |
| `cyberchef_magic` | **an operation**, not a meta-tool | force-exposed on every surface |

### `cyberchef_magic` is a third case the charter does not mention

The index lists **23** tools: 22 `META_TOOLS` plus `cyberchef_magic`, which is an entry in
`OperationConfig` dispatched through the operation path (`opName === "Magic"`) and pinned into every
surface. It is neither declared in the literal nor dispatched by a meta-tool branch.

Any "one table" that does not account for it will either omit the most important navigation tool on
the surface or report it as an orphan. The charter's two-way check has a third direction.

### Re-scope, and the order matters

The charter's kill criterion says the refactor does not happen unless the full meta-tool surface can
be asserted through a real client before and after. Read literally that makes the **gate the
prerequisite, not the deliverable** — so it is built first, and it is built on **behaviour rather
than syntax**:

1. every tool `tools/list` advertises is callable, verified by calling it and asserting the failure
   is not "unknown tool";
2. every meta-tool reachable by dispatch is advertised;
3. `cyberchef_magic` is present on every surface, stated as its own case rather than left to a
   pattern that cannot see it.

A behavioural gate is immune to the false positive above *because it asks the question the charter
actually cares about* — "can a caller use what we advertised?" — instead of a proxy for it.

### Scope decision

**v4.2.0, MINOR, unchanged in intent.** The consolidation still lands; the gate lands first and the
refactor happens behind it. If the refactor cannot be proven behaviour-preserving the gate is still
worth shipping on its own, which is the outcome the kill criterion already contemplates.
