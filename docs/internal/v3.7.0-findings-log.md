## F-01 — The 505-operation fix corrected three files and missed seven — **THE PLAN WAS WRONG**

v3.2.0's release notes and CHANGELOG say it fixed the operation-count discrepancy:

> **Three documents said 505 operations** where `OperationConfig` has 504

Three were corrected. **Nine live occurrences still say it**, two releases later:

```text
src/node/mcp-server.mjs                      "pulls all 505 operation implementations"
src/node/lib/node-api.mjs                    (twice)
tests/mcp/startup-cost.test.mjs
docs/guides/edge-deployment.md
deploy/grafana/README.md
deploy/grafana/alerts.yaml                   (an alert annotation an operator reads)
deploy/grafana/cyberchef-mcp-dashboard.json  (a panel description an operator reads)
deploy/helm/cyberchef-mcp/values.yaml        (the comment explaining a memory request)
```

> This paragraph first said **seven**, from reading the tree by hand. The tree-walking version of
> the check found two more — `alerts.yaml` and `values.yaml` — which is F-03 and is the argument for
> the whole change. A hand count of a claim's occurrences is the thing being replaced, so it would
> have been odd for the hand count to be right.

`npm run check:versions` reports all seven operation-count locations `ok` and has done since
v3.2.0, because it is checking a **four-file list**:

```js
[
    "deploy/helm/cyberchef-mcp/templates/prometheusrule.yaml",
    "deploy/compose/docker-compose.yml",
    "README.md",
    "docs/wiki/Release-History.md"
].map(file => ({ ... }))
```

The *pattern* is fine — `(?:all|loads|exposes|importing) ([0-9]{3})[- ]operation` matches
"all 505 operation implementations" exactly. The **file list** is the defect.

That is a particularly sharp version of a mistake this repository has already written down. The
check's own comment says:

> One pattern per file rather than per phrasing. The first version of this matched three
> hand-written phrases and missed five more occurrences in the same files, which review found — **a
> check that covers some occurrences of a claim reads as covering the claim.**

The lesson was learned at the level of *phrasings* and not applied at the level of *files*. A gate
that checks four of eleven files reads exactly like a gate that checks the claim.

### The number itself is not as simple as either figure

Worth recording, because it explains how "505" survived being read hundreds of times: **there is no
single count that makes every one of those sentences true.**

```text
OperationConfig entries                        504
operation implementations the bridge imports   494
wrapped operations on the chef object          495
function exports on the chef object            508
```

The sentences in question are about *the cost of eagerly importing the bridge*, where the exact
count was never load-bearing — which is precisely why a wrong one went unnoticed. They are corrected
to **504**, the catalogue figure, because that is what `check:versions` derives from
`OperationConfig` and what every user-facing document says; a document disagreeing with the gate is
worse than a document rounding.

### Scope decision

**v3.7.0, a MINOR.** Documentation corrections and a gate widening; no runtime behaviour, tool or
surface changes. v4.0.0 stays unscheduled — no MCP specification revision after 2026-07-28.

## F-03 — Widening the gate found two more files than reading did — **FIXED**

The fix for F-01 is not correcting seven files. It is that the check **discovers** the files it
checks instead of carrying a four-entry list, and the difference showed up immediately.

Reading the tree by hand found seven stale locations. Discovery found **nine**, including two that
manual grep missed:

```text
deploy/grafana/alerts.yaml               (missed by hand)
deploy/helm/cyberchef-mcp/values.yaml    (missed by hand)
```

Coverage went from **7 locations to 37**. Both extra files are operator-facing: a Grafana alert
annotation and the comment explaining a Helm memory request.

### It took three passes, and each mistake is the same mistake

**Pass one — the file list.** Fixed by walking the tree, with an exclusion list that is short and
about *history* rather than convenience: release notes, findings logs, the CHANGELOG and
`Release-History.md` record what was true when written, and correcting them would falsify the
record. `docs/reference/cyberchef-upstream.md` joins them for a different reason worth stating — it
documents **upstream's** tree at v10.19.4, where the count genuinely was 463, so "fixing" it to 504
would make it wrong.

**Pass two — the phrasing.** With discovery working, `src/node/lib/node-api.mjs` still slipped
through: its wording is *"imports **every one of the 505 operation implementations**"*, which
contains neither `all NNN operation` nor a barrel.

The fix was chosen by measurement rather than by adding alternatives until it passed. A deliberately
**wide** pattern (`NNN operation`) was run over the whole tree first: it catches all nine wrong
occurrences and **twenty more that are legitimately not 504** — the 100-operation batch limit,
upstream's 463, an external reference's "over 300", a generated docs page's 214, and
`HAS-160 operation` from a hash name. So a wide pattern plus a denylist would have been a denylist
that grows forever.

The nine wrong occurrences share one precise anchor: every one says **"operation implementations"**,
and none of the twenty false positives does. That is a phrase which in this repository always means
the whole catalogue. One anchor added; no exclusions needed.

**Pass three — the pattern was in two places.** Adding the third anchor to the check and not to the
discovery filter meant `node-api.mjs` was never discovered, so its two wrong counts stayed
invisible *after* the anchor that was written for them. Two copies of one rule, diverged inside a
single edit.

That is the same defect this release adds a guard for in `mcp-server.mjs`, committed in the fix for
it. `CATALOGUE_COUNT` is now one constant with two consumers — declared without the `g` flag, since
a shared global regex carries mutable `lastIndex` between callers and would make `.test()` alternate
on identical input.

## F-04 — A guard for the meta-tool duplication, which has not drifted — **ADDED**

`mcp-server.mjs` holds the meta-tools twice: the `META_TOOLS` literal that `tools/list` is built
from, and the `name === "cyberchef_..."` chain that `tools/call` dispatches on. The v3.0.0 plan
recorded *"adding a tool means editing two places"* and it was carried, unmeasured, for six
releases.

Measured: **23 declared, 23 dispatched, no drift.** So this is a guard against a latent hazard, not
a fix — and a guard is the proportionate response. Rewriting the chain into a dispatch table is a
large change to the hottest file in the server for a problem that has not yet bitten.

The hazard is credible rather than theoretical because it has bitten in the adjacent case: the
registry tools carry exactly this tripwire in `stdio-client-contract.test.mjs`, and it earned its
keep in v3.4.0 when `ecdsa_recover` was added.

`tests/mcp/meta-tool-parity.test.mjs` asserts both directions, and each has a distinct meaning:

- **declared but not dispatched** — a tool in `tools/list` with a full schema that fails on every
  call. The shape of the defect that hid ten flow-control tools until v2.1.0.
- **dispatched but not declared** — callable and undiscoverable, breaking the rule AGENTS.md states
  as *listing must never be stricter than dispatch*.

It reads the source, because `META_TOOLS` is module-private and the chain is control flow: a
protocol-level test would have to call all 23 tools and infer the mapping from what did not fail.
Two defences against the failure mode of a source-reading test — a floor on both set sizes so a
refactor cannot make it vacuously pass, and verification by injecting a declared-but-undispatched
tool, which fails with the offending name.

## F-05 — The gate was made to enforce a number that is not true — **FIXED IN REVIEW**

F-01 recorded that no single count makes those sentences true:

```text
OperationConfig entries                        504
operation implementations the bridge imports   494
```

and then chose 504 "because a document disagreeing with the gate is worse than a document
rounding". Review pointed out what that actually produced: **the gate now demanded that an
IMPLEMENTATION count equal the CATALOGUE count.** It would have preserved the operator-facing text
at a figure that is not true, and failed anyone who wrote the accurate 494.

The reasoning in F-01 was applied one step too late. It correctly identified that the count in those
sentences was never load-bearing — *"which is precisely why a wrong one went unnoticed"* — and then
replaced one wrong number with another instead of following that observation to its conclusion.

The phrase is removed from the prose rather than pinned to a number:

```text
"the Node API loading all 505 operation implementations"
"the Node API loading every operation implementation"
```

which is true regardless of how the modules are counted, and needs no gate. The third anchor goes
with it — an anchor for a phrase nobody writes is dead weight, and one comparing implementations to
504 is worse than dead.

Coverage settles at **19 locations** rather than 37. That is not a loss: the 18 that disappeared were
the same claim in a phrasing that no longer exists. Against the **7** this release started from, the
catalogue claim is still covered nearly three times as widely, and the remaining locations are ones
where a count genuinely means the catalogue.

Two smaller things from the same review: the anchoring comment had been duplicated verbatim by my
edit, and a capture group left dead by the anchor's removal was still being read. Both fixed.

`deploy/compose/docker-compose.yml` also carried the phrase and was missing from my rewording list —
found by grepping for what should no longer exist rather than by trusting the list, which is the
same lesson as F-03 in miniature.
