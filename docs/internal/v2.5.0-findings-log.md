# v2.5.0 findings log

What was measured while building Phase 5, including what the plan got wrong. Same purpose as the
v2.2–v2.4 logs: the numbers and the reasoning behind decisions, so a later reader inherits the
evidence rather than the conclusion.

---

## F-01 - The specification cut the work roughly in half, before any of it was written - **SCOPED**

The roadmap line reads "OAuth 2.1, RBAC, audit logging, multi-tenancy" and says nothing about which
transports it applies to. Reading the authorization specification for revision 2026-07-28 first
settled that, and it is the single most useful thing that happened in this release:

> *"Implementations using an STDIO transport **SHOULD NOT** follow this specification, and instead
> retrieve credentials from the environment."*

**stdio is the default transport and how every editor launches this server.** Excluding it is not a
shortcut — a bearer token protects nothing when the client already launched the process and owns
its stdin. It would be authenticating to itself.

Two other MUSTs shaped the implementation rather than its scope:

- RFC 9728 Protected Resource Metadata is mandatory, and must be reachable **without** a token.
  Discovery that requires the thing it is used to obtain is not discovery.
- RFC 8707 audience binding is mandatory. This is the check that stops a token minted for any other
  service by the same authorization server being replayed here.

Had this been built from the roadmap line alone, the likely outcome was authentication bolted onto
stdio — protecting nothing, breaking every existing editor integration, and non-conforming.

## F-02 - An authorisation bypass in the first wiring, invisible to every unit test - **FIXED**

The dispatch guard was placed where it read naturally: just above the quota acquire, alongside the
other pre-flight checks. That put it **after** the meta-tool branches in `handleCallTool`.

```text
line  715   if (name === "cyberchef_bake")        <- returns here
line  756   if (name === "cyberchef_recipe_create")
line 1066   const caller = currentAuth()          <- the guard
```

So `cyberchef_bake` and all ten recipe tools skipped authorisation entirely — a bypass on the most
powerful tool in the server, since bake runs a caller-supplied recipe containing any operation,
including `HTTP request`.

**Every unit test passed throughout.** The annotations were correct, the scope arithmetic was
correct, `requiredScopes` returned `cyberchef:network` for bake exactly as intended. The check was
simply never reached. It was found by an end-to-end test that called bake with a read-only token
and watched it return `aGk=`.

**A guard in the wrong place is indistinguishable from no guard**, and only a test that goes
through the real dispatch path can tell the difference. Testing the decision function proves the
decision function works; it says nothing about whether anything calls it.

## F-03 - "Null" and "empty" are different, and conflating them failed closed - **FIXED**

Per-request identity uses `AsyncLocalStorage`, because both HTTP legs build their `Server` from the
same zero-argument factory — the modern leg's `createMcpHandler` calls it itself — so there is no
signature to thread a context through. Verified that ALS survives the SDK's dispatch before relying
on it, rather than assuming.

The first wiring installed the context unconditionally:

```js
return await withAuthContext(auth, async () => { ... });   // auth = {scopes: [], ...}
```

With authorization **disabled**, `auth` was still a truthy object carrying no scopes. The dispatch
guard reads a present context as "this caller was authenticated, hold them to their scopes", so
every call in an unauthenticated deployment was refused against scopes nobody had configured.

The module comment claimed the opposite — *"`currentAuth()` is null whenever authorization is
off"* — which was true of the intent and false of the code. Found by the two-client HTTP example,
which no unit test covered because each module was individually correct.

`null` now means "unauthenticated deployment"; a present context means "hold this caller to their
scopes". The distinction is load-bearing and has its own test.

## F-04 - RBAC derived from annotations, not transcribed - **DESIGN**

The obvious implementation is a table mapping every tool to a scope. With 531 tools that table is
wrong the day upstream adds an operation — and wrong *silently*, since a missing entry either
denies everything or defaults to permitted.

The required scope is instead derived from the annotations the server already computes for
`readOnlyHint` / `destructiveHint` / `openWorldHint`:

```text
openWorldHint  -> cyberchef:network
not readOnly   -> cyberchef:write
otherwise      -> cyberchef:read
```

Those annotations were established by audit — the network set by checking which operations actually
make requests, not by reading names — so this inherits that work rather than repeating it. A test
asserts all 504 operations classify to exactly one scope.

**`network` is checked before `write`, deliberately.** An operation that reaches the internet is not
adequately described as "write", and ordering them the other way would let a token granted for
local mutation drive outbound requests.

## F-05 - No new dependency in the authentication path - **DESIGN**

JWKS verification usually means adding `jose` or `jwks-rsa`. Neither was needed:

- `jsonwebtoken` is already a **direct** dependency, used by CyberChef's own JWT operations, and
  validates issuer, audience and expiry natively.
- Node's `crypto.createPublicKey({ format: "jwk" })` imports a JWK directly, so fetching and
  caching a JWKS is a few lines rather than a package.

An authentication path is the last place to introduce a dependency that is not already inside this
project's audit surface.

## F-06 - Two of the six open alerts were self-inflicted, one commit earlier - **FIXED**

Six open alerts: two Dependabot, four code-scanning. They were not six problems — two pairs were
the same issue seen from both surfaces, and **two were created by the previous commit**, which
salvaged the measurement harnesses into `docs/internal/measurements/` and so put them in front of
CodeQL for the first time.

One of those is correct and unfixable by design. `strip-test.mjs` exists to demonstrate the
difference between the naive single-pass strip and the fixpoint version that replaced it, after
CodeQL flagged the real one. It therefore *contains* the vulnerable form as the control in a
comparison, and has no callers. Excluded by path, with the reasoning recorded next to it.

**A defensible exclusion still needs the property that makes it safe written down.** The entry
states it explicitly: nothing under that path is imported by `src/**`, and no gate runs it — so a
later reader can check whether that still holds rather than trusting the original judgement.

## F-07 - A YAML change that parsed, validated, and did nothing - **FIXED**

The first version of that CodeQL exclusion added a nine-line justification and **not the list
entry**. It was valid YAML, the file looked right in a diff, and `paths-ignore` was unchanged.

Caught by parsing the result and printing it rather than reading the diff:

```text
paths-ignore: ['src/vendor/**']          <- the addition is absent
```

Reviewing a configuration change by looking at the diff confirms you typed something. Parsing it
confirms the machine agrees with what you meant.

## F-08 - The rate limiter has never limited anything, and every unit test passed - **FIXED**

**Found:** auditing what multi-tenancy would need to key per tenant. Reading the call site rather
than the module is what surfaced it.

`handleCallTool` called `rateLimiter.checkLimit(requestId)`. `requestId` comes from
`logRequestStart`, which returns a fresh `randomUUID()` per request. Measured at a limit of 5/60s:

```text
keyed by requestId (as shipped):  1000 requests -> 0 denied, 1000 map entries
keyed by a stable caller:         1000 requests -> 995 denied, 1 map entry
```

Two defects in one line. Nothing was ever refused, since v1.7.0. And the tracking Map gained an
entry per distinct key and never dropped one -- `checkLimit` pruned timestamps *within* a caller's
array but never removed the caller -- so with the keying bug it grew by one entry per request,
forever, in a long-running server.

**Why the tests missed it, and this is the reusable part.** `lib-internals.test.mjs` covers the
sliding-window algorithm thoroughly and keys the limiter on a stable connection id, as any
reasonable unit test would. The module was correct. **A correct module reached through wrong wiring
fails, and only a test that goes through the wiring can see it** -- the same lesson as F-02 in this
same release. The regression tests run through the real dispatch path over `InMemoryTransport` and
were verified by mutation: restoring the old keying fails 2 of them.

A smaller trap inside the fix: one regression test was written as
`if (firstRefusal !== -1) expect(...)` and passed against the unfixed server, vacuously, because
nothing was ever refused. **A conditional assertion is not an assertion**, and it is most tempting
to write exactly where the behaviour is uncertain -- which is where it protects least.

## F-09 - Tenant identity is only worth its source - **DESIGN**

Three decisions, each rejecting a more convenient option:

- **Identity from a verified token claim only.** Not a header, not a query parameter, not an
  unverified token. Any of those lets the caller choose their own tenant, which is the appearance
  of isolation rather than isolation.
- **Tenancy without authorization is a startup error.** The tempting alternative -- run
  single-tenant and warn -- fails silently in the one direction that matters: the operator believes
  callers are separated and they are not. Failing to start is legible; a warning in a log is not.
- **An unplaceable token is refused, not defaulted.** Defaulting drops a caller the server cannot
  identify into the bucket everything else lives in.

The 403 for an unplaceable token deliberately carries **no** `insufficient_scope` challenge. The
token authenticated and its scopes are beside the point: no amount of extra scope adds a claim the
authorization server did not issue, so challenging for scope sends the client round a token upgrade
that cannot succeed.

Validation rejects rather than sanitises, because **sanitising collides tenants**: rewriting
`../../etc` to `etc` maps two distinct identifiers onto one storage key, which is the precise
failure the module exists to prevent.

## F-10 - Re-examining the worker-pool deferral, and three measurements that measured nothing - **DEFERRED**

Multi-tenancy appears to strengthen the case for routing registry tools through the worker pool:
concurrent tenants turn main-thread CPU contention into a fairness problem rather than a throughput
one. So the v2.4.0 deferral was re-tested rather than inherited.

A Fermat search against a 2048-bit modulus with far-apart factors, consuming its whole 10-second
budget, while trivial calls ran concurrently:

```text
heavy tool ran for                  10,004 ms  (full budget, factored: false)
trivial calls completed during it   10,218
  median / p99 / worst latency      0 / 1 / 19 ms
```

No starvation. v2.4.0's cooperative yielding already does the work; routing would buy multicore
throughput and nothing else. **Deferred again, now on a direct measurement of the actual concern**
rather than on an inferred bound.

**The three failed attempts are the finding.** Each produced a clean-looking number and each
measured nothing:

1. Passed `n` where the schema wants `modulus`, so the heavy call returned `INVALID_INPUT`
   immediately and the probe timed an error path.
2. Computed the heavy call's duration *after* the sampling loop, so its "3,204 ms" was the loop's
   own length rather than the tool's.
3. Chose factors close together -- Fermat's **fast** case -- so it finished in under 200 ms.

All three would have supported the same conclusion, which is what makes them dangerous. This is
v2.4.0's F-17 repeated three times in one sitting: **a measurement that does not exercise the case
it claims to is a measurement of something else.** What caught it was asserting that the heavy call
was still running at both ends of the sampling window -- a liveness check on the *setup*, not on
the result. Any probe of the form "does A interfere with B" needs one.

## F-11 - The plans and the releases had drifted a full version apart - **FIXED**

From v2.1.0 onward every release plan shipped one version later than its title, because an
unplanned v2.1.0 was cut and nothing renumbered afterwards. `ROADMAP.md` was kept current, so the
two disagreed: a plan headed "v2.4.0 - Enterprise Features" described what was being built as
v2.5.0.

Reconciled in two ways deliberately. Unshipped plans were **renumbered** -- they have no history to
protect and every reason to carry the right number. Shipped plans were **annotated, not renamed**,
because renaming a spent plan to match the release it became falsifies what was planned and when
rather than explaining it. `future-releases/README.md` records the mapping so the offset cannot be
rediscovered as a mystery.

Nine broken relative links surfaced while checking: the phase and strategy docs linked
`./release-v2.x.md` from directories those files have never lived in, so every one of those links
had been dead since it was written.

## F-12 - The v1 line cannot be published to npm by adding packaging metadata - **BLOCKED**

**Found:** while preparing a v1.9.x maintenance PR, by adding a `files` allowlist and renaming the
package -- and having CI reject it.

The v1 `package.json` name is `cyberchef`, which upstream publishes, and its `version` carries the
upstream base rather than the product version. Both look like the whole problem. They are not.

Two breakages from that one change, both self-inflicted, and neither is the real blocker:

1. The `files` allowlist excluded `Gruntfile.js`, while `postinstall` runs **five** grunt tasks
   that patch `node_modules` (`fixCryptoApiImports`, `fixSnackbarMarkup`, `fixJimpModule`,
   `fixSerializeJavascript`, `fixLoglevelMessagePrefix`). Any install of the tarball dies with
   `Unable to find local grunt`.
2. `Gruntfile.js` hardcodes `npm link cyberchef` and `tests/node/consumers/` requires the package
   by that name, so the rename breaks the consumer test independently of the allowlist.

**The actual blocker is `postinstall` itself**, which is what v2.2.0 recorded as F-14 and v2.3.0
closed as F-01. A published package cannot patch its own `node_modules`, so the v2 line only became
publishable by removing the *need* for the patching: vendoring `crypto-api` (24 files) and moving
`terser` out of devDependencies. Backporting that to a security-only maintenance branch means
editing `src/core` there, which is the one thing that line exists not to do.

**Disposition:** v1 npm publication stays blocked, and the packaging change is reverted rather than
left half-applied. The value in that branch was never the packaging -- it is release notes that are
not a 45-character stub, and PGP fixtures that let the line run its tests at all.

**The reusable point.** "Make it publishable" read like a metadata edit, and the metadata edit is
the part that is trivially reversible. What made it *look* done was that `npm pack` produced a
plausible tarball -- 12 MB, right files, no leakage -- which verifies packaging and says nothing
about whether the package **installs**. A pack is not an install, and only the consumer test, which
actually installs it, could tell the difference.

## F-13 - Every release tag in this project had its headings silently stripped - **FIXED**

**Found:** cutting the v2.5.0 tag with the documented command and reading the result before pushing.

`git tag -F <file>` applies git's default message cleanup, which treats every line beginning with
`#` as a **comment** and removes it. A markdown release note is mostly headings, so the tag message
loses all of them and becomes an unstructured wall of text:

| tag | headings in the notes file | headings surviving in the tag |
|---|---|---|
| v2.2.0 | 12 | **0** |
| v2.3.0 | 12 | **0** |
| v2.4.0 | 16 | **0** |
| v2.4.1 | 9 | **0** |
| v2.5.0 | 10 | 10 (after the fix) |

**Why nobody noticed for the whole v2.x line.** The GitHub *Release* is built from the same file by
`gh release create --notes-file`, which strips nothing -- so the artefact everyone actually reads
was always correct. Only `git show <tag>` and `git tag -n` were degraded, and those are read rarely
and by people who would assume the tag was written that way on purpose.

Fixed by adding `--cleanup=verbatim` to the documented command in `AGENTS.md`. Published tags are
immutable, so v2.2.0 through v2.4.1 stay as they are; v2.5.0 is the first tag with its structure
intact.

**A second, smaller lesson from the fix itself.** The obvious verification is
`diff <(git tag -l X --format='%(contents)') docs/releases/X.md` -- and it reports a mismatch on a
perfectly good tag, because `%(contents)` appends a trailing newline. A check that cries wolf by one
byte gets ignored within a release or two, so the documented check counts headings instead, which is
the property that actually broke.
