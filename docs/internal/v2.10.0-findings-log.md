# v2.10.0 findings log

What was measured before writing anything, including what the plan got wrong. Same purpose as the
v2.2–v2.9 logs: the numbers and the reasoning, so a later reader inherits the evidence rather than
the conclusion.

---

## F-01 — There is no v2.10.0 in the plan, and the release it does name is empty

The roadmap goes **v2.9.0 → v2.9.x (Pre-v3.0.0 Polish) → v3.0.0**. There is no v2.10.0 anywhere in
`docs/planning/`, so this release has no plan of its own; the nearest is
`release-v2.9.x.md`, whose stated Primary Goal is:

> Add deprecation warnings for all v3.0.0 breaking changes

That goal is **empty**, because v3.0.0's breaking changes have already happened, been withdrawn, or
were never real. Measured one by one against the running server:

| v3.0.0 breaking change | Deprecation | Measured state |
|---|---|---|
| 1. Tool naming convention | DEP001/007/008 | **WITHDRAWN in v2.0.0, permanently.** The `cyberchef_` prefix stays; withdrawal is recorded in the migration guide and in AGENTS.md |
| 2. Recipe schema v2 (named arguments) | DEP002/005/006 | **Already works.** `bake` accepts `args: {alphabet: "A-Za-z0-9+/="}` today |
| 3. Structured error responses | DEP003 | **Already shipped.** `createInputError` returns `code`, `context` and `toMCPError` |
| 4. Unified configuration | DEP004 | **Announced as shipped in v2.0.0, and never built** — see F-02 |

So three of the four are done or abandoned, and the fourth is not a *future* breaking change to warn
about: it is a **past** one that was announced and never delivered.

Writing deprecation warnings for changes that already happened would be the same mistake in a new
direction. The honest read is that the v2.x → v3.0.0 migration story does not need more warnings; it
needs the one promise that was made and not kept.

## F-02 — `cyberchef.config.json` is documented, instructed, and silently ignored — **THE RELEASE**

`docs/v2.0.0-breaking-changes.md` tells users, under a heading that reads "v2.0.0 (New)", to create
a unified config file:

```json
{
  "server":    { "maxInputSize": 10485760, "cacheTTL": 3600000 },
  "telemetry": { "enabled": false, "endpoint": null },
  "security":  { "allowedOperations": ["*"], "blockedOperations": [] }
}
```

**No loader exists.** The only occurrence of the string `cyberchef.config.json` anywhere in the
source is the deprecation *message* telling users to use it. Demonstrated rather than asserted:

```text
cyberchef.config.json present, asking for maxInputSize 1024
MAX_INPUT_SIZE actually in effect: 104857600
-> SILENTLY IGNORED
```

A user who follows the published migration guide writes a configuration file, restarts the server,
and gets no error, no warning, and none of their settings. That is the worst shape this project
keeps rediscovering — documentation asserting a behaviour the code does not have, with nothing that
would ever report the gap. It is the same failure as the SafeRegex incident
(`docs/security/2026-08-30-saferegex-reverted-by-upstream-sync.md`), where three documents claimed a
mitigation that had been reverted four releases earlier.

DEP004 has been emitting a warning telling users to adopt this file **since v1.8.0**.

Sharpening it: DEP004 is not even *warned* about. Of the eight deprecation codes, only four are ever
emitted, and three of those (DEP001/007/008) are withdrawal notices saying a rename is **not**
happening:

```text
DEP001 emitted at 1 site   DEP005 emitted at 1 site
DEP002 emitted at 0 sites  DEP006 emitted at 0 sites
DEP003 emitted at 0 sites  DEP007 emitted at 1 site
DEP004 emitted at 0 sites  DEP008 emitted at 1 site
```

DEP002, DEP003 and DEP006 need no warning — they were *enacted* in v2.0.0. DEP004 is the only code
that was neither enacted nor warned about, and it is the only one whose promise appears in the
user-facing guide as a thing to go and do.

## F-03 — What I nearly recorded as a defect, and was not

Two checks that came back clean, written down because each looked like a finding first.

**The v2 recipe shapes all work.** An initial probe reported three of four shapes throwing, which
would have been a large finding. The probe was wrong: it passed `args: []` to `To Base64`, and that
operation needs an alphabet, so the failure was a missing *argument* and had nothing to do with the
recipe *shape*. Re-run with valid arguments:

```text
OK  array [{op, args: [...]}]
OK  array [{op}]  (arguments defaulted)
OK  named args object -- DEP005's promise, delivered
```

`{name, operations}` is not accepted by `bakeOnCore`, which also looked like a defect: DEP006
promised that shape. It is not one — that shape belongs to the recipe-MANAGEMENT surface
(`cyberchef_recipe_create` takes `{name, operations}`, and does), while `bake` takes the operation
list. Two different objects with a similar shape, and the promise is kept in the right place.

**Environment-variable documentation is not the gap.** 46 of the 48 variables read by `src/node/`
appear in the README or the guides; only `CYBERCHEF_DRAIN_DELAY_MS` and
`CYBERCHEF_DRAIN_TIMEOUT_MS` are undocumented. The reverse comparison flagged eleven documented
variables as unread, which also looked like drift — all eleven are read through a destructured
`env.` parameter rather than `process.env.`, so the grep was too narrow, not the docs wrong.

## F-04 — The case for the file is stronger than the broken promise

Configuring this server means setting **50 environment variables**:

```text
CYBERCHEF_MAX_INPUT_SIZE      CYBERCHEF_OPERATION_TIMEOUT   CYBERCHEF_CACHE_MAX_SIZE
CYBERCHEF_RATE_LIMIT_ENABLED  CYBERCHEF_TOOL_SURFACE        CYBERCHEF_RECIPE_STORAGE
CYBERCHEF_OFFLINE             CYBERCHEF_METRICS_ENABLED     ... 42 more
```

There is no way to see a deployment's settings in one place, nothing validates them, and a
Helm values file or compose file has to carry every one as a separate string. A typo in any of them
is silently ignored, because an unset variable and a misspelt variable are indistinguishable to
`process.env`.

So the file is worth building on its own merits, independent of the promise. The promise is what
makes it this release rather than a later one.

## Scope for v2.10.0

**The configuration file that v2.0.0 promised.**

| | |
|---|---|
| Load | `cyberchef.config.json`, path overridable |
| Precedence | environment variable > config file > default, documented and tested |
| Validation | **fail closed** on malformed JSON and on unknown keys |
| Coverage | all settings, not only the 18 in `config.mjs` |
| Docs | the DEP004 section of the migration guide, corrected to describe what exists |

Fail-closed on an unknown key is the decision worth defending, because it will annoy someone. This
is a security toolkit, the example in the guide includes `blockedOperations`, and the bug being
fixed is *a setting that was silently ignored*. Accepting a typo'd security key and carrying on
would reproduce exactly that failure in a new place.

**On the version number.** The roadmap has no v2.10.0 — it names v2.9.x "polish" next. But this
work is additive and backward compatible (no file present means today's behaviour exactly), which
is a MINOR under SemVer, so `2.10.0` is the correct number and `2.9.1` would be wrong. The roadmap
entry is stale and is updated as part of this release rather than followed.
